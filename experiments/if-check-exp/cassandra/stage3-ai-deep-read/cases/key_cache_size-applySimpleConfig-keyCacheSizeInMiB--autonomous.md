## A. Constraint trace

**A1. The constraint.** `key_cache_size`, configuration entry ([`Config.java:467-468`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/Config.java#L467-L468), `LongMebibytesBound`, default `null` = auto; legacy `key_cache_size_in_mb`), yaml `conf/cassandra.yaml:525` (comment `:519-524`: auto = min(5% heap, 100MiB), 0 disables, only relevant to BIG). Unit MiB. Auto: `min(max(1, totalMemory*0.05/1MiB), 100)` ([`DatabaseDescriptor.java:815-817`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L815-L817); uses `Runtime.totalMemory()`, which equals the heap when `-Xms = -Xmx`). Negative → `ConfigurationException` (`:819-820`, `:825-829`; unreachable, see Estimate). Written back for the settings table (`:823`); getter `getKeyCacheSizeInMiB()` (`:3881-3884`). Runtime-settable via JMX `CacheServiceMBean.setKeyCacheCapacityInMB` ([`CacheService.java:336-342`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/CacheService.java#L336-L342), rejects negatives) and `nodetool setcachecapacity`; startup value needs restart only if set in yaml.


**Limit type (2026-10-29).** config: yaml entry. The traced constraint decides ([README §6](../../../stage3-ai-deep-read/README.md#6-rules-that-hold-for-both-agents)).
**A2. What it caps.** Heap held by the key cache (`KeyCacheKey` → `AbstractRowIndexEntry`). Runtime operand: Caffeine weighted size = Σ (`KeyCacheKey.unsharedHeapSize()` + `value.unsharedHeapSize()`) (`CaffeineCache.java:61-70`, `KeyCacheKey.java:59-62`, `RowIndexEntry.java:199-203`).

**A3. Mechanism.**
1. Startup check ([`DatabaseDescriptor.java:815-829`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L815-L829)).
2. `CacheService.initKeyCache` builds `CaffeineCache.create(keyCacheSizeInMiB * 1024 * 1024)` ([`CacheService.java:123-128`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/CacheService.java#L123-L128)) → `Caffeine.maximumWeight(capacity).weigher(...)` ([`CaffeineCache.java:51-59`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/cache/CaffeineCache.java#L51-L59)).
3. Readers with key-cache support insert on index lookup via `KeyCacheSupport.cacheKey` ([`KeyCacheSupport.java:79-86`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/io/sstable/keycache/KeyCacheSupport.java#L79-L86)); Caffeine evicts when the weighted size exceeds capacity.
- Overshoot/bypass: weights are estimates (`unsharedHeapSize`, not deep retained size); eviction is amortised; BTI-format SSTables do not use the key cache (yaml `:523`). The cache is saved to disk periodically (`key_cache_save_period`, default 4h, [`Config.java:469-470`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/Config.java#L469-L470); [`CacheService.java:132-134`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/CacheService.java#L132-L134)), disk outside this cap.

**A4. Other consumers.** Row cache (`row_cache_size`), counter cache, chunk cache, index summaries, memtables; saved-caches files in `saved_caches_directory`.

**A5. Evidence beyond the source.** `conf/cassandra.yaml:519-525` comment. Caffeine `maximumWeight` semantics: https://github.com/ben-manes/caffeine/wiki/Eviction#size-based.

## B. Verification solution

**B1. Claim under test.** With `key_cache_size: C`, the key cache's weighted size never exceeds C MiB (beyond transient slack of a few entries) and its entry count plateaus at ≈ C / (per-entry weight) once more distinct partitions are read than fit, so key-cache heap scales with C, not with the number of keys read. A negative value is rejected at parse time (before line 819).

- **Per-entry weight w_s, from the source.** The weigher is key.`unsharedHeapSize()` + value.`unsharedHeapSize()` (`CaffeineCache.java:61-69`), both measured by jamm with the JVM's memory layout (`ObjectSizes.java:31,56-59,251-254`, jamm `measure` / `measureArray`; 64-bit HotSpot with compressed oops and class pointers at a 2 GiB heap: object header 12 B, reference 4 B, array header 16 B, 8-byte alignment). Value: a `standard1` partition has no column index, so the serializer returns a plain `RowIndexEntry(position)` (`RowIndexEntry.java:341-348`, cached at `BigTableReader.java:325,343`), whose `EMPTY_SIZE` = header + `long position` (`AbstractRowIndexEntry.java:33`) = 12 + 8 = 20 → **24 B** (`RowIndexEntry.java:141,199-203`). **w_s = 32 + 32 + 24 = 88 B.** By alignment every key of 9–16 bytes weighs the same 88 B, so the stress keys contribute no spread.
- **(v) eviction and entry count (replaces (v)).** `Misses` during the main read ≥ 0.99 × (2,000,000 − 20,000) = 1,960,200, and `Entries` at main-done within **±0.5 % of E_s = ⌊Capacity / 88⌋ = 95,325 · 762,600 · 1,191,563** at 8 · 64 · 100 MiB (hence ≥ 0.8 M of the 2,000,000 distinct partitions read were evicted). Tolerance from the source: Caffeine evicts while the weighted size exceeds the maximum (`BoundedLocalCache$AddTask.run` → `evictEntries`, `javap -c`), so the stress entries leave less than one entry of slack; the cache also holds up to 200 system-table keys (B3h (a)), whose keys have other lengths and can each displace up to two 88 B entries (≤ 400 entries = 0.42 % of E_s at 8 MiB, less at 64 and 100 MiB). ±0.5 % covers both at every C.
- **(vii) real heap (replaces (vii)).** For the pairs (64, 8) and (auto, 8): D = live total(hi) − live total(lo) of the final histograms (`jmap -histo:live`, which runs a full collection first, so garbage — replaced map tables and sketch arrays — is not counted), S = Size(hi) − Size(lo) at main-done; **D/S within R_pred ± 0.25**. Derivation of R_pred: each cached entry holds (a) the weighed objects, exactly w_s = 88 B live (`KeyCacheKey` 32 + key `byte[]` 32 + `RowIndexEntry` 24); (b) Caffeine's node, unweighed. The builder at `CaffeineCache.java:53-57` sets strong keys and values, `maximumWeight` with a non-singleton weigher, no expiry and no refresh, so `NodeFactory.getClassName` (`javap -c`) selects **`PSMW`**: `PS` fields `key`, `value` (references), `PSMW` fields `queueType`, `weight`, `policyWeight` (ints) and `previousInAccessOrder`, `nextInAccessOrder` (references), `Node` none (`javap -p`): 12 + 4 × 4 + 3 × 4 = **40 B**; (c) the entry of Caffeine's backing map `data`, a `java.util.concurrent.ConcurrentHashMap` (`BoundedLocalCache.<init>`, `new ConcurrentHashMap(builder.getInitialCapacity())`): `ConcurrentHashMap$Node` = header + `hash` (int), `key`, `val`, `next` = 12 + 16 = 28 → **32 B**; (d) no key or value wrapper: with strong keys the map key is the `KeyCacheKey` itself and the node holds the `RowIndexEntry` directly (no `WeakKeyReference` / value reference objects; `InstrumentingCache` and `AutoSavingCache` wrap the cache, not entries, `CacheService.java:119-129`). Per entry: 88 + 40 + 32 = **160 B** (72 B unweighed). Per cache, growing in power-of-two steps: (e) the map table, `Node[L]`, 4 B per slot, L(E) = the smallest power of two ≥ 32 with E < 0.75 L (Caffeine's initial capacity 16 → table 32; JDK 11 `ConcurrentHashMap.addCount` resizes to 2n once the count reaches `sizeCtl` = 0.75 n); (f) the frequency sketch `long[T]`, T(E) = max(8, ceilingPowerOfTwo(E)) (`AddTask.run` calls `frequencySketch().ensureCapacity(data.mappingCount())` once the weighted size reaches half the maximum; `FrequencySketch.ensureCapacity` allocates `new long[max(ceilingPowerOfTwo(n), 8)]` only when the table is shorter; `javap -c`). So **R_pred = [ΔE × 160 + 4 ΔL + 8 ΔT] / S** with E = `Entries` at main-done in each lifetime. At E = E_s: L = T = 131,072 · 1,048,576 · 2,097,152; **R_pred(64, 8) = (667,275 × 160 + 4 × 917,504 + 8 × 917,504) / (667,275 × 88) = 117,774,048 / 58,720,200 = 2.006**, band **1.756–2.256**; **R_pred(auto, 8) = (1,096,238 × 160 + 12 × 1,966,080) / (1,096,238 × 88) = 198,991,040 / 96,468,944 = 2.063**, band **1.813–2.313**. Tolerance: the power-of-two steps add nothing at E_s ± 0.5 % (the nearest threshold, 0.75 × 131,072 = 98,304 at 8 MiB, is 2,979 entries above E_s, more than Caffeine's write buffer of 128 × ceilingPowerOfTwo(10 cores) = 2,048 pending insertions that could transiently enlarge the map; the other thresholds are farther), and if a measured E crosses one the formula uses the measured E; headers of the two arrays (16 B each) are ignored. The ± 0.25 (≈ ±14.7 MB at (64, 8), ±24.1 MB at (auto, 8)) is an allowance for reachable heap outside the key cache that this derivation does not count and that can differ between two node lifetimes after the full collection (system-table memtables and caches, metrics reservoirs, connection and request state of the driver and sampler); the source does not fix it, so it is taken over unchanged from the counter-cache file's B3f (vii), where it was set before any reading, and not chosen from this file's readings. Run 1's ratios (2.173 and 2.168, 0.17 and 0.11 above R_pred) lie inside these bands, so this amendment is tested by the re-run, not by run 1. The workload is identical across lifetimes, so other heap cancels in D to first order.
