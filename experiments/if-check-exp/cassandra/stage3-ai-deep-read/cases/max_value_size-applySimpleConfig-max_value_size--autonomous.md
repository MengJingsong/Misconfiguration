## A. Constraint trace

**A1. The constraint.** `max_value_size`, configuration entry ([`Config.java:309-310`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/Config.java#L309-L310), `IntMebibytesBound`, default `256MiB`; legacy `max_value_size_in_mb`), yaml `conf/cassandra.yaml:1864` (commented; comment `:1860-1863`: "Safety measure to detect SSTable corruption early … positive and less than 2GiB"). Checks at [`DatabaseDescriptor.java:944-948`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L944-L948). Getter `getMaxValueSize()` = `saturatedCast(MiB × 2^20)` (`:1928-1931`), read on every call (no caching), setter test-only (`:1933-1937`). No JMX; restart required in practice.


**Limit type (2026-10-29).** config: yaml entry. The traced constraint decides ([README §6](../../../stage3-ai-deep-read/README.md#6-rules-that-hold-for-both-agents)).
**A2. What it caps.** Heap (or the accessor's buffer) allocated for one deserialized value. Operand: the vint length `l` read from the stream (`AbstractType.java:590-597`).

**A3. Mechanism.**
1. Startup checks ([`DatabaseDescriptor.java:944-948`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L944-L948)).
2. `AbstractType.read(accessor, in, maxValueSize)`: fixed-length types skip the check (`:584-587`); otherwise read `l`, if `l > maxValueSize` throw `IOException("Corrupt value length … max_value_size …")` (`:594-597`), else `accessor.read(in, l)` allocates `l` bytes (`:599`).
3. Callers: cell values ([`Cell.java:339`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/rows/Cell.java#L339)), clustering components ([`ClusteringPrefix.java:517`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/ClusteringPrefix.java#L517), `:674`), partition key of a deserialized read command ([`SinglePartitionReadCommand.java:1352`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/SinglePartitionReadCommand.java#L1352)). On the SSTable read path the `IOException` surfaces as a corrupt-SSTable error.
- Bypass: skipped values ([`Cell.java:331-334`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/rows/Cell.java#L331-L334)) are not allocated; fixed-length types are not checked; the write path (CQL → memtable) does not call this, so values larger than the limit can be written if `max_mutation_size` and `native_transport_max_message_size` allow it.

> **Amendment 2026-10-25 (stage-4 audit, Claude Opus 5.5, before any reading), A3 (read paths, how an over-limit value reaches one, and which limits bind first; audit statement, no claim changed).** **How a value larger than `max_value_size` gets onto disk:** the local write path never calls `AbstractType.read` — a CQL write builds the mutation, `Mutation.apply` → `CommitLog.add` serializes it and the memtable stores the cell (no deserialization) — so a value of any length that passes the write-side limits is accepted whatever `max_value_size` is; the design writes under the default 256 MiB, flushes to an SSTable, drains, and restarts with a smaller value (alternatives not used: a crafted SSTable or stream). **Write-side limits that must admit the value** (pinned clone): `max_mutation_size` = `commitlog_segment_size`/2 = 16,777,216 B at the default 32 MiB segment ([`DatabaseDescriptor.java:898-899`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L898-L899); serialized size + 12, [`Mutation.java:169-176`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/Mutation.java#L169-L176)); `native_transport_max_message_size` default = min(`max_mutation_size`, in-flight = heap/10, in-flight per IP = heap/40) (`DatabaseDescriptor.java:649-656, 903-905, 3237-3244`) = 16,777,216 B at a 2 GiB heap; the 16 MiB `native_transport_max_frame_size` is the pre-v5 decoder's and does not bind at protocol 5 (finding of the `max_mutation_size` run). Every value written here is ≤ 12,582,912 B, so **no limit has to be raised**; a value above about 16 MiB would need a larger `commitlog_segment_size`. The guardrail `column_value_size` is unset (disabled) in the shipped yaml. **Read paths that check it and what each produces when l > V:** (1) SSTable read — `Cell.deserialize():339` inside the SSTable row iterator; the `IOException` is wrapped as `CorruptSSTableException` and the SSTable is marked suspect ([`AbstractSSTableIterator.java:401-433`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/io/sstable/AbstractSSTableIterator.java#L401-L433)); on a local read `LocalReadRunnable` reports `RequestFailureReason.UNKNOWN` and rethrows ([`StorageProxy.java:2243-2253`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageProxy.java#L2243-L2253)), so the client gets `ReadFailure` and the error is logged; `disk_failure_policy: stop` (shipped) takes no action for a corrupt SSTable (only `die`/`stop_paranoid` stop transports, [`DefaultFSErrorHandler.java:44-58`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/DefaultFSErrorHandler.java#L44-L58)) and a suspect SSTable is still read (suspect only filters compaction: [`CompactionController.java:318`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/compaction/CompactionController.java#L318), [`AbstractCompactionStrategy.java:240`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/compaction/AbstractCompactionStrategy.java#L240)). (2) The coordinator's decode of its own replica's response — [`StorageProxy.java:2211`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageProxy.java#L2211) `createResponse` serializes, `DigestResolver.getData():83` → `makeIterator` deserializes through `Cell.deserialize` — reached by a value still in the memtable; the `IOException` becomes `IOError` ([`UnfilteredRowIteratorSerializer.java:244`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/rows/UnfilteredRowIteratorSerializer.java#L244)) and reaches the client as `ServerError`. (3) Commit-log replay — `CommitLogReader.readMutation():426-431` deserializes every mutation of a segment after the global replay position (only the segment that holds the position is seeked, `:297-299`); a guard failure goes to `handleUnrecoverableError`, and the node does not start. `nodetool drain` flushes every table and force-recycles all segments ([`StorageService.java:5915-5965`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageService.java#L5915-L5965), [`AbstractCommitLogSegmentManager.java:357-392`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/AbstractCommitLogSegmentManager.java#L357-L392)), so a drained node replays none of the phase-1 mutations. (4) Internode messages, hints, batchlog and streaming deserialize mutations/partitions through the same `Cell.deserialize` — not reachable on one node, not tested. Clustering components (`ClusteringPrefix.java:517, 674`) and the partition key of a deserialized read command ([`SinglePartitionReadCommand.java:1352`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/SinglePartitionReadCommand.java#L1352)) use `readArray`/`readBuffer` with the same guard; the table here has a fixed-length `int` key and no clustering column, so they are not tested.

**A4. Other consumers.** `max_mutation_size` (write-side), `native_transport_max_message_size`, guardrail `column_value_size` (yaml `:2143`), memtables.

**A5. Evidence beyond the source.** `conf/cassandra.yaml:1860-1864`, `:2143` (guardrail is different from this setting). Existing guided case `max_value_size-read-maxValueSize--guided.md`.

## B. Verification solution

**B1. Claim under test.** (a) `0MiB` and `2048MiB` stop startup; `1MiB`, `2047MiB` are accepted. (b) With `max_value_size: V`, reading a stored value longer than V fails without allocating it, while values ≤ V read normally; so the largest single-value allocation on the read path is ≤ V.

### B2. Unit tier

**B2a. Environment and build.** Local clone `/local/c509`, `ant jar`; `ConfigProbe` (as in `prepared_statements_cache_size-applySimpleConfig-preparedStatementsCacheSizeInMiB--autonomous.md` B2a) with getter `getMaxValueSize`. Mechanism: small program `/local/probe/src/ValueReadProbe.java` (no node): after `DatabaseDescriptor.daemonInitialization()` (yaml with `max_value_size: V`), build a `DataOutputBuffer`, write `writeUnsignedVInt32(len)` + `len` bytes, wrap in `DataInputBuffer`, call `BytesType.instance.readBuffer(in, DatabaseDescriptor.getMaxValueSize())`; print result or exception; print `Runtime.totalMemory()-freeMemory()` around the call.
