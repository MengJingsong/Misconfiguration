## A. Constraint trace

**A1. The constraint.** `memtable_offheap_space` (configuration entry), declared `Config.java:188-189` (`DataStorageSpec.IntMebibytesBound memtable_offheap_space`, replaces `memtable_offheap_space_in_mb`). Unit MiB. Default (unset in `conf/cassandra.yaml:799`, commented out) is `Runtime.maxMemory() / (4 * 1048576)` MiB, i.e. 1/4 of max heap (`DatabaseDescriptor.java:583-584`). Set via yaml only (restart needed; no JMX setter found). `DatabaseDescriptor.getMemtableOffheapSpaceInMiB()` (`:4062`) is read in `AbstractAllocatorMemtable.createMemtableAllocatorPool` (`:82`), converted `<< 20` to bytes, passed to `NativePool` for `offheap_objects` (`:106-108`) and to `SlabPool` for `offheap_buffers` (`:104-105`). It is ignored for `heap_buffers` (SlabPool gets 0, `:102`) and the unslabbed heap types. The mode is `memtable_allocation_type` (`Config.java:524`, default `heap_buffers`; yaml `:825`).
Not-a-cap constants at the entry point: `MAX_CLONED_SIZE = 128 KiB` (`NativeAllocator.java:47`), `MIN/MAX_REGION_SIZE` 8 KiB/1 MiB (`:46,:48`). They only choose the allocation path.

**A2. What it caps.** Off-heap (native, `Unsafe`/malloc) memory owned by memtables: the sum of requested bytes of native keys, clusterings and cells. The compared quantity is `MemtablePool.SubPool.allocated` (`MemtablePool.java:~110`) via `tryAllocate`: `allocated + size > limit` (`:~149`), with `limit` = the configured bytes (`:~104`, `:56-58`).

**A3. Mechanism.**
1. Writes clone data via `NativeAllocator.cloner` / `rowBuilder` into `NativeDecoratedKey` (`NativeDecoratedKey.java:42`), `NativeClustering` (`:52`), `NativeCell` (`NativeCell.java:104`), all calling `NativeAllocator.allocate(size, opGroup)` (`NativeAllocator.java:138`).
2. Line 141 `offHeap().allocate(size, opGroup)` charges the request to the pool first, for every size.
3. `SubAllocator.allocate` (`MemtableAllocator.java:169-196`) loops: `parent.tryAllocate` succeeds -> `acquired(size)` (adds to `owns`, may trigger clean via `maybeClean`, `MemtablePool.java` `acquired`/`needsCleaning`). If it fails and `opGroup.isBlocking()` -> `allocated(size)` bypasses the limit (`:180-184`). Otherwise the writer registers on `hasRoom` and parks until a flush releases memory (`:185-195`).
4. Cleaning: `needsCleaning` is `used() > reclaiming + limit * cleanThreshold` (`MemtablePool.java` `updateNextClean`); the cleaner flushes the largest memtable (`MemtableCleaner`, `AbstractAllocatorMemtable::flushLargestMemtable`, `:86`). Threshold defaults to `1/(1+memtable_flush_writers)` (`DatabaseDescriptor.java:761-763`).
5. Only then the size branch (line 144): `size > 128 KiB` -> `allocateOversize` (`:186-198`), a dedicated `MemoryUtil.allocate(size)` region; else slice from `currentRegion`, swapping to a new region doubling 8 KiB -> 1 MiB (`:147-184`).
6. Release: `setDiscarded` frees all regions (`:200-206`) and `SubAllocator.setDiscarded` -> `releaseAll` -> `parent.released` signals waiters (`MemtableAllocator.java:140-155`).
Outcomes at the limit: writers block (`BlockedOnAllocation` timer, `MemtablePool.java:~55`) except blocking op groups, which overshoot.
Overshoot / bypass paths: (a) `isBlocking` branch (step 3) during flush barrier; (b) the tracker counts requested bytes, not malloc'd bytes: unused tail of the current region (up to 1 MiB per live memtable allocator), the 8 regions per size class stashed in static `RACE_ALLOCATED` (`:51,:209-227`, bounded ~8 x (8K+...+1M) ~ 16 MiB, only under CAS races), malloc overhead/fragmentation; (c) a memtable being flushed stays charged until `setDiscarded`, so the limit also counts flushing memtables (stricter, not looser); (d) `onHeap` is a separate limit (`memtable_heap_space`) and also applies in this mode (`BTreePartitionUpdater.java:182`).

**A4. Other consumers (not under this cap).** Chunk cache / buffer pool (`file_cache_size`), direct buffers for network/commitlog, bloom filters and index summaries off-heap, compression metadata, OHC row cache if enabled, Netty direct memory, JVM metaspace/thread stacks/code cache. The default `skiplist` memtable (`cassandra.yaml:783-790`) is assumed; `TrieMemtable` charges off-heap by `allocator.offHeap().adjust` (`TrieMemtable.java:484`) not through NativeAllocator, so use the default memtable here.

**A5. Evidence beyond the source.** none (design from source only; JDK NMT docs: https://docs.oracle.com/en/java/javase/11/vm/native-memory-tracking.html for `Unsafe.allocateMemory` appearing under category "Other").

## B. Verification solution

**B1. Claim under test.** With `memtable_allocation_type: offheap_objects`, memtable native memory (tracked: pool off-heap `used()`; actual: native process memory attributable to memtables) stays at or below `memtable_offheap_space` plus a small bounded slack (region tails, flush-barrier overshoot), and writers block at the limit; changing the limit moves the ceiling proportionally. Corollary for the entry point: allocations above 128 KiB (line 144 oversize path) are charged to the same limit, so `MAX_CLONED_SIZE` does not let data escape it.

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Copy the tree to local disk (`rsync -a ~/cassandra-5.0.9/ /local/tmp/c509/`), `cd /local/tmp/c509 && ant jar` (and `ant build-test` if using JUnit). Test/driver source goes in the copy (e.g. `/local/tmp/c509/test/unit/org/apache/cassandra/utils/memory/OffheapCapProbe.java`, in package `org.apache.cassandra.utils.memory` to reach package-private `SubPool.allocated`/`used()`; `used()` is public). Run with JVM `-Xmx512m -XX:NativeMemoryTracking=summary -Dcassandra.config=file:///local/tmp/c509/conf/cassandra.yaml` (needed only so `DatabaseDescriptor` initializes, e.g. `DatabaseDescriptor.daemonInitialization()`; the probe builds the pool directly).

**B2b. Knobs.** (i) Off-heap limit L passed to `AbstractAllocatorMemtable.createMemtableAllocatorPoolInternal(offheap_objects, heapLimit=1 GiB, L, 0.33f, cleaner)` (`AbstractAllocatorMemtable.java:92`): L = 32 MiB, 64 MiB, 128 MiB (shows proportional ceiling). (ii) Allocation size S: 100 B, 1 KiB, 100 KiB, 128 KiB (`== MAX_CLONED_SIZE`, in-region), 128 KiB+1 (oversize path), 1 MiB. (iii) Pool kind for the control: `heap_buffers` (SlabPool with off-heap limit 0).

**B2c. Workload.** One thread per run calls `NativeAllocator a = (NativeAllocator) pool.newAllocator("t")` then `a.allocate(S, group)` in a loop, `group = new OpOrder().start()` (non-blocking). The `MemtableCleaner` is a stub returning a completed future (`ImmediateFuture.success(false)` or similar) so no flush ever releases memory. Loop until `pool.offHeap.used() + S > L`. Count N = floor(L/S) allocations expected: e.g. L=64 MiB, S=1 KiB -> 65 536 allocations; S=128 KiB+1 -> 511 (`64Mi/131073`). Then issue one more allocate from a second thread and observe it parks.

**B2d. Observables and instruments.** `pool.offHeap.used()` (check operand), `a.offHeap().owns()`, `pool.offHeap.usedRatio()`; sum of region capacities via reflection on `NativeAllocator.regions` (`Region.capacity`); actual native bytes via `jcmd <pid> VM.native_memory summary` category Other (delta vs baseline) and `/proc/self/status` VmRSS; thread state of the extra allocator via `Thread.getState()` (WAITING/TIMED_WAITING). Not directly observable: malloc internal overhead (use RSS delta as bound).

**[Amended 2026-10-26, stage-4 step 0, B2d/B2f/B2g]** NMT cannot see this memory: `MemoryUtil.allocate` is `com.sun.jna.Native.malloc` (`MemoryUtil.java:25,81-83`), i.e. libc `malloc` called through JNA, not `Unsafe.allocateMemory`, so the "Other" category of `jcmd VM.native_memory` does not contain the regions (A5's remark was wrong). Every "NMT" in B2d-B2g reads instead **`RssAnon` of the probe JVM from `/proc/self/status`** (delta over the baseline taken after JVM start-up and class loading and before the first allocation). Because `malloc`ed pages become resident only when written, the probe writes one byte into each 4 KiB page of every allocation (`MemoryUtil.setByte`) before the next one, as Cassandra does when it copies the cell; the prediction on the real resource is then `used() - 1 MiB <= RssAnon delta <= capacity_sum + 4 MiB` (as amended in B2f) (page rounding, malloc headers and JVM warm-up noise inside the +4 MiB of B2f; the lower bound is `used()` because untouched region tails are not resident). The reading row "NMT delta >> capacity sum or grows after the plateau" is read on this `RssAnon` delta. NMT is still switched on and its summary kept in the logs as evidence that it does not see the memory.

**B2e. Procedure.**
1. Build as B2a. 2. For each (L, S): fresh JVM; record baseline NMT and RSS. 3. Fill until `used()+S>L`; record `used()`, `owns()`, N, region capacity sum, NMT delta. 4. Start the extra allocate thread; sleep 2 s; record its state. 5. Call `a.setDiscarding(); a.setDiscarded()` (needs LIVE->DISCARDING->DISCARDED; `MemtableAllocator.java:83-97`); record extra thread unparks and `used()` returns to 0 and NMT delta falls. 6. Repeat with an `OpOrder.Group` whose `isBlocking()` is true (call `barrier.issue()` on an `OpOrder.Barrier` before the allocate; `OpOrder.java:319-335`) to measure the overshoot path. 7. Control: `heap_buffers` pool, same loop.

**[Amended 2026-10-26, stage-4 step 0, B2e/B2h]** (i) The extra allocate in step 4 is made on a second allocator `b = pool.newAllocator("t2")` of the same pool (not on `a`), so step 5 (`a.setDiscarding(); a.setDiscarded()`) releases `a`'s charge and wakes the parked thread, which then completes on `b` with `pool.offHeap.used() == S`. (ii) The `heap_buffers` control pool is a `SlabPool(heapLimit, 0, ...)`, whose allocator is a `SlabAllocator`, not a `NativeAllocator`: the control loop calls `SlabAllocator.allocate(S, group)` (same sizes, same L as the on-heap limit passed to the pool) and reads `pool.offHeap.used()` (expected 0) and `pool.onHeap.used()` (expected to rise, positive control that the loop charges something). Reason: a cast of the control allocator to `NativeAllocator` cannot work; independent of any reading. (iii) Step 6: `barrier.issue()` alone does not make the group blocking; `isBlocking` is set by `OpOrder.Barrier.markBlocking()` (`OpOrder.java:407-415`, `Group.markBlocking :333`; Cassandra's flush calls `writeBarrier.issue()` then `writeBarrier.markBlocking()`, `ColumnFamilyStore.java:1238`), so the probe calls both on a barrier of the group's `OpOrder` before the extra allocations. (iv) The `heap_buffers` control fills the same count N = floor(L/S) of allocations with the on-heap limit 1 GiB (B2b(i)), so the extra allocate must not park.

**B2f. Predictions (before any run).** For every S: `used() == N*S` exactly (sum of requests) and `used() <= L`; `N*S > L - S`. Extra allocate blocks (state WAITING) for 2 s; after discard it completes and `used()==S`. Region capacity sum is >= `used()`; for S <= 128 KiB the excess is < one region (<= 1 MiB) plus rounding from the doubling sequence 8K,16K,...,1M (cumulative tail waste < 1 MiB); for S = 128 KiB+1 capacity sum == `used()` exactly (oversize regions are exact size). NMT "Other" delta ~ capacity sum (within ~5%). Ceiling scales with L: used at block = 32/64/128 MiB (within one S). With the blocking group: allocation proceeds past L (used() > L), proving the documented bypass (A3 step 3). With `heap_buffers`: `offHeap.used()` stays 0 and no blocking at any L.

**[Amended 2026-10-26, stage-4 step 0, B2f]** The sentence "for S <= 128 KiB the excess is < one region (<= 1 MiB) ... cumulative tail waste < 1 MiB" is wrong from the source alone: every region swap (`NativeAllocator.trySwapRegion`, lines 156-184) strands the unused tail of the old region (< S bytes), and for 8 KiB < S <= 128 KiB there is one swap per region of up to 1 MiB, so the cumulative excess `sum(region capacity) - used()` is < (number of regions) x S. The prediction is replaced by: `capacity_sum >= used()`; `capacity_sum - used() < (regions - 1) x S + C`, where C is the capacity of the last (partly filled) region, <= 1 MiB (the stranded tails are < S each; the unfilled remainder of the current region is also counted in the capacity sum but is not stranded); for S = 128 KiB the excess is 0 when L/S is a multiple of 8 (L = 32, 64, 128 MiB: 256, 512, 1024 allocations fill 1 MiB regions exactly; the first regions 8K/16K/... cannot hold one and are skipped by the `highestOneBit(minSize) << 3` rule, which gives 1 MiB); for S = 100 KiB it is `0.020 x used() <= excess <= 0.024 x used() + 1 MiB` (24 KiB stranded per full 1 MiB region plus the last remainder); for S = 128 KiB+1 and 1 MiB it is exactly 0 (oversize regions are exact). The `RssAnon` band is `[used() - 1 MiB, capacity_sum + 4 MiB]` (the +4 MiB is the measured JVM-warm-up noise floor of the instrument check, about 3 MiB at L = 1 MiB) and is applied for L >= 32 MiB; at L = 1 MiB it is a reading only. All other statements of B2f stand.

**B2g. Readings.**

| Observation | Meaning |
|---|---|
| `used()` plateaus at `<= L` and extra allocate parks, scaling with L | Claim holds at the operand level |
| S = 128 KiB+1 also plateaus at `L` (not at `L` + unbounded) | Oversize path (line 144) is charged: entry-point constant is not an escape |

**B2h. Controls.** The `heap_buffers` pool (limit has no effect); a pool with a tiny L (1 MiB) giving the same plateau at 1 MiB; blocking vs non-blocking group; cleaner stubbed so no flush frees memory.

### B3. Cluster tier

**B3a. Environment and build.** One node (second optional). Linux, JDK 11, Ant. `cp -a ~/cassandra-5.0.9 /local/tmp/c509n && cd /local/tmp/c509n && ant jar`. Data, commitlog, hints, saved_caches on local disk (`/local/tmp/node1/{data,commitlog,hints,saved_caches}`, >= 50 GiB free, verify with `df`). `cassandra.yaml` changes: `memtable_allocation_type: offheap_objects`; `memtable_offheap_space: <L>MiB`; `memtable_heap_space: 1024MiB`; `memtable_flush_writers: 1` (cleanup threshold becomes 0.5); `commitlog_total_space: 4096MiB`; `file_cache_size: 64MiB`; `key_cache_size: 0MiB`; `row_cache_size: 0MiB`; `concurrent_compactors: 1`; `compaction_throughput: 16MiB/s`. JVM (`conf/jvm11-server.options` / `JVM_EXTRA_OPTS`): `-Xms2G -Xmx2G -XX:NativeMemoryTracking=summary -XX:MaxDirectMemorySize=256m`; `listen/rpc` on loopback or local interface. Start `bin/cassandra -f` in background with logs on local disk.

**[Amended 2026-10-26, stage-4 step 0, B3a/B3c/B3d/B3f]** Four changes, all from the source and the arithmetic below, none from a reading. (1) `memtable_cleanup_threshold: 0.99` is added to the yaml (valid range 0.01-0.99, `DatabaseDescriptor.java:770-773`; default 0.5 with `memtable_flush_writers: 1`). Reason: with the default threshold a flush starts at 0.5 x L and the tracked peak is `0.5 L` plus whatever the writers add while the flush runs, i.e. a rate-times-flush-time term that does not scale with L, so neither the limit nor the 1:2:4 ratio would be reached or tested; at 0.99 the flush starts at 0.99 L, the writers reach L within milliseconds and park on `hasRoom` until the flush releases the memtable, which is the disallow branch (`MemtableAllocator.java:175-195`) and makes `BlockedOnAllocation` > 0 certain. The statement "flush triggered near 0.5*L" in B3f reads "near 0.99*L". (2) The JVM gets `-XX:+AlwaysPreTouch` (heap committed and resident at start) and RSS is read as `RssAnon` from `/proc/<pid>/status` (not `VmRSS`; sstable pages on tmpfs and mmap are file/shmem pages), otherwise heap churn alone grows the resident set by up to 2 GiB regardless of L and the RSS relation of B3f could not be read; NMT "Other" stays the primary real-resource reading. (3) Data, commit log, hints and saved caches go on a tmpfs (`/dev/shm/<work dir>`, no `/local/tmp`), as the repository lessons require for a node on a shared host. (4) `write_request_timeout: 30000ms` and `native_transport_timeout: 60000ms` so that writers parked at the limit are not timed out.

**B3b. Knobs.** L = 128, 256, 512 MiB (one restart each, fresh data dir); `memtable_allocation_type` heap_buffers as negative-mode control (same L=256); value size 1 KiB (in-region path) and 256 KiB (above `MAX_CLONED_SIZE`, oversize path, line 144-145).

**B3c. Workload.** Table `ks.t (pk bigint, ck int, v blob, PRIMARY KEY (pk, ck))`, compaction `SizeTieredCompactionStrategy` default, RF 1. Use `bin/cassandra-stress` (from the build): small values: `cassandra-stress write n=3000000 cl=ONE -col size=FIXED(1024) n=FIXED(1) -rate threads=128 -schema "replication(factor=1)"`. Arithmetic: 3 M x ~1.1 KiB ~ 3.3 GiB, i.e. >= 6x the largest L=512 MiB of memtable data, so the limit must be reached, and flushes must repeat. Large values: `n=2000` partitions via a small cqlsh/driver loop writing 256 KiB blobs, 3000 rows = 750 MiB (>1.4x of L=512; for L=128 repeat 2500 rows), with 16 client threads. Duration: until the workload finishes (minutes), sample throughout.
