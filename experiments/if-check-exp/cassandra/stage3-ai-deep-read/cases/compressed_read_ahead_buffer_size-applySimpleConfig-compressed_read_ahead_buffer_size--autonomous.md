A compaction of k SSTables opens all k scanners in its thread before reading ([`AbstractCompactionStrategy.java:256-266`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/compaction/AbstractCompactionStrategy.java#L256-L266)) and holds them until the task ends: k × B. Concurrent compactions (`concurrent_compactors`) and range reads (each `ReadStage` thread × SSTables it scans) add theirs. Nothing sums or limits the total: no counter, no pool, no cap (the only check on the value is the start-up/JMX range check). Release is on the closing thread's map (`clear(true)` looks up `blockMap.get()`, `:132-150`), so a scanner closed on another thread than it was opened on would leave its buffer allocated (not exercised here). **Two more facts the runs depend on:** (1) the JMX setter rejects 0 ([`DatabaseDescriptor.java:2554-2557`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L2554-L2557), "`compressed_read_ahead_buffer_size_in_kb must be at least 256KiB`") while start-up accepts 0 as "disabled" (`:960`), and a runtime change affects only `CompressedChunkReader.Standard` instances built afterwards ([`CompressedChunkReader.java:236`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/io/util/CompressedChunkReader.java#L236)); (2) *correction to B3a:* on this machine `bin/cassandra` sets `-XX:MaxDirectMemorySize` to a quarter of RAM (`conf/cassandra-env.sh:57-66, 139-140, 157-158`: 8192M at 32 GiB), not "= heap"; the run reads the value from the node's command line. **Other direct-memory consumers during a scan or a compaction** (bounding the tolerance bands below): each scanner's `BufferManagingRebufferer` takes a chunk-sized buffer from `BufferPools.forChunkCache()` ([`BufferManagingRebufferer.java:42-47`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/io/util/BufferManagingRebufferer.java#L42-L47)), which allocates direct memory in 8 MiB macro-chunks (`BufferPool.java:128, 385, 443-460`) and returns buffers to the pool on close (`:810-826`) without freeing the chunk; `ThreadLocalByteBufferHolder` keeps one per-thread direct buffer of the largest compressed chunk read ([`ThreadLocalByteBufferHolder.java:69-80`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/io/util/ThreadLocalByteBufferHolder.java#L69-L80); ≈ 16.5 KiB); the compaction writer's buffers are chunk-sized. Bloom filters, index summaries and compression offsets use `Memory` (`Unsafe`), not the direct pool. So the direct memory not from read-ahead buffers that a scan or compaction can add is at most one macro-chunk plus ≤ 1 MiB: **≤ 9 MiB**.

**A4. Other consumers.** Per-thread compressed/uncompressed chunk buffers (`ThreadLocalByteBufferHolder`, `CompressedChunkReader.java:125-131`), `BufferPool` (networking/chunk cache), memtable off-heap, bloom filters, index summaries.

**A5. Evidence beyond the source.** CASSANDRA-15452 (https://issues.apache.org/jira/browse/CASSANDRA-15452), `CHANGES.txt:148`.

## B. Verification solution

**B1. Claim under test.** (a) Values 1–255 KiB stop startup; 0 and ≥ 256 KiB are accepted. (b) With size B (> chunk length) and k SSTables scanned concurrently by one thread, the direct memory attributable to read-ahead is ≈ k × B while the scans are open and returns to baseline when they close; with B = 0 or B ≤ chunk length it is ≈ 0.
