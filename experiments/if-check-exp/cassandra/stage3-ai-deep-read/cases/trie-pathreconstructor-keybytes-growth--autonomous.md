## A. Constraint trace

**A1. The constraint.** There is no resource constraint at the entry point. Line 33 is inside `addPathByte`:
`if (keyPos >= keyBytes.length) keyBytes = Arrays.copyOf(keyBytes, keyPos * 2);`
(`TriePathReconstructor.java:31-36`). The field `keyBytes = new byte[32]` is declared at `:28`, `keyPos` at `:29` [amended 2026-10-25, R1: the filed `:26`/`:27` and `:31-35` were off by two/one lines; `addPathByte` is `:31-36`, with the growth `if` at `:33` and the `copyOf` at `:34`]. The "32" is a hard-coded constant, not settable by yaml, `-D`, or JMX; a change needs a code change. Nearest real limit that indirectly bounds it: the maximum partition-key size `FBUtilities.MAX_UNSIGNED_SHORT` (65535 bytes), enforced at `src/java/org/apache/cassandra/cql3/Validation.java:51-55` (kind: constant, bytes, not configurable). Clustering-key limits (`db/ClusteringPrefix.java:278-287`) apply to rows inside a partition and are not part of memtable trie paths (see A3).

**A2. What it caps.** Nothing deliberately. It is on-heap, per-iterator scratch space holding the byte-comparable path of the trie cursor's current position. The quantity that determines `keyBytes.length` is the max depth (bytes) of a path walked so far by that iterator, rounded up by the doubling policy.

**A3. Mechanism.**
1. Users: only `TrieEntriesIterator` (`db/tries/TrieEntriesIterator.java:30`, extends this class) and `TrieEntriesWalker` (`TrieEntriesWalker.java:28`); no other subclass in `src/java` (grep).
2. `Trie.entryIterator()` (`Trie.java:433-435`) builds `TrieEntriesIterator.AsEntries`; the iterator's `hasNext()` calls `cursor.advanceToContent(this)` (`TrieEntriesIterator.java:48`; default method `Trie.java:~200-220`), which calls `addPathBytes` for chain-node runs (through `advanceMultiple`, `InMemoryReadTrie.java:573`, at most one chain block, about 28 bytes, per call), then `addPathByte` for each incoming transition (`Trie.java:214`) and `resetPathLength` (`Trie.java:213`) when it ascends [amended 2026-10-25, R1].
3. `addPathByte` (`:31-36`): when `keyPos >= length`, new array of `keyPos*2` (so 32->64->...). `addPathBytes` (`:38-45`): grows to `max(newPos+16, 2*length)`. `resetPathLength` (`:47-50`) only moves `keyPos`; the array never shrinks for the iterator's life.
4. Each returned entry copies the used prefix: `toByteComparable` -> `Arrays.copyOf(bytes, byteLength)` (`:52-55`; used at `TrieEntriesIterator.java:84`, `TrieEntriesWalker.java:34`) [amended 2026-10-25, R1: `TrieEntriesWalker.java:53` was wrong]. These copies are per-entry garbage sized to the path.
5. Memtable use: `TrieMemtable` flush (`TrieMemtable.java:356`, the key-size pass over `toFlush.entryIterator()`, and `:392`, the iterator the flush writer consumes) and partition range reads (`:552`, in the `MemtableUnfilteredPartitionIterator` constructor, `source.entryIterator()`) [amended 2026-10-25, R1: `~356` is the first of two flush sites]. Memtable trie keys are partition keys (token-ordered prefix-free byte-comparable form), so the path length is about key length + small constant, [amended 2026-10-25, R3: the filed text bounded the path by 65535 + overhead and `keyBytes.length` by 131072; that is wrong. 65535 bounds the partition key (`Validation.java:51-55`), not the path. A memtable path is the byte-comparable `DecoratedKey`: the 8-byte Murmur3 token, a component separator, the key with every 0x00 escaped to two bytes plus an end-of-key escape, and a terminator (`DecoratedKey.java:105-114, 130-133`, `ByteSource.java:101-114, 133-138, 329-376`). So path = L + e + c, with e the number of extra bytes the escaping adds and c a small constant (about 10 to 12, measured by the unit tier). A 65535-byte key therefore has a path above 65535 [amended 2026-10-25, R9, AFTER unit run 1a (see B5): the filed text said each 0x00 is escaped to two bytes, so that a key of 65535 zero bytes would have a path of about 131082; wrong. `ByteSource.AbstractEscaper.next()` (`ByteSource.java:329-376`) writes the first 0x00 of a run as 0x00 and each further one as 0xFE, then one 0xFF at the end of the run, so e is at most one byte per maximal run of 0x00 (at most about L/2 runs) and a key of all zeros has e of one byte; the invariant P <= cap <= 2P is unaffected] The only bound the source gives is the invariant of the two growth rules: the longest path walked `P` satisfies `P <= keyBytes.length <= max(32, 2P)` (a first growth by `addPathBytes` can give `newPos + 16`, not a power of two).]
6. Outcomes at "limit": there is no check. Growth is unconditional; if the JVM cannot allocate, `OutOfMemoryError`. Nothing rejects, evicts or flushes because of it. Overshoot paths: every concurrent iterator holds its own array (one per concurrent range read / flush), so total = (#live iterators) x (<=128 KiB), governed by `concurrent_reads` and client concurrency, not by any memory limit.

**A4. Other consumers.** The same heap is used by the memtable itself (bounded by `memtable_heap_space`/`memtable_offheap_space`, `Config.java:186-189`; on-heap trie metadata via `InMemoryTrie` `InMemoryTrie.sizeOnHeap()`, `InMemoryTrie.java:975`) [amended 2026-10-25, R2: there are no methods `usedSizeOnHeap/usedSizeOffHeap`; they are `sizeOnHeap()` (`:975`) and `sizeOffHeap()` (`:969`), read by `TrieMemtable.java:477-485` to charge the allocator], row cache, key cache, chunk cache, read buffers, and the per-entry copies in A3.4. None are governed by this array.

**A5. Evidence beyond the source.** none (Cassandra CEP-19 trie memtables is the background for TrieMemtable, not relied on for any claim).

## B. Verification solution

**B1. Claim under test.** `keyBytes.length` of a `TriePathReconstructor` follows only the longest path length walked (32 * 2^k >= path length, or newPos+16 on bulk adds), regardless of any memtable memory setting, and the array is outside the memtable allocator's accounting; therefore no configured limit caps it. It is falsified if (a) its size changes with `memtable_heap_space`/`memtable_offheap_space` at fixed key length, or (b) its bytes appear in the memtable's accounted size (`InMemoryTrie.sizeOnHeap()/sizeOffHeap()`, `MemtablePool` allocated) [amended 2026-10-25, R2: method names].

**B2f. Predictions.** amended 2026-10-25,R5, before any reading: the filed staircase of exact powers of two is replaced by the invariant of the two growth rules (`TriePathReconstructor.java:33-34, 40-45`)]. (7) N iterators in N threads allocate at least N x `cap()` bytes in total over a single iterator (thread-allocated bytes, inferred scratch = N x `cap()`).
