# U10 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/default_page_size--unpaged-aggregate-whole-partition/default_page_size--unpaged-aggregate-whole-partition.md`](../cases/default_page_size--unpaged-aggregate-whole-partition/default_page_size--unpaged-aggregate-whole-partition.md)
(verdict true positive; `verified-OOM · deployment`, unprotected configuration + bypass of the internal row bound).

**Mechanism checked (case §4).** A plain aggregate (`SELECT count(v) … WHERE pk = ?`) sent with client paging off is paged
internally with `NO_LIMIT` (`AggregationPartitionIterator` maps page size ≤ 0 to `NO_LIMIT`; the `DEFAULT_PAGE_SIZE`
fallback "to avoid OOM" applies only to GROUP BY), so the replica serializes the whole slice into one heap
`DataOutputBuffer` (`LocalDataResponse.build`). The byte threshold (`read_thresholds_enabled`) ships off; nothing sums
concurrent reads → Java heap OOM on one query at 2 GiB.

**Label: `known-fixed (not in 5.0.9) (partial: CASSANDRA-11745)`** — fixed in 6.0-alpha3 / 7.0 as part of byte paging;
no issue reports the unpaged-aggregate OOM itself.

**Documented:** no. `conf/cassandra.yaml:2015` only has `# read_thresholds_enabled: false # scheduled to be set true in
4.2`; nothing in `doc/`, `NEWS.txt` says that an aggregate with paging off reads its whole input in one request. (Trunk's
yaml adds `aggregation_subpage_size`: "It aims to limit the memory used by aggregation queries when there is a lot of data
to aggregate" — not in 5.0.9.)

**Reason.** No issue reports that a plain aggregate with paging off is read in a single unbounded sub-page; stage 1's
JIRA check (2026-11-18) found the behaviour acknowledged in 9724/17222 and called the OOM `new`. Since then (2026-10-27,
missed by stage 1) CASSANDRA-11745 was committed to `cassandra-6.0` and `trunk`: aggregation queries now use
`aggregation_subpage_size` (2 MiB, bytes) whenever the client sends no page size, which removes this case's trigger by
construction (read from trunk's `SelectStatement.getPager`; not run). 11745 reports the same holder class (count-bounded
reads held whole) and its discussion names the aggregation internal page, but not this trigger, so the match is
**partial**; it is **fixed**, and `git merge-base --is-ancestor 8f6787959e cassandra-5.0.9` is false, and the commit is
on no 5.0/4.x branch → **known-fixed (not in 5.0.9)**, fix versions 6.0-alpha3 / 7.0. The 5.0 line remains exposed.
