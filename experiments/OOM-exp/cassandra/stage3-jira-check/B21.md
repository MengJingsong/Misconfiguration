**Mechanism checked (case §4).** Holder: each replica's eagerly built Top-K result for an ANN query
(`VectorTopKProcessor.takeTopKThenSortByPrimaryKey` / `ScoreOrderedResultRetriever` → `TreeMap<…, TreeSet<Unfiltered>>`)
plus its serialized response `DataOutputBuffer`. Trigger: concurrent `ORDER BY … ANN OF … LIMIT 1000` queries over wide
rows. Controls: Top-K always runs unpaged (exempt from paging, by design, warned); `MAX_TOP_K` counts rows, not bytes;
the read-size thresholds ship off and, when on, fire only after the top-K map exists; nothing sums bytes across queries.

## Documented

**no.** The only shipped statement on the Top-K limit is a row cap with no memory warning:
`doc/modules/cassandra/pages/vector-search/_query-vector-data-cycling.adoc:28` "* The limit must be 1,000 or fewer."
`NEWS.txt:178` only announces the feature ("Added ANN vector similarity search via ORDER BY ANN OF syntax on SAI indexes").
`conf/cassandra.yaml:2012-2026` documents the read thresholds as off by default without mentioning Top-K.

## Reason

Re-checked stage 1's queries and added identifier searches for the measured holder (`VectorTopKProcessor`,
`takeTopKThenSortByPrimaryKey`) and the newer issues. The forced-unpaged Top-K execution is by design (18715), the
over-materialization of the pre-5.0.7 path was fixed in 5.0.7 (20086, present in 5.0.9 and not removing the holder), and the
general byte limit (11745) lands only in 6.0 and still skips Top-K. No issue names the holder with this or any trigger, and
none reports an OOM from it, so there is no exact or partial match; the docs state the row cap but warn about no memory cost.
Hence **new**.
