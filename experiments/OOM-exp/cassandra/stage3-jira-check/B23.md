# B23 — stage 3 JIRA check (2026-11-23)

**Case:** [`../cases/maxHintsInProgress--uncharged-destination-hint-backlog-non-replica-coordinator/maxHintsInProgress--uncharged-destination-hint-backlog-non-replica-coordinator.md`](../cases/maxHintsInProgress--uncharged-destination-hint-backlog-non-replica-coordinator/maxHintsInProgress--uncharged-destination-hint-backlog-non-replica-coordinator.md)
(verdict true positive, `verified-OOM · deployment`; owner rulings 2026-11-23).

**Mechanism checked (case §4).** Holder: `HintRunnable` tasks (`StorageProxy$7`), each holding its whole `Mutation`, queued
on the unbounded MutationStage of a non-replica coordinator while the single hint writer is parked at the 3 × 32 MiB slab
cap. Control that fails: `checkHintOverload` / `maxHintsInProgress` (128 × cores tasks) can never refuse, because
`StorageProxy.hintsInProgress` is a bare Guava `CacheLoader`, not a `LoadingCache`, so the per-destination operand is a
fresh `AtomicInteger(0)` on every call. Secondary (condition X): even a working limit counts tasks, not bytes.

**Label: known-open (exact: CASSANDRA-10825)**

## Reason

CASSANDRA-10825 is still open and its comment thread names exactly the root cause that B23's intervention fixed: the
per-destination counter lives in a `CacheLoader`, so `checkHintOverload` can never throw; maintainers agreed in 2017 that the
feature "never worked as intended" and that a `LoadingCache` is the fix, but nothing was committed (the 5.0.9 and trunk
sources still have the `CacheLoader`). That is the same control and the same root cause that the B23 trigger exercises, so
the match is **exact**; what 10825 lacks is the consequence (B23's measured heap OOM 3/3 at 2–15.5 GiB with 0 refusals) and
the "tasks, not bytes" sizing point (condition X), which only 8415 touches (it chose the task count). The hint-backpressure
issues (10972, 19958) bound or separate other parts of the path, not the queued hint tasks. Not documented.
