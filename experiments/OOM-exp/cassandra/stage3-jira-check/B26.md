**Mechanism checked (case §4).** Holder: the `LOCAL_READ_TIME` sampler of `nodetool profileload`
(`TableMetrics.topLocalReadQueryTime`, a `MaxSampler` whose `MinMaxPriorityQueue` keeps the slowest reads), whose items are
whole rendered CQL strings: while the sampler is on, every local read calls `command.toCQLString()` in
`ReadExecutionController.addSample` (`ReadExecutionController.java:236-242` at 5.0.9) and offers the string. Trigger: an
operator runs `profileload` with its shipped defaults (`-s 256`, 10 s, all samplers; or the all-tables form) while clients
send single-partition reads with large clustering-`IN` lists of large blobs (≈ 8 MB requests, inside the 16 MiB native frame;
the IN cartesian-product guardrail ships off), each rendered to a ≈ 16 MB hex string. Controls that fail: the capacity counts
strings, not bytes (`maximumSize(Math.max(1, capacity))`, `MaxSampler.java:46`); nothing bounds the string size except the
request size × ≈ 2; `finishSampling` takes only `count + 2` entries (`:52-59`), so the rest stay until the next session on that
table. Intervention that removed it: keep only the first 1,024 characters of each sample (render unchanged); `-s 32` as dose.

**Label: new**

## Reason

B26's mechanism (while `profileload` runs, every local read renders its whole command to a CQL string and the `LOCAL_READ_TIME`
`MaxSampler` keeps up to 256 of them per table, counted and never sized, so large clustering-`IN` reads make each kept item
≈ 16 MB and the queue, which outlives the session, fills the heap) is not reported in JIRA. The issue that created the holder
(CASSANDRA-14436) introduced exactly this code (`String cql = command.toCQLString()` in `ReadExecutionController`) and documents
capacity only as a number of items with a generic "understand the memory trade offs"; its review discussed CPU overhead, not
the size of a sampled query. Later profileload work (18022, 17821) extended the samplers without touching what an item holds;
the other `toCQLString` hits use the string for one-off log messages, and the toppartitions issues are command errors. All are
`related` or `none`. The code and defaults are unchanged in 5.0.x, 6.0 and trunk, so there is no newer fix, and the shipped
docs and help give no warning (the help calls it "Low footprint"). Label **new**. The stage-1 prior-art check (§1, 9 queries,
verdict `new`) agrees; this check adds the reading of 14436's review thread, the history-clone version check and the docs check.
