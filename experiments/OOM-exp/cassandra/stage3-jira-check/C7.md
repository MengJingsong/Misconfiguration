# C7 — stage 3 JIRA check (2026-11-24)

**Case file:** [`../cases/repair_session_space--coordinator-merkle-tree-backlog/repair_session_space--coordinator-merkle-tree-backlog.md`](../cases/repair_session_space--coordinator-merkle-tree-backlog/repair_session_space--coordinator-merkle-tree-backlog.md)
(verdict true positive; `verified-OOM · deployment`, convergence under an unprotected default: `concurrent_merkle_tree_requests` 0).

**Mechanism checked (case §4).** `repair_session_space` (heap/16) bounds the Merkle trees built for **one** validation
request to `repair_session_space / RF`, but the repair coordinator receives one tree set from every replica for every
(session × table) job, and the aggregate control `concurrent_merkle_tree_requests` ships at 0 (no limit), so every job
requests its trees at once (`RepairCoordinator.java:127`, `NoopScheduler`). Each set waits in direct memory on the
coordinator until all RF sets of its job arrive; the coordinator, a replica in every session, validates ≈ 3 × as much as
each peer, so the peers' sets pile up. `nodetool repair --full` of 106 small tables on a 4-node RF 2 cluster killed the
coordinator with `OutOfMemoryError: Direct buffer memory` in `MerkleTree.allocate` 3/3 at a 2 GiB direct limit (164 sets
held, 96 % of live direct memory in `MerkleTree$OffHeapInner`); 4 tables and `concurrent_merkle_tree_requests: 1` both
completed 3/3.

**Label: `known-fixed (incomplete) (exact: CASSANDRA-19336, CASSANDRA-17787)`**, also **documented**.

**Documented:** yes. `conf/cassandra.yaml:848-849` (`concurrent_merkle_tree_requests`): "There isn't a limit by default for
backwards compatibility, but this can produce OOM for  commands repairing multiple tables or multiple virtual nodes." with
the default at `conf/cassandra.yaml:861` ("# concurrent_merkle_tree_requests: 0") and a pointer to CASSANDRA-19336 (l. 858);
`conf/cassandra.yaml:827-829` (`repair_session_space`): "Limit memory usage for Merkle tree calculations during repairs of a
certain table and common token range. Repair commands targetting multiple tables or virtual nodes can exceed this limit
depending on concurrent_merkle_tree_requests."; `CHANGES.txt:352`: "Add new concurrent_merkle_tree_requests config
property to prevent OOM during multi-range and/or multi-table repairs (CASSANDRA-19336)". The docs do not say that the
trees are direct memory on the coordinator or how many tables reach the direct limit.

**Reason.** The case is reported exactly in JIRA: 17787 describes the same many-table full repair dying with a direct OOM
from remote trees held on the coordinator, and 19336 (its duplicate target) diagnoses the same root cause — every validation
request in flight at once — and adds the bound. Its fix commit is in 5.0.9, but the bound ships disabled by choice
("keeps the previous behaviour"), so at defaults the fix does not cover the mechanism: by the owner's ruling of 2026-11-23,
an incomplete fix in the pinned version is **known-fixed (incomplete)**. The shipped yaml warns of exactly this OOM, so the
case is also documented. Two readings are flagged for the owner: (a) the unbounded default is a deliberate, documented
choice, which reads as `known-wontfix / by design` for the default; (b) the 16909 umbrella still lists the unbounded
in-flight trees as a bug and 21377 (open, partial) proposes moving the trees to disk, which could support `known-open`.
`known-fixed (incomplete)` is kept because the issue that reports the case is closed with a fix in 5.0.9 that does not
apply at defaults (as B8 under the same ruling). Stage 1 recorded "documented / known-open at defaults" (2026-11-18);
the label differs by the 2026-11-23 rulings, not by new evidence.
