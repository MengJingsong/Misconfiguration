# B28 — stage 3-a JIRA check (2026-11-24)

**Case:** [`../cases/tracing_stage_queue_limit--traced-16MiB-query-text-backlog/tracing_stage_queue_limit--traced-16MiB-query-text-backlog.md`](../cases/tracing_stage_queue_limit--traced-16MiB-query-text-backlog/tracing_stage_queue_limit--traced-16MiB-query-text-backlog.md)
(verdict true positive, `verified-OOM · deployment`; bypass, accounting omission; heap 2, 4 and 8 GiB 3/3, 12 GiB survives;
from OC-453). Checked by a fresh session that did not design or verify the case; owner rulings of 2026-11-23 and 2026-11-24
applied.

**Mechanism checked (case §4).** Holder: trace mutations queued on the single-thread TRACING stage, each carrying the uncut
query text of a client-traced unprepared QUERY: the `system_traces.sessions` start row (`parameters['query']`,
`QueryMessage.java:138`) and the `"Parsing <query>"` event (`QueryProcessor.java:896`), ≈ 2 × S bytes per request. Trigger: an
ordinary client sets the frame's tracing flag (`0x02`, no permission or server setting needed) on 16 MB QUERYs from a few
connections, faster than the one tracing thread can write 16 MB mutations through the commit log and memtable. Controls that
fail or are missing: the TRACING queue limit counts tasks, not bytes (`withQueueLimit(1000)`, `Stage.java:200-202`); the
request does not wait for its trace writes (`cassandra.wait_for_tracing_events_timeout_secs` = 0,
`CassandraRelevantProperties.java:627`); the native in-flight charge is released when the response is flushed, so the queued
copies are charged by nothing → `OutOfMemoryError: Java heap space`, TRACING queue 64–77 % of every dump. Intervention that
removed it: a 64 MiB byte bound on queued trace work.

**Label: `new`** (closest issues all `related`: CASSANDRA-13157 open, 10444 open, 8303 open, 12750 open, 1123, 12754 / 12755,
11719, 4672, 5658 Not A Problem)

**Alternative for the owner.** CASSANDRA-13157 (Open, 2017, "reduce overheads of tracing") says that storing "a string
description for every trace line of every request that gets traced ... adds a completely unnecessary memory and IO overhead".
It names the same kind of payload (trace strings) but reports only a per-request overhead, with no queue, no size or OOM, and
no query text; it is rated **related**, as stage 1 rated it. If the owner counts a report of the memory cost of trace strings
as **partial**, the label becomes **`known-open (partial: CASSANDRA-13157)`**.

## Reason

B28's mechanism (any client can trace an unprepared QUERY; each traced request leaves two uncut copies of its query text as
mutations on the single-thread TRACING stage, after its native in-flight charge is released and without waiting for them; the
stage bounds the queue at 1000 tasks, not bytes, so 16 MB query texts from a few connections outrun the one writer and fill the
heap) is not reported in JIRA. The pieces are known separately and for other reasons: 1123 designed the asynchronous
single-thread stage with a count-bounded queue that drops when full; 4672 made `_TRACE` droppable; 12754 stopped requests from
waiting on trace writes, for latency; 11719 cut bound values to 1000 chars because they "can become quite big", but not the
query text; 12750, 10444 and 8303 report dropped `_TRACE` and performance overhead from client-enabled tracing and ask for a
server-side off switch (open); 13157 calls trace strings a needless memory and IO overhead (open, no OOM). All are `related`;
none is fixed in 5.0.x, 6.0 or trunk in a way that bounds queued trace bytes, and the shipped docs give no warning. Label
**new**, agreeing with stage 1 (§1, 10 queries, `new`, related 13157 and 10444); this check adds 1123's design rationale for the
count-bounded queue, 4672, 12754 / 12755, 8303's dropped-`_TRACE` comment, 11719's size cut, the history-clone version check
and the docs check. If the owner rates 13157 partial, the label is `known-open (partial: CASSANDRA-13157)`.
