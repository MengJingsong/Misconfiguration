# B19 — stage 3 JIRA check (2026-11-23)

**Case:** [`native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed`](../cases/native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed/native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed.md)
(true positive on T2, `verified-OOM · deployment`; T `candidate`, V4 partial; owner ruling on T2's form still open).

**Mechanism checked (§4).** On a v3/v4 connection with LZ4 negotiated in STARTUP, `LZ4Compressor.decompress` allocates
`heapBuffer(uncompressedLength)` from the client-declared first 4 body bytes before any check (`Compressor.java:184`): **T2**, one
22-byte frame declaring 1.90 GiB OOMs a 2 GiB node. **T**: the decompressed body is kept until the response is flushed while
both in-flight limits and the frame cap charge the compressed length (U/K ≈ 287).

**Label: `known-open` (exact: CASSANDRA-14997)** for T2, the condition the verdict rests on. T (in-flight charged at the
compressed size) is **new**.

## Reason

CASSANDRA-14997 reports exactly T2 (an erroneous uncompressed length tipping the node over through the native-protocol
decompressor) and is still Open with an uncommitted 2019 patch whose author noted it would not cover `Integer.MAX_VALUE`; the
5.0.9 code still allocates at `Compressor.java:184`. So the verdict condition is `known-open`. The re-check found no newer issue on
the native LZ4 path apart from library CVEs. T's accounting gap (charge = compressed size, U/K ≈ 287) has no issue: stage 1's
`new` for T stands.
