# R18 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/index_summary_capacity--parked-load-and-merge-overlap-2560/index_summary_capacity--parked-load-and-merge-overlap-2560.md`](../cases/index_summary_capacity--parked-load-and-merge-overlap-2560/index_summary_capacity--parked-load-and-merge-overlap-2560.md)
(verdict true positive; A `verified-OOM · deployment` mixed, B `verified-OOM · deployment` unprotected accumulation).

**Mechanism checked (case §4).** BIG-format index summaries are JNA-malloc'd outside `-Xmx` and `MaxDirectMemorySize`.
`index_summary_capacity` (5 % of heap) is enforced only by the 60-min redistribution, so summaries loaded or written in the
window sit at full sampling (A: 316 MB parked vs a 64 MB pool). A default STCS merge then holds its inputs' summaries, the
output bloom filter and compression metadata, and the growing output summary (`SafeMemoryWriter`, old + new block at each
growth, one more copy at the trim) at once. A (parked P + one merge) and B (one large merge alone) are memcg-killed 3/3 in a
2,560 MiB container at heap 1,280 / direct 640.

**Label: `documented only`**

**Documented:** yes (pool overshoot only). `conf/cassandra.yaml:931-936` (`index_summary_capacity`): "A fixed memory pool
size in MB for for SSTable index summaries. If left empty, this will default to 5% of the heap size. If the memory usage of
all index summaries exceeds this limit, SSTables with low read rates will shrink their index summaries in order to meet
this limit. However, this is a best-effort process. In extreme conditions Cassandra may need to use more than this amount
of memory." and `conf/cassandra.yaml:941-944` (`index_summary_resize_interval: 60m`): "This is done periodically to
redistribute memory from the fixed-size pool…". The docs do not mention the merge's output summary, its growth/trim copies,
the output bloom filter, or that this memory is outside the heap and direct limits.

**Reason.** No issue reports a compaction's input summaries + output summary builder (with its growth/trim copy) + bloom
filter + compression metadata, alone or on top of a parked uncapped summary load, as the cause of an OOM. JIRA has the
design of the periodic pool (5519), the trim bug that made the copy larger (14649, fixed in 5.0.9's code base; R18's copy is
the corrected one, so not a regression), and OOM-kill reports in large compactions without a holder (8552 Cannot
Reproduce, 10821 Won't Fix, 20565 Not A Bug); none is exact or partial. The shipped yaml, however, warns that the summary
pool is best-effort and that "Cassandra may need to use more than this amount of memory", which is the U > C that both
conditions exercise (A's parked P, B's input summaries above the pool), and the 60-min resize interval is documented. So the
label is `documented only`, with the limit that the docs cover the pool overshoot but not the merge's transient
native memory that completes the kill (that part is unreported and undocumented). Stage 1 (2026-11-21) recorded `new`; the
difference is the documented-source rule of stage 3, not new JIRA evidence.
