# R14 — stage 3 JIRA check (2026-11-23)

**Case:** [`in_select_cartesian_product--select-IN-ck-product-growth-step`](../cases/in_select_cartesian_product--select-IN-ck-product-growth-step/in_select_cartesian_product--select-IN-ck-product-growth-step.md)
(true positive, `verified-OOM · deployment`).

**Mechanism checked (§4).** `SELECT … WHERE pk = 0 AND c1 IN ? AND c2 IN ?` is expanded by `MultiCBuilder` into the full
clustering cartesian product on the request thread (one `ArrayList` + `Object[2]` per combination) before any limit; the only
control on that count, the `in_select_cartesian_product` guardrail, ships at −1 and is skipped for superusers (every client under
`AllowAllAuthenticator`), and when enabled checks only after each column's product exists. One 12.8 MB request OOMs an 8 GiB heap.

**Label: `known-open` (exact: CASSANDRA-15250)**, also **documented** (opt-in guardrail, off by default).

## Reason

CASSANDRA-15250 is still Open with no fix version or update since 2019, and reports the same unbounded materialization of an IN
cartesian product that R14 measured (on partition-key IN; the clustering form goes through the same `MultiCBuilder`). The
mitigating guardrail (17187, which itself cites the clustering-key form) is in 5.0.9 but ships disabled and does not apply under the
default authenticator. Newer `MultiCBuilder` work (2024–2026) only trims allocations. Stage 1's verdict (`known-open` + documented)
holds under the new rules, with 15250 now rated exact on root cause.
