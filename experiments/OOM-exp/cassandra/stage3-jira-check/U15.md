# U15 — stage 3 JIRA check (2026-11-23)

**Case:** [`../cases/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog.md`](../cases/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog.md)
(verdict true positive, `verified-OOM · deployment`).

**Mechanism checked (case §4).** Trigger: a CQL slice `DELETE … AND ck > ?` never runs `ClusteringPrefix.validate()`
(`ModificationStatement` slice branch), so a > 65,535-B bound is accepted; the memtable flush then fails in `StatsMetadata`
serialization and `Flush.run` only records the failure, so the memtable's pool share stays "reclaiming" forever. Two such
flushes leave the cleaner unable to fire, all 32 MutationStage writers park in the allocator. Holder: local writes queued
without bound on MutationStage (≈ 70 % of the heap) → Java heap OOM.

**Label: known-open (partial: CASSANDRA-13213) — the trigger (slice-bound validation bypass poisoning flushes) is new**

## Documented

**no.** No shipped doc warns that a slice-bound DELETE or a conditional write skips the 64 KiB clustering check, or that a
failed flush pins memtable memory. `conf/cassandra.yaml` memtable section and `doc/` (grep for 65535 / 64 KB / flush
failure) only state limits of other kinds (for example `cql_singlefile.adoc:3017` "Collections cannot have more than 65535
elements").

## Reason

The trigger is unreported: no issue says that a slice DELETE (or `INSERT … IF NOT EXISTS`) bypasses `ClusteringPrefix.validate()`
or that such a bound poisons a flush and pins the memtable pool; 11882 fixed the INSERT route only, and its fix is in 5.0.9.
The holder and endpoint — writers parked on an exhausted memtable pool behind stalled flushes, with mutations piling up on
the unbounded MutationStage until the heap is gone — are reported several times with other triggers (19564, 20084, 12689,
each fixed for its own trigger and present in 5.0.9) and once as an open OOM report without a root cause (13213). Under the
match rules these are **partial** matches (same holder, different trigger / symptom without root cause); the open one makes
the label **known-open (partial)**. Nothing bounds the queue in 5.0.9 or trunk; the case's new contribution is the
validation-bypass trigger plus the failed-flush pool pin.
