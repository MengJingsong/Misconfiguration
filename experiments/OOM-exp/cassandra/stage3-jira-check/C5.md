# C5 — stage 3 JIRA check (2026-11-24)

**Case file:** [`../cases/hints_compression-compressionBuffer--per-destination-writers/hints_compression-compressionBuffer--per-destination-writers.md`](../cases/hints_compression-compressionBuffer--per-destination-writers/hints_compression-compressionBuffer--per-destination-writers.md)
(verdict true positive; `verified-OOM · deployment`, JVM direct-buffer OOM, convergence · multiplicity; claim limited to
deployments that enable `hints_compression`).

**Mechanism checked (case §4).** With `hints_compression` on (LZ4), every open `CompressedHintsWriter` keeps its own
grow-only direct `compressionBuffer` (`CompressedHintsWriter.java:39, 51-56`), sized to the LZ4 bound of the largest
record it was handed (up to 16.06 MiB for a 16 MiB hint). One writer stays open per unreachable destination until its
file rolls at 128 MiB, the destination returns, or shutdown. No hints setting, `BufferPool` or reservation counts these
buffers, so only `MaxDirectMemorySize` bounds their sum: 62 legal 15 MiB writes hinted to 64 unreachable remote-DC nodes
killed the coordinator 3/3 at a 896 MiB direct limit (51 buffers = 768.0 MiB at the failure; 1/1 at 1,024 MiB), the
29-destination control survived 3/3, and one buffer shared by all writers (as the `HintsWriteExecutor` comment intends)
survived 3/3.

**Documented:** no. `conf/cassandra.yaml:122-128` describes `hints_compression` only as "Compression to apply to the hint
files. If omitted, hints files will be written uncompressed. LZ4, Snappy, and Deflate compressors are supported.";
`NEWS.txt:1295-1296` announces the feature and that it is "disabled by default"; `CHANGES.txt:3230` lists 9428. Nothing in
`conf/`, `NEWS.txt` or `doc/` says the compressor keeps a direct buffer per open hints file or per destination.
*Side finding (doc inconsistency, not a warning):* `doc/modules/cassandra/pages/managing/operating/hints.adoc:81-82` says
"By default hints are compressed using `LZ4Compressor`", and its settings table (l. 153-155) gives `LZ4Compressor` as the
default, while the shipped yaml and `NEWS.txt:1296` say hints are uncompressed by default. An operator reading the doc page
would believe every node runs with the holder.

**Reason.** No issue reports direct (or any) memory held per open compressed-hints writer, nor an OOM from many
simultaneously hinted destinations with compression on. The only issue naming `CompressedHintsWriter` (11678) is about file
corruption; the hints direct-memory issues (21657 the shared write buffer, 15006 the chunk cache) name other buffers; the
design intent to share one compression buffer (6230's comment) was never carried out by 9428 and was never reported as a
problem. All key 2026-11-17 queries of stage 1 rerun with broader terms; no new relevant hit, and no relevant issue changed
since 2026-11-10. The holder is unchanged after 5.0.9 on `cassandra-5.0` and trunk (only an import reorder in
`CompressedHintsWriter.java`), so nothing fixes it incidentally.
