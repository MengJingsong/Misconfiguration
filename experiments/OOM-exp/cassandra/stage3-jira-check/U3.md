# U3 — stage 3-a JIRA check (2026-11-24)

**Case:** [`items_per_collection--whole-collection-read-materialization`](../cases/items_per_collection--whole-collection-read-materialization/items_per_collection--whole-collection-read-materialization.md)
(true positive, `verified-OOM · deployment`).

**Mechanism checked (§4).** A non-frozen collection grown by appends (the `items_per_collection` / `collection_size` guardrails
ship off and, when on, count only the written fragment) is deserialized whole into one row on the replica for every read
(`UnfilteredSerializer.readComplexColumn` → one `ArrayCell` + `CellPath` + `HeapByteBuffer` + `byte[]` per item, ≈ 150 B per item);
16 concurrent reads of 10⁶-item sets hold ≈ 15 such rows and OOM a 2 GiB heap. No control sums heap across reads; the read-size
threshold (off) is checked only after the row is built.

**Label: `documented only`** (no exact or partial issue; closest related: CASSANDRA-17153, CASSANDRA-12623). The CQL docs say
collections are read whole, not paged internally, and are not for data that grows unbounded.

## Reason

Stage 1 rated U3 `new` with documented whole-collection reads. The re-run plus new searches (code identifiers
`readComplexColumn`/`ComplexColumnData`/`CellPath`, "whole/entire collection", non-frozen + GC/OOM, summary terms) found no
issue that reports heap exhaustion or GC from **reading** a large stored collection: the collection-memory issues are write-side
(12623, 6534), the guardrail issue states the fragment-only check as intended (17153), and the byte-limit work (16896, 11745) is
checked after a row is built. No exact or partial issue, no fix, but the shipped docs advise against the data shape and say the
read is whole and unpaged → `documented only`.
