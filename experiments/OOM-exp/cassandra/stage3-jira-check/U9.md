# U9 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/big-row-index-buffer--64KiB-clustering-wide-partition/big-row-index-buffer--64KiB-clustering-wide-partition.md`](../cases/big-row-index-buffer--64KiB-clustering-wide-partition/big-row-index-buffer--64KiB-clustering-wide-partition.md)
(verdict true positive; `verified-OOM · deployment`, unprotected accumulation).

**Mechanism checked (case §4).** The BIG-format partition writer (`BigFormatPartitionWriter.addIndexBlock` →
`IndexInfo$Serializer.serialize`) serializes one `IndexInfo` with full copies of the first and last clustering per 64 KiB
block into one heap `DataOutputBuffer` for the whole partition. With 65,535-byte clustering keys the buffer is ≈ 2 × the
partition's data and grows ×1.5 by copying; no counter, guardrail or `column_index_cache_size` bounds it → Java heap OOM
on the `CompactionExecutor` (or flush writer) for a ≈ 1 GB partition at a 2 GiB heap.

**Label: `known-open (exact: CASSANDRA-16764)`** — changes stage 1's `new`.

**Documented:** partly, as a sizing recommendation, not a memory warning. `conf/cassandra.yaml:1174-1183`: "Using
smaller granularities with the BIG format is not recommended because bigger collation indexes cannot be cached efficiently
or at all if they become sufficiently large. Further, if large rows, or a very large number of rows per partition are
present, it is recommended to increase the index granularity or switch to the BTI SSTable format." Nothing says the
writer holds the whole index on heap or can exhaust it.

**Reason.** Stage 1 (2026-11-18) read CASSANDRA-16764 from the survey as "one ≈ 2 GB cell serialized into a compaction
`DataOutputBuffer`" and filed U9 as `new`. Reading the issue in full shows its stack traces are U9's holder (the row-index
`IndexInfo` serialization in the BIG writer during compaction), the trigger is a very wide partition with long clustering
keys, and later comments report heap exhaustion at 16–24 GiB and OOMs in production. That is the same holder and the same
root cause (an unbounded per-partition index buffer whose size scales with clustering size × blocks), so the match is
**exact**. The issue is unresolved (Triage Needed, no assignee, no fix version), so the label is **known-open**. U9 adds
what 16764 lacks: the OOM below the 2 GiB array cap at shipped defaults (2/4/6/8 GiB heaps), the ≈ 2 × data ratio, and a
working intervention (`column_index_size: 4MiB`).
