(verdict true positive, `verified-OOM · deployment`, with the owner's budget caveat on the explicit `MaxDirectMemorySize`).

**Mechanism checked (case §4).** Holder: the SAI `RowMapping` off-heap `InMemoryTrie` built at every memtable flush of an
SAI table (one full primary key per flushed row), charged to no budget (not the memtable pool, not the SAI segment limiter,
no direct budget), with whole-buffer doubling and buffers freed only by GC. Trigger: write load with long clustering keys
on an SAI table; two flush writers overlap → `OutOfMemoryError: Direct buffer memory` in the flush thread when the direct
limit is ≲ heap/4.

**Label: new**

## Documented

**no.** `conf/cassandra.yaml:1791-1794` documents only the segment-build budget ("Total permitted memory allowed for writing
SAI index segments … # segment_write_buffer_size: 1024MiB"), which does not cover flush. The SAI read/write-path page states
the opposite of the measured behaviour: `doc/modules/cassandra/pages/developing/cql/indexing/sai/sai-read-write-paths.adoc:34`
"SAI flushes Memtable index contents directly to disk when the flush threshold is reached, rather than creating an
additional in-memory representation." No doc mentions the RowMapping or its direct memory.

## Reason

Stage 1's queries were rerun (same hit sets, plus 21529 and 21894 as newer hits) and extended with the writer and trie
identifiers (`StorageAttachedIndexWriter`, `discardBuffers`, `SpaceExhaustedException`) and direct-memory symptom searches
since 2022. Every SAI memory issue found is about a different holder (compaction segment builder, on-disk components,
memtable-index sharding), and the open direct-OOM report (21529) is a chunk-cache/BufferPool stack. No issue reports the
flush-time `RowMapping` trie's direct memory, with this trigger or any other, so there is no exact or partial match; the
docs even say no extra in-memory representation is built. Hence **new**.
