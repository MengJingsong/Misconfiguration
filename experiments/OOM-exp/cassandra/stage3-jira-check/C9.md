# C9 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable.md`](../cases/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable.md)
(verdict true positive; `verified-OOM` · convergence by multiplicity · `deployment`, owner ruling 2026-11-18).

**Mechanism checked (case §4).** Each partition-range read command opens a scanner on every intersecting sstable at once,
and each scanner allocates a 256 KiB direct read-ahead buffer (`ThreadLocalReadAheadBuffer.getBlock`,
`compressed_read_ahead_buffer_size`) charged to no pool or counter. Live buffers = range commands in flight (≤
`concurrent_reads` 32) × intersecting sstables (uncapped) × 256 KiB, bounded only by `MaxDirectMemorySize`: direct OOM
3/3 at 2 GiB and at the auto 7,936 MiB with 2,000 sstables and 40 concurrent scans.

**Label: `new`**

lists "Improve disk access patterns during compaction and range reads (CASSANDRA-15452)" without memory notes; nothing in

**Reason.** JIRA has several issues on this exact holder (15452, 20551, 21671, 21684, 21522), but every reported problem is
retention, leak or close-path allocation, all fixed; none reports that the buffers **live at the same time** multiply as
(range commands × intersecting sstables) against `MaxDirectMemorySize`. The 15452 review OOM is the nearest mention: same
holder and symptom on `ReadStage`, but attributed to retention and fixed in 5.0.4. Under the playbook's levels this is
"related" (a different root cause); if the owner reads "same holder, different trigger" as covering it, it would be
`partial` with state fixed-in-5.0.9-for-a-different-root-cause, which none of the case labels fits, so `new` is kept and
the borderline is flagged here. The 5.0.10 fix (21671) keeps one buffer per scanner and does not bound the multiplicity
(from its diff). No issue on point filed since.
