# C4 — stage 3 JIRA check (2026-11-24)

**Case file:** [`../cases/index_summary_capacity--full-sampling-load-window/index_summary_capacity--full-sampling-load-window.md`](../cases/index_summary_capacity--full-sampling-load-window/index_summary_capacity--full-sampling-load-window.md)
(verdict true positive; `verified-OOM · deployment`, kernel memcg OOM-kill, unprotected accumulation in the documented periodic window).

**Mechanism checked (case §4).** BIG-format index summaries are JNA-malloc'd native memory, outside `-Xmx` and
`MaxDirectMemorySize`. Their pool, `index_summary_capacity` (auto = 5 % of the heap), is applied only by the
60-min redistribution task (`index_summary_resize_interval`). `nodetool import` opens every new sstable and loads its
`Summary.db` at the level it was saved (full sampling for flush/compaction/`CQLSSTableWriter` output), and nothing
triggers a redistribution. An import of 90 M partitions (summaries 678.6 MiB against a 51 MB pool, plus compression
metadata) got the JVM memcg-killed 3/3 in a 2,048 MiB container (heap 1,024); half the data and the same sstables with
summaries downsampled to the cap survived 3/3.

**Label: `documented only`**

**Documented:** yes. `conf/cassandra.yaml:931-936` (`index_summary_capacity`): "A fixed memory pool size in MB for for
SSTable index summaries. If left empty, this will default to 5% of the heap size. If the memory usage of all index
summaries exceeds this limit, SSTables with low read rates will shrink their index summaries in order to meet this
limit. However, this is a best-effort process. In extreme conditions Cassandra may need to use more than this amount of
memory." and `conf/cassandra.yaml:941-944` (`index_summary_resize_interval: 60m`): "How frequently index summaries should
be resampled. This is done periodically to redistribute memory from the fixed-size pool to sstables proportional their
recent read rates." The docs do not say that the memory is outside the heap and direct limits, nor that an import or
restart loads summaries at full size until the next run (`doc/…/table-properties.adoc:118-125` and
`doc/…/managing/operating/bulk_loading.adoc` are silent on memory).

**Reason.** No issue reports an OOM (heap, direct or kernel) from index summaries loaded over the pool between two
redistribution runs, on `nodetool import` or on any other open of full-sampling sstables. JIRA has the design that makes
the pool best-effort and periodic (5519, by design), an old leak on the `sstableloader` path (6359, a different root cause,
fixed), the open documentation ticket that names `index_summary_capacity` as the limit of this memory (20491), and kernel
OOM kills with no holder (8552, 10821, 20565); none is exact or partial. The 2026-11-21 import ticket (21913) does not touch
summary memory. The shipped yaml warns that the pool is best-effort and may be exceeded and documents the 60-min timer,
which is the U > C the case exercises, so the label is `documented only`, the same as R18 (the related index-summary case),
with the limit that the docs give no size or duration for the overshoot and do not mention the import path. Stage 1
recorded `new` (2026-11-17); the difference is the documented-source rule of stage 3-a, not new JIRA evidence.
