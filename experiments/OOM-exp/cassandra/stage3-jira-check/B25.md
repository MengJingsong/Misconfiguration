# B25 — stage 3-a JIRA check (2026-11-24)

**Case:** [`../cases/profileload-capacity--read-sampler-pins-slab-regions/profileload-capacity--read-sampler-pins-slab-regions.md`](../cases/profileload-capacity--read-sampler-pins-slab-regions/profileload-capacity--read-sampler-pins-slab-regions.md)
(verdict true positive, `verified-OOM · deployment`, bypass — accounting omission; from OC-585 + OC-588). Checked by a fresh
session that did not design or verify the case; owner rulings of 2026-11-23 and 2026-11-24 applied.

**Mechanism checked (case §4).** Holder: the read-path samplers of `nodetool profileload` / `toppartitions` (`READS` =
`FrequencySampler.summary`, `READ_ROW_COUNT`, `READ_TOMBSTONE_COUNT`, `READ_SSTABLE_COUNT` = `MaxSampler.queue`), whose entries
keep the partition-key `ByteBuffer` by reference. For a read served from a memtable under the default `heap_buffers` /
`SkipListMemtable`, that key is a slice of a 1 MiB on-heap slab region, so each retained entry keeps its whole region alive after
the memtable is flushed and the pool has stopped counting it. Trigger: an operator profiles table after table with the default
command (`-s 256`, all samplers, 10 s) while each table takes read-after-write traffic; `finishSampling` leaves ≥ 244 of 256
entries per sampler in place until the next session on the same table. Controls that fail: the sampler capacity counts entries,
not the bytes behind them; `memtable_heap_space` stops counting regions at discard; no control sees the pinned regions. Intervention
that removed it: copy the key in `Sampler.addSample` (`ByteBufferUtil.minimalBufferFor`, the `retainable()` idea already used by
`TopPartitionTracker`).

**Label: new**

## Reason

B25's mechanism (read-sampler entries keep partition-key slices of memtable slab regions, so a count-bounded sampler pins whole
1 MiB regions that the memtable pool no longer counts, and the leftovers stay after `finishSampling`) is not reported in JIRA. The
same bug class is known and was fixed twice for another holder — sstable min/max column names keeping slab regions referenced
(CASSANDRA-6077, 2.0.2) and its return as a heap OOM of 1 MiB `HeapByteBuffer`s (CASSANDRA-11026, 3.0.3) — and the key-copying
remedy exists for the newer top-partition tracker (CASSANDRA-16310, `retainable()`), but none of these covers the samplers: they
are `related` (same pattern or component, different holder). The issues that built the samplers (7974, 14436, 18022, 17821) treat
capacity as an item count and never discuss what an item retains; 17254 even shows the sampled key is a view into a larger array,
but only fixes its rendering. The sampler code and the defaults are unchanged in 5.0.x, 6.0 and trunk, so there is no newer fix,
and the shipped docs and help text give no warning (the help calls it "Low footprint"). Label **new**. The stage-1 prior-art check
(§1.4, 12 queries, verdict `new`) agrees; this check adds the 6077/11026 precedent and the 18022 origin of three of the holders.
