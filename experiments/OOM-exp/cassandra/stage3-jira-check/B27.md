# B27 — stage 3-a JIRA check (2026-11-24)

**Case:** [`../cases/native_transport_receive_queue_capacity--v5-per-connection-allowance-outside-reserves/native_transport_receive_queue_capacity--v5-per-connection-allowance-outside-reserves.md`](../cases/native_transport_receive_queue_capacity--v5-per-connection-allowance-outside-reserves/native_transport_receive_queue_capacity--v5-per-connection-allowance-outside-reserves.md)
(verdict true positive, `verified-OOM · deployment`; convergence by multiplicity, unprotected configuration; heap 2 GiB 3/3,
also 4 and 8 GiB 3/3; from OC-269 and its cluster). Checked by a fresh session that did not design or verify the case; owner
rulings of 2026-11-23 and 2026-11-24 applied.

**Mechanism checked (case §4).** Holder: decoded protocol-v5 requests (`QueryMessage` + its heap `byte[]` value copy,
`CBUtil.readValue`) queued on `Native-Transport-Requests` until the response is flushed. Control that fails: each v5
connection's `CQLMessageHandler` admits request bytes against its own exclusive `queueCapacity`
(`native_transport_receive_queue_capacity`, 1 MiB, `Config.java:302`) and returns SUCCESS without touching any reserve
(`AbstractMessageHandler.acquireCapacity`, `AbstractMessageHandler.java:419-423` at 5.0.9); only the excess beyond 1 MiB is
charged to the global (heap/10) and per-IP (heap/40) reserves (`:425-436`). Missing control: the connection count,
`native_transport_max_concurrent_connections` / `_per_ip`, ships −1 (`Config.java:289-290`; the `ConnectionLimitHandler` is not
installed). Trigger: many well-behaved v5 connections (3,500 at 2 GiB), each keeping ≤ 8 requests (< 1 MiB) in flight against a
slow read, so N × < 1 MiB of decoded requests sit on the heap while the reserves read ≤ 44 B, nothing is refused and no
"bytes in flight" warning is sent → `OutOfMemoryError: Java heap space`. Intervention that removed it: the connection limit
set to 1,000.

**Label: `new`** (closest issues all `related`: CASSANDRA-21091 open, 15013, 4265 Won't Fix, 8086, 15299, 20052, 19534, 21884)

**Alternative for the owner.** CASSANDRA-21091 (Patch Available, unresolved) states this case's accounting root cause in a
comment: the v5 handler "only touches the reserve once a connection's local queue budget (1MiB by default) is exceeded - normal
traffic never gets close to that, so the gauge just sits at 0." It reports it only as a missing metric (`Client.RequestsSize`
reads 0), with no memory, heap or connection-count consequence, and its patch only makes the gauge sum per-connection queued
bytes. It is rated **related** here (counter, not holder; no OOM symptom), as B10's check rated it. If the owner counts a report
of the same uncharged admission as **partial**, the label becomes **`known-open (partial: CASSANDRA-21091)`**.

## Documented

**no.** At the pinned 5.0.9 source: `conf/cassandra.yaml:1046-1052` says only "The maximum number of concurrent client
connections. The default is -1, which means unlimited." (and the same per source IP), with no memory note;
`native_transport_receive_queue_capacity` and `native_transport_max_request_data_in_flight[_per_ip]` appear nowhere in
`conf/`, `doc/` or `NEWS.txt`. The analogous warning exists only for internode messaging (`conf/cassandra.yaml:1370-1383`:
"The basic per-link limit is consumed in isolation before any endpoint or global limit is imposed … any given node may have a
maximum of N*3*(internode_application_send_queue_capacity+internode_application_receive_queue_capacity) messages queued without
any coordination between them"; same in `doc/modules/cassandra/pages/architecture/messaging.adoc:89`), which does not cover
client connections. `doc/native_protocol_v5.spec:483-487` and `conf/cassandra.yaml:1069-1075` describe the default as
backpressure, without saying that each connection's allowance is outside the reserves. `CHANGES.txt:1344, 2097, 4050` are the
feature entries of 15299, 15013 and 8086.

## Reason

B27's mechanism (each v5 connection admits up to 1 MiB of requests on its own queue without charging the per-IP or global
reserve, and the connection count ships unlimited, so many well-behaved connections hold N MiB of decoded requests while every
reserve reads 0, until the heap runs out) is not reported in JIRA as a memory problem. The pieces are known separately: 15013's
review foresaw that small per-connection limits outside the shared limits could "consume a great deal in combination" with many
clients, but only as a design caveat before the v5 allowance existed; 15299 built that allowance without discussing it; 8086 made
the connection limit opt-in on purpose; 4265 reported the same product (connections × per-connection buffer → OOM) for the removed
Thrift server and was closed Won't Fix; and 21091 (open) noticed that v5 traffic never reaches the reserves, but only as a gauge
that reads 0, and its patch changes the metric, not the admission. 20052's fix and 19534's shedding are in 5.0.9 and bound other
things (one message's size, a task's age). All are `related`; nothing in 5.0.x, 6.0 or trunk changes the admission or the
defaults, and the shipped docs give no warning for client connections. Label **new**, agreeing with stage 1 (§1, 6 queries,
`new`, related 4265); this check adds 21091's comment, Benedict's 15013 remark, the 8086 design decision, the history-clone
version check and the docs check. If the owner rates 21091 partial, the label is `known-open (partial: CASSANDRA-21091)`.
