# B29 — stage 3-a JIRA check (2026-11-24)

**Case:** [`../cases/cached_rows_fail_threshold--rfp-static-fetch-whole-partition/cached_rows_fail_threshold--rfp-static-fetch-whole-partition.md`](../cases/cached_rows_fail_threshold--rfp-static-fetch-whole-partition/cached_rows_fail_threshold--rfp-static-fetch-whole-partition.md)
(verdict true positive, `verified-OOM · deployment`; bypass · accounting omission × multiplicity; pc72, 2 instances RF 2,
defaults, 2 GiB coordinator heap: OOM 3/3 at Q = 8; controls and intervention 0/3; OOM up to 12 GiB; from OC-470 + OC-480).
Checked by a fresh session that did not design or verify the case. Owner rulings of 2026-11-23 and 2026-11-24 applied.

**Mechanism checked (§4).** A single-partition filtering read with a **static-column predicate**
(`SELECT * … WHERE k = ? AND s = 'x' ALLOW FILTERING`) at CL QUORUM is coordinated by a **stale replica** that missed a partition
deletion and a newer static value. Replica filtering protection (RFP) marks the static row unresolved
(`ReplicaFilteringProtection.java:505-510`, `unresolvedStatic = command.rowFilter().hasStaticExpression()`). In its second phase it
completes the row by reading that replica's **entire partition**: the command's clustering filter, `RowFilter.none()` and
`DataLimits.NONE`, no paging (`:618-632`). Because the source is the coordinator itself, the partition is serialized into one heap
`DataOutputBuffer` per query (`LocalDataResponse`: 262 MB of stale rows in a 324 MiB array) to return one CQL row. **Holder:**
the completion-fetch response on the coordinator. **Controls that fail or are missing:** the fetched rows never pass
`incrementCachedRows`, so `cached_rows_fail_threshold` (32,000) charges 2 per query. The byte read-size thresholds do not apply
to the fetch command even when they are enabled (O-thr arm). Nothing bounds bytes across queries, so the only limits are the 32
READ permits and the 5 s read deadline. Intervention that removed the OOM: fetch the named rows only.

**Label: `new`** (no exact or partial issue. Closest issues, all `related`: CASSANDRA-19018 (Fixed 5.0-rc1, in 5.0.9; it
introduced the whole-partition fetch and notes the hazard), 20323 (Fixed 5.0.4, in 5.0.9; it removed the fetch's limit),
20243 (Fixed 5.0.4, in 5.0.9), 15907 (Fixed 4.0, in 5.0.9; first-phase holder), 21118 (Open; SAI replica side), 8272. No
newer fix. Docs: partly (the hazard, not the gap), not counted.)

**For the owner (two alternatives).**
1. **CASSANDRA-19018 as partial.** C. Rackliffe, 2024-02-16, in the issue that introduced the fetch: "I think it's also
   probably appropriate to note that static columns have become even more dangerous, as matches on static columns can now entail
   pulling entire partitions through RFP in coordinator space or post-filtering entire partitions locally", and "when large
   divergences and large quantities of unrepaired data are allowed to persist, there will be pain." This names B29's holder (an
   entire partition pulled into coordinator space on a static match) and its precondition (divergence). It says nothing about
   memory exhaustion, OOM, the cached-rows count or concurrency. It is a design-time note on a cost the authors accepted, not a
   report. As with CASSANDRA-8272's reviewer remarks for R24 and CASSANDRA-1123 for B28, it is rated **related**. If the owner
   rates it partial, the hazard was accepted knowingly, so the label becomes
   **`known-wontfix / by design (partial: CASSANDRA-19018)`**.
2. **CASSANDRA-15907 as partial.** 15907 is the RFP heap-risk issue, and its fix (in 5.0.9) is the row count that B29 bypasses.
   Its holder is RFP's first-round cache, and the second-round fetch rows were never counted. It is rated **related** here
   (different holder). R24 rated it partial because R24's holder is that cache. If the owner counts any RFP heap-risk report
   with a stale-replica trigger as partial, the label becomes **`known-fixed (incomplete) (partial: CASSANDRA-15907)`**,
   as for R24.

## Reason

B29's mechanism is not reported in JIRA as a memory problem: a static-column filtering query at CL > ONE, coordinated by a
replica that missed a partition deletion, makes RFP read that replica's whole partition with no limit, uncounted by
`cached_rows_fail_threshold`, into one coordinator heap buffer per query, and concurrent queries exhaust the heap. The fetch itself
is well known to the developers, who built it on purpose for correctness:
- 19018 (in 5.0.0) introduced the whole-partition completion for unresolved static rows and noted that static matches "can now
  entail pulling entire partitions through RFP in coordinator space" ("there will be pain" under large divergence);
- 20243 (5.0.4) restricted it to queries with a static expression;
- 20323 (5.0.4) removed its row limit for B29's exact data shape (static predicate + missed partition delete), stating that "we
  have no way of knowing how many stale rows we might read on a silent replica";
- 21332 (5.0.9) restates that the completion "must read the entire partition".

None of these discusses memory, OOM, the cached-rows threshold or concurrency. The RFP heap-risk issues (8272's review, 15907) are
about the first-round cache, and 15907's row-count fix in 5.0.9 never counted the second-round fetch. That fetch was a names-only,
row-limited read until 5.0. All closest issues are therefore `related`, and no exact or partial issue exists. No newer version
bounds the fetch: `cassandra-5.0`, 6.0 and trunk still use `DataLimits.NONE`, and 21354/21285 only change how a local response is
built. The yaml names the stale-replica heap hazard but offers the row threshold as the remedy, which does not apply here. Label
**`new`**, agreeing with stage 1 (§1: 5 queries, `new`; closest 20243, 20323, 15907, 16896).

This check adds:
- 19018 as the origin of the fetch, with its hazard note;
- the version history showing that the unbounded fetch exists only from 5.0.4 (20323 removed `cqlLimits(1)`);
- 8272's and 15907's first-phase scope, 21118, 21332, 19007, 21354/21285, the newer-branch check and the docs check.

The two owner alternatives above (19018 or 15907 as partial) would give `known-wontfix / by design` or `known-fixed (incomplete)`.
