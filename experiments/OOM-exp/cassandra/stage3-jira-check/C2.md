# C2 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/convergence/coordinator_read_size_fail_threshold-concurrent-reads/coordinator_read_size_fail_threshold--concurrent-reads.md`](../cases/convergence/coordinator_read_size_fail_threshold-concurrent-reads/coordinator_read_size_fail_threshold--concurrent-reads.md)
(verdict true positive; S-A `verified-OOM · deployment`, unprotected configuration).

**Mechanism checked (case §4).** Native transport, protocol v4: each finished read response is encoded on the request
thread into Netty pooled direct memory (`Message.encode` → `CBUtil.allocator`) and queued in the channel's
`ChannelOutboundBuffer`; the request thread, the request-bytes in-flight charge and the read thresholds are all released
or satisfied before the socket drains. Nothing checks channel writability (`isWritable()`; the 8/32 KiB watermark is set but
unused), so with slow-draining clients outstanding response memory = outstanding reads × page size → Netty
`OutOfDirectMemoryError`.

**Label: `known-open (exact: CASSANDRA-11082)`**

**Documented:** no. `conf/cassandra.yaml` has no text on outstanding responses or slow clients
(`native_transport_max_threads`, l. 1035; read thresholds, l. 2017–2030, are per query); `native_transport_max_request_data_in_flight`
is not in the yaml; nothing in `doc/`, `NEWS.txt`.

**Reason.** CASSANDRA-11082 reports exactly this holder and root cause: slow receivers make Netty's outbound buffer grow
because Cassandra sets write watermarks but never checks `isWritable()`. It is still Open with no fix version and no
activity since 2019 (re-read 2026-11-23; no update since the 2026-11-16 check). The later request-side bounds (15013,
19534) and the 21508/21766 changes do not bound encoded response bytes on a connected channel. The 5.0.9 source still
has the watermark and no `isWritable()` in `transport/` (case §1.2). C2 adds the default-config reproduction that 11082
lacked. No newer issue on point was found.
