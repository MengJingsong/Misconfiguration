# B17 — stage 3 JIRA check (2026-11-23)

**Case:** [`cql-row-limit--in-order-by-limit-after-materialization`](../cases/cql-row-limit--in-order-by-limit-after-materialization/cql-row-limit--in-order-by-limit-after-materialization.md)
(true positive, `verified-OOM · deployment`).

**Mechanism checked (§4).** For `IN` on the partition key plus `ORDER BY`, `getDataLimits` leaves the read's row limit at
`NO_LIMIT` (post-query ordering) and paging is refused, so every listed partition is serialized whole into its replica
`DataOutputBuffer` and copied into the coordinator `ResultSet` before `LIMIT 10` is applied; read-size thresholds and the
`partition_keys_in_select` guardrail ship off. One 10-row query OOMs a 2 GiB heap.

**Label: `new`** (closest: CASSANDRA-10729 and CASSANDRA-6722, related).

## Reason

The re-check adds CASSANDRA-10729 to stage 1's list: it is where the read lost the user LIMIT for post-query ordering (a
wrong-results fix, 2015), and CASSANDRA-6722 is where paging was refused. Both are fixed correctness changes whose memory
consequence nobody filed; byte limits (4304 Later, 11745 6.0-only and scoped to internal paging) do not cover this path. No issue
reports this holder with this trigger, so `new`; the paging refusal itself is by design.
