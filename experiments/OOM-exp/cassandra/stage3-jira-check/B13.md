# B13 — stage 3-a JIRA check (2026-11-24)

**Case:** [`networking_cache_size--v5-stalled-client-frame-overflow`](../cases/networking_cache_size--v5-stalled-client-frame-overflow/networking_cache_size--v5-stalled-client-frame-overflow.md)
(true positive, `verified-OOM · deployment`; heap 2 GiB, direct 2 GiB 3/3, also 4 / 7.75 / 15.5 GiB direct).

**Mechanism checked (§4).** Over protocol v5 every response is copied into 128 KiB frames from the `networking`
`BufferPool`; `networking_cache_size` (128 MiB) caps only its pooled slabs, past it each frame is an unchecked
`ByteBuffer.allocateDirect` overflow. `Flusher` writes every frame at once, no transport code checks
`Channel.isWritable()`, and request permits are returned once the response is framed. A client that sends requests but
does not read makes the node hold every frame in the channel's `ChannelOutboundBuffer` until `MaxDirectMemorySize`
throws `OutOfMemoryError: Direct buffer memory` (`BufferPool.allocate:238` in `Flusher.flushLargeMessage`), then the
forced heap OOM kills the JVM.

**Label: `known-open`** (exact: CASSANDRA-11082; partial: CASSANDRA-19535, Cannot Reproduce)

**Documented: no.** `conf/cassandra.yaml:729-737` presents the knob as the maximum: "Maximum memory to use for
inter-node and client-server networking buffers. Defaults to the smaller of 1/16 of heap or 128MB. This pool is
allocated off-heap, so is in addition to the memory allocated for heap." Nothing says that frames beyond it are
allocated unpooled without a limit, or that responses to a non-reading client are held; `doc/` and `NEWS.txt` have no
warning either.

## Reason

CASSANDRA-11082 (open since 2016) reports exactly the trigger and root cause B13 exercises: responses accumulate in the
channel's outbound buffer for a client that sends but does not read, because the server never checks writability. It
was confirmed by two maintainers and left open; the 5.0.9 code (and trunk) still has no writability check, and the v5
framing path added later routes those bytes through the networking pool's unchecked overflow, which is why the
`networking_cache_size` cap does not help. The issue does not name the v5 frames or the pool, but the holder (outbound
buffer of the stalled channel) and the missing control are the same, so it is rated exact, as for C2 (v4). CASSANDRA-19535
shows the same allocation site failing at defaults in the field and was closed Cannot Reproduce (partial). Label
`known-open (exact: CASSANDRA-11082)`, matching stage 1.
