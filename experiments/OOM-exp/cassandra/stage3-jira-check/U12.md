# U12 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/sstable-row-body-scratch-DOB--appended-collection-row-compaction/sstable-row-body-scratch-DOB--appended-collection-row-compaction.md`](../cases/sstable-row-body-scratch-DOB--appended-collection-row-compaction/sstable-row-body-scratch-DOB--appended-collection-row-compaction.md)
(verdict true positive; `verified-OOM · deployment`, unprotected accumulation).

**Mechanism checked (case §4).** When compaction (or flush) writes a row, `UnfilteredSerializer.serialize` first copies the
whole row body into the thread's scratch `DataOutputBuffer`, which is **direct** memory by default (CASSANDRA-16471) and
grows with no capacity check (×2 to 64 MiB, then ×1.5, old and new live during each copy); `DOB_MAX_RECYCLE_BYTES` only
trims it at `close()`. No setting bounds a stored row: a non-frozen map grown by 1 MiB appends to 600 MiB needs a 729 MiB
growth step on top of a live 486 MiB buffer → `OutOfMemoryError: Direct buffer memory` on `CompactionExecutor` at 1 GiB direct.

**Label: `documented only`** (no exact or partial issue; the CQL docs advise against the unbounded-collection data shape —
an advisory, not a memory warning; see Reason).

**Documented:** yes, as data-modelling advice. `doc/modules/cassandra/pages/developing/cql/types.adoc:216-221`:
"Collections are meant for storing/denormalizing relatively small amount of data. … But when items are expected to grow
unbounded (“all messages sent by a user”, “events registered by a sensor”...), then collections are not appropriate and a
specific table (with clustering columns) should be used." (and l. 225-227: "even to access a single element of a
collection, the whole collection has to be read"). No shipped text gives a size limit or mentions direct memory at flush
or compaction; `conf/cassandra.yaml` has no row-size bound at defaults.

**Reason.** No issue reports the row-body scratch buffer's in-use size, or a direct-memory OOM from one large row at
compaction: the searches on the holder (`scratchBuffer`, `serializeRowBody`, `expandToFit`, `DataOutputBuffer`,
`dob_max_recycle_bytes`/`dob.allocate_type`), the trigger (large row / large collection with compaction or flush) and the
symptom ("Direct buffer memory" in compaction) find only 16471 (moved the buffer to direct, related), pool-sizing direct
OOMs (21529) and pre-3.0 large-row tickets. Stage 1's closest match, 16764, turns out to be U9's row-index buffer. So
there is no exact or partial issue. The shipped CQL docs tell users that collections which grow unbounded are not
appropriate, which is the data shape that triggers the case, so the label is **documented only**. That doc is an advisory
without a byte figure or a memory consequence, and every write was accepted at defaults; if the owner requires a memory
warning for "documented", the label is `new`.
