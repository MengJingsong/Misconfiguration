# R12 — stage 3 JIRA check (2026-11-23)

**Case:** [`monitoring_max_operations+traced-render--slow-query-monitor-stacked`](../cases/monitoring_max_operations+traced-render--slow-query-monitor-stacked/monitoring_max_operations+traced-render--slow-query-monitor-stacked.md)
(true positive; condition B `verified-OOM · deployment`, condition A mixed under fallback F).

**Mechanism checked (§4).** The slow-query monitor (`MonitoringTask`) caps its queues at `monitoring_max_operations` = 50
operations each but keeps every finished slow/aborted `ReadCommand` with its bound filter value after the in-flight limit has
released it; each drain (`popOperations`) renders every polled command to an uncut hex CQL string and keeps every distinct one,
and polling frees queue slots, so under steady slow load with distinct 16 MB values the drain's map grows past the count cap
(119 ops, 3.46 GB at 4 GiB). Condition A adds the uncharged traced render (`ExecuteMessage.traceQuery`).

**Label: `new`** (closest: CASSANDRA-7392, related).

## Reason

The re-run of stage 1's queries and new ones on the drain methods (`logSlowOperations`, `popOperations`, `SlowOperation`: 1 hit,
13001) found nothing newer than the 2026-11-20 check. The only text on point is a 2015 design-review comment in the issue that
introduced the monitor; it foresaw retention of large queries and value truncation but no issue was filed and the shipped monitor
bounds only the count. That is not a report of the holder's failure (not partial), so the case is `new`; the review comment is
worth citing in any report.
