# R21 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/memtable_heap_space--stale-btree-updater-pins-discarded-memtables/memtable_heap_space--stale-btree-updater-pins-discarded-memtables.md`](../cases/memtable_heap_space--stale-btree-updater-pins-discarded-memtables/memtable_heap_space--stale-btree-updater-pins-discarded-memtables.md)
(verdict true positive; `verified-OOM · deployment`, bypass — release defect).

**Mechanism checked (case §4).** Each write merges into a memtable partition through a `BTree.Updater` pooled per thread
(`TinyThreadLocalPool`); `Updater.reset()` (5.0.9 `BTree.java:3600-3604`) never nulls `updateF` (or `comparator`), so each
SEP worker keeps a reference to the `AtomicBTreePartition$Updater` of its last write and through it the whole partition of
a flushed, DISCARDED memtable whose charge `memtable_heap_space` already released. A few pinned hot-partition memtables
fill a 2 GiB heap while the pool counter stays below its limit; nulling the two fields removes the OOM.

**Label: `known-fixed (not in 5.0.9)`** (fixed incidentally by CASSANDRA-20780, commit 54e39a90b0, 6.0/trunk; match level related: no issue reports it)

**Owner ruling (2026-11-23):** a fix in a newer version counts as known-fixed even when its issue does not describe the mechanism, so the label is **`known-fixed (not in 5.0.9)`** (fixed incidentally by CASSANDRA-20780, commit 54e39a90b0, 6.0/trunk). Match level stays `related`: no issue reports the retention.

**Label (stage 3 as first filed): `new`** — no issue reports the retention; note that the code was fixed incidentally on 6.0/trunk (below).
