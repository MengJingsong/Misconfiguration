# R7 — stage 3-a JIRA check (2026-11-24)

**Case:** [`concurrent_writes+max_mutation_size--inflight-DOB-fill-R7`](../cases/concurrent_writes+max_mutation_size--inflight-DOB-fill-R7/concurrent_writes+max_mutation_size--inflight-DOB-fill-R7.md)
(true positive, `verified-OOM · deployment`, with the case's validity-window caveat).

**Mechanism checked (§4).** On a replica, each `MutationStage` thread serializes an incoming 16 MiB − 1 KiB mutation in
`CommitLog.add` into its thread-local `DataOutputBuffer` scratch, direct by default since 5.0 (`cassandra.dob.allocate_type`
DIRECT), which grows to 2(S − 1) (3S transient in `expandToFit`) and is held through segment allocation and the copy;
`DOB_MAX_RECYCLE_BYTES` trims only at `close()`, `max_mutation_size` bounds one mutation, and `concurrent_writes` (32) is a thread
count, so 32 writers exceed a 896–1,024 MiB direct budget (`OutOfMemoryError: Direct buffer memory` in `CommitLog.add:308 →
expandToFit:178`).

**Label: `known-open` (partial: CASSANDRA-21656)** — same holder as [S1](S1.md)'s DOB layer; the issue reports the commit-log
intermediate buffer of large mutations as per-write native over-allocation, not the concurrent peak or an OOM.
