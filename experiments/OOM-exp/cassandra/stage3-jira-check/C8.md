# C8 — stage 3 JIRA check (2026-11-24)

**Case file:** [`../cases/segment_write_buffer_size--fixed-1GiB-index-build-small-heap/segment_write_buffer_size--fixed-1GiB-index-build-small-heap.md`](../cases/segment_write_buffer_size--fixed-1GiB-index-build-small-heap/segment_write_buffer_size--fixed-1GiB-index-build-small-heap.md)
(verdict true positive; `verified-OOM · deployment`, Java heap OOM, convergence (possibly mixed)).

**Mechanism checked (case §4).** SAI index builds outside memtable flush (`CREATE INDEX` on existing data,
`rebuild_index`, compaction of an SAI-indexed table) buffer segments on heap under one global soft limit,
`sai_options.segment_write_buffer_size`, whose default is a fixed **1,024 MiB** whatever the heap
(`StorageAttachedIndexOptions.java:26`); the `NamedMemoryLimiter` only counts and flushes, it reserves nothing. Every
other large heap pool scales with the heap. At a 1.5 GiB heap (what `cassandra-env.sh` picks on a 3 GiB machine) an SAI
build over 2 M distinct terms with concurrent writes ended in a heap OOM 3/3: the builder held its full contract
(983–994 MiB live) next to the memtable pool (≈ 230 MiB) and the key cache (≈ 190 MiB held); the build alone, the writes
alone and the limit at H/8 all survived.

**Label: `new`**

**Documented:** no. `conf/cassandra.yaml:1791-1794`: "Total permitted memory allowed for writing SAI index segments. This
memory is split between all SAI indexes being built so more indexes will mean smaller segment sizes." with
`# segment_write_buffer_size: 1024MiB` — no relation to the heap. The SAI docs present the buffer as a protection:
`doc/modules/cassandra/pages/developing/cql/indexing/sai/sai-read-write-paths.adoc:86` "To avoid issues such as exhausting
available heap resources, SAI uses an accumulated segment buffer, which is flushed to disk synchronously by using a
proprietary calculation." and `doc/…/sai/operations/monitoring.adoc:73-74` "In cassandra.yaml, `segment_write_buffer_space_mb`
limits the amount of heap used to build on-disk column indexes during compaction and initial builds. The default is 1024 MB."
None warns that the fixed default is a large share of a small heap. *Side finding:* monitoring.adoc:73 names the setting
`segment_write_buffer_space_mb`, which does not exist in 5.0.9 (the key is `sai_options.segment_write_buffer_size`).

**Reason.** No issue reports a heap OOM, or heap pressure, from the SAI segment-build buffer at its fixed 1 GiB default on a
small heap, nor asks to derive the default from the heap. The SAI memory issues in JIRA are a retention bug on sharded
compaction (20752, fixed in 5.0.6, a different root cause; nearest mention, same holder), the limiter refactor (18673) and
SASI-era OOMs on another implementation. As with C9 / CASSANDRA-15452, 20752 is "related (borderline partial)": if the owner
reads "same holder, different trigger" as covering it, it would be `partial` with its fix in 5.0.9 for a different root
cause, which no case label fits, so `new` is kept and the borderline is flagged. The default is unchanged on
`cassandra-5.0` and trunk (`DEFAULT_SEGMENT_BUFFER_MB = 1024`, `config/StorageAttachedIndexOptions.java:26` on trunk), so no
newer version fixes it. Same label as stage 1 (2026-11-18).
