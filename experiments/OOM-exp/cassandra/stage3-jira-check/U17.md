# U17 — stage 3-a JIRA check (2026-11-24)

**Case:** [`../cases/vector_dimensions--vector-literal-per-element-parse/vector_dimensions--vector-literal-per-element-parse.md`](../cases/vector_dimensions--vector-literal-per-element-parse/vector_dimensions--vector-literal-per-element-parse.md)
(verdict true positive, `verified-OOM · deployment`, unprotected accumulation + unprotected configuration).

**Mechanism checked (case §4).** An unprepared QUERY `INSERT … VALUES (0, [0,0,…,0])` into a large `vector<tinyint, D>`
column: the CQL parser keeps every token (`CQLFragmentParser.parseAnyUnhandled` → ANTLR `CommonTokenStream`, two
`CommonToken`s per element) and `listLiteral` (`Parser.g:1572-1575`) builds one `String` + `Constants.Literal` per element;
`Vectors.Literal.prepare` (`Vectors.java:116-142`) then builds a `Constants.Value` + a one-byte `HeapByteBuffer` per element.
Measured ≈ 168 B of heap per element on the Native-Transport-Requests thread, while every check on the request (16 MiB frame,
in-flight bytes, 16 MiB mutation) counts ≈ 2 B per element. The element count is unbounded (`vector_dimensions_fail_threshold`
ships −1; the documented 8K dimension limit is not enforced by `VectorType`), concurrent parses are bounded only by the 128
native threads → two concurrent 13 MB INSERTs OOM a 2 GiB heap. The same holds with 8,192-dimension vectors in one
single-partition unprepared BATCH (no batch-size check applies).

**Label: `new`** (no exact or partial issue; closest related CASSANDRA-18730, CASSANDRA-19959, CASSANDRA-12618; not documented)

## Documented

**no.** `conf/cassandra.yaml:2183-2186` ("# Guardrail to warn or fail when creating a vector column with more dimensions than
threshold. # Default -1 to disable.") names the control but no memory hazard. `NEWS.txt:176` announces `VectorType` and
`NEWS.txt:209` lists "Vector dimensions" among the new guardrails, without a warning. As for U8,
`doc/modules/cassandra/pages/reference/vector-data-type.adoc:15` states "Vectors are limited to a maximum dimension of 8K (2^13)
items." — a limit 5.0.9 does not enforce, not a warning about the behaviour (and the case's condition W shows the OOM within that
limit). `cql_singlefile.adoc:278-295` discusses prepared statements only as a cache (overhead of re-preparing), not the cost of
parsing literals. No doc says that the size of an unprepared request on the heap can be ~80× its wire bytes.

## Reason

The search covered the holder (`CqlParser`/ANTLR/`CommonTokenStream`/`BufferedTokenStream`, `listLiteral`/`ArrayLiteral`,
`Vectors.Literal`), the trigger (vector/list/collection literals, unprepared or large query strings, large list inserts), the
control (`vector_dimensions`, dimension limits, frame/parameter limits) and the symptom (OOM/heap/memory with parser, vector,
literal, insert), plus everything filed since 2026-11-01. No issue reports parse or prepare memory of a CQL literal growing per
element against byte-counted limits, for vectors or any other type. The nearest are the disabled dimension guardrail (18730),
a generic static-analysis list that names a set literal's prepare among unrelated sites (19959, untriaged, no reproduction),
and a fixed OOM from a malformed **bound** list size (12618) — all related only. The mechanism is unchanged on `cassandra-5.0`,
`cassandra-6.0` and trunk, so nothing counts as an incidental fix, and no shipped doc warns. Stage 1 (2026-11-24) reached the
same result; label **`new`**.
