# R24 — stage 3-a JIRA check (2026-11-24)

**Case:** [`cached_rows_fail_threshold--rfp-whole-partition-sized-protection`](../cases/cached_rows_fail_threshold--rfp-whole-partition-sized-protection/cached_rows_fail_threshold--rfp-whole-partition-sized-protection.md)
(true positive, `verified-OOM · deployment`, bypass · accounting omission × multiplicity; retry of B22; pc82, 2 instances RF 2,
defaults, 2 GiB coordinator heap: OOM 3/3 at Q = 7, controls and intervention 0/3).

**Mechanism checked (§4).** A filtering range read (`… WHERE v = 'x' ALLOW FILTERING`, no partition key) at CL QUORUM goes
through replica-filtering protection (RFP). Because the read is not limited to one partition, `consumeEntirePartitions` is true
(`ReplicaFilteringProtection.java:143`), so RFP's first phase drains the **whole merged partition** (`:387-396`), with
short-read protection fetching page-sized chunks from each replica until the partition ends, and stores every non-null row
version of every replica on the coordinator heap (`PartitionBuilder.addRow` → `contents`, `:477-492`) until the partition
closes. The only bound, `cached_rows_fail_threshold` (32,000, `incrementCachedRows`, `:319-332`), counts **rows per query**,
not bytes, and nothing sums concurrent queries. Holder = RFP's `PartitionBuilder.contents` (held row versions); trigger =
agreeing replicas, a partition of a few thousand 64 KiB rows (4,096 versions = 257 MiB per query, K ≤ 4,096 of 32,000) and
7 concurrent queries, independent of the client's fetch size (128).

**Label: `known-fixed (incomplete)`** (partial: CASSANDRA-15907; its fix in 5.0.9 bounds RFP's cached **rows** per query,
not bytes and not across queries; no issue reports large rows, the whole-partition hold on range reads, or concurrency)

## Reason

CASSANDRA-15907 reports R24's holder as a memory risk (RFP's cached first-round rows with no upper bound, "GC nodes into
oblivion") and deliberately chose a per-query **row count** over "actual heap usage" and over a global scope; that fix is in
5.0.9 (`git merge-base --is-ancestor 292650d968 cassandra-5.0.9` → true, also `e5c3d08a14`) and bounds a different unit than
the one R24 exhausts (rows of 64 KiB, K ≤ 4,096 of 32,000, × 7 queries), so under the owner's 2026-11-23 ruling ("a fix in the
pinned version that does not cover the mechanism, for example it bounds a different unit") the label is `known-fixed (incomplete)`;
not a regression, and the case's root cause is not wrong. 15907 is rated **partial**, not exact: its trigger is stale or silent
replicas expanding the count, while R24 needs no divergence (replicas agreed, the second phase never ran) and is driven by row size,
the whole-partition drain on range reads and concurrency, none of which an issue reports. CASSANDRA-20639 names the drain itself
but only as an SRP-latency problem with no memory content, and its fix (in 5.0.9) covers single-partition reads only; it is rated
related (borderline partial; either way the label stays `known-fixed (incomplete)`). Stage 1's `new` is superseded under the 3-a
rules, where a partial issue with an incomplete fix in the pinned version decides the label. No newer fix exists on
`cassandra-5.0` or trunk (11745's byte paging of RFP touches the single-partition branch only).
**For the owner:** if 15907 is read as related (its count unit a by-design trade-off, as 6117 was for B16), the label becomes
`new`.
