# B20 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/indexing_target_page_size--table-mean-page-on-wide-partition/indexing_target_page_size--table-mean-page-on-wide-partition.md`](../cases/indexing_target_page_size--table-mean-page-on-wide-partition/indexing_target_page_size--table-mean-page-on-wide-partition.md)
(verdict true positive; `verified-OOM · deployment`, bypass / accounting mismatch).

**Mechanism checked (case §4).** The legacy secondary-index build turns its 32 MiB page target into a row count once per
build from the **table-wide** mean row size (`SecondaryIndexManager.calculateIndexingPageSize`, 5.0.9 `:1149-1170`); the
pager bounds rows only and `indexPartition` copies each page whole into an `ImmutableBTreePartition` (`:1066`). With
1,000,000 small partitions plus one partition of 4,000 × 1 MiB rows the page is 6,618 rows → one 4.19 GB page → Java heap
OOM in the index-build thread at 2 and 4 GiB.

**Label: `known-fixed (not in 5.0.9) (partial: CASSANDRA-11745)`** — changes stage 1's `new`.

**Documented:** no. Neither `conf/cassandra.yaml` (`concurrent_index_builders` and index settings) nor `doc/` says how the
index-build page is sized or that a skewed table can make one page hold a whole wide partition.

**Reason.** Stage 1 (2026-11-21) found no issue on the mean-based page and called it `new`. Rerunning its queries confirms
no issue describes the skew. But CASSANDRA-11745, committed on 2026-10-27 to `cassandra-6.0`/`trunk` (6.0-alpha3), replaced
the mean-derived row count with a real 32 MiB **byte** page for index builds, removing B20's root cause in 6.0; the issue's
own discussion names index rebuilds as a user of byte paging and states the count-vs-size problem, so it is a **partial**
match (same holder and root-cause class, trigger not described). It is fixed, the fix commit is not an ancestor of
`cassandra-5.0.9` and not on the 5.0 or 4.x branches → **known-fixed (not in 5.0.9)**, fix versions 6.0-alpha3 / 7.0. The
5.0 line keeps the mean-based page.
