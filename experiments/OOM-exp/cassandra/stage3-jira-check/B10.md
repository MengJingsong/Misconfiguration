# B10 — stage 3-a JIRA check (2026-11-24)

**Case:** [`native_transport_receive_queue_capacity--refused-v5-request-uncharged-drift`](../cases/native_transport_receive_queue_capacity--refused-v5-request-uncharged-drift/native_transport_receive_queue_capacity--refused-v5-request-uncharged-drift.md)
(true positive, `verified-OOM · deployment`; heap 2 GiB 3/3, also 4 and 8 GiB 3/3).

**Mechanism checked (§4).** In the default non-throwing mode a protocol-v5 **single-frame** request that fails
`acquireCapacityAndQueueOnFailure` (`CQLMessageHandler.java:223`) is still decoded and dispatched to
`Native-Transport-Requests` with `Overload.BYTES_IN_FLIGHT` (`:245-260`) without its bytes being charged, and its
completion `release(header)` → `releaseCapacity(M)` (`:506-510`) subtracts bytes never added, so the per-connection
`native_transport_receive_queue_capacity` (1 MiB) and the per-IP / global in-flight reserves read "at the bound"
(≤ 53.7 MB at 2 GiB) while the node holds 25–28 × that bound in decoded requests, bounded only by connections × client
window (20 connections × 1,024 in flight → `OutOfMemoryError: Java heap space`).

**Label: `known-fixed (incomplete)`** (partial: CASSANDRA-20052; its fix in 5.0.9 stops the uncharged admission of
**multi-frame** messages only, the single-frame path is unchanged)

**Alternative for the owner.** If CASSANDRA-20052 is rated **related** (it names large messages only, and its reviewer
judged small messages safe), the label is **`new`**, as stage 1 found. The partial rating is preferred here because
the issue reports the same defect of the same control — "The overload logic just allows to process huge messages for
free" — and the 5.0.9 fix covers only that message class (the B8 / CASSANDRA-8639 pattern).

## Reason

The new search found CASSANDRA-20052, which stage 1 listed only as "v5 message size not limited": its description
reports the v5 overload logic processing refused messages "for free", the same failure of the same control, for large
(multi-frame) messages. The fix in 5.0.3 (`git merge-base --is-ancestor 6f90e962f5 cassandra-5.0.9` → true) closed that
path, and the review explicitly left the single-frame path (`processOneContainedMessage`) as it was, on the argument
that a frame payload is ≤ 128 KiB. B10 shows that argument does not hold: each refused single-frame request is small,
but the node admits a connection's whole client window of them uncharged, and the release-side drift keeps the counters
"at the bound". So the mechanism was reported for one message class and fixed there, and the fix is incomplete for the
class B10 exercises → `known-fixed (incomplete)` (partial). The counter drift itself (release of bytes never acquired)
is reported nowhere; CASSANDRA-21091 only notices the v5 metric reading 0. No newer fix: trunk still dispatches with
`BYTES_IN_FLIGHT` on the single-frame path.
