# B9 — stage 3-a JIRA check (2026-11-24)

**Case:** [`native_transport_max_request_data_in_flight--v4-frames-per-connection`](../cases/native_transport_max_request_data_in_flight--v4-frames-per-connection/native_transport_max_request_data_in_flight--v4-frames-per-connection.md)
(true positive, `verified-OOM · deployment`; heap 4 GiB, direct 1,280 MiB, 128 v4 connections × one 15 MiB write).

**Mechanism checked (§4).** On protocol v4 a whole request frame is accumulated in Netty's pooled direct memory
(`Envelope.Decoder`, a `ByteToMessageDecoder` cumulation from `CBUtil.allocator`, one 16 MiB chunk per 15 MiB frame)
**before** `LegacyDispatchHandler.checkLimits` charges it against `native_transport_max_request_data_in_flight`
(heap/10); connections are unlimited at defaults (`native_transport_max_concurrent_connections: -1`). With 128
connections reading a frame at once Netty's own direct counter reached 1,280 MiB (3.0 × C) while the in-flight counter
held 75–180 MiB and no connection had been paused → `io.netty.util.internal.OutOfDirectMemoryError` in
`ByteToMessageDecoder.cumulate` on the event loop, then `JVMStabilityInspector`'s forced heap OOM and `kill -9`. (The
force-admit overshoot of one frame per connection, the design's hypothesis, is real at large budgets but did not drive
the failures.)

**Label: `new`** (best match related; no issue reports request frames held in Netty's direct memory before the
in-flight check × unlimited connections)

## Reason

The searches by identifier (`PreV5Handlers`, `LegacyDispatchHandler`, `Envelope.Decoder`/`ByteToMessageDecoder`,
`cumulation`, the in-flight and connection settings) and by symptom (`OutOfDirectMemoryError`, Netty / native-transport
direct memory OOM) found no issue that reports v4 request frames held in Netty's pooled direct memory before the
in-flight limit is consulted, or an OOM from many connections each reading a large frame. CASSANDRA-15013 is the design
of the control (charged after decode, overshoot accepted), CASSANDRA-4265 the same per-connection × connection-count
shape in the removed Thrift server, CASSANDRA-8670 Netty pool retention for large values, CASSANDRA-12034/21556 the
handling and observability of Netty direct OOMs: all related only. This agrees with stage 1's prior-art verdict
(`new`). The 5.0 branch head and trunk still check limits after decode (no newer fix found).
