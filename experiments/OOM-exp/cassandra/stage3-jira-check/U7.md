# U7 — stage 3 JIRA check (2026-11-23)

**Case:** [`in_select_cartesian_product--modification-IN-product-row-build`](../cases/in_select_cartesian_product--modification-IN-product-row-build/in_select_cartesian_product--modification-IN-product-row-build.md)
(true positive, `verified-OOM · deployment`).

**Mechanism checked (§4).** One prepared `UPDATE … WHERE k IN ? AND c IN ?` (or `DELETE`) makes the coordinator build all
P × Q rows (`PartitionUpdate.Builder` / `BTreeRow` / `BufferCell` in `ModificationStatement.addUpdates` ← `getMutations`) on one
NTR thread before anything is applied. The `in_select_cartesian_product` guardrail ships at −1, is skipped for superusers, and
when enabled bounds P and Q separately, never P × Q; `max_mutation_size` is per mutation; the in-flight limit charges 176 KB.

**Label: `new`** (closest: CASSANDRA-15250, related — the SELECT form).

## Reason

cartesian with UPDATE/DELETE): every cartesian-product issue is about SELECT, and no issue reports an UPDATE/DELETE IN × IN
expansion, its memory, or the per-side scope of the guardrail. 15250 is the SELECT-side sibling (same idea, different holder), so it
is related, not partial. Label `new`; the SELECT form stays `known-open` (see R14).
