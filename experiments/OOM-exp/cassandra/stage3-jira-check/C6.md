# C6 — stage 3 JIRA check (2026-11-24)

**Case file:** [`../cases/memtable_heap_space-slab-region--written-table-multiplicity/memtable_heap_space-slab-region--written-table-multiplicity.md`](../cases/memtable_heap_space-slab-region--written-table-multiplicity/memtable_heap_space-slab-region--written-table-multiplicity.md)
(verdict true positive; `verified-OOM · deployment`, mixed: D1 bypass by accounting omission + D2 unprotected configuration).

**Mechanism checked (case §4).** Under the shipped `memtable_allocation_type: heap_buffers` each memtable written since its
last flush holds one 1 MiB on-heap `SlabAllocator` region (`SlabAllocator.java:51, 139`), while the memtable pool
(`memtable_heap_space`, heap/4) is charged only the bytes written (≈ 1.5 KiB per 1 KiB row). The pool's flush trigger sees
only counted bytes, no age flush runs by default, the commit-log trigger is far away, and the table-count guardrail ships at
−1, so N lightly written tables pin ≈ N MiB of heap that no control counts. With 2,500 tables (≈ 0.32 MiB of schema heap
each) one row into ≈ 1,040 tables ended in a heap OOM 3/3 at 2 GiB (1,071–1,074 live regions = 2.1 × the pool while its
counter read 0.16 ×); the same rows into one table and `unslabbed_heap_buffers` both survived 3/3.

**Label: `known-open (exact: CASSANDRA-6794)`**

**Documented:** no. `conf/cassandra.yaml:792-795` (`memtable_heap_space`): "Total permitted memory to use for memtables.
Cassandra will stop accepting writes when the limit is exceeded until a flush completes" — the opposite of the case, and
nothing says the region slack is outside it; `conf/cassandra.yaml:814-825` lists `heap_buffers` as "on heap nio buffers"
with no per-table cost; `conf/cassandra.yaml:2037-2040` documents the table-count guardrail as disabled (−1) without a
memory reason; `NEWS.txt:576-579` only records the threshold rename (CASSANDRA-17195). No text in `doc/` mentions slab
regions or a per-table heap cost.

**Reason.** CASSANDRA-6794 states this case's root cause — a fixed 1 MiB slab per written table, which limits how many
tables a node can hold — and is still open, with the fix it proposes (ramped regions) applied only to the off-heap
allocator (7882) and the region size itself refused as a setting (7884). CASSANDRA-5935 states the same cost and added the
`unslabbed_heap_buffers` escape hatch, deliberately left out of the yaml, so its fix in 5.0.9 does not cover the default.
CASSANDRA-20298 shows the same holder producing a 5.0 heap OOM and the maintainer naming the accounting gap, but only the
test was changed. No issue reports the whole chain at defaults (many lightly written tables + pool counter blind to the
regions + guardrail off → heap OOM), so 6794 is exact on the root cause and the case is `known-open`. Same label as
stage 1 (2026-11-18). Not documented. The holder is unchanged after 5.0.9 (`SlabAllocator.java` has only logging and
cleaner changes on trunk), so no newer version fixes it.
