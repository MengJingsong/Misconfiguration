# B16 — stage 3 JIRA check (2026-11-23)

**Case file:** [`../cases/tombstone_failure_threshold--range-marker-bound-bytes/tombstone_failure_threshold--range-marker-bound-bytes.md`](../cases/tombstone_failure_threshold--range-marker-bound-bytes/tombstone_failure_threshold--range-marker-bound-bytes.md)
(verdict true positive; `verified-OOM · deployment`, bypass).

**Mechanism checked (case §4).** `tombstone_failure_threshold` (100,000) counts range-tombstone markers, not bytes; each
marker carries its clustering bound (12,000 B here), and the replica serializes every scanned marker into one heap
`DataOutputBuffer` (`LocalDataResponse.build`), ≈ 1.6 GiB for one read of 99,998 markers with 0 live rows. The byte
guard ships off, and when on it is blind to marker bounds (`RangeTombstoneBoundMarker.unsharedHeapSize()` omits the
clustering); the read timeout cannot cancel a marker-only scan (`QueryCancellationChecker` has no `applyToMarker`).

**Label: `new`**

**Documented:** partly — the hazard, not the bypass. `conf/cassandra.yaml:1805-1809`: "When executing a scan, within or
across a partition, we need to keep the tombstones seen in memory so we can return them to the coordinator … With
workloads that generate a lot of tombstones, this can cause performance problems and even exaust the server heap." The text
presents `tombstone_failure_threshold: 100000` (l. 1815) as the guard; it does not say the guard counts markers regardless
of their size, so a workload under the threshold (as here) reads as safe. Not counted as `documented only`.

**Reason.** Rerunning stage 1's queries (2026-11-18) and adding marker-class, cancellation, and size/heap-summary queries
found nothing that reports a read OOM from counted markers with large bounds under the default threshold, the
`unsharedHeapSize()` omission in the local read-size tracker, or marker scans escaping timeout cancellation. The
threshold being a count is by design (6117), and tombstone-heap OOMs on older holders exist (12707, 13624), but none has
B16's holder (the 3.0+ replica response buffer) with this trigger. No exact or partial issue and no doc that warns about
the byte size of counted markers → **new**.
