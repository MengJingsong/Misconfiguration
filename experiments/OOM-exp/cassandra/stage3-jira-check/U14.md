(verdict true positive, `verified-OOM · deployment`).

**Mechanism checked (case §4).** Holder: per-table heap state that every loaded table carries: 214 JMX MBeans per table
(107 metrics under the `Table` and `ColumnFamily` names), their `ObjectName` / property strings embedding the keyspace and
table names (≈ 205 KB `byte[]` per long-named table, ≈ 574 B per name character), and reservoir/histogram `long[]`
(≈ 138 KB); 0.480 MiB per empty long-named table (0.336 short). `MetricName` objects are not retained in 5.0.9. Trigger:
DDL creating empty tables; control missing: `tables_fail_threshold` ships −1, no byte budget.

**Label: known-open (partial: CASSANDRA-20446, CASSANDRA-20332)**

## Documented

**no.** `conf/cassandra.yaml:2037-2040` "# Guardrail to warn or fail when creating more user tables than threshold. # The two
thresholds default to -1 to disable." and `NEWS.txt:370-372` (guardrails "such as limiting the number of tables") name the
control but say nothing about a per-table heap cost; no doc page gives a per-table memory figure or a safe table count.

## Reason

Re-check of stage 1 with the new rules changes the closest issue. CASSANDRA-19567 (stage 1's anchor) is fixed only in 6.0 and
targets `MetricName` objects that 5.0.9 does not retain, so it is related, not the measured holder. Two newer open issues,
20446 (JMX `ObjectName` string duplication, measured per table on 4.1) and 20332 (per-table metric memory multiplied by the
table count), report the holder the dumps attribute 85 % of the heap to, but as a footprint concern without an OOM and
without the uncapped table count as trigger: **partial** matches, both open. The count control is known to ship disabled
(21664, unmerged, would only warn). Hence **known-open (partial)**; the OOM itself, the 0.48 MiB per-table figure and the
name-length dial are not reported.
