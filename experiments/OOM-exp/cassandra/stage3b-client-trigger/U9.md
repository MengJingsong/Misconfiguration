# U9 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/big-row-index-buffer--64KiB-clustering-wide-partition/big-row-index-buffer--64KiB-clustering-wide-partition.md`](../cases/big-row-index-buffer--64KiB-clustering-wide-partition/big-row-index-buffer--64KiB-clustering-wide-partition.md)

Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** The BIG-format partition writer serializes one `IndexInfo` (full first and last clustering) per 64 KiB
block into one heap `DataOutputBuffer` for the whole partition. With 65,535-byte clustering keys every row is a block and
the buffer is ≈ 2 × the partition's data, grown ×1.5 by copying; a ≈ 1 GB partition kills a 2 GiB (and 4 GiB) heap on
the `CompactionExecutor` or flush writer.

**Condition assessed:** **B2** (all default, autocompaction on, 15,000 writes, no operator action; heap OOM 3/3 at
2 GiB). The headline arm T2/T4 (3/3 at 2 and 4 GiB) used `nodetool disableautocompaction`, `flush` and `compact`, which a
client cannot run; B2 shows the same holder without them. M6/M8 (two concurrent compactions, 6 and 8 GiB) are discussed
under blast radius.

**Label: `client-triggerable · data role; replicas of a partition key the attacker chooses, repeatable per replica set (likely crash loop on restart)`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` on a table with a `blob`/`text` clustering column — a common
admin-made shape, e.g. CASSANDRA-16764's URI-path clustering key); a DDL role can create such a table itself.

## Condition and how common

None beyond ≈ 1 GB written into one partition with long clustering keys — at a modest write rate a few minutes of
traffic. The data stays inside every documented limit at defaults.

## Blast radius

- **Which node:** every **replica** of the chosen partition key — each one flushes and compacts its own copy, so with
  RF 3 the whole replica set hits the holder at about the same time. The attacker steers it by choosing `pk` (token
  ownership is readable by any role from `system.local`/`system.peers`).
- **Repeatable:** yes — one such partition per replica set takes the cluster down set by set. The sstables persist, so
  after a restart STCS picks the same fragments again: a **crash loop** until an operator removes data or raises
  `column_index_size` (inferred from B2's background trigger; restart not run).
- **Heap range:** single writer 2 and 4 GiB (3/3); two concurrent compactions 6 GiB (3/3) and 8 GiB (2/3) — reachable by
  writing two such partitions to two tables (DDL role, or two admin tables) so `concurrent_compactors` = 2 run together.
  Above ≈ 16,383 rows the buffer hits the 2 GiB array cap and compaction fails with `BufferOverflowException` instead
  (CASSANDRA-16764): no OOM, but compaction of that table is stuck — still a denial of service for larger nodes.
- **Other tenants:** requests whose replica set includes a dead node lose that replica: at RF 3 / QUORUM one dead node is
  tolerated, the whole replica set dead means `Unavailable` for every tenant whose keys share those token ranges;
  hints accumulate for the dead nodes.

## Operator visibility

Before: little at defaults — no partition-size guardrail warning (null); the only signal is sstable stats (large
partition in `nodetool tablestats`/`tablehistograms`, Index.db ≈ 2 × Data.db). During: compaction progress on one huge
partition, GC warnings. Attribution: the partition key and table are in the compaction log/hprof; with authentication on,
the table's writers are not logged (audit log ships off, `conf/cassandra.yaml:1893-1894`).

## 3-b confirm

Worthwhile: B2 at 2 GiB with authentication on, a non-superuser role holding only `MODIFY`/`SELECT` on an admin-made
`(pk int, ck text, v blob)` table writes the 15,000 rows; a victim role reads/writes another table. Add one restart
after the OOM to check the crash loop. ≈ 15–20 min per run; a 3-node RF 3 run would show the replica-set kill.

## Reason

The B2 arm, which reproduced the OOM 3/3 with no operator action, consists of a table shape that is common (a long
text/blob clustering key) and ordinary CQL writes that pass every check at defaults; the flushes and the compaction that
build the buffer are triggered by the node itself as a consequence of the write volume. The `nodetool` steps of T2/T4
only make the run deterministic. Hence `client-triggerable` alone, at data role. The writer runs on every replica of the
chosen key and the trigger survives a restart, so the attacker can take down replica sets of its choice.
