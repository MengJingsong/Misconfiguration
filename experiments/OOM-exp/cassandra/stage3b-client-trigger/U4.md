# U4 — stage 3-b client trigger check (2026-11-24)

**Case:** [`cql-row-limit--wide-row-default-pages`](../cases/cql-row-limit--wide-row-default-pages/cql-row-limit--wide-row-default-pages.md)
(true positive, `verified-OOM · deployment`, unprotected configuration). Stage 3-a: not run yet (the case file's own JIRA
check: `by design` for the row-count page in 5.0.x, byte paging only in 6.0-alpha3 via CASSANDRA-11745; read thresholds
`documented` as off). Analysis only (no node run). Code references are to the pinned 5.0.9 tree
`systems/cassandra/source/`, paths below `src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** A page is bounded only in rows (`rowsCounted`), and the byte bound (`read_thresholds_enabled`) ships off. So
each in-flight 5,000-row page of 48 KiB rows (234 MiB of values) is held as the replica's serialized `DataOutputBuffer`
(216–324 MiB) plus the coordinator's `ResultSet`. Three concurrent default-page reads OOM a 2 GiB heap.

**Label: `client-triggerable · data role; the replica serving the read (steerable by key) + the coordinator, repeatable on every replica set; heap OOM shown at a 2 GiB heap, larger nodes die in Netty direct memory (C2's domain) at higher concurrency`**

Reach: **alone**. Lowest privilege: **data role**: `MODIFY` + `SELECT` on any admin-made table with a clustering column and
a `blob`/`text` value. A role with `SELECT` only needs an existing partition (or range) holding ≳ 0.25 GiB to fill one page,
which is less common but not rare for wide tables. That variant is untested.

**Condition:** none.

**Above 2 GiB heap.** The same client workload at higher c killed every larger node-class budget tested, but first in
Netty direct memory: an `OutOfDirectMemoryError` in `Message.encode` escalated by `JVMStabilityInspector` to a forced heap
OOM and `kill -9`. This happened at c = 8 (4 GiB / 2 GiB), 16 (8 / 4 GiB) and 32 (15.5 / 7.75 GiB, 2/2). For a client this is
the same node death, but the holder is C2's (encoded responses). C2's own label is `alone · data role; coordinator`.

## Blast radius

- **Which node:** the **replica that executes the data read** holds the serialized page (`ReadResponse.build`). In a
  multi-node cluster the coordinator separately holds the received response and the `ResultSet` (≈ 2 × page). The attacker
  chooses the replica set by partition key. A token-aware client connected to a replica makes both roles hit one node, as
  tested. Digest reads do not build the page.
- **Repeatable:** yes. The wide partitions stay on disk, so reads can resume as soon as the node is back. Any node can be
  reached by placing a few wide partitions in its ranges.
- **Other tenants:** the replica (and/or coordinator) is killed. Its connections drop, its ranges lose a replica, and
  killing a range's replicas in turn gives `Unavailable`/timeouts to every tenant there. Before death, GC pauses slow every
  request on the node.

## Operator visibility

Before: nothing at defaults (read thresholds and page-size guardrail off). Wide partitions show in `tablehistograms` /
`tablestats`. During: GC warnings and slow-query entries for reads that complete. The heap dump shows `LocalDataResponse` /
`DataOutputBuffer` of the table. With audit/FQL (off by default) the role is attributable. Turning on
`read_thresholds_enabled` with a local read-size fail threshold stops it (I-2G 0/3), but stage 2 showed it then refuses
every default-page read of such rows.

## 3-b confirm (not run): worth it?

Worth it, moderate cost.

**Needs:**
- one node, `MAX_HEAP_SIZE=2G`, with the direct limit as in stage 2;
- `PasswordAuthenticator` + `CassandraAuthorizer`;
- an admin-made `(pk, ck, v blob)` table, with `GRANT SELECT, MODIFY` on it only to the attacker role;
- the attacker loads 3–4 partitions × 5,000 × 48 KiB (≈ 1 GiB, a few minutes), then runs the case's `U4Load` at c = 3;
- a victim role on its own keyspace.

Stage 2's rate is 4/5 at c = 3, so plan 2 runs, or step to c = 4 as a pre-declared second arm.

## Reason

Every step is ordinary CQL from a role that can write and read one wide table. It loads 48 KiB values, then sends default
paged SELECTs at CL ONE with three in flight. The only byte control ships off, the page-size guardrail is off and counts
rows, and no fault, operator action or diagnostic aid is in the verified arm. Lowest privilege: **data role**. Reach:
**alone**. Blast radius: the data-read replica of the chosen keys and the coordinator, repeatable on every replica set.

Raw logs: `pc91:/mydata/s4/3b-U4/runs/` (≈ 43 MB, logs and GC logs only).

**Result.** The attack was **confirmed** with authentication and authorization on, by a role holding only
`SELECT` + `MODIFY` on one admin-made table (**data role**).
- **At the verified arm's c = 3** the node survived the 160 s step **0/2** (`A-1`, `A-2`). Stage 2 on pc75 had 4/5.

- **The victim** (its own role and table, 40 ops/s) saw **no errors** up to the OOM, with p99 at most 137 ms. It then saw

Notes on the table:
- **First stack (`A-3`).** `OutOfMemoryError.<init>` ← `HeapByteBuffer.<init>` ← `ByteBuffer.allocate` ←
  `BufferedDataOutputStreamPlus.allocate:77` ← **`DataOutputBuffer.expandToFit:178`** ← … ←
  `Cell$Serializer.serialize:304` ← `UnfilteredSerializer.serializeRowBody`. This is stage 2's first stack (T-2G-2..5):
  a request thread growing a replica page buffer. The shipped `-XX:OnOutOfMemoryError="kill -9 %p"` then killed the
  node. The `.hprof` was scanned and deleted.
- **STW.** STW fraction ≤ 2–3 % per 60 s in every lifetime: no service loss before death.
- **Attack-client errors in `A-3`.** The client's 8.5 M errors all came after the death (first error 1.8 s after the
  `HeapDumper` safepoint). They are its closed loop spinning on `NoHostAvailable`.
- **Rate.** At c = 3 this node did 0.44 pages/s against stage 2's 0.36 on pc75 (Xeon E5-2660 v2 2.2 GHz). The OOM needs
  three page buffers in their last growth step at once, and stage 2's survivor T-2G-1 had the same profile (old post-GC
  ≤ 1,207 MiB). Authentication adds nothing to a read's heap holder: the permission check is cached per role, and the
  page buffer does not change. So the c = 3 survivals are read here as the margin on faster cores, not as an effect of
  auth. That reading was not separated by a run without auth on pc91.

### Deviations

1. **c = 4 for the third run.** After `A-1` and `A-2` survived at c = 3, the last allowed run used c = 4, the second arm
   pre-declared in "3-b confirm (not run)" above, instead of a third c = 3 run. Concurrency is the attacker's choice, not
   a budget or a constraint. The OOM at c = 4 is n = 1.
2. **Different node, same budget.** The node was pc91, not pc75: a different CPU (3.3 vs 2.2 GHz) and pc91's own build
   of the pinned tree. The budget pair (2 GiB / 15,872M) is identical.
3. **LOAD lifetime as harness mechanics.** The `LOAD` lifetime (8 GiB, flush/compact/drain/template) is harness
   mechanics as in stage 2. The attacker's own load at a 2 GiB heap, followed directly by the attack, was not run.
4. **Probe rows in the template.** The attacker's probe wrote and deleted one row at pk 99, so `tablestats` counts
   17 partitions (one tombstone). The attack reads pk 0–15 only.
5. **Shared host.** The victim, the attack client and the sampler share the host with the node (no CPU pinning), as in
   stage 2's single-node arm.
