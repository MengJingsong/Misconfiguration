# U8 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/vector_dimensions--select-json-element-slices/vector_dimensions--select-json-element-slices.md`](../cases/vector_dimensions--select-json-element-slices/vector_dimensions--select-json-element-slices.md)
· **Stage 3-a:** [`../stage3-jira-check/U8.md`](../stage3-jira-check/U8.md) (`new`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** `SELECT JSON` of one `vector<boolean, 16000000>` cell (16 MB serialized, accepted because only serialized
bytes are checked) makes `VectorType.toJSONString` `split()` the cell into 16 M `HeapByteBuffer` slices (≈ 832 MB per
request, 52×) on the coordinator's native-transport thread. Two concurrent reads kill a 2 GiB heap; N ≈ 1.25·H/GiB + 1
reads kill any heap up to 16 GiB tested.

**Condition assessed:** T (2 GiB heap, N = 2 concurrent `SELECT JSON`, 3/3); the budget arms B (4 GiB N = 6, 16 GiB
N = 21, 3/3 each) are the same steps with more concurrency.

**Label: `client-triggerable · DDL role; the coordinator the attacker connects to, repeatable on every node`**

Reach: **alone**. Lowest privilege: **DDL role** (create its own table with a very large vector column). A **data role**
suffices only if an admin made a table with a vector column of millions of dimensions — implausible (real embedding
columns are 10²–10⁴ dimensions, and the split list for those is tiny), so it is not counted.

## Condition and how common

None beyond the client's own schema, one write and N concurrent reads. N scales with the heap (2 at 2 GiB, 6 at 4 GiB,
21 at 16 GiB; ≤ 128 threads), which any client reaches with a few connections.

## Blast radius

- **Which node:** the **coordinator** that receives the `SELECT JSON` (the list is built in `Selection.rowToJson` on the
  request thread, `cql3/selection/Selection.java:339`). The attacker picks it by connecting to it; replicas only ship
  16 MB.
- **Repeatable:** yes, on every node in turn (or all at once, N connections per node) with the same one row: the whole
  cluster can be taken down from one table. At large heaps the node first spends minutes in ≥ 90 % GC (16 GiB: 4–6 min)
  before the OOM.
- **Other tenants:** every request coordinated by the victim node fails or times out during the GC thrash and after the
  `kill -9`; drivers fail over to other coordinators, so tenants see a latency spike and errors until the attacker moves
  on — but with every node targeted, the cluster is unavailable. Replica-side losses (hints, unavailable at QUORUM) follow
  when the dead coordinator is also a replica.

## Operator visibility

Before: nothing at defaults — no guardrail warning (dimension guardrail −1), no read-size warning (thresholds off). The
`CREATE TABLE` of a 16 M-dimension vector is visible in the schema (`system_schema.columns`) and in the schema-change log
line, and is an unusual shape an operator could alert on. During: GC pause warnings (`GCInspector`), long native-transport
requests. Attribution: a heap dump shows `VectorType.toJSONString` frames; with authentication on, the owning role of the
keyspace and `system_views.clients` identify the attacker; the audit log ships off (`conf/cassandra.yaml:1893-1894`).

## 3-b confirm

Worthwhile and cheap (minutes per run, 2 GiB heap on one victim node): `PasswordAuthenticator` + `CassandraAuthorizer`,
a non-superuser role granted only `CREATE` on one keyspace (DDL role) runs the T arm (create table, insert, two
concurrent `SELECT JSON`); a victim role on another keyspace runs steady reads/writes and records success and latency.
Also worth one run with the dimension guardrail enabled (`vector_dimensions_fail_threshold: 8192`) as an intervention,
to show it now applies to the non-superuser (it is skipped for superusers).

## Reason

Every step of T is a CQL statement an ordinary role can issue: its own keyspace/table (DDL role), one 16 MB insert that
passes every byte check at defaults, and two concurrent `SELECT JSON` reads. No operator action, fault or diagnostic aid
is involved (the flush is a convenience). The only control that would refuse the schema — `vector_dimensions` — ships
off, and on a stock node (`AllowAllAuthenticator`) every client is a superuser that guardrails skip anyway. A data role
alone would need an admin-made multi-million-dimension vector column, which is not a plausible schema, so the lowest
realistic privilege is DDL role. Because the expansion happens on the coordinator, the attacker chooses the victim node
and can repeat it across the cluster.
