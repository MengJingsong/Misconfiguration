# B21 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/sai_vector_search_max_top_k--unpaged-topk-wide-rows/sai_vector_search_max_top_k--unpaged-topk-wide-rows.md`](../cases/sai_vector_search_max_top_k--unpaged-topk-wide-rows/sai_vector_search_max_top_k--unpaged-topk-wide-rows.md)
· **Stage 3-a:** [`../stage3-jira-check/B21.md`](../stage3-jira-check/B21.md) (`new`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** An ANN query (`ORDER BY emb ANN OF […] LIMIT 1000`) always runs unpaged: the server raises any smaller page
size to the LIMIT, and its only cap (`MAX_TOP_K` = 1,000) counts rows. Each replica eagerly builds the whole top-K map of
1,000 wide rows and serializes it into one growing buffer before any byte check, and nothing sums these bytes across
concurrent queries: 12 concurrent queries over 120 KiB rows exhaust a 2 GiB heap (32 at 4 GiB).

**Condition assessed:** the single verified condition (arm A, 2 GiB heap, c = 12 concurrent ANN queries, LIMIT 1000,
120 KiB `text` rows, every constraint at its default). 4 GiB / c = 32 is the same path.

**Label: `client-triggerable · data role; every node the ANN scan contacts (one node in stage 2), repeatable at will`**

Reach: **alone**. Lowest privilege: **data role** (SELECT + MODIFY on an admin-made table with a `vector` column, an SAI
index on it and a wide `text`/`blob` column; SELECT alone suffices if such wide rows already exist). A DDL role can make
the whole schema itself.

## Condition and how common

None beyond the client's own schema/data: no fault, restart or stall. The verified OOM is at heaps up to 4 GiB; at
8–15.5 GiB stage 2 measured no OOM but a node that served ≈ 0 queries at c ≥ 16 (a service loss the same client causes).

## Blast radius

- **Which node:** in stage 2 the single node (the replica side holds 91–97 % of the heap; first error on ReadStage). On a
  ring an ANN query fans out to every node needed to cover the token ring (`ScanAllRangesCommandIterator`), and each builds
  a top-K of up to LIMIT local rows, so one attacker's concurrent queries load **every node that holds ≥ 1,000 wide
  matching rows** of the table at once, plus the coordinator it connects to (coordinator copies were rare on one node
  because the 128 MiB internode reserve drops all but one response; untested on a ring).
- **Repeatable across nodes:** yes; the attacker chooses the coordinator, and the replica work is ring-wide by design.
- **Other tenants:** ReadStage (32 threads) and the heap are shared, so other tenants' reads time out during the attack
  and fail with `Unavailable` / timeouts at their CL once nodes die; at large heaps the node stays up but serves ≈ 0.

## Operator visibility

Before/during: the Top-K page-size warning goes to the client only (`ClientWarn`, `SelectStatement.java:328`); queries
slower than `slow_query_log_timeout` (500 ms, `config/Config.java:173`) are logged in `debug.log` with their text;
internode "overloaded; dropping" lines and dropped-message metrics on the self/peer connection; GC warnings. The read-size
thresholds, if an operator turns them on, refuse every query (`ReadSizeAbort`) but still OOM (arm I 3/3). Attribution by
role: `system_views.clients` / `nodetool clientstats`; the audit log ships off.

## 3-b confirm

Worthwhile and feasible on one node with the stage-2 harness: `PasswordAuthenticator` + `CassandraAuthorizer`, an admin
creates `b21.docs` and its SAI index, the attacker role holds only `SELECT, MODIFY` on that table and loads the 4,000 wide
rows itself, then runs T at c = 12 (2 GiB); a victim role on another table runs paged reads/writes at a low rate and
records its own success rate and latency. A ring variant (≥ 3 instances, the per-node fan-out) would answer the
multi-node blast radius but is beyond stage 2's one-victim rule (owner's call).

## Reason

Every step of the verified arm is ordinary CQL that a non-superuser can issue: the schema is a common vector-search
shape (or a DDL role's own), the 120 KiB rows pass every default limit, and the ANN SELECT needs only `SELECT`
(`SelectStatement.java:243-253`). The server itself removes paging for Top-K (`:322-338`), its only cap counts rows
(`StorageAttachedIndex.java:503-504`), and none of the guardrails that would apply to an ordinary role ships enabled for
this path (read thresholds false, page size −1, column value size null). No step needs a fault, restart, timeout change or
diagnostic aid, and nothing is reachable before authentication. Hence **client-triggerable alone at data role**, with a
ring-wide replica footprint per query (inferred from the code, not run).

## 3-b confirm (pc72, 2026-11-23)

### Deviations

1. Node and architecture: `pc72` x86_64 instead of `ms0604` aarch64 (different jar hash of the same 5.0.9 tree); the
   OOM came ≈ 1–2 s into c = 12 instead of 10–11 s.
2. No `nodetool flush` / `compact` in the load (above); layout still 1 SSTable.
3. Authentication + authorization on (the point of the confirm); a victim-tenant client adds 40 small requests/s.

   sampler retrying against the dead node). Not treated as invalidating.
5. One extra lifetime with the SELECT-only role (TSEL-AUTH-2G-1).
6. AUTHCHECK ran twice: try 1 lost the pre-auth steps after P2 (the server reset the connection and the script did not

   agreed with try 2. Both logs are kept (`AUTHCHECK/try1/`).
7. A launcher argument error started one lifetime labelled `BATCH` at 16:43:57; it was stopped by me at the ready step
