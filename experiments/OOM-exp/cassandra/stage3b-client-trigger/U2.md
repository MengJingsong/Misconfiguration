# U2 — stage 3-b client trigger check (2026-11-24)

**Case:** [`native_transport_max_concurrent_connections--prelogin-frame-multiplicity`](../cases/native_transport_max_concurrent_connections--prelogin-frame-multiplicity/native_transport_max_concurrent_connections--prelogin-frame-multiplicity.md)
(true positive, `verified-OOM · deployment`, unprotected configuration). Stage 3-a: not run yet (the case file's own JIRA
check: `known-open`, CASSANDRA-21756 open, 4265 Won't Fix). Analysis only (no node run). Code references are to the pinned
5.0.9 tree `systems/cassandra/source/`, paths below `src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Each TCP connection to the native port that sends a v4 header declaring a 16 MiB − 9 B body and all but the
last byte pins one 16 MiB chunk of Netty pooled direct memory in `InitialConnectionHandler`'s cumulation buffer. No Cassandra
counter charges it, and at defaults neither a connection limit nor an idle timeout applies. At k = D/16 MiB − arenas − 1
connections (927 at the automatic 15,872 MiB direct limit, 106 at 2 GiB) Netty throws `OutOfDirectMemoryError`. Cassandra
escalates it to a forced heap OOM and the shipped `kill -9`.

**Label: `client-triggerable · pre-auth; coordinator, repeatable on every node`** (pre-auth by construction: the verified arm
never sends STARTUP, so no authenticator is ever consulted)

**Condition:** none. The only control that stops it, `native_transport_max_concurrent_connections`, is an operator setting.
It ships off. AI1–3 show it removes the endpoint at 512, but it then also refuses legitimate new connections while it is full.

**Where pre-auth could fail:** only under non-default transport security. If the operator sets `client_encryption_options`
with `require_client_auth: true`, the attacker needs a client certificate before any frame. With the default (encryption
off) or encryption without client auth, a TLS handshake is enough. An auth timeout (CASSANDRA-21756) is not in 5.0.9.

## Blast radius

- **Which node:** the node whose native port the attacker connects to. Every node listens, and the frame is held on its
  event loops before any routing.
- **Repeatable:** yes, every node in parallel from one host, and again immediately after each restart. No data or schema
  is left behind, so there is no crash loop. There are no credentials, so there is no role to revoke. Only network
  filtering of the source address helps.
- **Other tenants:** the node is `kill -9`ed. At 2 GiB direct this happens 1–2 s after the first OODME. At the automatic
  budget it takes 40 s, while the heap dump is written, and the probe timed out throughout. Every client connected to that
  node loses its connections. Requests needing its replicas fail at their consistency level until restart. With every node
  attacked the cluster is down. Stage 2's probe (an authenticated-style STARTUP + QUERY connection) was served up to the
  first OODME. The holder costs other clients nothing before the endpoint.

## Operator visibility

Before the failure there is almost nothing. Cassandra counts these sockets in no metric (`ConnectedNativeClients` 0,
in-flight bytes 0) and logs nothing per connection. Only OS-level tools (`ss`: hundreds of established connections on 9042
from few addresses, with full receive queues drained into Netty) and process RSS show it. At the failure, `system.log` shows
"Unknown exception in client networking" with `OutOfDirectMemoryError`, then "Force heap space OutOfMemoryError". No
identity exists for audit logging.

## 3-b confirm (not run): worth it?

Low priority. Pre-auth holds by construction: the test arm never sent STARTUP, and with `PasswordAuthenticator` the
pre-STARTUP pipeline is byte-identical. A confirm could add two things the analysis cannot:
1. the attacker on a **separate host** over the real network (stage 2 used loopback);
2. a victim role measuring its own success rate.

Cheapest set-up: the B budget (`MAX_HEAP_SIZE=4096M MAX_DIRECT_MEMORY_SIZE=2048M`, 106 connections, ≈ 1.7 GiB sent),
`PasswordAuthenticator` + `CassandraAuthorizer`, the stage-2 `stall_client.py` from a second node, and a victim client on the
same node.

## Reason

The verified arm is a stream of stalled, legal-length pre-STARTUP frames from one address. It needs no schema, no data, no
credentials and no protocol state beyond TCP. Every step runs in the initial pipeline before the connection can even ask to
authenticate, and the two operator controls that would bound it (connection limit, idle timeout) ship off. Lowest privilege:
**pre-auth**. Reach: **alone**. Blast radius: the connected node is killed, and the attack repeats on every node at once.
