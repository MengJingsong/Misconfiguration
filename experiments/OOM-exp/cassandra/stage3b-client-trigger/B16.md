# B16 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/tombstone_failure_threshold--range-marker-bound-bytes/tombstone_failure_threshold--range-marker-bound-bytes.md`](../cases/tombstone_failure_threshold--range-marker-bound-bytes/tombstone_failure_threshold--range-marker-bound-bytes.md)
· **Stage 3-a:** [`../stage3-jira-check/B16.md`](../stage3-jira-check/B16.md) (`new`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** `tombstone_failure_threshold` (100,000) counts range-tombstone markers, not bytes; a partition of 99,998
markers with 12,000-byte bounds and no live rows passes it, and the replica serializes every marker into one heap
`DataOutputBuffer` (≈ 1.6 GiB). One read kills a 2 GiB heap; 6 concurrent reads kill a 31,744 MiB heap. The read timeout
does not cancel a marker-only scan.

**Condition assessed:** T (2 GiB heap, c = 1, 3/3); CAL/REP at 31,744 MiB, c = 6 (3/3) for the heap range.

**Label: `client-triggerable · data role; the replica serving the data read (steerable by key), repeatable on every replica set, any resolved heap`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` + `SELECT` on a table with a `text`/`blob` clustering
column — a common admin shape).

## Condition and how common

None. ≈ 1.2 GB of range deletes into one partition and one read; at larger heaps a handful of concurrent reads (and reads
that time out keep scanning on the replica, so retries add up).

## Blast radius

- **Which node:** the **replica that executes the data read** (`LocalDataResponse.build`); chosen by the partition key,
  made local by a token-aware client; repeats hit the other replicas of the key as the dynamic snitch moves the read.
  Digest reads do not serialize the data; the coordinator copy of a remote response (OC-162) was not tested.
- **Repeatable:** yes, on every replica set, at every heap `cassandra-env.sh` resolves (up to 31,744 MiB tested); the
  tombstones stay 10 days (`gc_grace_seconds`), so the same partition kills a node again after restart with one read.
- **Other tenants:** a dead replica (QUORUM tolerates one per set; the whole set dead means `Unavailable`); before the
  end, ReadStage saturation (active 32 marker scans that ignore timeouts) slows every read on the node.

## Operator visibility

Before/during: the replica logs the tombstone **warning** (`tombstone_warn_threshold` 1000, `conf/cassandra.yaml:1814`;
`db/ReadCommand.java:629-647`) with the table and key for each such read, and the client receives the warning — a clear
signal and attribution to the partition (not to the role; audit log off, `conf/cassandra.yaml:1893-1894`). GC warnings.
Lowering `tombstone_failure_threshold` (I: 10,000) or enabling the byte guard with bounds counted (I2, a patch) stops it.

## 3-b confirm

Worthwhile and cheap (≈ 10 min, 2 GiB heap): T with authentication on, a data role with `MODIFY`/`SELECT` on an
admin-made `(pk int, ck text, v int)` table writes the 49,999 deletes and reads once; a victim role reads/writes another
table. Optional: a second read after restart without re-writing (persistence).

## Reason

All of T is ordinary CQL by a role with read/write access to a common table shape: range deletes with long bounds and a
single `SELECT`, every value inside the defaults; the only read guard on by default counts markers and is passed by
construction. No operator step, fault or diagnostic aid is needed (flush/compact only fixed the layout). The holder is on
the data-read replica, which the attacker chooses by key; the endpoint holds at every resolved heap.
