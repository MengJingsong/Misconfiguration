# C6 — stage 3-b client trigger check (2026-11-24)

**Case file:** [`../cases/memtable_heap_space-slab-region--written-table-multiplicity/memtable_heap_space-slab-region--written-table-multiplicity.md`](../cases/memtable_heap_space-slab-region--written-table-multiplicity/memtable_heap_space-slab-region--written-table-multiplicity.md)
· **Stage 3-a:** not filed yet (the case file names CASSANDRA-5935 / 6794, open).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Under the shipped `heap_buffers`, each memtable that has received a write holds a whole 1 MiB on-heap slab
region (`utils/memory/SlabAllocator.java:51`, `:137-139`). The memtable pool is charged only the bytes written (≈ 1.5 KiB
for a 1 KiB row), so it never flushes. Each table in the schema also costs ≈ 0.32 MiB of heap, and the table count is
uncapped. N lightly written tables in a large schema → Java heap OOM.

**Condition assessed:** T at 2 GiB (`verified-OOM · deployment`): 2,500 tables, one 1 KiB row into each in turn at 100
rows/s → heap OOM 3/3 after ≈ 1,040 tables. The same run at 4 GiB with 4,500 tables OOMed 1/1.

**Label: `client-triggerable · DDL role; every replica of the attacker's keyspace (RF up to every node), schema heap on every node`**

Reach: **alone.** Every step is CQL. The role needs CREATE ON ALL KEYSPACES, or CREATE on one keyspace an admin made.
**Also:** `client-triggerable given a schema of ≈ 2,500+ tables (2 GiB heap) · data role` (MODIFY on ≈ 1,000 of them): rare.

## Condition and how common

None at DDL role. Creating 2,500 tables takes ≈ 3 min, and writing one row each takes ≈ 10 s. Schema changes propagate to
every node, so the per-table heap (≈ 0.32 MiB) is paid cluster-wide, whatever the RF. At data role, the admin's schema
must already hold thousands of tables (an anti-pattern, though it occurs in multi-tenant clusters) with MODIFY granted on
≈ 1,000 of them: **rare**.

## Blast radius

- **Which node:** every replica of the attacker's tables. With RF = node count every node gets every row, and every node
  carries the schema heap, so all nodes die together.
- **Repeatable / persistent:** yes, the attacker writes again after any restart. The schema (≈ 0.32 MiB of heap per table)
  stays after restart. Commit-log replay re-applies the acknowledged one-row mutations into ≈ 1,000 memtables, one region
  each, before its final flush. Replay may therefore reach the same heap state and die again. That is probable and
  unverified.
- **Other tenants:** a Java heap OOM after ≈ 30 s of back-to-back full GCs (timeouts for everyone on the node), then
  `kill -9`. Cluster-wide unavailability if every node is hit. Even without the writes, the schema bloat leaves every node
  with ≈ 800 MiB less heap.

## Operator visibility

Before: thousands of `CREATE TABLE` schema-change lines in `system.log` (no guardrail warning: thresholds −1);
`system_schema.tables` count; the memtable pool shows nothing unusual (K ≈ 0.16 C, no flush). During: `GCInspector` long
pauses, `StatusLogger`. After: `OutOfMemoryError: Java heap space` with a heap dump full of `byte[1048576]` (slab regions).
The keyspace's owner identifies the role; the audit log ships off.

## 3-b confirm

**Worthwhile.** It needs pc91 (or any node) at heap 2 GiB with `PasswordAuthenticator` + `CassandraAuthorizer` and an
attacker role with `CREATE ON ALL KEYSPACES` only. The attacker creates `ks` and 2,500 tables on the running node (no
template, no restart), then writes one 1 KiB row into each. A victim role on its own keyspace measures success and
latency. An admin restart with the same data tests the replay claim.

## Reason

Every step of the verified arm is a CQL step for a role that may create its own keyspace and tables. The table-count and
keyspace-count guardrails ship disabled. The writes are one ordinary small INSERT per table, and the slab region is
allocated by the server for each newly written memtable while the pool counts only bytes. The template restore was a
harness convenience, not a step the endpoint needs. No fault, restart or aid is needed. Hence **client-triggerable alone at
DDL role**: the attacker's RF choice reaches every node, and the schema heap lands on every node.

## 3-b confirm (ms0617, 2026-11-24)

Fresh session, owner-approved confirm run, 09:19–10:02 MST on `ms0617` (node lock held for that span). **Result: confirmed.**
A role holding only `CREATE ON ALL KEYSPACES` created `ks` and 2,500 tables on the running node, then wrote one 1 KiB row into
each in turn. The node died with `OutOfMemoryError: Java heap space` after 1,050 acknowledged rows; the dump held **1,086**
`byte[1048576]` slab regions (stage 2: 1,071–1,074). The claim that a restart replays into the same OOM, which the analysis
called probable and unverified, **held 1/1**: an admin restart on the same data died in commit-log replay, in
`SlabAllocator.getRegion`, with 1,093 regions, and never opened the native port. Evidence: [`logs/C6/`](logs/C6/) (`A-1/`,
`RP-1/`, `harness/`). Small logs stay on the node under `ms0617:/mydata/s4/3b-C6/runs/<run>/` (big logs gzipped). The
dumps, the data and commit-log directories and the copied tree were deleted.

### Deviations

- Node `ms0617` (aarch64 m400) instead of pc91, with its own build of the 5.0.9 tree; numbers are not pooled with stage 2.
  Address 127.0.0.1 and JMX 7199 instead of 127.0.9.1 and 7196.
- The schema was created live by the attacker, which tests the claim that the template is not needed. Stage 2 restored an
  8 GiB-built template.
- Two `jcmd GC.class_histogram` after the DDL (diagnostic; L0) cost the victim 47 ticks. No histogram ran during the writes.
- RP-1 is one run. Its rewrite step (an attacker writing again after a restart) did not run, because the node never came up.
- No matched control or intervention under auth (stage 2 has them 3/3). The victim's workload is light (10 ops/s).

### Which code-reading claims held

- **"Every step is CQL for a role with CREATE ON ALL KEYSPACES" — held.** The attacker held one permission
  (`<all keyspaces> CREATE`) and was refused on the victim's table, on roles and on grants. Every attack statement it sent
  succeeded.
- **"The creator gets all permissions" (`AlterSchemaStatement.java:145-155`) — held.** After the DDL,
  `LIST ALL PERMISSIONS OF attacker` returned 17,514 rows: CREATE/ALTER/DROP/SELECT/MODIFY/AUTHORIZE/UNMASK/SELECT_MASKED on
  `<keyspace ks>`, and ALTER/DROP/SELECT/MODIFY/AUTHORIZE/UNMASK/SELECT_MASKED on each `<table ks.tN>`
  (`A-1/auth-after-ddl.json`, trimmed). So the MODIFY the writes need came from creating the tables; no grant gave it.
- **"Table/keyspace guardrails ship disabled" — held.** The settings read back −1. None of the 2,501 DDL statements
  returned a client warning, and `system.log` has no guardrail line.
- **"The template restore is a harness convenience; the schema heap is the same when the tables are made live" — held.**
  L0 after live creation was 909.6 MiB, against stage 2's 923.4 MiB restored, and the OOM came at the same N.
- **"One 1 MiB region per written memtable; the pool is charged only the bytes, so it never flushes" — held.** 1,086
  regions at the OOM, K 0.18 C, `BlockedOnAllocation` 0, no flush of `ks`.
- **"Creating 2,500 tables takes ≈ 3 min" — not held on this node.** It took 23.1 min here (aarch64 m400, with
  authentication on: each `CREATE TABLE` also writes the creator's 7 permissions). It is still a single unthrottled client
  session. During the DDL the victim saw 99.9 % success, so the build-up phase is nearly invisible to other tenants.
  **"Writing one row each takes ≈ 10 s" — held** (863 rows in 10 s; the heap was full from +12 s).
- **"Commit-log replay may reach the same heap state and die again" (probable, unverified) — held, 1/1.** The admin
  restart OOMed in `CommitLogReplayer` → `SlabAllocator.getRegion` with 1,093 regions and never served a client. The
  attacker does not need to come back: **the node stays down across restarts** until an operator removes the commit log
  (losing those writes), raises the heap, or changes `memtable_allocation_type`.
- **"The attacker writes again after any restart" — not tested** (the node never came up).
- **"RF up to every node; schema heap on every node" — not tested** (single node). **Data-role variant — not tested.**
- **Operator visibility — held as stated.** Before the writes: 2,500 `Initializing ks.tN` lines in `system.log`, no
  guardrail warning; the memtable pool looks normal (K 95.5 MB). During: `GCInspector` WARNs (G1 Old Generation GC ≈ 1.1 s),
  after which `system.log` stops. After: `OutOfMemoryError: Java heap space` and a dump full of `byte[1048576]`. On restart:
  `Replaying …CommitLog…` and then the same OOM. The attacker can be attributed through `LIST ALL PERMISSIONS ON KEYSPACE ks`
  (the role holding ALL on it). Audit logging ships off.
