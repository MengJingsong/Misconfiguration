# B20 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/indexing_target_page_size--table-mean-page-on-wide-partition/indexing_target_page_size--table-mean-page-on-wide-partition.md`](../cases/indexing_target_page_size--table-mean-page-on-wide-partition/indexing_target_page_size--table-mean-page-on-wide-partition.md)
· **Stage 3-a:** [`../stage3-jira-check/B20.md`](../stage3-jira-check/B20.md) (`known-fixed (not in 5.0.9) (partial: CASSANDRA-11745)`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** The legacy secondary-index build turns its 32 MiB page target into a row count from the **table-wide** mean
row size (`index/SecondaryIndexManager.java:1148-1170`), and `indexPartition` copies each page whole into an
`ImmutableBTreePartition` (`:1066`). With 1,000,000 small partitions plus one partition of 4,000 × 1 MiB rows the page is
6,618 rows → one 4.19 GB page → heap OOM in the index-build thread at 2 and 4 GiB.

**Condition assessed:** T2/T4 (2 GiB and 4 GiB heaps, `CREATE INDEX t_ck ON ks.t (ck)`, 3/3 each).

**Label: `client-triggerable · DDL role; every replica holding a wide partition — one CREATE INDEX can hit every node; heap ≤ 4 GiB for a 4.2 GB partition, larger partitions for larger heaps`**

Reach: **alone**. Lowest privilege: **DDL role** (create an index on a table it owns, or `ALTER` on someone's table). A
**data role** cannot start an index build: builds run only on `CREATE INDEX`, `nodetool rebuild_index`, and at startup
for an unbuilt index.

## Condition and how common

None beyond the data shape (≳ 760,000 small partitions per wide one of this size, both written by the client) and one
`CREATE INDEX`. Heap coverage scales with the wide partition (page up to 10,000 rows × row size), so a larger partition
reaches larger heaps (5 GiB survived for this 4.2 GB partition).

## Blast radius

- **Which node:** every node holding a **replica of a wide partition** — each node builds its local index on
  `CREATE INDEX`. With one wide partition per replica set (and enough small partitions everywhere), **one statement can
  kill every node of the cluster at once**. The attacker places wide partitions by key.
- **Repeatable / persistent:** the index stays unbuilt after the OOM; at startup an unbuilt legacy index is rebuilt
  (`index/internal/CassandraIndex.java:169-173`, `isBuilt()` from `SystemKeyspace`), so the restarted node probably runs
  the same build and dies again — a **crash loop** until the index or data is dropped (code reading; restart not run).
- **Other tenants:** with every replica set hit, the cluster is unavailable for all tenants; with one set, `Unavailable`
  for keys in those ranges at QUORUM once two replicas are down.

## Operator visibility

Before: `CREATE INDEX` is a schema change (logged, visible in `system_schema.indexes`) on a table with a huge partition
(`tablehistograms`). During: "Index build of t_ck" log line and the build in `compactionstats`; then the OOM with
`SecondaryIndexManager.indexPartition` in the stack, which names the table and index. Attribution to the role by the
table's owner/grants; audit log off (`conf/cassandra.yaml:1893-1894`). Operators can deny it by not granting `ALTER`/
`CREATE` or by `secondary_indexes_enabled: false` (applies to non-superusers).

## 3-b confirm

Worthwhile but slower (≈ 25 min data load, then minutes): T2 with authentication on, a role holding only `CREATE` on one
keyspace loads the data with **no nodetool steps** (natural flushes, autocompaction on) and issues `CREATE INDEX`; victim
role on another keyspace. This checks the one inferred step (page size without the operator's layout) and, with a
restart, the crash loop.

## Reason

Every step the endpoint needs — table, small and wide partitions, `CREATE INDEX` — is CQL an ordinary role with DDL
rights in its own keyspace can issue, inside every default; the operator steps of the data preparation only fix the
sstable layout and, by the page-size code, are not needed for the skew. A data role cannot start a build, so the lowest
privilege is DDL role. Because every replica builds its own index, one statement can take down every node holding a wide
partition, and the unbuilt index is likely rebuilt at restart.

## 3-b confirm (pc75, 2026-11-23)

Run by a fresh OOM-agent session (Claude Opus 5.5, `claude-opus-5-5`), 2026-11-23 16:38–17:18 EST on `pc75`, on the
owner's approval of the confirm runs (2026-11-23). Evidence (small files, no dumps): [`logs/B20/`](logs/B20/); the harness
used is copied under [`logs/B20/harness/`](logs/B20/harness/) (adapted from the case's `harness/`).

**Result: confirmed, 3/3.** An ordinary login role holding only `CREATE ON KEYSPACE atk` loaded the B20 data shape over CQL
with **no nodetool step** and issued one `CREATE INDEX`; the node died with `OutOfMemoryError: Java heap space` in the
index-build thread 78.9 s later in every run, and on an operator restart the unbuilt index was rebuilt at startup and
the node died again (3/3: a crash loop). A second tenant on the same node went from 100 % success to 0 % for as long as the
node was down.

### Deviations

- Node `pc75` (x86_64, 40 cores; G1 `ParallelGCThreads=40`) instead of stage 2's `ms0640` (aarch64, 8 cores); jar sha256
  differs (each node's own build of the same pinned source).
- Data written by the attacker at the 2 GiB test budget with autocompaction on (by design of this confirm); the sstable
  layout was therefore not fixed and differed per run (table above). The load itself cost the victim 20–157 client
  timeouts (p99 up to 2 s) during the 1 MiB writes; up to 11 % of the wide writes of a 500-row chunk returned
  `WriteTimeout` at CL ONE and were retried (83–184 retries per run; every chunk ended with 0 missing rows).
- R1's automatic `kcalc` found 0 sstables (a path regex bug in `run-3b.sh`); K for R1 was computed by hand from the same
  `Submitting index build` sstable lists before R1's data was deleted (`R1/kcalc-man-a.txt`, `kcalc-man-r.txt`). The
  script was fixed and replaced atomically before R2 (R1's running instance unaffected); the copy in `logs/B20/harness/` is
  the fixed one. After SHAKE (a scaled-down harness check: 16 wide rows, 2,000 small, build complete) the `run.meta`
  config grep was anchored (it matched `internode_authenticator`); no reading affected.
- `NEG` (data-role check) was an extra lifetime, not in the task's list; ≈ 1 min.
- Not run: the 4 GiB and 5 GiB arms (stage 2 covers the heap range), multi-node topology.
