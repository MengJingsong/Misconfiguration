# R13 — stage 3-b client trigger check (2026-11-23)

**Case:** [`native_transport_max_request_data_in_flight--v5-tiny-value-batch-decode-expansion`](../cases/native_transport_max_request_data_in_flight--v5-tiny-value-batch-decode-expansion/native_transport_max_request_data_in_flight--v5-tiny-value-batch-decode-expansion.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`R13.md`](../stage3-jira-check/R13.md) (`new`, owner ruling). Analysis only (no node run).

**Mechanism.** The native in-flight limit charges a v5 request's wire body bytes, but `BatchMessage` decode copies every
bound value into its own `byte[]` + `HeapByteBuffer` on the Netty event loop, ≈ 10× the wire size for one-byte values,
before any batch check; 14 admitted 15.8 MB batches (206 MB charged) hold ≈ 2 GiB.

**Label: `client-triggerable · pre-auth; coordinator, repeatable on every node`** (pre-auth by code reading; the verified
runs used the shipped `AllowAllAuthenticator` and real prepared ids)

**Condition:** none.

## Blast radius

- **Which node:** the coordinator the attacker connects to (every node listens on the native port); decode happens on its
  event loops before any routing.
- **Repeatable:** yes, every node at once from the same address set; no credentials, so no role to revoke.
- **Other tenants:** the node is killed (heap OOM 3/3 at 2–8 GiB) or stalls in back-to-back Full GCs (16 GiB); every
  client connected to it loses its connections; requests needing its replicas fail at their CL while it restarts. With
  every node attacked, the cluster is down.

## Operator visibility

Only connection-level traces: many native connections from a few addresses that send STARTUP and never complete SASL,
each frame answered with a protocol error ("Unexpected message BATCH, expecting SASL_RESPONSE") — at debug level or not
logged; `ClientMetrics` `RequestsSize` near the in-flight cap. No authenticated identity, so audit logging cannot
attribute it. Under the default `AllowAllAuthenticator` the same holds trivially.

## 3-b confirm

Worthwhile and needed: the pre-auth claim rests on code reading. Re-run `P2` at 2 GiB with `PasswordAuthenticator` +
`CassandraAuthorizer`, the client sending STARTUP, receiving `AUTHENTICATE`, never answering it, then sending v5 BATCH
frames with arbitrary 16-byte ids (16 connections, ≥ 5 source addresses), plus a victim role on another connection set
measuring its own success rate. If the server closes the connection on the first refused frame, repeat with reconnects
and record it.

## Reason

The holder is the decoded request on the event loop, and decoding needs neither a schema, nor a prepared statement, nor
an authenticated connection: the v5 pipeline is set up at STARTUP, admission charges wire bytes at the first frame, and
`BatchMessage` decode copies every value before the dispatcher checks the connection stage. The verified arm's other
steps (prepared ids, keyspace, rejection by the batch-size check) are not needed for the decode expansion. The only
operational need is several source addresses (the per-IP limit). Lowest privilege by the code: pre-auth; the node that
dies is the coordinator, and the attack repeats on every node.

## 3-b confirm (ms0625, 2026-11-23)

Fresh session, owner-approved confirm runs (claim-settling case), 14:33–15:40 MST on `ms0625`. **Result: the pre-auth
claim does not hold; the endpoint is reached 3/3 by a LOGIN role with no grants at all.** A pre-auth client cannot send
the 15.8 MB multi-frame BATCH (refused and disconnected at its first frame, 3/3 runs, ≈ 4,100 reconnects each), and the
pre-auth path that is open (single-frame BATCHes, decoded then refused) did not grow the heap (1 exploratory run). The
same verified payload sent after a successful SASL login as a role with zero permissions, with random statement ids and
no `r13` schema, reached `OutOfMemoryError: Java heap space` **3/3**, plus 1/1 in the 5-address diagnostic. Evidence:
[`logs/R13/`](logs/R13/) (one folder per run, `harness/` with the 3-b harness and the run lists). Small logs stay on the
node under `ms0625:/mydata/s4/3b-R13/runs/<run>/`; dumps, data and the copied tree were deleted.

### Deviations

- Node `ms0625` instead of `ms0604` (same m400 aarch64 class, same base build path); stage 2's numbers are not pooled
  with these.
- Payload P with random statement ids and no schema instead of real prepared ids into `r13.t` (tests the claim that
  decode needs no schema); the responses are therefore `0x2500 Unprepared` instead of `0x2200 Batch too large`, and a
  request that completes decode is released quickly. This changes the time to OOM (+25 to +84 s vs stage 2's +23 to +25 s)
  but not the holder.
- Pre-auth single-frame run PF-1 and the source-address diagnostics D-ip1/D-ip5 are additions (n = 1 each), not part of
  the 3-run attack.
- No matched control or intervention under auth (stage 2 has them); the victim role's workload is light (10 ops/s).
- In A-1..3 the networking pool overflow reached ≈ 520 MiB of direct memory (first frames of refused messages), far
  below the 15,872 MiB limit; noted, not a holder.

### Which code-reading claims held

- **"The v5 pipeline is installed when the STARTUP response is flushed, whatever it is" — held.** After `AUTHENTICATE`
  the server parses v5 segments on the unauthenticated connection (A: it reads the envelope header and names type and
  size; PF: it decodes whole messages).
- **"A never-authenticated connection's BATCH is fully decoded, then refused" — held only for single-frame messages
  (≤ 128 KiB).** PF-1: 142,259 pre-auth BATCHes decoded (up to 12 event loops in `BatchMessage$1.decode`) and refused by
  `ServerConnection.validateNewMessage` (`Unexpected message BATCH, expecting SASL_RESPONSE`, not logged). **It does not
  hold for the multi-frame messages the endpoint needs:** `CQLMessageHandler.processFirstFrameOfLargeMessage`
  (`transport/CQLMessageHandler.java:537-547`) checks `serverConnection.stage() != ConnectionStage.READY` on the first
  frame and raises a fatal `OversizedAuthMessageException` ("The connection is not yet in a valid state to process multi
  frame CQL Messages … authentication is still pending"), marks the request discarded and closes the connection — before
  the in-flight charge and before any decode. The 3-b analysis read the single-frame path and missed this guard. A-1..3:
  12,448 attempts with reconnects, every one refused at its first frame, K = 0, heap ≤ 80 MiB, victim unaffected.
- **"Admission charges the wire body regardless of connection stage" — not held for large messages** (the guard runs
  first, K stayed 0 in A-1..3); for single-frame messages the code charges per message, but the charge is released within
  milliseconds after the refusal and never showed in the 5 s samples (PF-1).
- **Pre-auth single-frame flood as an OOM path — not reached** (exploratory, n = 1): each decoded message (≈ 2 MB of heap)
  is refused on an NTR thread right away, so the heap stayed ≤ 111 MiB; it costs event-loop CPU (victim p99 290 ms).
- **"Decode needs neither schema nor prepared statement" — held.** Random 16-byte ids, no `r13` keyspace: requests were
  decoded in full before `0x2500 Unprepared` (SH-L, L-1/L-2), and the OOM 3/3 has the stage-2 holder (OOME thread in
  `BatchMessage$1.decode` → `CBUtil.readBoundValue:480` in L-2, L-3, D-ip5; L-1 dump 95.8 % decoded-request objects).
- **"The other steps of the verified arm (prepared ids, keyspace, rejection by the batch-size check) are not needed" —
  held** (none was present).
- **"≥ 5 source addresses at 2 GiB" (per-IP limit heap/40 = 3 requests) — held.** One address: 3 admitted
  (K 44,209,299 B), no OOM in 180 s (but 56 % GC STW and the victim at 53 %); five addresses: 14 admitted, OOM.
- **Blast radius "coordinator killed, every client loses its connections" — held.** Every OOM run ended with the shipped
  `kill -9`; the victim role, which holds no relation to the attacker's role or tables, was unavailable from +2 to +51 s
  and refused afterwards. (Repeat on other nodes: not run, single-node set-up.)
- **Operator visibility:** pre-auth multi-frame refusals log one rate-limited WARN per minute
  (`NoSpamLogger … ProtocolException$Fatal: The connection is not yet in a valid state …`); pre-auth single-frame
  refusals are not logged; the login attack logs only `GCInspector` warnings before the kill, but its connections carry
  the authenticated role `attacker` (`AuthSuccess` +16 per run), so it can be attributed (e.g. `system_views.clients`,
  audit log) and the role revoked.
