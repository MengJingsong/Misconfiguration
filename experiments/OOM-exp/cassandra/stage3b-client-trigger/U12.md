Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** When compaction (or flush) writes a row, `UnfilteredSerializer.serialize` copies the whole row body into
the thread's scratch `DataOutputBuffer` — direct memory by default, grown ×2/×1.5 with old and new live during each copy
and no capacity check. A non-frozen map grown by 1 MiB appends to 600 MiB needs 486 + 729 MiB → `OutOfMemoryError: Direct
buffer memory` at a 1 GiB direct limit.

**Condition assessed:** **N** (natural path: fresh node, autocompaction on, 700 appends at one request in flight, the
automatic flushes and the first STCS compaction; direct OOM 3/3, no operator action). The headline arm T restored a golden
data set built with `disableautocompaction` and `nodetool flush` (operator steps) and also gave 3/3.

**Label: `client-triggerable · data role; replicas of the row's partition (steerable by key), repeatable, crash loop on restart; nodes with ≤ ~3 GiB direct (≤ ~12 GiB RAM)`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` on a table with a non-frozen `map`/`list`/`set` of `blob` or
`text` — a common admin shape); a DDL role can create one.

## Condition and how common

None beyond ≈ 0.5–1.6 GiB appended to one collection row. Node size is the limit: verified at 1 GiB direct, arithmetic
up to ≈ 3 GiB direct; nodes whose resolved direct limit is ≥ ≈ 4 GiB are out of reach of one row on one thread (two
concurrent compactions of two such rows might reach them; not run).

## Blast radius

- **Which node:** every **replica of the row's partition** (each compacts its own copy); chosen by partition key.
- **Repeatable:** yes, per replica set; the fragments persist, and T shows the same OOM **3/3 right after a restart** (the
  restarted node's STCS picks the fragments again): a **crash loop** until an operator deletes the row/sstables or
  disables compaction for the table.
- **Other tenants:** dead replicas (QUORUM tolerates one per set; the whole set dead gives `Unavailable`), repeatedly, as
  the node restarts and dies; hints build up on coordinators.

## Operator visibility

Before: nothing at defaults (collection guardrails off). `tablestats`/`tablehistograms` show one huge partition/row;
reads of the row are slow. During: compaction start lines for the table, then `Direct buffer memory` on
`CompactionExecutor` — names the table, which an operator can tie to the row. Role not logged (audit log off,
`conf/cassandra.yaml:1893-1894`). Enabling `collection_size_fail_threshold` would stop further growth for non-superusers
(it is checked per write, so an existing row stays).

## 3-b confirm

Worthwhile and cheap (≈ 10 min at 2 GiB/1 GiB): N with authentication on, a data role with only `MODIFY` on an admin-made
`map<int, blob>` table, victim role on another table; add a restart after the OOM to show the crash loop with the
non-superuser's data.

## Reason

The natural-path arm N reproduced the OOM 3/3 with nothing but the client's appends to one collection row; the flushes
and the compaction that copy the row into the scratch buffer are the node's own response to the write volume, and no
default setting bounds a stored row. So `client-triggerable` alone at data role, limited to nodes whose direct limit one
row's growth sequence can exceed (verified at the 4 GiB node's 1 GiB; ≤ ≈ 3 GiB by arithmetic). The persistence of the
data makes it a restart crash loop on the replicas the attacker chose.
