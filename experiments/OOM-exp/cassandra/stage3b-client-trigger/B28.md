# B28 — stage 3-b client trigger check (2026-11-24)

**Case:** [`tracing_stage_queue_limit--traced-16MiB-query-text-backlog`](../cases/tracing_stage_queue_limit--traced-16MiB-query-text-backlog/tracing_stage_queue_limit--traced-16MiB-query-text-backlog.md)
(true positive, `verified-OOM · deployment`, bypass / accounting omission; heap 2 GiB 3/3 at N = 2 connections, 4 and 8 GiB
3/3 at N = 8, 12 GiB survives 0/1 because the 1000-task count cap binds first; x86 `pc82`). Stage 3-a: `new`
([`../stage3-jira-check/B28.md`](../stage3-jira-check/B28.md); owner alternative `known-open (partial: CASSANDRA-13157)`).
Analysis only (no node run), by a fresh session that did not design or verify the case. Code references are to the pinned
5.0.9 tree, paths below `src/java/org/apache/cassandra/` unless they start with `conf/`.

**Mechanism.** A client sets the frame's tracing flag (`0x02`) on an unprepared QUERY. Before the statement is parsed or
authorized, the request thread queues two mutations on the single-thread TRACING stage that each carry the **uncut query
text**: the `system_traces.sessions` start row (`parameters['query']`, `transport/messages/QueryMessage.java:110-111`,
`:138`, `:146`; `tracing/TracingImpl.java:53-66`) and the `"Parsing <query>"` event (`cql3/QueryProcessor.java:896`). The
request does not wait for them (`cassandra.wait_for_tracing_events_timeout_secs` = 0,
`config/CassandraRelevantProperties.java:627`; `tracing/TraceStateImpl.java:76-80`), its native in-flight charge is released at
response flush, and the TRACING queue is bounded at 1000 **tasks**, not bytes (`concurrent/Stage.java:196-202`). With 16 MB
query texts the one tracing thread (≈ 8–12 big writes/s) falls behind two connections, and the queued copies fill the heap.

**Label: `client-triggerable · login role, no grants; coordinator, repeatable on every node`** (nodes with heap ≤ 8 GiB, the
largest failing budget; ≥ 12 GiB survives this payload). Any authenticated role with **no permission at all** can send the
traced 16 MB QUERY: tracing needs no permission or server setting, both big copies are queued before
`statement.authorize` runs, and the verified statement itself (`USE <ks>`) needs only a login. The verified arm's
admin-created keyspace `b28` is not needed (`USE system /*…*/` succeeds for any role, and a failing USE still leaves both
copies). Pre-auth is ruled out by the connection state check, which runs before the tracing session starts. Two to eight
connections suffice; nothing is visible as overload (no dropped `_TRACE`, no "bytes in flight" line) until the node dies.

**Possible extension above 8 GiB (untested, code reading).** The 12 GiB survival rests on 4 TRACING tasks per request.
A text that lexes but fails to parse (for example the long comment followed by an invalid token) stops before
`Tracing.trace("Preparing statement")` (`QueryProcessor.java:903`), leaving 3 tasks per request with the same 2 big copies:
≈ 666 big tasks (≈ 10.4 GiB) at the count cap. PREPARE also traces the uncut text (`transport/messages/PrepareMessage.java:126-127`)
and then `"Parsing"`. Neither variant was run; the label rests on the verified `USE` arm only.

## Condition and how common

None beyond the defaults (reach **alone**), within the failing budget: a node whose heap is ≤ 8 GiB (verified 2, 4, 8 GiB),
which covers small and mid-size nodes and the widespread explicit 8 GiB heap. The client needs a login and the ability to
send a 16 MB query text with the tracing flag set — both ordinary.

## Blast radius

- **Which node:** the coordinator the attacker connects to: the trace mutations are built and queued there (the holder is
  its TRACING queue). The attacker picks it.
- **Repeatable:** yes, on every node at once (2 connections per node at 2 GiB, 8 at 8 GiB; one client host suffices). Stage 2
  reached OOM 79–141 s after full load at 2 GiB, 5–15 s at 4/8 GiB. The shipped `-XX:OnOutOfMemoryError="kill -9 %p"`
  (`conf/cassandra-env.sh:209`) kills the node; it stays down until restarted. Nothing in the attack persists in a way that
  blocks restart (not tested: commit-log replay of the 16 MB `system_traces` mutations already logged, into a memtable pool
  bounded at heap/4), so the attacker can repeat after each restart.
- **Other tenants:** every client of the killed coordinator loses its connections; on the replicas of the dead node's ranges
  requests at CL ≥ QUORUM with RF 3 survive one node down but not two of a replica set, so killing several nodes makes
  ranges unavailable cluster-wide. Before the kill, other tenants' requests on that node share 128 NTR threads with the
  16 MB lexing work and a heap under Full GC. Side effects that survive a restart: 16 MB rows in `system_traces.sessions`
  and `events` for 24 h (`trace_type_query_ttl: 1d`, `conf/cassandra.yaml:1752`) on the trace replicas, so any tool or
  driver that fetches those traces pulls 16 MB rows.

## Operator visibility

Little before the kill: no "Request breached limit(s) on bytes in flight" line (K stays far below heap/10), **no dropped
`_TRACE`** below the count cap (0 in every failing run), no refusal or `OverloadedException` to the client. Visible:
`nodetool tpstats` TracingStage `Pending` in the hundreds, GC pauses, `system_traces.sessions` rows with a 16 MB
`parameters['query']` and the client address (`tracing/TraceKeyspace.java:77-83`; no role column), and
`system_views.clients` (each connection shows its authenticated role, so the role is attributable and can be dropped).
There is no server-side switch to refuse client-requested tracing (CASSANDRA-10444 / 8303, open); audit logging ships off.

## 3-b confirm

**Worthwhile, cheap.** Run `T2` (2 GiB, N = 2, traced 16,000,000-byte QUERY) with `PasswordAuthenticator` +
`CassandraAuthorizer`: admin only creates the roles; attacker role with **no grants** sending `USE system /*…*/` (a variant
with the admin's `b28` keyspace and no grant on it shows the failing-USE path); a victim role on its own table measuring
success rate and latency. Expected: OOM at 2 GiB as in T2, TRACING queue the largest dump owner. Optional: a 3-node cluster
arm at 2 GiB to measure the tracing consumer rate with remote `system_traces` replicas (the open point above), and a
12 GiB arm with the parse-error text (3 tasks per request). Stage 2's harness (`pc82:/mydata/s4/b28/harness/`,
`client.py`, raw v4) needs only a SASL PLAIN step after STARTUP.

## Reason

Every step of the verified arm is ordinary client behaviour once the client has a login: a few connections, each sending
an unprepared QUERY with the protocol's tracing flag and a long (16 MB) but valid query text. Tracing is chosen by the
client with no permission check and no server-side switch, and both uncut copies of the text are queued on the TRACING
stage before the statement is even parsed or authorized, so neither a grant nor a valid target keyspace is needed;
pre-auth is excluded only because the connection-state check runs before the tracing session starts. The bound that
would stop it (bytes of queued trace work, or waiting for the trace writes) does not exist at defaults, the count cap acts
only above ≈ 7.8 GiB of queued copies, and no overload warning precedes the kill. Lowest privilege: **login role, no
grants**; reach **alone** on nodes with heap ≤ 8 GiB; blast radius: the chosen coordinator, repeatable on every node.

## 3-b confirm (ms0625, 2026-11-24)

**Session.** A fresh stage 3-b confirm session (Claude Opus 5.5), owner-approved 2026-11-24. Node lock taken 20:50 MST and
released 21:14 MST on `ms0625` (node clock MST = EST − 2 h). The node was used for ≈ 24 min of the 3 h cap. Evidence (small
files): [`logs/B28/`](logs/B28/), with `harness/` (as run), `SH/` (probes and traces) and `L-1`, `L-2`, `L-3` (one folder
per attack lifetime: `driver.txt`, `summary.txt`, `victim-summary.txt`, `victim-persec.txt`, `victim.txt`, `jmx*.csv`,
`client-p0.txt`, `completions-p0.txt`, `auth-setup.txt`, `resolved.txt`, `conf-diff.txt`, `system.log`, `stdout-excerpt.txt`,
plus `oome-thread.txt` and `owners.txt` for the failing runs). Raw logs: `ms0625:/mydata/s4/3b-B28/runs/` (2.6 MB, logs only).

**Result.** A role with **LOGIN and no grant at all**, connecting from **one** source address, crashed the 2 GiB coordinator
with `java.lang.OutOfMemoryError: Java heap space`. With **4** connections it failed **2/2** (`L-2`, `L-3`), 15.8 s and 16.6 s
after full load. In both dumps the TRACING queue was the largest owner (60.6 % and 63.8 %), and the initiating stack was the
same as stage 2's. The verified arm's **N = 2** did **not** fail on this node (`L-1`, 300 s survived, 0/1). On the slower
aarch64 node the two producers (2.73 req/s ≈ 10.9 tasks/s) only matched the one tracing consumer (9.7 tasks/s), so the
queue settled at 110–128 tasks.

The victim role on its own table kept 99.9 % success at N = 2 and 61–66 % during the N = 4 attacks. Every victim request
failed from +15–16 s on, when the node died (the shipped `kill -9`).

Pre-auth was ruled out: before a successful login, the server answers a traced QUERY with `0x000A` and creates no trace task,
also for a 16 MB v4 frame. Every claim from the code reading that was tested held, except two:
- "two connections suffice" depends on the node: N = 2 balanced the consumer here, and N = 4 was needed;
- "no bytes-in-flight line": at N = 4 from one address, one INFO backpressure line appears at +1.1 s (see "Claims" below).

### Deviations

1. **Node class.** `ms0625` (aarch64 m400) instead of stage 2's x86 `pc82` (the node assigned to this confirm). Its tracing
   consumer is about half as fast and its lexer slower, so the verified N = 2 did not fail.
2. **N = 4 in the failing runs.** The task allowed 1 attack run plus up to 2 more "to tell a fluke". `L-1` (N = 2) was not a
   fluke but a rate balance. The two further runs used N = 4 (the next step of stage 2's `R2` ramp, below its N = 8), and
   both failed. No N = 2 repeat was run, and no N = 8 run.
3. **One source address.** Stage 2 used one address per connection. Here all attacker connections came from `127.1.0.1`, to
   test the per-IP claim (above).
4. **Statement.** `USE system /*…*/` instead of `USE b28 /*…*/`, so that no admin schema is needed. The text length is the
   same, 16,000,000 bytes.
5. **Not repeated under auth.** No matched control (untraced) or intervention: stage 2 has them. The victim workload is
   light (10 ops/s). Client, victim and server share the node's 8 cores, so the victim's `missed` ticks partly reflect CPU
   contention with the lexing work.
6. **Logs kept and removed.** GC logs were summarised (`summary.txt`) and deleted with the tree copy. The full `stdout.txt` is
   not kept; `stdout-excerpt.txt` has the OOM lines.
