# U17 — stage 3-b client trigger check (2026-11-24)

**Case file:** [`../cases/vector_dimensions--vector-literal-per-element-parse/vector_dimensions--vector-literal-per-element-parse.md`](../cases/vector_dimensions--vector-literal-per-element-parse/vector_dimensions--vector-literal-per-element-parse.md)
· **Stage 3-a:** [`../stage3-jira-check/U17.md`](../stage3-jira-check/U17.md) (`new`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` or `src/antlr/` is named.

**Mechanism.** An unprepared QUERY `INSERT INTO u17.t (pk, v) VALUES (0, [0,0,…,0])` with 6.5 M elements (13.0 MB of
text, under the 16 MiB frame and the 16 MiB mutation limit) is parsed with every token kept (`CQLFragmentParser.java:66-76`,
ANTLR `CommonTokenStream`: two `CommonToken`s per element) and `listLiteral` builds a `String` + `Constants.Literal` per
element (`src/antlr/Parser.g:1572-1575`); `Vectors.Literal.prepare` then builds a `Constants.Value` + a one-byte
`HeapByteBuffer` per element. D1 measured ≈ 168 B of heap per element (≈ 1.09 GB per request) against the ≈ 2 B per element
that every check counts. Two such INSERTs at once kill a 2 GiB heap (3/3); 8 GiB 3/3 (N = 9), 12 GiB 3/5 (N = 13); above
that GC service loss.

**Condition assessed:** T (2 GiB heap, N = 2 concurrent VEC INSERTs, 3/3), with the budget arms B (same steps, more
connections) and the documented-limit form W (793 × 8,192-dimension INSERTs in one single-partition unlogged BATCH, 3/3).

**Label: `client-triggerable · login role, no grants; the coordinator the attacker connects to, repeatable on every node`**

Reach: **alone**. Lowest privilege: **login role, no grants** (by code reading). The verified arm used its own keyspace and a
`vector<tinyint, 6500000>` table (a **DDL role** step). That table is not needed. The holder that OOMed is built in
`parseStatement`, before `prepare` looks up the table and before `authorize` checks `MODIFY`. So an INSERT naming a keyspace
that does not exist, or a table the role has no grant on, parses the same 6.5 M-element literal and only then fails. The
three T dumps/stacks put the OOM in the parse, not the prepare. Not pre-auth: the parse runs only after the
connection-stage check.

**Where the OOM happened (deciding for the privilege).** T2: OOME thread a Native-Transport-Requests thread in
`ArrayList.grow` ← `BufferedTokenStream.fetch` (the token list). T1 and T3: OOME raised on a bystander logback thread, with
**both** NTR threads in `Lexer.emit` / `BufferedTokenStream.fetch` ← `Cql_Parser.listLiteral`. T1 dump: 19.96 M
`CommonToken`, 9.98 M `Constants$Literal`, `ErrorCollector` 2 (two parses in progress), 0 prepared values. W2: an NTR thread
in `Lexer.emit`. Every B at-85 % histogram is `CommonToken`/`Constants$Literal`/`String`, with all N NTR threads in the parse.
The parse peak (≈ 1.09–1.18 GB per request, D1 s18 at 91 % of the tokens) is at least the prepare peak (1.09 GB, s19).
So the part of the holder that exhausts the heap is the part that needs neither schema nor grant.

## Condition and how common

None. The attack needs a logged-in connection and N concurrent 13 MB QUERYs: 2 at 2 GiB, ≈ 5 at 4 GiB, 9 at 8 GiB,
13 at 12 GiB, ≤ 128. That is one host and a few connections. The 4 GiB and 8 GiB counts are still under the per-IP
in-flight limit (heap/40), and a pause would not stop processing anyway.

## Blast radius

- **Which node:** the **coordinator** that receives the QUERY (parse and prepare on its request thread). The attacker picks
  it by connecting to it.
- **Repeatable:** yes, on every node in turn, or all at once with N connections per node, from one host with one login (the
  same credentials work cluster-wide). The parse-only form leaves nothing behind (no schema, no row, no hint, no
  commit-log entry), so a restarted node can be hit again at once.
- **Heap size:** OOM up to 8 GiB (3/3) and 12 GiB (3/5). At 16 GiB and 31,744 MiB the outcome within 600 s was GC service
  loss (≥ 90 % STW for ≥ 13 min, 0 requests answered), which also takes the node away from other users.
- **Other tenants:** every request coordinated by the victim node times out during the Full-GC thrash and fails after the
  `kill -9` (`OnOutOfMemoryError`). Drivers fail over to other coordinators. If the node is also a replica, its ranges lose a
  replica until restart (unavailable at QUORUM with RF 3 if two replicas of a range are hit, hints accumulate elsewhere).
  With every node targeted, the cluster is down.

## Operator visibility

Before: nothing at defaults. There is no size or element-count warning on a QUERY, and the dimension guardrail is −1 and
would not see a parse-only request anyway. The case's own form leaves a `CREATE TABLE` of a 6.5 M-dimension vector in
`system_schema.columns`; the parse-only form leaves no schema. During: `GCInspector` pause warnings, then the OOM line and
heap dump. Per request, the client gets a write timeout (case form) or `Invalid`/`Unauthorized` (parse-only form). Neither
is logged at default levels (`QueryMessage.java:129-131`). A `0x1100` on the case form may show as dropped `MUTATION`
messages. Attribution: the heap dump shows `CommonToken` / `Constants$Literal` frames under `Cql_Parser.listLiteral`. With
authentication on, `system_views.clients` names the role per connection. The audit log ships off
(`conf/cassandra.yaml:1893-1894`). Revoking the role's `LOGIN` stops it.

## 3-b confirm

**Worthwhile and cheap** (one 2 GiB node, ≈ 5 min per lifetime). It would turn the label's privilege (login role, no
grants) from code reading into a run, one step below the verified arm's DDL schema. Setup:

- `PasswordAuthenticator` + `CassandraAuthorizer`, every capacity at its default.
- Attacker role `u17nogrant` with `LOGIN = true` and **no grants**, with a privilege check first: `SELECT` on any user
  table and `CREATE KEYSPACE` both `Unauthorized`.
- A victim role on its own keyspace (admin-made) at a fixed ≈ 20 ops/s, measuring success and latency (as U8).
- Arm **T-NG**: the case's `u17client.py` with the VEC payload re-targeted to a keyspace that does not exist
  (`INSERT INTO nosuch.t (pk, v) VALUES (0, [0,…,0])`, D = 6,500,000), N = 2, R = 5. Predicted: Java heap OOM in round 1
  with both NTR threads in `listLiteral`/`BufferedTokenStream.fetch`. If it survives, raise N to 3 and then 4 at 2 GiB
  (4 × 13.0 MB = 52.0 MB < 53.7 MB per-IP).
- Optional second arm **T-NG2**: the same role against an admin-made `u17.t` it has no grant on (parse + prepare, then
  `Unauthorized`).

If T-NG does not OOM, fall back to the verified arm under auth as a DDL role (`CREATE ON ALL KEYSPACES`, own table), as U8.

## Reason

Every step of T is a CQL statement over the native protocol. The only steps that need a privilege above login are the
attacker's own keyspace and vector table. They are not needed, because the per-element token, `String` and literal objects
that exhausted the heap are allocated in `parseStatement` (`cql3/QueryProcessor.java:897`). That comes before the INSERT's
table lookup (`cql3/statements/ModificationStatement.java:953`) and before the `MODIFY` check
(`cql3/QueryProcessor.java:271`). The three T stacks and dump put the OOM in that parse. The connection-stage check
(`transport/Dispatcher.java:412`) keeps it from being pre-auth, but any authenticated role suffices. On a stock node
(`AllowAllAuthenticator`), anyone who reaches the port does. No control counts the per-element objects: the dimension
guardrail ships off, it applies only at `CREATE TABLE` (and to non-superusers), and every other check counts bytes. The
attacker chooses the coordinator and can repeat it across the cluster.

### Validity and deviations

- **Valid run, one only.** `T-NG-1` followed T's design (base build, shipped capacities, 2 GiB, N = 2, R = 5, same D and
  payload shape, dump analysis then delete) with authentication on. It reached the endpoint in round 1, in the same frame
  and with the same holder as stage 2, so no further runs were needed to tell a fluke.
- **Target difference (deliberate).** Stage 2 sent `INSERT INTO u17.t` to a table it had created (a DDL step). Here the
  keyspace `nosuch` did not exist and the attacker could not have created one (`CREATE` refused). The parse, and the OOM,
  are the same; the prepare half of the holder (per-element `Constants.Value` + `HeapByteBuffer`) never ran, and the OOM came

- **Instrument limits:** in-flight `RequestsSize` was not sampled (the per-IP margin is arithmetic); `Thread.print` at +0 s

- **Not run:** repeating the attack on other nodes (single node); audit logging on; more source addresses (not needed at

### Label

**`client-triggerable · login role, no grants; the coordinator the attacker connects to, repeatable on every node`
(confirmed).** A LOGIN role holding no permission, naming a keyspace that does not exist, killed the 2 GiB coordinator
with two unprepared 13-MB QUERYs from one address in ≈ 4.6 s (heap OOM in `Cql_Parser.listLiteral`, parse classes 94.6 %
of the dump). Authentication is required: pre-auth QUERYs are refused before the parse. The reach is alone: no schema,
fault or operator step. The victim role on the same node went from 100 % to 98.5 % (requests stretched to 1 s) to 0 %,
then the node was gone. The confirm covers one coordinator; repetition across nodes is not tested.
