# R20 — stage 3-b client trigger check (2026-11-23)

**Case:** [`ErrorCollector_errorMsgs--humongous-trigger-matched-set-4GiB`](../cases/ErrorCollector_errorMsgs--humongous-trigger-matched-set-4GiB/ErrorCollector_errorMsgs--humongous-trigger-matched-set-4GiB.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`R20.md`](../stage3-jira-check/R20.md) (`new`). Analysis only (no node run).

**Mechanism.** The CQL lexer reports every unmatched character of a query and `ErrorCollector` keeps each message in an
unbounded `LinkedList` (`cql3/ErrorCollector.java:52,81,90`; ≈ 138 B per character, ≈ 2.2 GB per 16 MiB query) although
only the first is thrown (`:100-101`). The retained messages leave 1–6 free regions and the next large request's humongous
decode buffer fails → heap OOM.

**Label: `client-triggerable · data role; coordinator, repeatable on every node`** (any login suffices; no grant is checked)

## Threat-model walk of the verified test arm (4 GiB, H × 3 + 3 ordinary triggers)

| Step | As run in stage 2 | Client-reachable? | Privilege / why (code) |
|---|---|---|---|
| Schema / data | none | not needed | The query never parses. |
| Load requests H | three connections, closed loop of 16 MiB QUERY frames of `#` characters, protocol v4 | yes, **after login** | The query string is parsed in `QueryMessage.execute` (`transport/messages/QueryMessage.java:116`) before any permission check (`cql3/QueryProcessor.java:271`), so no grant is needed; but `execute` runs only after the connection-stage check (`transport/Dispatcher.java:412` → `ServerConnection.java:69-73`), so with `PasswordAuthenticator` the client must be logged in. |
| Trigger requests | three further 16 MiB QUERYs (comment payload) sent ≈ 30 s into the GC thrash | yes, pre-auth for the allocation itself | The trigger only needs its 32 MiB decode buffer (`CBUtil.decodeString` ← `QueryMessage$1.decode:50`), which runs at decode (`transport/CQLMessageHandler.java:390`) before the stage check. The holder still needs the logged-in H load. |
| Admission | in-flight charge 16.8 MB per request; K ≤ 0.47 of the per-IP limit | yes, one source IP | Nothing paused; connection and rate limits ship off. |
| Timing | the trigger fires on a GC-log rule (harness reads `gc.log`) | yes, without the log | A client sees the thrash as its own latency and can simply send triggers periodically; the 2 GiB `P2-1` and 16 GiB `T16-1` runs pre-sent the trigger frame minus one byte. |

**Condition:** none. Without a trigger the outcome is GC service loss (U6, R15), which already affects other users.

## Blast radius

- **Which node:** the coordinator the attacker connects to (parse and decode run there).
- **Repeatable:** yes, every node, from one host; the same credentials work cluster-wide.
- **Other tenants:** first ≥ 90 % STW (all requests on that node time out), then heap OOM and kill; their connections
  drop, the node's replicas are missing until restart.

## Operator visibility

Each H request returns a `SyntaxException`; the server logs nothing per request at default levels. GC pause warnings in
`system.log`. With authentication on, audit/FQL logging (off by default) would record the role and the failed queries.

## 3-b confirm

Worthwhile. At 4 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`, a role with LOGIN and **no grants** runs the
`T4` load and triggers; a victim role reads/writes another table. Also try the triggers from unauthenticated
connections to see whether the pre-auth decode buffer alone can end the thrash.

## Reason

The holder is filled by parsing a query string, which needs a logged-in connection but no permission on any object:
parsing fails before authorization. The trigger is any further large request. Nothing in the verified arm needs a schema,
data, fault, operator action or diagnostic aid, and one client address suffices. Lowest privilege: data role in the
playbook's scale, and in fact any login without grants. The coordinator dies and the attack repeats on every node.
