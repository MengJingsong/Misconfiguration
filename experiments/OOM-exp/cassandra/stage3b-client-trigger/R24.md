# R24 — stage 3-b client trigger check (2026-11-24)

**Case:** [`cached_rows_fail_threshold--rfp-whole-partition-sized-protection`](../cases/cached_rows_fail_threshold--rfp-whole-partition-sized-protection/cached_rows_fail_threshold--rfp-whole-partition-sized-protection.md)
(true positive, `verified-OOM · deployment`; heap OOM 3/3 at a 2 GiB coordinator heap, 4 GiB at Q = 14 reached 96 % live heap
without OOM, 8 GiB at Q = 28 survived; x86 `pc82`, two instances RF 2). Stage 3-a: [`R24.md`](../stage3-jira-check/R24.md).
Analysis only (no node run), by a fresh session that did not design or verify the case. Related: B22 (the earlier,
page-sized attempt at the same holder; retry, no 3-b). Code references are to the pinned 5.0.9 tree, paths below
`src/java/org/apache/cassandra/` unless they start with `conf/`.

**Mechanism.** A filtering range read (`… WHERE v = 'x' ALLOW FILTERING`, no partition key) has a non-empty row filter, so
the coordinator resolves it through replica-filtering protection (`service/reads/DataResolver.java:122-123`, `:132-144`).
For a range read `consumeEntirePartitions` is always true (`service/reads/ReplicaFilteringProtection.java:143`;
`db/PartitionRangeReadCommand.java:497-502`), so the first phase drains the whole merged partition (`RFP.java:387-396`),
and with ≥ 2 contacted replicas short-read protection keeps fetching page-sized chunks from each replica until the
partition ends (`DataResolver.java:192`, `:202-214`; `service/reads/ShortReadRowsProtection.java:128`, `:165-171`). Every
version is stored on the coordinator heap (`RFP.java:477-492`) and charged as a **row count** against
`cached_rows_fail_threshold` 32,000 (`RFP.java:319-345`; `conf/cassandra.yaml:1835`); nothing bounds bytes or the sum over
concurrent queries. A 2,048-row partition of 64 KiB rows is 4,096 versions = 257 MiB per query whatever the fetch size;
7 concurrent queries killed a 2 GiB coordinator. The only other bound is time: every short-read fetch must finish within
`read_request_timeout` (5 s) of the query's start (`service/reads/ReadCallback.java:98-101`), which capped the hold at
larger heaps.

Reach: **alone** (heap OOM shown at a 2 GiB coordinator heap). Lowest privilege: **data role** — SELECT on a table whose
partitions hold a few thousand large rows the attacker's filter matches, or SELECT + MODIFY on any table with a
clustering column and a text/blob column in a keyspace with RF ≥ 2 (the attacker writes the partition itself).

**Label: `client-triggerable · data role; the coordinator the attacker connects to (any node, not only a replica), repeatable on every node; heap OOM shown at a 2 GiB heap (4 GiB reached 96 % live heap, 8 GiB survived)`**

## Condition and how common

None beyond the deployment: a coordinator at a 2 GiB heap (small nodes, or operators who cap the heap) and a keyspace
with RF ≥ 2 the attacker can read and, unless suitable data already exists, write. Both are common. The attacker's own
part is ≈ 134 MB of 64 KiB rows in one partition and 7 concurrent filtering range reads.

## Blast radius

- **Which node:** the coordinator the attacker connects to. It need not own the data, so the attacker can aim at any
  node; the replicas of the partition serve small chunks and are not at risk.
- **Repeatable across nodes:** yes, from the same partition, by connecting to each node in turn (or all at once). No
  crash loop: nothing of the attack is replayed at restart, and the attacker can repeat it as soon as the node is back.
- **Other tenants:** the coordinator dies of `Java heap space` (dump, `kill -9`) ≈ 20–40 s into the load; every client
  connected to it loses its connections, and reads/writes needing it as a replica fail at their CL while it restarts
  (QUORUM at RF 2 for every range it holds; at RF 3 once two replicas of a range are taken down). With every node
  attacked, the cluster is down. Before the OOM the coordinator spends 16–47 % of each minute in GC pauses (T), slowing
  every request it coordinates.

## Operator visibility

Node 1's `system.log` shows the RFP warning (`Replica filtering protection has cached over 2000 rows during query
<CQL>`, `RFP.java:333-342`, logged at most once a minute) with the table and filter but not the role; the attacker
receives the same text as a client warning. Read timeouts, `ShortReadProtectionRequests` and
`ReplicaFilteringProtectionRowsCachedPerQuery` metrics rise; GC warnings and slow-query entries precede the OOM. The
large partition itself raises no warning (`partition_size_*` off). The heap dump shows `ReplicaFilteringProtection$PartitionBuilder`s
holding the 64 KiB values. Attribution to a role needs the audit log (off by default).

## 3-b confirm

**Worthwhile.** Re-run T at 2 GiB (Q = 7, F = 128, `w2k`) with `PasswordAuthenticator` + `CassandraAuthorizer`: an admin
creates `r24.w2k` (RF 2); the attacker role holds only `SELECT, MODIFY` on it, loads the 2,048 rows at CL ALL (no
`nodetool flush/compact`, to test the server-flushed data state), then runs the 7 queries; a victim role on another
table measures its own success rate and latency on node 1. A second arm with an attacker holding **SELECT only** on
admin-loaded data would settle the SELECT-only reading. Reason it is not a formality: the arm runs through ≈ 100–200
full GCs before the OOM, and with `CassandraAuthorizer` each new query's permission check reloads the 2-s permission/role
caches with a local read (`conf/cassandra.yaml:300`, `:327`); in U7 such a reload timed out in a GC spiral and the
request was aborted, turning an OOM into recoverable service loss. Here the check happens once per query at its start
(`QueryProcessor.java:270`), so an aborted check would only stop new queries joining, but it could still keep the hold
below the heap. Cost ≈ 30 min on the stage-2 harness (pc82 or same class).

## Reason

What RFP holds is set by the partition the client reads (rows × row size × contacted replicas), and the only bound
counts rows; the fetch size, LIMIT and page do not reduce it for a range read. Every step of the verified arm is ordinary
CQL open to a role with SELECT (and MODIFY to write its own partition) on a table with a clustering key and a large-value
column in a keyspace with RF ≥ 2: `ALLOW FILTERING` is enabled by default, the consistency level, fetch size, concurrency
and coordinator are client choices, and nothing limits concurrent queries below 128 request threads. No path for a role
without grants was found (the readable replicated `system_traces` tables cannot be filled with wide partitions of large
rows by such a role), and the request needs an authenticated connection. The OOM was shown at a 2 GiB coordinator heap
only; at 4–8 GiB the 5-s short-read deadline capped the hold on this node.

### Deviations

1. **Runs beyond the brief.** The brief's "1 attack run (up to 2 more to tell a fluke)" was A-1..3 (0/3). Six diagnostic
   lifetimes followed (≈ 6 min each): D-noauth, AS-1, D-T, A-NV1, A-NV2, A-V2only1. They were added to attribute the
   negative and to see whether the labelled role reaches the endpoint without the victim. AS-1's Q = 11 is stage 2's
   pre-declared Q step for a T that survives its first two runs.
2. **Victim placement.** The victim keyspace is RF 2 on the 2-node ring, so node 1 is a replica of every victim row. In the
   runs with V1 the victim also coordinates through node 1 (as the confirm asks). The surviving runs therefore cannot tell
   "another tenant on the coordinator" from "this harness's client mix". The NOVICTIM runs are stage 2's T plus auth.
3. **system_auth RF 2 + full repair** before creating roles (admin; the yaml's advice). It is also what makes the
   cluster-wide refusal after node 1's death possible on 2 nodes. At the shipped RF 1 the role rows would sit on one node.
4. **Data state.** Attacker-written, no flush/compact command, then one SSTable per node from the LOAD lifetime's stop
   (drain); stage 2 used flush + compact. The memtable-resident case was not run.
5. **Sampler.** It sampled `w2k` in both table slots (no `s2k` table here); `steps.py` reads only the wide column.
6. The 30-s pre-attack wait also ran in the NOVICTIM lifetimes (no victim during it).
7. **Node.** pc72 (the design's node), not stage 2's pc82. These numbers are not pooled with stage 2's.

### Updated label

**Label: `client-triggerable given an otherwise idle coordinator · data role; the coordinator the attacker connects to
(any node); heap OOM at a 2 GiB heap; with authentication on, its death also refuses every tenant whose role lookup needs
it (system_auth quorum)` (partly confirmed)**

- **Confirmed** with `PasswordAuthenticator` + `CassandraAuthorizer` at the labelled privilege: a role with only
  SELECT + MODIFY on one admin-made RF 2 table loaded the partition and killed the 2 GiB coordinator 3/3. The selonly probe
  showed SELECT alone authorizes the query.
- **Not confirmed** with the protocol's victim on the same coordinator: 0/3, plus 0/2 diagnostics (Q = 11; auth off). Light
  other-tenant traffic through the coordinator kept the hold just under the heap, giving latency degradation (p50 ×15,
  p99 up to 3.3 s) instead of an OOM. The reach therefore needs a coordinator carrying no other client traffic (an idle or
  little-used node, which the attacker may pick). How common that is, and whether it holds on pc82 or at other tenant
  rates, was not measured.
- **Blast radius when it fires.** Wider than the analysis had it: with system_auth at RF 2 (or the shipped RF 1, or a quorum
  of its replicas on the dead node), every authenticated client on every remaining coordinator was refused (`Unauthorized …
  LOCAL_QUORUM`), even at CL ONE, until the node is restarted.
- Pre-auth and no-grants paths: none found (pre-auth refused by frames; `nogrant` refused).
