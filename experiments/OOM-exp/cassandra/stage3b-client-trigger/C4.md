# C4 — stage 3-b client trigger check (2026-11-24)

**Case file:** [`../cases/index_summary_capacity--full-sampling-load-window/index_summary_capacity--full-sampling-load-window.md`](../cases/index_summary_capacity--full-sampling-load-window/index_summary_capacity--full-sampling-load-window.md)
· **Stage 3-a:** not filed yet (the case file's §1 search: periodic-only enforcement by design, CASSANDRA-5519; the
load-window OOM path new).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** BIG-format index summaries are JNA-malloc'd native memory, outside `-Xmx` and `MaxDirectMemorySize`. Their
pool, `index_summary_capacity` (auto 5 % of the heap, 51 MB at 1 GiB), is applied only by the redistribution task, first
run one interval (60 min) after start (`io/sstable/indexsummary/IndexSummaryManager.java:117-147`). Any sstable opened or
written in between carries its summary at the level it was written: full sampling, one entry per `min_index_interval`
partitions (`io/sstable/format/big/BigTableWriter.java:255`). In stage 2, `nodetool import -q` loaded 678.6 MiB of
full-sampling summaries at once → kernel memcg OOM-kill of the JVM.

**Condition assessed:** T (`verified-OOM · deployment`): container 2,048 MiB, heap 1,024 / direct 512 (what
`cassandra-env.sh` gives a 2 GiB node), four offline-written sstables, 90 M partitions with 1,000-byte keys, imported with
`nodetool import -q`; memcg kill 3/3 at anon-rss 2,030 MiB, 2.9 s into the import.

**Label: `client-triggerable · DDL role (CQL substitute for the import, unverified); every replica of the attacker's keyspace, probable crash loop on restart`**

Reach: **alone**, with one substitution, flagged below. **As run**, the arm is `not client-triggerable (sstables delivered
by nodetool import)`, the same step as [R18](R18.md). A DDL role can reach the same holder state, summaries far above the
cap before the next redistribution run, without the import. It creates its own table with the table option
`min_index_interval = 1` and writes long-keyed rows by CQL, and every flush then writes a summary holding every key. This
needs about 128 times fewer key bytes than the verified data set. **Also:** `client-triggerable given a ≈ 2 GiB node and ≈ 77 GB
of long-key writes inside one 60-min window · data role` (rare; at the default interval 128).

## Condition and how common

At DDL role: none. The window is up to 60 min after every node start and after every redistribution run, so it is always
open somewhere. The attacker needs only ≈ 0.6 GB of 1-KB-key inserts on a 2 GiB node (minutes). If the attacker also sets
`max_index_interval = 1`, the redistribution's floor is the full level (`io/sstable/indexsummary/IndexSummaryBuilder.java:304`,
`(BASE × min) / max = 128`), so the summaries are never shrunk. That variant has no window at all; it goes beyond this
case's mechanism and is noted only. At data role (an admin table with a long text key, default interval 128): ≈ 128 ×
the free RAM in key bytes (≈ 77 GB on a 2 GiB node) inside one 60-min window, written by CQL: **rare**.

## Blast radius

- **Which node:** every replica of the attacker's table. A DDL role picks the RF (`maximum_replication_factor_*` −1,
  `conf/cassandra.yaml:2220-2221`), up to every node. Every replica flushes its own interval-1 sstables.
- **Repeatable / persistent:** the summaries are saved in `Summary.db` at the written level and reloaded at that level on
  start (`BigSSTableReaderLoadingBuilder.java:99`, `:249`). The restarted node opens them all before its first redistribution
  run, 60 min later. A restart therefore probably dies again while it loads (crash loop) until an operator removes the table
  or lowers its sstables' summaries. This is probable and unverified: stage 2 never restarted a killed node.
- **Other tenants:** the kernel kills the JVM (`SIGKILL`, no Java error, no heap dump). All clients of that node fail over,
  and replica sets lose members, cluster-wide if the RF spans every node.

## Operator visibility

Before: `system_schema.tables` shows `min_index_interval = 1` (a table-properties *warned* list could flag it, but it ships
empty); `IndexSummaries` MBean `MemoryPoolSizeInMB` far above `MemoryPoolCapacityInMB`; `nodetool tablestats` "Index summary
off heap memory used". During: RSS growth outside heap and NMT. After: kernel `oom-kill … CONSTRAINT_MEMCG` (or a global
OOM) in `dmesg`, no `OutOfMemoryError` in the Cassandra log. The table owner identifies the role (the audit log ships off).

## 3-b confirm

**Worthwhile**, to test the substitution (cheaper than stage 2: no 92 GB dataset). It needs pc96 (or any node) with stage
2's 2,048 MiB container, heap 1,024 / direct 512, `PasswordAuthenticator` + `CassandraAuthorizer`, and an attacker role
with `CREATE ON ALL KEYSPACES` only. The attacker creates `t (pk text PRIMARY KEY, v int) WITH min_index_interval = 1` and
inserts ≈ 1 M partitions with 1,000-byte keys until the kill. A victim role on another keyspace measures its success rate
and latency. Then an admin restart with the same data tests the crash-loop claim. A second arm at the default interval would
show that the data-role volume is out of reach in the window.

## Reason

The holder, summaries above `index_summary_capacity` until the next 60-min run, is reached in the verified arm only through
`nodetool import`, a JMX operation on offline-written sstables, which no client can do. This is R18's step. The holder
itself does not depend on the import, though. Every sstable a node flushes is saved at full sampling, nothing triggers the
redistribution before its timer, and the sampling density is the table option `min_index_interval`, which a role that owns
its table may set to 1 under the shipped (empty) table-properties guardrail. That cuts the key bytes needed by 128 ×, to
≈ 0.6 GB on the verified 2 GiB node. The lowest privilege that triggers it alone is therefore the DDL role, with the
substitution unverified. A data role needs ≈ 77 GB of long-key writes inside one window on a 2 GiB node: rare.
