# C9 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable.md`](../cases/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable/compressed_read_ahead_buffer_size--range-read-scanner-per-sstable.md)
· **Stage 3-a:** [`../stage3-jira-check/C9.md`](../stage3-jira-check/C9.md) (`new`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Each partition-range command opens a scanner on every intersecting sstable at once
(`db/PartitionRangeReadCommand.java:331-340`), and each scanner allocates an uncounted 256 KiB direct read-ahead buffer
(`io/util/ThreadLocalReadAheadBuffer.java:84`). Range commands in flight (≤ `concurrent_reads` 32) × sstables (uncapped)
× 256 KiB is bounded only by `MaxDirectMemorySize` → direct OOM.

**Condition assessed:** the `verified-OOM · deployment` condition (owner ruling 2026-11-18): a table with 2,000 sstables
(held by `compaction = {'enabled': 'false'}`; RC with compaction re-enabled also failed), 40 concurrent paged full scans
`SELECT pk FROM t`; direct OOM 3/3 at 4 GiB / 2 GiB, 3/3 at the auto 15.5 GiB / 7,936 MiB.

**Label: `client-triggerable · DDL role; every replica of the attacker's keyspace (RF chosen by the attacker, up to every node)`**

Reach: **alone** at DDL role, with one substitution flagged below (sstables produced by a table option instead of the
harness's JMX flush). **Also:** `client-triggerable given a table with a large sstable count (backlog, large LCS table) ·
data role` — SELECT alone suffices on such a table.

## Condition and how common

At DDL role: none — the attacker builds the sstable count in its own table (≈ 2,000 flushes) and then scans. At data
role: a table that already has many intersecting sstables — an STCS/L0 backlog (stage 4 measured 211 L0 sstables with
nothing refused), compaction paused for a bulk load, or a large LCS table (2,000 × 160 MiB ≈ 320 GB): **occasional**. The
arithmetic for 211 sstables (≈ 2.2 GiB at 32 commands) is at the edge of a 2 GiB limit and was not run.

## Blast radius

- **Which node:** every replica of the scanned table: range commands at CL ONE go to one replica per range, so with the
  attacker's own keyspace at RF = number of nodes, or spread over the ring, the scans reach every node holding the
  sstables. RF 1 in the run (coordinator = replica).
- **Repeatable:** yes, across the cluster at once (the 2,000 sstables exist on every replica); death in 6–33 s.
- **Other tenants:** killed nodes (forced heap OOM, `kill -9`) drop all their clients; replica sets lose members —
  cluster-wide unavailability if every node is hit. The 2,000-sstable table also costs ≈ 6,000 fds per node.

## Operator visibility

Before: `nodetool tablestats` shows the table's sstable count climbing (and compaction disabled in `system_schema.tables`;
a table-properties *warned* list could flag it, but it ships empty); periodic flush log lines (`MEMTABLE_PERIOD_EXPIRED`);
schema-change log lines name the keyspace/table. During: ReadStage active 32 with pending. After: `OutOfMemoryError: Direct
buffer memory` on `ReadStage` through `ThreadLocalReadAheadBuffer.getBlock` ← `PartitionRangeReadCommand.queryStorage`.
The table's owner (role granted on creation) identifies the attacker.

## 3-b confirm

**Worthwhile**, mainly to verify the substitution. Needs: pc99 single node (or a 3-node ring to show the multi-node blast),
`PasswordAuthenticator` + `CassandraAuthorizer`, an attacker role with CREATE on ALL KEYSPACES only, which creates its
keyspace and table with `compaction.enabled = false` and `memtable_flush_period_in_ms` set (no JMX), writes the 2,000
rounds, then runs the 40 scans; a victim role on another table measuring success and latency. A second arm with a data
role scanning an admin table that has a natural backlog (e.g. 211–500 sstables) would test the data-role reach.

## Reason

Every step of the verified arm is a CQL step for a role that may create its own keyspace and table — the paused-compaction
table option passes the default (empty) table-properties guardrail, the data is plain inserts and the attack is 40
ordinary full-table scans — except the per-round flush, which the harness issued through JMX. A DDL role can obtain the
same flushes from the server with the table option `memtable_flush_period_in_ms` (`AbstractAllocatorMemtable.java:204-240`),
so the lowest privilege that triggers it alone is the DDL role; this substitution is the one unverified step. A data role
with SELECT needs an existing large sstable count (backlog or a large LCS table), an occasional operational state. The OOM
occurs at every auto-resolved budget, and the attacker can choose RF so that every node holds the sstables.

### Result

**Confirmed.** A role holding only `CREATE ON ALL KEYSPACES`, using nothing but CQL over the native port with
authentication and authorization on and every capacity constraint at its default, built a 2,000-sstable table through the
table options `compaction.enabled = false` and `memtable_flush_period_in_ms = 200` (no JMX), then killed the node with
`OutOfMemoryError: Direct buffer memory` in `ThreadLocalReadAheadBuffer.getBlock` ← `PartitionRangeReadCommand.queryStorage`
in 3/3 runs (10.9–11.5 s), and again after each restart (3/3, 8.3–11.0 s), at the verified 4 GiB heap / 2 GiB direct budget.
A second tenant on its own keyspace lost all requests from 3.5 s into the attack until the node was restarted. The
substitution the analysis flagged as unverified holds. The data-role reach also holds: a role with only `SELECT` on an
admin table with 220 sstables killed the node 3/3 (and 3/3 on repeat). The needed sstable count at a 2 GiB direct limit is
≈ 220–250, not 2,000, so the DDL attacker needs ≈ 45–50 s of writes at a 200 ms period.

**Label:** `client-triggerable · DDL role; every replica of the attacker's keyspace (RF chosen by the attacker, up to every node) (confirmed)`
