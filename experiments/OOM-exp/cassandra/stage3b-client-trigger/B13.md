# B13 — stage 3-b client trigger check (2026-11-24)

**Case:** [`networking_cache_size--v5-stalled-client-frame-overflow`](../cases/networking_cache_size--v5-stalled-client-frame-overflow/networking_cache_size--v5-stalled-client-frame-overflow.md)
(true positive, `verified-OOM · deployment`; heap 2 GiB / direct 2 GiB 3/3, also direct 4 / 7.75 / 15.5 GiB 1/1 each;
aarch64 `ms0617`). Stage 3-a: pending (`—` in `_INDEX.md`). Analysis only (no node run), by a fresh session that did not
design or verify the case. Code references are to the pinned 5.0.9 tree, paths below `src/java/org/apache/cassandra/`.

**Mechanism.** Over protocol v5 every response is copied into 128 KiB frames from the `networking` `BufferPool`; past its
128 MiB cap each frame is an unchecked `allocateDirect` overflow. Frames stay in the channel's outbound buffer until the
socket drains, no transport code checks `isWritable()`, and request permits are returned once a response is framed. A
client that keeps sending and never reads makes the node hold every response frame until `MaxDirectMemorySize` throws
(`OutOfMemoryError: Direct buffer memory` in `Flusher.flushLargeMessage`, then forced heap OOM and `kill -9`). The v5 twin
of C2.

**Label: `client-triggerable · data role; coordinator, repeatable on every node`** — SELECT on a table with MiB-sized
partitions (or MODIFY on a blob table to write one). A login role with no grants may suffice by reading `system_schema`
(code reading, untested).

**Lower privileges.** *Login role, no grants:* any authenticated role may SELECT `system_schema.*`, `system.local` and
`peers` (`service/ClientState.java:77-93`, `:463-464`). An unpaged `SELECT * FROM system_schema.columns` returns one row
per column of every table (system keyspaces included), plausibly tens to a hundred KB; held frames are held whatever the
response, so ≈ 20–40 k such requests (≈ 100 KB each) would fill 2 GiB at the same lack of backpressure. Not run. *Pre-auth:*
requests on an unauthenticated v5 connection get small error responses (R13 PF-1: decoded and refused, connection kept
open), which would also be held unread; at ≈ 100–200 B each that is ≈ 10⁷ requests per 2 GiB, and their per-entry heap
objects may fill the heap first. Speculative, not tested. C2 (v4 twin, confirmed at data role) makes the same assessment.

## Condition and how common

None beyond the defaults (reach **alone**). The prerequisite is a readable table with large partitions (or MODIFY to write
one); smaller responses lengthen the attack but do not stop it.

## Blast radius

- **Which node:** the coordinator the attacker connects to (it frames and holds the responses); the attacker picks it.
- **Repeatable:** yes, every node at once from one client host (16 connections and ≈ 1,000 tiny requests per node at 2 GiB
  direct; ≈ 5 min per node at the 15.5 GiB auto limit).
- **Other tenants:** the probe client on the same node lost service at the OOM; the JVM is killed (forced heap OOM,
  `kill -9`) and needs an operator restart; requests needing it as a replica lose one replica (two nodes of a replica set →
  `Unavailable` at QUORUM).

## Operator visibility

`BufferPool` logs once per second "Maximum memory usage reached (128MiB) for networking buffer pool, cannot allocate chunk
of 8MiB" (`utils/memory/BufferPool.java:447`, INFO, `NoSpamLogger`); the networking pool's `OverflowSize` gauge and JDK
direct `MemoryUsed` climb; `ss` shows full Send-Q on the attacker's connections. `ClientMetrics` see nothing
(`RequestsSize` ≈ 0, no paused connections). The connections carry the role (`system_views.clients`), so the attack is
attributable; audit logging ships off.

## 3-b confirm

**Worthwhile.** Re-run `T` (heap 2 GiB, direct 2 GiB) with `PasswordAuthenticator` + `CassandraAuthorizer`: admin loads
`b13.t`, attacker role with **SELECT only** on it, `stall5.py` with a SASL PLAIN login added, the stage-2 probe replaced by
a victim role on its own table. Expected: the same direct OOM in ≈ 38 s. A second arm is the more informative one: the
same attacker role with **no grants**, stalled, sending unpaged `system_schema.columns` (and `system_schema.tables`)
SELECTs — if it reaches the endpoint the label drops to login role, no grants. Record the response size first.

## Reason

Every step of the verified arm is a client step: an ordinary table read at CL ONE, issued over v5 by a client that stops
reading its socket. Authorization gates only the SELECT; the holder is created after authorization by the framing path,
which has no writability check and returns the request's permits before the frame is written. No operator-side condition
is needed (the endpoint appears at every direct limit tested, including the node's own), so the lowest verified-shape
privilege is a data role, with a plausible but untested route at login role through the always-readable schema tables.
