# B15 — stage 3-b client trigger check (2026-11-24)

**Case:** [`commitlog_max_outstanding_replay_bytes--smaller-heap-restart`](../cases/commitlog_max_outstanding_replay_bytes--smaller-heap-restart/commitlog_max_outstanding_replay_bytes--smaller-heap-restart.md)
(true positive, `verified-OOM · deployment`, owner-accepted 2026-11-18; replaying heap 1 GiB 3/3, 1,280 MiB 1/1, 1,536 MiB
starts; aarch64 `ms0611`). Stage 3-a: pending (`—` in `_INDEX.md`). Analysis only (no node run), by a fresh session that
did not design or verify the case. Related: [B8](B8.md) (same replay bound, restore + Byteman flush stall). Code references
are to the pinned 5.0.9 tree, paths below `src/java/org/apache/cassandra/`.

**Mechanism.** Commit-log replay re-applies what the *writing* JVM's memtable pool held (≈ 2.08 GiB from an 8 GiB writer),
not anything sized by the replaying JVM. If the node restarts at a 1 GiB heap while its data disk stalls, all 32 appliers
park on the full 256 MiB pool and the reader queues deserialized mutations up to the replay bound, which counts serialized
bytes (`db/commitlog/CommitLogReplayer.java:513-531`); dense tiny-cell map mutations hold ≈ 14× that → `Java heap space`
during start-up.

**Label: `client-triggerable given a crash, a restart at a smaller heap (≤ 1,280 MiB, log written at 8 GiB) and a data-disk stall during replay · data role; only the restarting replica(s) of the attacker's keys`**
— the three node-side events together are **rare**.

## Condition and how common

Three node-side events at once: an unclean stop with a full memtable pool, a restart of that data directory at a heap of
≤ ≈ 1.25 GiB when it was written at ≥ 8 GiB (restore to a smaller node or downsizing), and a data-disk write stall during
the start-up. Each is occasional at most; together **rare**. The client's part is only to have written dense collection
mutations that are still in the replayed log.

## Blast radius

- **Which node:** only the node that restarts under the condition, and only if the attacker's dense mutations are in its
  commit log (the replicas of the attacker's keys; the attacker can choose them by key but cannot cause the restart).
- **Repeatable across nodes:** no, not by the client; each node fails only on its own restart + downsizing + stall.
- **Other tenants:** the node fails to start (crash loop while the stall lasts and the heap stays small); its ranges run
  with one replica fewer (RF 3 / QUORUM unaffected unless a second replica is down). No runtime effect on other tenants.

## Operator visibility

The heap change and the stall are operator-visible events; the start-up log shows `Replaying …` and the OOM before
`Log replay complete`. The dense map writes leave no warning (collection guardrails off); with
`items_per_collection_warn_threshold` set they would be logged per write. Operator remedies: start at the writer's heap,
or lower `cassandra.commitlog_max_outstanding_replay_count` (the intervention, count 64, started 3/3).

## 3-b confirm

Not worthwhile as a client confirm: the deciding steps (crash, restart at a smaller heap, storage stall) are node-side and
would be re-run exactly as in stage 2. The only client step (a non-superuser role with MODIFY writing 5,900-entry maps) is
ordinary CQL and needs no confirmation (B8 makes the same call).

## Reason

What the replay queue holds depends on what the attacker wrote (dense tiny-cell collections, ≈ 14× their serialized size),
and any data role with MODIFY on a table with a collection column can write that shape within every default guardrail.
But stage 2 showed that the OOM needs the replayed volume to exceed the replaying JVM's pool (log written at 8 GiB,
replayed at 1 GiB) and the appliers to stall (a 30 s/write disk stall); a same-heap restart and a restart without the stall
both started 3/3. Neither step is open to a client, so the case is client-triggerable only given a rare node-side
condition, and it affects only the restarting replica.
