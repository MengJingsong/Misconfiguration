# C2 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/convergence/coordinator_read_size_fail_threshold-concurrent-reads/coordinator_read_size_fail_threshold--concurrent-reads.md`](../cases/convergence/coordinator_read_size_fail_threshold-concurrent-reads/coordinator_read_size_fail_threshold--concurrent-reads.md)
· **Stage 3-a:** [`../stage3-jira-check/C2.md`](../stage3-jira-check/C2.md) (`known-open (exact: CASSANDRA-11082)`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** On protocol v4 each finished read response is encoded on the request thread into Netty pooled direct
memory and queued on the channel; the thread, the in-flight request bytes and the read thresholds are all released before
the socket drains, and nothing checks `isWritable()`. Clients that read their sockets slowly keep outstanding reads ×
page size in direct memory → Netty `OutOfDirectMemoryError`, forced heap OOM, `kill -9`.

**Condition assessed:** **S-A** (`verified-OOM · deployment`, unprotected configuration): shipped defaults, 64
connections × 16 outstanding 3.5 MiB single-partition reads, drained at 2 MiB/s per connection; direct OOM 3/3 in ≈ 11 s,
also at the auto heap 7,965 MiB and at direct 7,936 MiB. S-B (thresholds enabled) gives the same result, so enabling the
read-size guardrail does not change the label.

**Label: `client-triggerable · data role; the coordinator the attacker connects to, repeatable on every node`**

Reach: **alone**. Lowest privilege: **data role** (SELECT on a table whose pages are MiB-sized; with MODIFY on any table
with a blob/text column the attacker writes such a partition itself). Under the shipped `AllowAllAuthenticator`
(`conf/cassandra.yaml:198`) anyone who reaches the native port can do it.

## Condition and how common

None beyond the defaults. The only prerequisite is a readable table with MiB-sized pages, or MODIFY on any blob/text
table. Unverified extension: smaller responses need proportionally more outstanding reads (stream ids and connections are
unbounded), so even modest pages may suffice; not tested.

## Blast radius

- **Which node:** the coordinator the attacker connects to; the attacker picks it (any node with an open native port).
- **Repeatable:** yes, on every node in turn or at once (≈ 11 s per node, one client host with 64 connections). A whole
  replica set or cluster can be taken down; the node is killed (`-XX:OnOutOfMemoryError="kill -9 %p"`) and does not come
  back without an operator restart.
- **Other tenants:** every client connected to that coordinator loses its connections; requests whose replicas include
  the dead node lose a replica (RF 3 / QUORUM survives one node; repeating on two nodes of a replica set gives
  `UnavailableException` at QUORUM); hints accumulate on the survivors.

## Operator visibility

Before: nothing at defaults — read thresholds are off, no outbound-bytes metric; the reads look normal (only 36 reads/s
complete). With thresholds enabled each 3.5 MiB page logs the 1 MiB warning (table, no user). During: `system_views.clients`
/ `nodetool clientstats` show 64 connections from one address (and, with authentication, the role). After: the log has
`OutOfDirectMemoryError` in `Message.encode` on a `Native-Transport-Requests` thread; the heap dump holds ≈ 1,700
`ChannelOutboundBuffer$Entry` on the attacker's channels (attributable by remote address / `ClientState` user). Audit
logging ships off.

## 3-b confirm

**Worthwhile and cheap.** Needs: one victim node at defaults with `PasswordAuthenticator` + `CassandraAuthorizer`, an
attacker role with SELECT (and MODIFY, to write its own 3.5 MiB partition) on one table only, the stage-2 `slowread.py`
client, and a victim role on another table measuring its success rate and latency at CL=ONE. Expected: the same direct
OOM in ≈ 11 s. A variant with SELECT only on an admin table of ordinary rows (smaller pages, more outstanding) would show
how far the data-role prerequisite can be relaxed.

## Reason

Every step of S-A is a client step: the schema is an ordinary blob table, the data is plain CQL writes, and the attack
itself is a v4 connection that issues reads and reads its socket slowly. Authorization only gates SELECT
(`SelectStatement.java:252` after `ClientState.validateLogin`, `service/ClientState.java:565`), no guardrail bounds page
size or read size at defaults, and the server has no outbound backpressure (`PipelineConfigurator.java:139` watermark,
never checked) and no connection or rate limit. So the lowest privilege is a data role and no operator-side condition is
needed. Not pre-auth: the large responses exist only for authorized SELECTs. Other conditions: S-B (thresholds on) gives
the same label; F-B (fast clients, heap 512–640 MiB, thresholds enabled) needs an operator-enabled guardrail and a small
heap and was negative at defaults (F-A 0/3).
