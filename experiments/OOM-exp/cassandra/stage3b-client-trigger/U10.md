Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** A plain aggregate sent with client paging off (`SELECT count(v) … WHERE pk = ?`) is paged internally with
`NO_LIMIT`, so the replica serializes the whole selected slice into one heap `DataOutputBuffer`
(`LocalDataResponse.build`). One query over ≈ 1 GiB of rows kills a 2 GiB heap; c = 2/4/10 concurrent queries kill
4/8/16 GiB.

**Condition assessed:** T (2 GiB heap / 1 GiB direct, one unpaged `count(v)` over 65,536 × 16 KiB rows, 3/3); budget
search 4/8/16 GiB (16 GiB 3/3) with more concurrency.

**Label: `client-triggerable · data role; the replica serving the data read (steerable by key), repeatable on every replica set, heaps ≤ 16 GiB`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` + `SELECT` on any table with a clustering column and a
`blob`/`text` value — the commonest admin-made shape). A role with `SELECT` only needs an existing partition of
≳ 0.5 GiB, which is rare.

## Condition and how common

None beyond writing ≈ 0.5–1 GiB into one partition and sending one unpaged aggregate (more concurrent ones on larger
heaps). Holds at heaps ≤ 16 GiB (tested); at 31 GiB the read timeout bounded it on that hardware.

## Blast radius

- **Which node:** the **replica that executes the data read** (`LocalDataResponse.build`). At CL ONE the coordinator sends
  one data read; a token-aware client connected to a replica makes it local. The attacker chooses the replica set by the
  partition key and, across repeats, hits every replica of it (the dynamic snitch moves the data read after the first
  death). Digest reads do not build the buffer. A remote read also copies the response to the coordinator (not tested,
  single node).
- **Repeatable:** yes — one big partition per replica set; the attack is one statement per kill and needs no restart of
  anything; it can be repeated immediately after the node comes back.
- **Other tenants:** a dead replica: at RF 3 / QUORUM tolerated per node, but killing the replicas of a range in turn
  gives `Unavailable`/timeouts for every tenant with keys there; during the build-up, ReadStage threads and GC pauses
  slow every read on the node.

## Operator visibility

Before: nothing at defaults (read thresholds off; no warning for paging-off aggregates). Large partitions are visible in
`tablehistograms`. During: GC warnings; slow-query log entries (`monitoring`) only for reads that complete. Attribution:
the hprof shows one `LocalDataResponse` for the table; the query text is not logged (audit/FQL off,
`conf/cassandra.yaml:1893-1894`). Operators can block it by enabling `read_thresholds_enabled` with a local read size
limit (I1: refuses the query).

## 3-b confirm

Worthwhile and cheap: T at 2 GiB with authentication on, a data role with `SELECT`/`MODIFY` on an admin-made table loads
1 GiB and sends one unpaged `count(v)`; victim role reads/writes another table. Optionally a 3-node RF 3 run to see the
data-read replica die and the next one die on repeat.

## Reason

Every step of T is ordinary CQL by a role with read/write access to a common table shape; turning paging off is a client
option, and the server, not the client, drops its stated internal row bound for plain aggregates. No operator action or
fault is needed (the flush/compact only fixed the sstable layout). The holder sits on the replica, which the attacker
chooses through the partition key, so replica sets can be taken down one by one. The 5 s timeout bounds it only on very
large heaps.
