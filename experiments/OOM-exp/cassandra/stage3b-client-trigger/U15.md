# U15 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog.md`](../cases/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog/ClusteringPrefix-validate--slice-delete-poisoned-flush-write-backlog.md)
· **Stage 3-a:** [`../stage3-jira-check/U15.md`](../stage3-jira-check/U15.md) (`known-open (partial: CASSANDRA-13213)`, trigger new).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** A slice `DELETE … WHERE pk = ? AND ck > ?` never runs `ClusteringPrefix.validate()`, so a 70,000-B bound
is accepted. The memtable flush then fails in `StatsMetadata` (`writeWithShortLength` asserts ≤ 65,535 B) and the failed
flush never releases its memtable's pool share. Two such flushes leave the cleaner unable to fire: every writer parks,
and local writes queue without bound on MutationStage until the heap is gone.

**Condition assessed:** arm T (2 GiB, and 15,872 MiB), the only verified condition. The flush stall that earlier
summaries listed as an operator-side condition is **created by the client itself** here (the poison statement); no
external stall, fault or restart is used.

**Label: `client-triggerable · data role; replicas of the poisoned table stall (steerable by key, repeatable on every node), OOM on nodes that coordinate local writes for it`**

Reach: **alone**. Lowest privilege: **data role** (MODIFY on any table with a variable-length clustering column).

## Condition and how common

None outside the client. Limiters (not conditions the attacker needs): the shipped `storage_compatibility_mode:
CASSANDRA_4` (with `NONE`, set by operators after a completed 5.0 upgrade, the improved min/max path `StatsMetadata.java:515-522`
serializes the bound differently; whether the flush still fails there was not checked).

## Blast radius

- **Which node:** every replica of the poisoned partitions (each replica flushes its own memtable and fails the same way),
  steerable by choosing partition keys (token ownership readable by any role, `service/ClientState.java:77-85`). The
  memtable pool is **node-wide**, so once two memtables are pinned **every table's writes stall on that node**, not just
  the attacker's.
- **OOM:** verified on one node with local writes (coordinator = replica). On a ring, local writes on a stalled replica
  queue without bound (the attacker uses that node as coordinator for keys it owns, as token-aware drivers do), while
  writes arriving over internode keep their receive reserve until processed (`net/InboundMessageHandler.java:436-440`),
  which probably bounds that part (not run). So: stall on all chosen replicas, OOM where local writes keep coming.
- **Repeatable across nodes:** yes; with keys spread over the ring, one poisoned DELETE per replica set and ≈ ⅔ of the
  memtable pool of writes per node (≈ heap/6) stall the whole cluster.
- **Persistence:** the failed flush skips the commit-log discard (`db/ColumnFamilyStore.java:1149-1159`), so a restart
  replays the poison; by the same assertion it presumably fails again (case §1.2, not tested).
- **Other tenants:** all writes on stalled nodes time out (`WriteTimeout` at every CL that needs those replicas); after
  the OOM, those nodes' ranges are unavailable.

## Operator visibility

From the first poisoned flush: `ERROR … AssertionError: Attempted serializing to buffer exceeded maximum of 65535 bytes`
on `MemtablePostFlush` and an NPE at `MemtableCleanerThread.java:97`; afterwards "Flushing largest … flushing 0.33" lines,
then MutationStage pending growing and write timeouts. The poison statement itself is not logged (audit log ships off);
the table is known, the role only via audit log or `system_views.clients`. One poison alone leaves a lasting sign (pool
⅓ pinned) before the second.

## 3-b confirm

**Worthwhile** and feasible on one node: authentication on, attacker role with `MODIFY` only on an admin-made
`(pk bigint, ck blob, v blob)` table, sending the poison and the 1 MiB write stream; a victim role writing to a
**different** table (and keyspace) records its success rate — this would show the cross-tenant write stall through the
shared memtable pool, the key "affects other users" claim. A ring variant (stall on all replicas, remote-write bound) and
the restart/replay leg need owner approval (beyond stage 2's one-victim rule / a restart).

## Reason

The whole trigger is two ordinary CQL statement types: a slice DELETE whose bound exceeds 64 KiB, which the server accepts
because the slice branch skips `validate()` (`ModificationStatement.java:762-787`), and plain writes. Both need only
`MODIFY` (`:249`), no guardrail applies, and the flush stall — usually an operator-side condition in this family — is
produced by the client's own statement. No fault, restart or diagnostic aid is used. Hence **client-triggerable alone at
data role**, with a node-wide (and cross-tenant) write stall on every replica the attacker chooses and a heap OOM where
local writes keep arriving.

**Why three failed flushes, not two:** each poisoned memtable was switched at 170.17 MiB (stage 2: 171.17–172.17), so after
two of them `reclaiming + ⌈L/3⌉` = 340.3 + 170.7 = 511.0 MiB < L = 512 MiB, and the cleaner could fire once more (used 1.00,

`reclaiming` ≈ L and no further flush was enqueued. Same mechanism, same stall and endpoint; with the 1/s poison every
memtable is poisoned, so the count of pinned memtables before the stall is 2 or 3 depending on δ.

### Code-reading claims checked by the run

- **Held:** `MODIFY` alone authorizes both the slice DELETE and the data INSERTs (`ModificationStatement.authorize`, `:249`):
  the attacker had only `MODIFY` on `u15.t` and every poison and data write was accepted. The slice branch skips
  `validate()` (`:762-787`) under auth too (12 poison `ok`, no `InvalidRequest`). Pre-auth is not enough: an
  unauthenticated connection is refused before any statement. No guardrail or limit stopped the attack at defaults. The
  memtable pool is **node-wide**, so another tenant's writes stall: the victim's `vks.kv` writes timed out 267 of 270 from
  W+13 while its reads kept working until the Full-GC phase. Operator signs as stated (the `AssertionError` and the
  `MemtableCleanerThread.java:97` NPE per failed flush, then write timeouts); the role is visible only in
  `system_views.clients` (and the audit log, which ships off), not in `system.log`.
- **Not tested here (single node):** steering to replicas by key and repetition across nodes, the internode-write bound on
  non-coordinator replicas, the restart / commit-log replay leg, `storage_compatibility_mode: NONE`, DESC order or an
  oversized upper bound, the CAS route under auth.

### Result

**Confirmed** in 1/1 run: with `PasswordAuthenticator` + `CassandraAuthorizer` and every capacity constraint at its default,
a login role holding only `MODIFY` on an admin-made `(pk bigint, ck blob, v blob)` table took a 2,048 MiB node to
`java.lang.OutOfMemoryError: Java heap space` at W+44.0 s (stage 2 without auth: W+42.7–49.0 s), with the queued local
writes (`StorageProxy$4` → 1 MiB `byte[]`) ≈ 70 % of the heap beside the three pinned memtables, and a victim tenant on
another keyspace lost all writes from W+13 s and the node at W+44–48 s.
