**Mechanism.** Every loaded table carries eager heap state no budget counts: 214 JMX MBeans (`TableMetrics`, created per
`ColumnFamilyStore`, `db/ColumnFamilyStore.java:543`) whose `ObjectName` strings embed the keyspace and table names, plus
reservoir/histogram arrays — 0.480 MiB per empty long-named table (0.336 with short names). The table-count guardrail
ships disabled, so empty tables created by DDL fill the heap (3,975–3,978 tables at 2 GiB, 8,137–8,225 at 4 GiB).

**Condition assessed:** arm T (2 GiB, 48-char keyspace, 222-char table names, no rows, one serial DDL client); the 4 GiB
follow-up and the short-name run S8 are the same path. Stage 2 already ran as an **ordinary role** under
`PasswordAuthenticator` (with `AllowAllAuthorizer`).

**Label: `client-triggerable · DDL role; every node in the cluster at once (schema is cluster-wide)`**

Reach: **alone**. Lowest privilege: **DDL role** (`CREATE` on one keyspace suffices; `CREATE` on ALL KEYSPACES not needed).

## Condition and how common

None outside the client. Practical limiter: time. At 2–4 GiB heaps the OOM comes after ≈ 4,000–8,200 tables (minutes to
≈ 1.5 h); a production heap of 16–31 GiB would need ≈ 33–65 k tables at seconds per CREATE (DDL latency grows with the
table count), i.e. many hours of conspicuous DDL. Not tested above 4 GiB.

## Blast radius

- **Which node:** **every node** — schema is cluster-wide and each node registers the metrics of every table, so all nodes
  with the same heap fill together (the smallest heap first). The attacker does not need to choose a node.
- **Repeatable:** inherent (one attack hits the whole cluster). A restart reloads the same schema and its per-table state,
  so nodes are expected to fail again at startup until tables are dropped or the heap raised (inferred from the
  mechanism; not tested).
- **Other tenants:** whole-cluster outage; before it, GC service loss on every node (87–98 % GC per minute at 4 GiB for
  ≈ 10 min in `H4-T-1`) and slow schema changes for everyone.

## Operator visibility

Highly visible if watched: every CREATE logs "Create new table" in `system.log` on every node, `system_schema.tables`
grows, the heap baseline rises linearly, CREATE latency rises. No guardrail warning (warn threshold also −1). Attribution
by role needs the audit log (ships off); with `CassandraAuthorizer` the creator's grants in `system_auth.role_permissions`
name the role for each table. Enabling `tables_fail_threshold` stopped it (arm I, 0/3).

## 3-b confirm

**Worthwhile and cheap**: one node, 2 GiB, `PasswordAuthenticator` + **`CassandraAuthorizer`** (stage 2 used
`AllowAllAuthorizer`), an admin-made keyspace with a short name, the attacker role holding only `GRANT CREATE ON KEYSPACE`;
a victim role reads and writes its own table and records success and latency through the GC service loss to the OOM.
Checks that the creator grants do not change the slope. A multi-node run (all nodes failing together) and the restart leg
are beyond stage 2's rules (owner's call).

## Reason

The trigger is DDL only: creating empty tables needs `CREATE` on a keyspace (`CreateTableStatement.java:164`), the only
count control is a guardrail that ships at −1 (`Config.java:865-866`, check `CreateTableStatement.java:138-145`), and no
byte budget charges the per-table metrics. Stage 2 already ran it as a non-superuser. A data role (SELECT/MODIFY) cannot
create tables, so the lowest privilege is **DDL role**; no fault, restart or aid is needed (**alone**). Because schema is
cluster-wide, the blast radius is every node at once, limited in practice by how long the DDL takes at large heaps.
