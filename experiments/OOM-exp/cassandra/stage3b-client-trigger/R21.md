# R21 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/memtable_heap_space--stale-btree-updater-pins-discarded-memtables/memtable_heap_space--stale-btree-updater-pins-discarded-memtables.md`](../cases/memtable_heap_space--stale-btree-updater-pins-discarded-memtables/memtable_heap_space--stale-btree-updater-pins-discarded-memtables.md)
· **Stage 3-a:** [`../stage3-jira-check/R21.md`](../stage3-jira-check/R21.md) (`known-fixed (not in 5.0.9)`, fixed incidentally by CASSANDRA-20780 on 6.0/trunk).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Each write merges through a per-thread pooled `BTree.Updater` whose `reset()` never nulls `updateF`
(`utils/btree/BTree.java:3600-3604`), so every SEP worker keeps the partition of its last write — and through it whole
flushed, DISCARDED memtables already released from `memtable_heap_space`. With one hot partition a few pinned memtables
fill a 2 GiB heap in 7–8 s.

**Condition assessed:** U2-T (unmodified build, 2 GiB, all defaults, gated hot-partition writer, OOM 3/3). Same holder
at all defaults with 4 hot partitions (U-Q 2/2) and at 15,872 MiB (R16 H16-T 3/3). The I arm (`concurrent_writes: 4`) is
a non-default supporting shape, not used.

**Label: `client-triggerable · data role; replicas of the hot partition (steerable by key), repeatable per replica set`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` + `SELECT` on any table with a clustering column and a
`blob`/`text` value).

## Condition and how common

None. Seconds of hot-partition writes at a high rate. One uncertainty for a shared node: a pin is released when the SEP
worker writes again, so other tenants' writes on the same node reuse workers and may shorten pins (pins persisted 300 s
at idle; the case did not run concurrent unrelated writes). Q (4 hot partitions) shows the shape does not need a single
partition.

## Blast radius

- **Which node:** every **replica of the hot partition** (each runs the merges on its own SEP workers); the attacker picks
  the replica set by partition key.
- **Repeatable:** yes, per replica set, quickly (7–8 s at 2 GiB); at idle the pinned memory stays (≈ 0.4–0.6 GiB), so an
  attack also leaves a node with less headroom. After a restart nothing persists (memtables are gone; commit-log replay
  writes from the replay thread) — the attacker must write again.
- **Other tenants:** a dead replica; at RF 3 / QUORUM one per set is tolerated, the whole set dead gives `Unavailable` for
  their token ranges; before the OOM, memtable allocation waits and GC pauses slow every write on the node.

## Operator visibility

Little before the OOM: the attack lasts seconds; flush logs ("Writing … Memtable" lines, overshoot to 148–157 % of the
pool) and "High update contention" for the hot partition may appear; `nodetool toppartitions` would show the key. The
pool metrics read below the limit, so memtable metrics do not explain the heap. Attribution: the hprof chain
`TinyPool` → `BTree$Updater.updateF` → discarded allocator names the table; the role is not logged (audit log off,
`conf/cassandra.yaml:1893-1894`). The fix is in trunk (two lines), not in any 5.0 release.

## 3-b confirm

Worthwhile and cheap (seconds per run at 2 GiB): U-T with authentication on, a data role with `MODIFY`/`SELECT` from one
host first (to see the per-IP limit's effect), then four addresses; a victim role doing steady small writes to another
table — that run also answers whether other tenants' writes dilute the pins.

## Reason

The verified arm consists of ordinary high-rate writes (single-partition batches) to one partition by a role with write
access, plus reads for gating; the flush/discard cycle that leaves the stale references is the node's own response to the
write volume. No operator action, fault or diagnostic aid is involved, every value is inside the defaults, so the case is
`client-triggerable` alone at data role, against the replicas of the chosen key.
