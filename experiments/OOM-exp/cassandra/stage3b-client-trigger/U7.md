# U7 — stage 3-b client trigger check (2026-11-23)

**Case:** [`in_select_cartesian_product--modification-IN-product-row-build`](../cases/in_select_cartesian_product--modification-IN-product-row-build/in_select_cartesian_product--modification-IN-product-row-build.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`U7.md`](../stage3-jira-check/U7.md) (`new`). Analysis only (no node run).

**Mechanism.** One prepared `UPDATE … WHERE k IN ? AND c IN ?` (or `DELETE`) makes the coordinator build all P × Q rows
(`ModificationStatement.addUpdates` ← `getMutations`) on one request thread before anything is applied; the
`in_select_cartesian_product` guardrail ships at −1 and, when enabled, bounds P and Q separately; a 176 KB request builds
4 × 10⁷ rows and OOMs a 2 GiB heap.

**Label: `client-triggerable · data role; coordinator, repeatable on every node`**

**Condition:** none.

## Blast radius

- **Which node:** the coordinator the attacker connects to (the rows are built there before any replica is contacted).
- **Repeatable:** yes, one 176–480 KB request per node, every node.
- **Other tenants:** the coordinator dies (2–4 GiB) or sits in ≥ 90 % STW for as long as measured (8–16 GiB: 500 s and
  1,220 s); clients on it time out or lose connections; its replicas' ranges lose a replica. Note: the shipped
  `OnOutOfMemoryError` kill did not fire in U7's runs, so the node may stay up but unusable until killed.

## Operator visibility

None before the failure: no guardrail warning (off), no write applied (memtables 0), in-flight charge 176 KB. With
authentication and audit/FQL logging on, the role and statement are attributable afterwards.

## 3-b confirm

Partly done in stage 2: `IA-1..3` ran the test arm as a non-superuser with `PasswordAuthenticator` (but
`AllowAllAuthorizer`) and OOMed 3/3. A full confirm adds `CassandraAuthorizer` with MODIFY only on `u7.t` and a victim
role; low priority given IA.

## Reason

Every step is a single prepared write with two bound lists that any role with MODIFY on an ordinary (pk, ck) table can
send; nothing else (data, fault, operator action, diagnostic aid) is in the verified arm, and the case's own IA arms show
the OOM as a non-superuser under password authentication. The only counting control is off for everyone at defaults and
per-side when on. Lowest privilege: data role (MODIFY); the coordinator dies and the attack repeats on every node.

## 3-b confirm (ms0611, 2026-11-23)

Fresh OOM-agent session, owner-approved confirm run (2026-11-23), 14:33–15:12 node time (America/Denver). Evidence:
[`logs/U7/`](logs/U7/) (per run: `driver.txt`, `ddl.txt`, `privcheck.txt`, `settings.txt`, `client.txt`, `summary.txt`,
`victim-summary.txt`, `victim-persec.csv`, `victim.csv.gz`, `auth-failures.txt`, `gcinspector.txt`, `threads.txt`, `jmx.csv`;
harness copy with every change in `logs/U7/harness/`).

**Result: the privilege is confirmed, but the OOM is not, 0/3.** With `CassandraAuthorizer` on, the attacker's single
176 KB UPDATE (MODIFY only) fills the 2 GiB coordinator heap and drives it into a full-GC spiral for 2–3 min, every
time. But in all three runs the request is then aborted by `UnauthorizedException: Unable to perform authorization of
super-user permission: Operation timed out`. The per-cell superuser check has to reload the expired roles-cache entry,
that reload is a local read, and the read times out in the spiral. The rows are released and the node recovers fully.
The victim tenant gets 49–58 % success during the attack (p50 0.6–0.9 s, up to 62 s in a row with no success) and 100 %
after.

### Why the endpoint differs from stage 2 (code + logs)

The attack's NTR thread asks `ClientState.isOrdinaryUser()` → `Roles.hasSuperuserStatus` for every cell. The path is
the `column_value_size` guardrail in `UpdateParameters.addCell:166` → `Guardrail.enabled` (`Guardrail.java:93-96`); this
frame appears in stage 2's IA-3 OOME stack. The roles cache is built with `refreshAfterWrite` = `expireAfterWrite` =
2,000 ms (`AuthCache.java:344-345`, `roles_validity` default `cassandra.yaml:300`), so every 2 s the entry has expired
and the request thread reloads it synchronously. The reload is a CQL read of `system_auth.roles`
(`CassandraRoleManager.getRole:549-551`) with the 5,000 ms `read_request_timeout` (`cassandra.yaml:1322`). With back-to-back
full GCs of 3–18 s (`gcinspector.txt`), one such reload eventually exceeds 5 s. It then throws `UnauthorizedException`
(`Roles.java:102-105`), which ends the build, and the rows become garbage. So the build races the reload timeout:
under these runs the timeout won 3/3 (at +118 to +172 s). Stage 2's IA-1..3 had `PasswordAuthenticator` with
`AllowAllAuthorizer`, no victim and no 60-s baseline, and they OOMed 3/3. IA-3's OOME was thrown *inside*
`Roles.hasSuperuserStatus`, so the same reload ran there without timing out first. **Which difference tips the race**
(the authorizer's own permission-cache reloads, the victim's auth reads on the same ReadStage, the node, or the scope
change below) **was not separated**: the task allows at most three runs.

### Deviations

1. **No `systemd-run --user --scope -p MemorySwapMax=0`.** That needs `loginctl enable-linger` (sudo), which was refused
   for this session. The daemon ran under plain `setsid nohup`. Swap use was logged instead: `VmSwap` 0 kB in every
   sample of every run. There is no memory limit either way.
2. **Victim load and a 60-s baseline** added to the test arm (by the task). K includes the victim's in-flight bytes.
3. **After the endpoint the daemon was left up 120 s** (stage 2: 30 s) for the victim's after-view. In these runs the
   endpoint was the request's abort, after which the harness's post-step watch (120 s) ran.
4. **Different node** (`ms0611`, the same build tree). Stage 2 ran on `ms0625`.
5. 3 runs (the first did not reach the endpoint; 2 more were allowed to tell a fluke from a difference). T-2 and T-3
   ended as T-1, so this is a real difference, not a fluke.

### Which code-reading claims held

- **MODIFY alone is enough to send the request, and it is checked before the build** (`ModificationStatement.authorize`,
  `QueryProcessor`): **held**. `privcheck` shows the role can do nothing else. The request was accepted and built
  ≈ 1.97 GiB of rows before any replica write (memtable 0).
- **Guardrail −1 at default and no bound for a non-superuser**: **held** (settings −1/−1, no guardrail rejection).
- **176 KB ≪ 16 MiB, in-flight charge tiny**: **held** (K ≤ 0.22 MB including the victim).
- **"The coordinator dies (2–4 GiB)"**: **did not hold** with `CassandraAuthorizer` at 2 GiB, 0/3. The coordinator goes
  through 2–3 min of GC service loss and then recovers, because the request is aborted by the roles-cache reload
  timeout (above). This mechanism was not in the analysis.
- **"Repeatable on every node"** and **repeated sends**: **not tested** (single node, one send per run). By code
  reading, nothing stops the attacker from re-sending after each abort; every send would cost ≈ 2–3 min of service
  loss. Untested.
- **Other tenants time out or lose connections**: **held** for timeouts (victim 49–58 % ok, p99 ≈ 4.7 s). The victim
  never lost its connection while the node was up.
