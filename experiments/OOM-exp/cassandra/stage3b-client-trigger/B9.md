# B9 — stage 3-b client trigger check (2026-11-24)

**Case:** [`native_transport_max_request_data_in_flight--v4-frames-per-connection`](../cases/native_transport_max_request_data_in_flight--v4-frames-per-connection/native_transport_max_request_data_in_flight--v4-frames-per-connection.md)
(true positive, `verified-OOM · deployment`; heap 4 GiB, direct 1,280 MiB, aarch64 `ms0617`). Stage 3-a: pending (`—` in
`_INDEX.md`). Analysis only (no node run), by a fresh session that did not design or verify the case. Code references are
to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below `src/java/org/apache/cassandra/` unless under `conf/`.

**Mechanism.** On protocol v4 a request frame is accumulated in a Netty pooled direct cumulation buffer (a 16 MiB chunk
for a 15 MiB frame) **before** `native_transport_max_request_data_in_flight` is consulted; with connections unlimited,
128 connections reading 15 MiB frames at once filled Netty's direct counter (U = 1,280 MiB = 3.0 × C) while the in-flight
counter held 75–180 MiB and no connection was paused → `OutOfDirectMemoryError` in `ByteToMessageDecoder.cumulate`,
forced heap OOM, `kill -9`.

**Label: `client-triggerable given a direct limit ≤ 1,280 MiB · pre-auth (by code reading); coordinator, repeatable on every node`**
— the verified limit is an explicit `MAX_DIRECT_MEMORY_SIZE` beside a 4 GiB heap (**occasional**); `cassandra-env.sh`
resolves ≤ 1,280 MiB by itself on a node with ≤ 5 GiB RAM (untested pairing). The verified runs used the shipped
`AllowAllAuthenticator` and a data-role-shaped workload (prepared INSERT); the lower privilege is a code-reading claim.

## Condition and how common

A direct-memory limit at or below ≈ 1,280 MiB on the attacked node: an explicit `MAX_DIRECT_MEMORY_SIZE` (containers and
hand-sized nodes; **occasional**) or a small node whose own resolution is that low (≤ 5 GiB RAM; heap ≤ 2.5 GiB is common
for test and small production nodes, but this pairing was not run). The client cannot see or change the limit.

**Unverified extension to "alone".** The demand is ≈ 16 MiB per connection that is reading a frame, connections are
unlimited, and nothing times out a half-sent frame. By code reading, an attacker who opens ⌈D/16 MiB⌉ connections and
leaves each frame one byte short (≈ 1,000 connections and ≈ 15 GB sent for the 15,872 MiB auto limit; 128 connections /
2 GB for a 2,048 MiB limit) holds Netty's whole counter without any timing race, at any budget. Not run in stage 2; it is
the main question for a confirm run.

## Blast radius

- **Which node:** the coordinator the attacker connects to (every node listens on the native port); the frames are held
  on its event loops before any routing.
- **Repeatable:** yes, on every node in turn or at once from one client host; with no login, there is no role to revoke.
- **Other tenants:** the first failing allocation is on an event loop; `JVMStabilityInspector` turns the Netty error into
  a forced heap OOM (`transport/PreV5Handlers.java:368`) and the shipped `-XX:OnOutOfMemoryError="kill -9 %p"` kills the
  JVM 6–8 s later. Every client of that node loses its connections; requests needing it as a replica lose one replica
  until an operator restarts it (RF 3 / QUORUM survives one node; two nodes of a replica set → `Unavailable`).

## Operator visibility

Before the failure: nothing specific (no idle timeout, no warning for large frames in progress; `ClientMetrics`
`RequestsSize` stays low because the bytes are not yet charged). After: `ERROR … io.netty.util.internal.OutOfDirectMemoryError`
on `epollEventLoopGroup` threads in `ByteToMessageDecoder.cumulate` (31–49 lines per run), then the forced heap OOM.
Pre-auth connections carry no role, so only source addresses identify the attacker; audit logging ships off.

## 3-b confirm

**Worthwhile and needed** (the privilege rests on code reading, and R13's pre-auth claim failed on a guard the analysis
missed). Re-run `T` at heap 4 GiB / direct 1,280 MiB with `PasswordAuthenticator` + `CassandraAuthorizer`, the client
**never logging in**: 128 v4 connections that (a) send STARTUP, receive `AUTHENTICATE`, then each send one 15 MiB frame
(e.g. `AUTH_RESPONSE` or `QUERY` with a 15 MiB body), and (b) a variant that sends 15 MiB `OPTIONS` frames before
STARTUP; plus a victim role on its own table measuring success rate and latency. Needs a raw v4 frame client (the stage-2
`B9Load` uses the driver and a prepared statement, so it cannot send pre-auth frames) and B9's harness otherwise. A
second arm worth one run: the half-sent-frame variant at the node's own auto direct limit (and at 2,048 MiB), to test
whether the label can drop its budget condition.

## Reason

The memory that fails is the v4 frame cumulation, which Netty fills before Cassandra looks at the frame: no permission,
no connection stage and no in-flight charge is involved until the whole frame has arrived, and on v4 (unlike v5) nothing
refuses large frames from an unauthenticated connection. So any host that reaches the native port can, by the code, hold
16 MiB of direct memory per connection with unlimited connections. The verified OOM, however, needed a direct limit of
1,280 MiB beside a 4 GiB heap (an operator override; the auto 15,872 MiB survived 128 connections), so the verified label
carries that condition; the half-sent-frame variant would remove it but is untested.
