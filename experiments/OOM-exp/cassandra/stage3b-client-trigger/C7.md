**Mechanism.** A repair command starts every (session × table) job at once, because `concurrent_merkle_tree_requests` ships
at 0, meaning unlimited (`repair/RepairCoordinator.java:127`, `config/Config.java:210`). The repair coordinator receives
each replica's tree set into direct memory (`use_offheap_merkle_trees` true, `Config.java:212`). It holds each set until
all replicas of that job have answered, and it falls behind because it is a replica in every session. With ≈ 100 tables,
164 held sets of ≈ 15.6 MiB exhaust a 2 GiB direct limit.

**Condition assessed:** T (`verified-OOM · deployment`): 4 instances, RF 2, 16 vnodes, n1 heap 2 GiB / direct 2 GiB,
`nodetool repair --full c7 <106 tables>` from n1 → direct OOM in `MerkleTree.allocate` 3/3.

**Label: `client-triggerable given an operator-run repair covering the attacker's keyspace (routine) · DDL role; the repair coordinator`**

Reach: **given an outside condition.** The trigger itself, a repair command, is admin only: `nodetool repair` over JMX
(`StorageServiceMBean.repairAsync`, `service/StorageServiceMBean.java:476`), and 5.0.9 has no CQL path. As run the label
would be `not client-triggerable (nodetool repair)`. The client's part is the multiplicity. A DDL role creates ≈ 100+
tables with ≈ 1 M partitions each in its own RF ≥ 2 keyspace and waits for the operator's routine repair, which must run at
least once per `gc_grace_seconds` (10 days). Lowest privilege: **DDL role**. A data role would need an admin keyspace that
already has ≈ 100+ tables: rare.

## Condition and how common

A repair, run by the operator, that covers the attacker's keyspace with all its tables in one command, from a node whose
direct limit the held sets exceed. Anti-entropy repair is a routine operation (at least every 10 days by the default
`gc_grace_seconds`), and plain `nodetool repair` / `-pr` cron jobs cover every keyspace: **routine** where repair is run
that way. Subrange tools (Reaper) send one token range per command, which gives fewer sessions and smaller trees. There the
attacker needs more tables, and whether the backlog still forms is untested. The attacker cannot start the repair or
choose its time.

## Blast radius

- **Which node:** the repair coordinator, which the operator chooses. With `nodetool repair -pr` run on each node in turn,
  each node dies when it coordinates.
- **Repeatable:** at every repair cycle; a failed repair is retried by operators or schedulers. There is no crash loop: a
  restart aborts the repair.
- **Other tenants:** the killed coordinator drops its clients and replica role for the restart time. Repairs of every
  keyspace keep failing, so tombstone and consistency maintenance stalls for all tenants. That is a slow, cluster-wide harm.

## Operator visibility

Before: the attacker's keyspace has 100+ tables (no guardrail warning), and `nodetool tablestats` shows them. During: the
repair log shows S × T jobs started; `MemoryUsed` of the direct pool climbs; the yaml's own comment on
`concurrent_merkle_tree_requests` warns of OOM. After: `OutOfMemoryError: Direct buffer memory` in `MerkleTree.allocate` on
the coordinator, during a repair of the attacker's keyspace. The keyspace owner identifies the role.

## 3-b confirm

**Not worthwhile as a confirm:** the operator-run repair decides it. The client steps (DDL plus inserts) need no
privilege test. If the owner wants the condition checked, the informative arm is on stage 2's 4-instance setup with
authentication on: an attacker role with `CREATE ON ALL KEYSPACES` writes its 106 tables by CQL (no hard links), then the
admin runs a plain default `nodetool repair` (incremental, all keyspaces) on n1. That tests the CQL-written data and the
incremental default in one arm.

## Reason

The multiplicity that the case needs (≈ 100 tables × sessions of tree sets held at once on the coordinator) is fully in a
DDL role's hands: its own keyspace, RF ≥ 2, ≈ 100 tables, ordinary inserts. No guardrail bounds tables, and the aggregate
tree control ships disabled. The repair command that turns that schema into held trees is a JMX/nodetool operation no
client can issue, but operators run it routinely, and a plain all-keyspace repair includes the attacker's keyspace. Hence
**client-triggerable given an operator-run repair (routine) at DDL role**. The hard-linked clones and the `--full` flag of
the verified arm are the two untested differences from that routine path.
