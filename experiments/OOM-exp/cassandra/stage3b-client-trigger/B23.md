Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** With one replica down, every CL=ONE write through a coordinator that is not a replica is acked by the live
replica and leaves a `HintRunnable` holding the whole mutation on the coordinator's unbounded MutationStage queue, while
the single hint writer is parked at the 3 × 32 MiB slab cap. `checkHintOverload` (5,120 tasks) never refuses because
`hintsInProgress` is a bare `CacheLoader` (`service/StorageProxy.java:203`, `:2764-2768`): a fresh zero counter on every
call (`:1585-1597`). At 64,000-B writes faster than the hint disk drains, the heap fills with hint tasks.

**Condition assessed:** arm T (3 instances, n3 stopped, n1 non-replica coordinator, 2 GiB heap, 64,000-B CL=ONE writes
from 200 threads); the same at 4, 8 and 15,872 MiB; condition X (1 MiB values) noted.

**Label: `client-triggerable given a replica down (within max_hint_window) · data role; any coordinator the attacker picks, repeatable on every live node`**

Reach: **given a replica down** (occasional to routine). Lowest privilege: **data role** (MODIFY on any table in a keyspace
with RF ≥ 2 that has a `blob`/`text` column).

## Condition and how common

One replica down, for less than `max_hint_window` (3 h by default). **Occasional to routine**: every rolling restart
(upgrade, config change) takes each node down for minutes, and node failures happen; a client sees a down replica as
`Unavailable`/timeouts at CL ALL or via the driver's node-down events (`system.peers` and protocol events are available to
any role). The attacker needs sustained write bandwidth above the coordinator's hint-disk drain rate (≈ 130 MB/s here).

## Blast radius

- **Which node:** the coordinator the attacker connects to (non-replica for the chosen keys); free choice of node.
- **Repeatable across nodes:** yes, against every live node in parallel (each as coordinator for keys it does not own),
  while one node is already down — so a second node loss can push ranges below QUORUM, and with all coordinators dead the
  cluster is down.
- **Other tenants:** writes through the stalled coordinator queue behind the hint tasks and time out; after the OOM,
  clients fail over, the dying coordinator loses the hints it held (the down replica then needs repair), and the dead
  node's own ranges lose a replica.

## Operator visibility

Before the OOM: `TotalHintsInProgress` (Storage metric) climbing past `MaxHintsInProgress` with no refusals; MutationStage
pending; hint-directory growth on the coordinator; the down node in `nodetool status`. The enforcement message "Too many
in flight hints" never appears (the check cannot fire). Attribution: high write throughput from one role is visible in
`nodetool clientstats` / `system_views.clients`; the audit log ships off.

## 3-b confirm

**Worthwhile**: stage 2's 3-instance setup with authentication on; the attacker role holds `MODIFY` on one admin-made RF 2
table and computes keys off n1 itself (`num_tokens` 16, no `initial_token`, to show the placement is a client choice); the
operator stops n3 (the condition); a victim role writes small rows through n1 to another table at RF 2 and records its
success and latency. One victim node, defaults, 2 GiB, as stage 2.

## Reason

Every client step — choosing the coordinator and keys, CL ONE, 64 KB writes at a high rate — needs only `MODIFY`
(`ModificationStatement.java:249`) and passes every default limit; the coordinator's only claimed bound on hint tasks
(`checkHintOverload`, `StorageProxy.java:1585-1597`) can never refuse because of the `CacheLoader` defect (`:203`,
`:2764-2768`), and the single-token placement of stage 2 only made the non-replica path universal, which a client gets by
key choice. The step no client can take is the replica being down, so the reach is **given a replica down**, at **data
role**, on any coordinator the attacker chooses.

## 3-b confirm (pc82, 2026-11-23)

Fresh OOM-agent session (Claude Opus 5.5) on the owner's approval of 2026-11-23. The runs took 16:37–17:20 America/New_York
on `pc82` (node1.jason92-326665: 40 cores, 125 GiB RAM, `/mydata` = an LVM on one rotational PERC H710P volume, the same class
as stage 2's `pc75`, `dd … conv=fdatasync` 180 MB/s; OpenJDK 11.0.33, G1 as shipped). Build: `/mydata/s4/cassandra-base`
(5.0.9) as is, with each instance getting its own `conf` copy. Run data is in `/mydata/s4/3b-B23/`. Before the runs no java
process was running and the node had 120 GiB free and 712 GiB of disk. Evidence is in [`logs/B23/`](logs/B23/) and the
harness copy is in [`logs/B23/harness/`](logs/B23/harness/).

### Setup

- **Topology.** Stage 2's three instances on loopback: n1 `127.0.0.31` (the victim coordinator, 2 GiB heap, data, commit
  log and hints on `/mydata`), n2 `127.0.0.32` (seed), n3 `127.0.0.33`. n2 and n3 run with an 8 GiB heap and keep their data
  on `/dev/shm`, as E3. The difference from stage 2 follows this file's "3-b confirm" plan: **`num_tokens: 16` as shipped,
  with no `initial_token`**. That gives a vnode ring in which n1 owns 76 % (effective). Stage 2's single-token placement
  (E2) is **not** used: the attacker picks the placement itself.
- **Auth settings (all three nodes, `n1-conf.diff`):** `authenticator: PasswordAuthenticator`,
  `authorizer: CassandraAuthorizer`, `role_manager: CassandraRoleManager`. Apart from these, the diff from the shipped
  yaml/env changes only the cluster name, addresses, seeds, directories, JMX port and a GC-log line. **Every capacity
  constraint stays at its default.** `MaxHintsInProgress` read over JMX was **5,120**.
- **Budget (V7, as the verified test arm T):** n1 `-Xms2G -Xmx2G -XX:MaxDirectMemorySize=15872M` (as `cassandra-env.sh`
  resolves it), G1, `HeapDumpOnOutOfMemoryError` and `OnOutOfMemoryError=kill -9 %p` as shipped. No cgroup memory limit:
  `systemd-run --user --scope -p MemorySwapMax=0` only.
- **What the superuser did** (the default `cassandra` role; `admin1.txt`, `admin2.txt`):
  `ALTER KEYSPACE system_auth WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3}`, followed by
  `nodetool repair -full system_auth`. This is the usual operator practice that lets logins work with one node down; it
  is not a capacity constraint. The superuser then created the roles, the admin-made schema and the grants:
  ```
  CREATE ROLE attacker WITH PASSWORD = '…' AND LOGIN = true AND SUPERUSER = false;
  CREATE ROLE victim   WITH PASSWORD = '…' AND LOGIN = true AND SUPERUSER = false;
  CREATE KEYSPACE app WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 2};
  CREATE TABLE app.data (key blob PRIMARY KEY, v blob);
  GRANT MODIFY ON TABLE app.data TO attacker;
  CREATE KEYSPACE vks WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 2};
  CREATE TABLE vks.t (k int PRIMARY KEY, v blob);
  GRANT SELECT ON TABLE vks.t TO victim;
  GRANT MODIFY ON TABLE vks.t TO victim;
  ```
  `LIST ALL PERMISSIONS OF attacker` returns exactly one row, `<table app.data> MODIFY`. The victim has `SELECT` and
  `MODIFY` on `<table vks.t>`.
- **Attacker role check, with all three nodes up (`probe-attacker.txt`):** reading `system.peers` and
  `system_schema.keyspaces` works, and so does `INSERT INTO app.data`. The role gets `Unauthorized` for `SELECT` on
  `app.data`, `SELECT` and `INSERT` on `vks.t`, `CREATE KEYSPACE`, `CREATE TABLE app.extra` and `ALTER TABLE app.data`.
- **Attack (everything through the `attacker` login, native protocol v4):** `B23Client attack`
  (`harness/B23Client.java`, DataStax Java driver 3.12.1 from the build's `lib/`) connects only to n1 (whitelist) from
  client IP `127.0.0.41`. It builds the ring from what the role can read (`system.local`, `system.peers`,
  `system_schema`). It then takes candidate keys 0, 1, 2, … (8-byte blobs) and keeps only those whose replicas
  (`Metadata.getReplicas`) exclude n1. In both runs 24 % of the candidates qualified. For each kept key it sends
  `INSERT INTO app.data (key, v)` with a 64,000-B value at CL ONE. It keeps 200 requests in flight, sends no retries
  (`FallthroughRetryPolicy`) and offers N = 250,000 writes. Stage 2 also offered 250,000, counting stress's warm-up, from
  200 threads. Because stress cannot choose keys or log in without schema rights, this client replaces it.
- **Operator condition:** n3 is stopped with `nodetool stopdaemon` 30 s after the victim starts. The attack starts 30 s
  after n1 shows n3 as `DN`.
- **Victim:** `B23Client victim` runs as role `victim` from client IP `127.0.0.51`, through n1 only. It sends a steady
  100 requests/s: 50 writes of 100 B and 50 reads, at CL ONE on `vks.t`, with a 12 s driver timeout and no retries. It
  runs from 60 s before the attack to 60 s after the stop rule, and it logs every request.
- **Instruments and stop rules as stage 2:** `Poll.java`, `hprofhist.py` and `summary.py` are unchanged (sha256 equal to
  the case's `harness/`). The JMX poller (unauthenticated local JMX, which ships that way) is the operator's view, not part
  of the attack. The driver is `harness/run3b.sh`. A smoke run (N = 2,000, not a reading) passed first. The first smoke
  attempt failed on a missing client-classpath jar before any load.

### Deviations (none changes a capacity constraint or the budget)

1. **Topology: vnodes plus client key choice instead of E2.** This follows this file's confirm plan. It removes stage 2's
   one non-default topology setting (`num_tokens: 1` + `initial_token`). n1 owns 76 % of the ring here, and the attacker
   discards the 76 % of keys n1 replicates.
2. **Client:** `B23Client` instead of `cassandra-stress`, with the same request shape: 64,000-B blob, CL ONE, protocol v4,
   200 in flight, no retries, whitelist n1. The table is `app.data (key blob, v blob)`, made by the admin, instead of
   stress's `keyspace1.standard1`. There is no warm-up phase. Attacker and victim use distinct loopback source IPs so
   that the per-IP native limits apply per tenant.
3. `system_auth` RF 3 plus a full repair, an operator setting for auth availability.
4. Node `pc82`, not `pc75` (same hardware class). Work directory is `/mydata/s4/3b-B23/`, and n2/n3 data sit under
   `/dev/shm/3b-B23/<run>/`.
5. **Two runs, not one.** R1 reached the endpoint, but the harness's teardown (stop rule "attack done + 60 s", then the
   60 s victim after-window) killed the thrashing JVM before HotSpot wrote its dump. That is the B4G effect from stage 2,
   here with no dump at all. The case's holder attribution is a dump scan, so R2 was run with a harness amendment, made
   after R1 and dated: once n1's stdout shows `OutOfMemoryError`, wait for the JVM's own dump and exit, up to the 600 s
   cap. `dumpproc.sh` now skips empty dumps. R2 needed no extension, because n1 exited by itself at L+51. That is 2 runs
   of the 3 allowed; no run failed to reach the endpoint.
