# R22 — stage 3-b client trigger check (2026-11-23)

**Case file:** [`../cases/range-tombstone-list--forced-thrash-queues-large-local-writes/range-tombstone-list--forced-thrash-queues-large-local-writes.md`](../cases/range-tombstone-list--forced-thrash-queues-large-local-writes/range-tombstone-list--forced-thrash-queues-large-local-writes.md)
· **Stage 3-a:** [`../stage3-jira-check/R22.md`](../stage3-jira-check/R22.md) (`known-open (partial: CASSANDRA-13235)`).
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** One hot memtable partition with ≈ 1.2 M range tombstones makes each of the 32 MutationStage writers copy
its `RangeTombstoneList` per optimistic attempt, so the stage completes only a few writes/s. Every other local write
queues in the unbounded MutationStage queue and stays there after its 2 s timeout; 12 MiB writes pile up to a heap OOM
at 15,872 MiB.

**Condition assessed:** T (15,872 MiB heap, defaults; hot partition filled to K₀, two bursts of 64 hot deletes, paced
hot stream + 4/s of 12 MiB blob writes; OOM 3/3 at W+446–580 s). The **stall is created by the client's own range
deletes**, not by an operator-side flush or compaction stall. B8 (8 GiB) and S512 did not enter the thrash with this
client.

**Label: `client-triggerable · data role; replicas of the hot partition (steerable by key), repeatable per replica set; shown at a 15,872 MiB heap only`**

Reach: **alone**. Lowest privilege: **data role** (`MODIFY` on a table with a clustering column for the range deletes and
on any table taking large `blob`/`text` values — both common admin shapes; or one table serving both).

## Condition and how common

No operator-side condition: the stall is the client's own data shape. Limits of the evidence: the OOM is shown only at
the 15,872 MiB heap; at 8 GiB the paced client did not enter the thrash and a commit-log flush came first, and at 512 MiB
the paced client did not either (R17's unpaced client got GC service loss there). So the reach is "alone" for large-heap
nodes as tested; smaller heaps are unproven.

## Blast radius

- **Which node:** every **replica of the hot partition** (each applies the range deletes and stalls its own
  MutationStage), plus whatever blob writes the attacker steers to those replicas by key. The attacker chooses both by
  partition key.
- **Repeatable:** yes — a hot range-tombstone partition per replica set; the tombstones stay in the memtable until a
  flush, and the stall must be re-entered after a restart (the commit log replay brings the tombstones back, untested).
- **Other tenants:** **all writes** on a stalled replica, for every table, sit in the same MutationStage queue: tenants
  sharing the replica see write timeouts for minutes before the OOM (2 s timeout, hints written by coordinators); reads
  slow under ≥ 90 % GC before the end. After the OOM: lost replica as usual (QUORUM tolerates one node; the whole replica
  set means `Unavailable` for those token ranges), hint backlog on coordinators.

## Operator visibility

Before: `nodetool tpstats` MutationStage pending in the thousands and active 32, write-latency and timeout metrics,
`WriteTimeout` errors at clients, GC pause warnings (`GCInspector`) for minutes; "High update contention" may appear in
logs for the hot partition. Range-tombstone counts are only warned on reads (`tombstone_warn_threshold` 1000) — an
operator reading the partition would see it. Attribution: the hot partition's key/table from the hprof or
`toppartitions`; with authentication on, the writing role is not logged (audit log off,
`conf/cassandra.yaml:1893-1894`). Mitigation without a fix: flush the hot table (`nodetool flush`) ends the stall.

## 3-b confirm

Worthwhile but costly: needs a ≥ 64 GiB node at the 15,872 MiB heap, ≈ 15 min per run. Run T with authentication on,
one data role (`MODIFY` only) from **one source address** first (to see whether the per-IP limit protects), then three;
a victim role writing small rows to another table measures its own timeouts. A second item: a run on an un-pinned node
(all cores) to check that the thrash forms without E3.

## Reason

Every client step of T — range deletes into one partition, two bursts of 64 concurrent writes, and a stream of 12 MiB
inserts — is ordinary CQL by a role with `MODIFY`, inside every default limit; the stall that keeps the queue from
draining is produced by those deletes, not by an operator-side condition. The environment deviations (tmpfs, CPU
pinning, three source addresses) are either neutral or available to any multi-host client. So the case is
`client-triggerable` alone at data role, with the caveat that it is shown only on a large-heap node; it also degrades
every other tenant's writes on the stalled replicas well before the OOM.

### Deviations

1. Authentication + authorization on, a victim tenant (10 small requests/s, up to 122 in flight at the end) and two
   `ops` instrumentation reads; NTR active reached 128 (stage 2 ≤ 114). The OOM came earlier than any stage-2 T run
   (W+398.5 s vs 445.8–579.7 s) — within the design's 220–600 s range.
2. Fill to a fixed tombstone count (1,231,000) instead of the JMX-read K₀; same resulting state.
3. Run data on tmpfs `/dev/shm/3b-R22/<label>` (the verified arm's E2) rather than on `/mydata/s4/3b-R22/`, which holds
   the logs, harness and excerpts; the tmpfs folder was emptied after each lifetime and removed.
4. No kept dump: the dump was scanned with `hprofhist.py` (niced, CPUs 0–3) right after the JVM exited and deleted.
5. The JMX poller's last sample was at W+342.5 s (refused under the GC thrash, as in stage 2); later trends from the GC
   log, client CSVs and the dump.
6. AUTHCHECK try 1 sent the 12 MiB INSERT as a non-prepared statement (the blob inlined as a 24 MiB hex literal →
   "Request is too big"), a harness bug; fixed (prepared, as the attack client) and re-run as AUTHCHECK2; every other
   check agreed in both. Both kept.
7. One attack run, as briefed (the endpoint was reached, so no extra runs); the analysis's one-source-address run and
