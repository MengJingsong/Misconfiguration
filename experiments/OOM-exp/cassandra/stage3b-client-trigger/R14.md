# R14 — stage 3-b client trigger check (2026-11-23)

**Case:** [`in_select_cartesian_product--select-IN-ck-product-growth-step`](../cases/in_select_cartesian_product--select-IN-ck-product-growth-step/in_select_cartesian_product--select-IN-ck-product-growth-step.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`R14.md`](../stage3-jira-check/R14.md) (`known-open`, CASSANDRA-15250; documented). Analysis only (no node run).

**Mechanism.** `SELECT … WHERE pk = 0 AND c1 IN ? AND c2 IN ?` is expanded by `MultiCBuilder` into the full clustering
cartesian product on the request thread (one `ArrayList` + `Object[2]` per combination, `db/MultiCBuilder.java:358-359`)
before any limit; the `in_select_cartesian_product` guardrail ships at −1. One 12.8 MB request (160 × 1,600,000) OOMs an
8 GiB heap.

**Label: `client-triggerable · data role; coordinator, repeatable on every node`**

**Condition:** none.

## Blast radius

- **Which node:** the coordinator the attacker connects to (the product is built on its request thread before any
  replica is contacted).
- **Repeatable:** yes, one request per node, on every node; the same shape at 2 GiB gives GC service loss (U5) and the
  PK form OOMs at 2 GiB.
- **Other tenants:** the coordinator dies (heap OOM, dump, `kill -9`); all clients connected to it lose their
  connections and in-flight requests; its replicas' ranges lose one replica until restart.

## Operator visibility

None before the failure: no guardrail warning (off), no slow-query entry (the request never reaches a read), in-flight
charge 12.8 MB. The heap dump shows `MultiCBuilder` frames. With authentication and audit/FQL logging on, the role and
statement are attributable afterwards.

## 3-b confirm

Worthwhile and cheap: one request. At 8 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`, a role with SELECT on
`u5.ck` only sends the T request while a victim role runs a closed loop on another table. Optionally a no-grant login
against `system_schema.columns` (`keyspace_name = ? AND table_name IN ? AND column_name IN ?`) to test the lower
privilege.

## Reason

The deciding allocation is made on the coordinator's request thread from bound lists that any role with SELECT on a table
with two clustering columns can send in one 12.8 MB request; no data, fault or operator action is involved, and the only
control that counts the product is off for everyone at defaults (and skipped for superusers when on). Lowest privilege:
data role (by code even a login without grants, through the always-readable schema tables; not tested). The coordinator
dies and the attack repeats on every node.

### Deviations from the stage-2 arm

- Node ms0604 (**aarch64**, 8 CPUs, 62 GiB) instead of pc91 (x86_64, 32 CPUs, 125 GiB), a different build of the same
  5.0.9 tree (jar sha256 `b3fa4929…` vs `570b5249…`); the step-window model predicted 8 GiB inside the 157.7M window for
  b = 100–250 MiB on any architecture, and U5 had already thrown at 8 GiB on aarch64 (+158–160 s). Throw +156 s here vs
  +37–47 s on pc91 (slower memmove on this CPU), with a 62 s GC spiral before it.
- `MaxDirectMemorySize=15872M` set explicitly (stage 2 left it to `cassandra-env.sh`, which resolved 15872M on pc91).
- Fresh node directory per lifetime with the schema and the one row made by the superuser in the same lifetime (stage 2
  copied a `template-A` made in a LOAD lifetime); no `nodetool flush` (not a client step; the row stays in the memtable,
  which does not matter — the product is built before any read).
- Disk refusal threshold heap + 10 GiB instead of heap + 20 GiB (this node's `/mydata` is 39 GiB; the dump took 14.5 GB
  of 28.9 GiB free).
- One run (n = 1), as the task asks; no matched control or intervention under auth (stage 2 has them).
- Extra (instrumentation/probes, not the attack): a `nogrant` LOGIN role used for two small probes; one superuser read of
  `system_views.clients` at +4 s.

### Which code-reading claims held

- **SELECT on one admin-made table is enough — held.** A role with exactly `SELECT ON TABLE u5.ck` (no MODIFY, no
  CREATE, no access to the tenant's table) sent the one request and killed the coordinator. No data written by the
  attacker (the product does not depend on stored rows).
- **Authorization is checked before the product is built — held.** The `nogrant` role's PREPARE of the same statement
  succeeded but its EXECUTE was refused `0x2100 … no SELECT permission on <table u5.ck>` in 2 ms (`precheck-nogrant.jsonl`),
  so a role without SELECT on such a table cannot reach the build there; `atk` with SELECT reached it.
- **Guardrail off for non-superusers too — held.** `in_select_cartesian_product_*=-1` at startup; no guardrail message
  for the non-superuser `atk`; the product was built to 157.7M composites.
- **Not pre-auth — held.** STARTUP is answered with AUTHENTICATE; a QUERY sent before AUTH_RESPONSE gets
  `Unexpected message QUERY, expecting SASL_RESPONSE` and no rows.
- **Under the frame and message limits — held.** The 12,801,331 B body was accepted under `PasswordAuthenticator`.
- **Same allocation, same thread — held.** Thrower, frames, humongous count and holder counts match stage 2.
- **Lower privilege via `system_schema` — partly.** By probe only: the `nogrant` login (no grants at all) ran
  `SELECT … FROM system_schema.columns WHERE keyspace_name = 'u5' AND table_name IN ('ck','zz') AND column_name IN
  ('c1','c2','v')` and got 3 rows, so authorization lets a grantless login send an IN × IN on two clustering columns of
  a schema table. The 256M-combination request against `system_schema.columns` (text values) was **not run**; the label
  stays at data role until it is.
- **Operator visibility — held.** Nothing warned before the failure; the attacker's role is visible in
  `system_views.clients` while the request runs; the dump has the `MultiCBuilder` frames.
- **New observation:** on this node the tenant on the same coordinator was degraded for ≈ 2.5 min **before** the OOM
  (81 % → 46 % → 28 % of its schedule with 2 s timeouts during the GC spiral), then 0 % for the 222 s dump and after.
- **Not tested here:** "repeatable on every node" and multi-node blast radius (single-node run; rests on the analysis).
