# R14 — stage 3-b client trigger check (2026-11-23)

**Case:** [`in_select_cartesian_product--select-IN-ck-product-growth-step`](../cases/in_select_cartesian_product--select-IN-ck-product-growth-step/in_select_cartesian_product--select-IN-ck-product-growth-step.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`R14.md`](../stage3-jira-check/R14.md) (`known-open`, CASSANDRA-15250; documented). Analysis only (no node run).

**Mechanism.** `SELECT … WHERE pk = 0 AND c1 IN ? AND c2 IN ?` is expanded by `MultiCBuilder` into the full clustering
cartesian product on the request thread (one `ArrayList` + `Object[2]` per combination, `db/MultiCBuilder.java:358-359`)
before any limit; the `in_select_cartesian_product` guardrail ships at −1. One 12.8 MB request (160 × 1,600,000) OOMs an
8 GiB heap.

**Label: `client-triggerable · data role; coordinator, repeatable on every node`**

**Condition:** none.

## Blast radius

- **Which node:** the coordinator the attacker connects to (the product is built on its request thread before any
  replica is contacted).
- **Repeatable:** yes, one request per node, on every node; the same shape at 2 GiB gives GC service loss (U5) and the
  PK form OOMs at 2 GiB.
- **Other tenants:** the coordinator dies (heap OOM, dump, `kill -9`); all clients connected to it lose their
  connections and in-flight requests; its replicas' ranges lose one replica until restart.

## Operator visibility

None before the failure: no guardrail warning (off), no slow-query entry (the request never reaches a read), in-flight
charge 12.8 MB. The heap dump shows `MultiCBuilder` frames. With authentication and audit/FQL logging on, the role and
statement are attributable afterwards.

## 3-b confirm

Worthwhile and cheap: one request. At 8 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`, a role with SELECT on
`u5.ck` only sends the T request while a victim role runs a closed loop on another table. Optionally a no-grant login
against `system_schema.columns` (`keyspace_name = ? AND table_name IN ? AND column_name IN ?`) to test the lower
privilege.

## Reason

The deciding allocation is made on the coordinator's request thread from bound lists that any role with SELECT on a table
with two clustering columns can send in one 12.8 MB request; no data, fault or operator action is involved, and the only
control that counts the product is off for everyone at defaults (and skipped for superusers when on). Lowest privilege:
data role (by code even a login without grants, through the always-readable schema tables; not tested). The coordinator
dies and the attack repeats on every node.
