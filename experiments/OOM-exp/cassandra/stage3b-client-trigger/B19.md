# B19 — stage 3-b client trigger check (2026-11-23)

**Case:** [`native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed`](../cases/native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed/native_transport_max_request_data_in_flight--v4-lz4-body-charged-compressed.md)
(true positive on T2, `verified-OOM · deployment`; T `candidate`). Stage 3-a: [`B19.md`](../stage3-jira-check/B19.md) (`known-open`, CASSANDRA-14997 for T2). Analysis only (no node run).

**Mechanism.** On a v3/v4 connection that chose LZ4 in STARTUP, `LZ4Compressor.decompress` allocates
`heapBuffer(uncompressedLength)` from the client-declared first 4 body bytes before any check
(`transport/Compressor.java:174-184`): one 22-byte frame declaring 1.90 GiB OOMs a 2 GiB node in 0.3–0.4 s (T2).

**Label: `client-triggerable · pre-auth; coordinator, repeatable on every node`**

## Threat-model walk of the verified test arm (T2)

| Step | As run in stage 2 | Client-reachable? | Privilege / why (code) |
|---|---|---|---|
| Schema / data | `b19.t` with 1 M rows (used by T only) | not needed for T2 | The frame never reaches message decode. |
| STARTUP | `{CQL_VERSION: 3.0.0, COMPRESSION: lz4}` on protocol v4 | yes, pre-auth | `StartupMessage.execute` sets the compressor (`transport/messages/StartupMessage.java:101-103`) before it asks the authenticator, and answers `AUTHENTICATE` if authentication is required (`:122-124`); the legacy pipeline with `Envelope.Decompressor` is installed at STARTUP (`transport/InitialConnectionHandler.java:141-148`, `PipelineConfigurator.java:391-396`). |
| The frame | one v4 frame, flags COMPRESSED, 13-byte body declaring L = 2,040,109,465 | yes, pre-auth | `Envelope.Decompressor.decode` decompresses any compressed frame once a compressor is set (`transport/Envelope.java:521-539`), before the message decoder, the in-flight charge (`PreV5Handlers.java:105`) and the connection-stage check (`transport/Dispatcher.java:412`). The frame-size check sees 13 bytes. |
| Concurrency | one connection, one frame | yes | — |
| Environment | single node, 2 GiB (3/3); `S_vm`: `bogus 2147483647` killed a 15,872 MiB heap with a VM-limit `OutOfMemoryError` (diagnostic) | — | No fault or diagnostic aid in the test arm (the patched build only in I2). |

**Condition:** none. Other conditions: **T** (valid 255:1 LZ4 bodies charged at their compressed size, `candidate`) also
decompresses pre-auth, but its bodies are held until a response is written; before login every frame is refused at
once, so T's pile-up needs a logged-in role with SELECT on a table whose `count(*)` is slow (data role).

## Blast radius

- **Which node:** the coordinator the attacker connects to — any node with the native port reachable.
- **Repeatable:** yes, one frame per node, the whole cluster within a second; repeatable on every restart. At heaps above
  ≈ 2 GiB a declared 2,147,483,647 gives the VM-limit `OutOfMemoryError` (`S_vm`), which the shipped OOM handling also
  kills; several 1.9 GiB frames on parallel connections are the other route.
- **Other tenants:** the node is killed within half a second; all its client connections drop; with every node hit, the
  cluster is down until restarted (and can be hit again at once).

## Operator visibility

Practically none: the JVM dies within 0.4 s of a 22-byte frame; the heap dump shows the OOM thread in
`Compressor.java:184` ← `Envelope$Decompressor.decode`. No authenticated identity exists; only the peer address (if
connection logging or a network capture is on).

## 3-b confirm

Worthwhile and cheap. At 2 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`: STARTUP with LZ4, receive
`AUTHENTICATE`, send the T2 frame without answering it; a victim role on another connection measures its own errors. One
frame per run, × 3.

## Reason

The allocation is sized by an untrusted 4-byte field and made in the pipeline's decompressor, which is enabled by the
STARTUP options any client sends before authenticating and which runs before every other check. The verified arm needs
nothing else: no schema, data, credentials, fault or diagnostic aid. Lowest privilege: pre-auth; the coordinator dies
and the attack repeats on every node instantly. Under the shipped `AllowAllAuthenticator` this is the default exposure
for anyone who can reach port 9042.

## 3-b confirm (ms0625, 2026-11-23)

Fresh 3-b confirm session (did not design, verify or analyse B19), owner-approved 2026-11-23. Node `ms0625`, 17:41–17:54
EST (node clock MST). Evidence: [`logs/B19/`](logs/B19/): the measured lifetime in
[`logs/B19/T2-AUTH-r1/`](logs/B19/T2-AUTH-r1/) (`steps.txt`, `admin.txt` roles/grants/permission listing,
`authcheck.txt`, `client.log` attacker, `victim.out` per-second tenant log, `vsum.txt` tenant view per window,
`samples.csv` 500 ms JMX, `cg.csv`, `gc-attack-excerpt.txt`, `stdout-oom-excerpt.txt`, `oome-thread.txt`,
`hprofhist.txt`, `hprof.ls`, `node-config-excerpt.txt`, `V-flags.txt`, `V-yaml.diff`, `V-cmdline.txt`, `outcome.txt`);
`summary.txt`; harness as run in [`logs/B19/harness/`](logs/B19/harness/). Run data `ms0625:/mydata/s4/3b-B19/`
(build copy, data dirs and the dump deleted; 2.5 MB of logs kept).

**Result: 1/1 heap OOM (`Java heap space`, then the shipped `kill -9`) from one 22-byte frame sent on a connection that
never authenticated, with `PasswordAuthenticator` + `CassandraAuthorizer` on and every capacity constraint at its
default. The OOM thread is the stage-2 site (`Compressor.java:184` ← `Envelope$Decompressor.decode:539`). The tenant on
its own keyspace went from 40/40 ok per second to 0 within about 1.1 s of the frame and stayed at 0. The label is
confirmed for one node.**

### Deviations

- One aborted lifetime before the run (17:45–17:46 EST, `logs/B19/ABORTED-setup-classpath/steps.txt`): the driver
  clients' classpath lacked `failureaccess-1.0.1.jar`, so the superuser setup failed; the node was stopped before any
  attack frame was sent, and the run was restarted from a fresh node. Not a reading. `run.sh` now aborts a lifetime
  whose setup fails.
- Harness changes (all in [`logs/B19/harness/`](logs/B19/harness/)): `ctl.sh` (root `/mydata/s4/3b-B19`, build copy,
  the three auth lines, empty data dir by default, scope units `b3b19V-*`); `B19AuthClient.java` = stage-2
  `B19Client.java` with an authentication-aware STARTUP (AUTHENTICATE accepted; with `-Duser/-Dpass` it logs in with SASL
  PLAIN, without them it leaves AUTHENTICATE unanswered) and the `authcheck` mode; new `B19Admin.java`, `B19Victim.java`,
  `run.sh`, `vsum.py`; `B19Sample.java`, `cg.sh`, `hprofhist.py`, `hprof_oome_thread.py` unchanged. The frame bytes and
  the attack are those of stage 2's `bogus` mode.
- Stage 2's preflight "before 13:15 EST" clause was dropped (a stage-2 time plan); the 4-h per-case cap applied (used
  ≈ 15 min).
- The time to the endpoint is measured from the frame (client `BOGUS ms − dt`) to the `HeapDumper` safepoint in the GC
  log, and to the JVM's disappearance (100 ms poll); stage 2 quoted 0.3–0.4 s on the first measure.

### Label after the confirm

**Label: `client-triggerable · pre-auth; coordinator, repeatable on every node` (confirmed)** — confirmed on one node
with authentication and authorization on: an unauthenticated client (no role, no credentials) killed the node it

the same code path on every node but was not run.
