# B12 — stage 3-b client trigger check (2026-11-24)

**Case:** [`paxos_cache_size--weigher-omits-partition-key`](../cases/paxos_cache_size--weigher-omits-partition-key/paxos_cache_size--weigher-omits-partition-key.md)
(true positive, `verified-OOM · deployment`; 2 GiB 3/3, 4 GiB 3/3, 16 KiB keys at 2 GiB 1/1; aarch64 `ms0611`). Stage 3-a:
pending (`—` in `_INDEX.md`). Analysis only (no node run), by a fresh session that did not design or verify the case. Code
references are to the pinned 5.0.9 tree, paths below `src/java/org/apache/cassandra/`.

**Mechanism.** Every v1 `SERIAL` read leaves a `Snapshot` in the Paxos state cache `PaxosState.RECENT` on each replica
(`service/paxos/PaxosState.java:514-528`); the weigher charges only the two stored updates (128 B for an absent partition,
`:72-76`) and never the partition key the entry holds. With 60 KiB keys each entry holds ≈ 62 KB, so the 20 MiB auto cap
(2 GiB heap) would admit ≈ 10 GB; the heap died at ≈ 26,400 distinct keys.

**Label: `client-triggerable · data role; every replica of the chosen keys (one replica set, or all nodes with spread keys), repeatable`**
— SELECT on any table with a `blob`/`text` partition key (keys ≥ ≈ 16 KiB at a 2 GiB heap; ≈ H × 2.1 KiB above 5 GiB).

**Lower privileges.** A login role with no grants can read only `system.local`, `peers(_v2)`, size estimates and
`system_schema` (`service/ClientState.java:77-93`), none of which has a large client-chosen key; SERIAL reads there are
not a path to big keys. Pre-auth: no request executes. So data role is the floor.

## Condition and how common

None beyond the defaults (reach **alone**). The prerequisite is a readable table with a `blob`/`text` partition key; the
attacker supplies the large keys itself.

## Blast radius

- **Which nodes:** every replica that answers the prepare. With keys of one token range the attacker fills one replica set
  (RF nodes die together, so QUORUM on that range fails); with spread keys every node fills at ≈ RF/N of the rate, so the
  whole cluster can be driven to OOM in one run.
- **Repeatable:** yes; the cache is in memory only, so a restarted node starts empty and can be filled again.
- **Other tenants:** the replicas are killed (`kill -9` on OOM) and need an operator restart; their ranges lose replicas
  (LWT and QUORUM traffic of every tenant on those ranges fails first, since Paxos needs a quorum).

## Operator visibility

No warning from the cache (its weight stays at ≈ 3 MB of 20 MiB). Visible: `CASRead` latency/count and the table's
`CasPrepare`/`CasPropose` metrics rising, `system.paxos` memtable flushes, and slow-query log lines that print the 60 KiB
keys (one OOM landed in that rendering). Connections carry the role, so the reads are attributable (`system_views.clients`);
audit logging ships off.

## 3-b confirm

**Worthwhile, cheap.** Re-run `T` at 2 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`: admin creates `b12.t`,
attacker role with **SELECT only** on it, the stage-2 `client.py` with a SASL PLAIN login added, plus a victim role on its
own table measuring success rate and latency. Confirms that SELECT alone reaches the SERIAL path for a non-superuser and
that the auth caches do not change the time to OOM (≈ 26 k keys). A multi-node run would settle the "every replica" claim
but is optional.

## Reason

The only client inputs are SERIAL reads with large partition keys of the role's own choosing, on a table it may read; the
cache entry is created on the replicas as a side effect of the read, charged at 128 B while it holds the key. No guardrail
or default setting bounds key size or SERIAL reads for a non-superuser, and no operator-side event is needed. The nodes
that die are the replicas of the chosen keys, which the attacker can aim at one replica set or spread over the cluster.

### Deviations

1. **No milestones.** Stage 2 paused the client every 4,000 keys for forced-full-GC class histograms and `nodetool` (a
   diagnostic aid no client can take). Here the load ran continuously. Holder evidence comes from the dumps, the
   1-s JMX samples and CHECK-1's histograms.
2. **Node and build:** ms0604, not ms0611 (same m400 aarch64 class); ms0604's own build of `cassandra-5.0.9` (clean, same
   yaml md5). The node ran from a separate node directory with a copied conf, as in B19 3-b: loopback `127.0.0.12`,
