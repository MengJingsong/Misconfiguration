# R12 — stage 3-b client trigger check (2026-11-23)

**Case:** [`monitoring_max_operations+traced-render--slow-query-monitor-stacked`](../cases/monitoring_max_operations+traced-render--slow-query-monitor-stacked/monitoring_max_operations+traced-render--slow-query-monitor-stacked.md)
(true positive; condition B `verified-OOM · deployment`, condition A `verified-OOM · deployment` mixed, under fallback F).
Stage 3-a: [`R12.md`](../stage3-jira-check/R12.md) (`new`). Analysis only (no node run).

**Mechanism.** The slow-query monitor keeps up to 50 finished slow/aborted `ReadCommand`s per queue with their bound filter
values after the in-flight limit has released them, and each drain renders every polled command to an uncut hex string;
with distinct 16 MB values per read the drain's map grows past the count cap (condition B: 3.46 GB at 4 GiB). Condition A
adds the uncharged traced render of the bound value (`ExecuteMessage.traceQuery`).

**Label: `client-triggerable · data role; replica of the chosen key (plus the coordinator for the traced render), repeatable on every node`**

**Condition:** none.

## Blast radius

- **Which node:** the replica that executes the read holds the monitored commands, so the attacker steers it by choosing
  the partition key; under condition A the traced render also loads the coordinator it connects to. At RF > 1 and CL ONE
  the coordinator picks one replica per read; with keys spread over the ring every node can be hit.
- **Repeatable:** yes, on every node at once (keys per token range, several connections each), up to 8 GiB heaps (3/3);
  12 GiB reached 96 % in 180 s.
- **Other tenants:** the replica dies (`OnOutOfMemoryError` kill) or stalls in GC first; requests needing it time out or
  become unavailable at their CL; at RF 3 two replicas of one range taken down break QUORUM for that range.

## Operator visibility

`debug.log` shows the monitor's aggregated "operations were slow / timed out" lines with very long query strings (the
render itself); `system.log` GC pause warnings. Nothing charges or rejects the requests; with authentication on, the
role is attributable by audit/FQL logging (off by default).

## 3-b confirm

Worthwhile. Re-run `TB` at 2 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`, a role holding SELECT (and MODIFY
for the seed load) on `r12.t` only, 13 connections from ≥ 5 source addresses, and a victim role reading/writing another
table at CL ONE, measuring its success rate and latency. Optionally `FTA` (traced, empty partition) as the same role.

## Reason

Every step of both verified arms is ordinary CQL that a role with SELECT on a table having a blob/text regular column can
send: the 16 MB value fits the frame, filtering is allowed at defaults, and the tracing flag needs no permission. Condition B
also needs a wide partition to make reads slow, which the role writes itself with MODIFY (or finds in an existing table);
condition A needs no data at all. No operator condition, fault or diagnostic aid is part of the test arm. The node that
dies is the replica the attacker selects by key (and the coordinator for the render), so the attack is repeatable across
the cluster. Lowest privilege: data role.

The victim shares nothing with the attacker but the node: a different role, keyspace, table and set of source addresses.

victim request fail with `AttributeError` before it was sent; see Deviations.

### Deviations (none changes a capacity constraint or the budget)

1. **Node and CPU:** `pc82` (x86_64, 40 cores), not `ms0640` (aarch64, 8 cores).
2. **`k_sel` = 3, not 2.** The frozen calibration rule (§2.5) was re-applied on this node, as the attacker role. The attacker
   writes the partition itself with MODIFY, so it picks the partition width; the width a read needs to pass 500 ms depends
   on the CPU.
3. **Two runs, not one.** TBA-1 reached the endpoint, but its victim client was broken by a harness bug in the code written
   for this confirm, so the run is invalid for the victim view. Under the case's "one rerun per invalid run" rule, TBA-2 was
   run with the fix (`wid`/`rid` locals instead of socket attributes). TBA-2 was not run because TBA-1 missed the endpoint,
   and the "up to 2 more" allowance was not used. TBA-1's endpoint and dump readings are valid and are reported.
4. **Client:** the case's raw protocol-v4 client plus a SASL PLAIN login, `--admin` (CQL file as the logged-in role),
   `--victim` and `--victim-load` modes ([`client.py`](logs/R12/harness/client.py)). The attack frames, source addresses
   and request loop are unchanged.
5. **Driver** [`run3b.sh`](logs/R12/harness/run3b.sh) (from `run.sh`) adds the victim, time markers and an operator
   restart after the endpoint. The restart is not in stage 2, and it only measures recovery. The seed is built by
   [`seed3b.sh`](logs/R12/harness/seed3b.sh) (roles, grants and probe, with the load done by the attacker role). Victim
   summary: [`victimsum.py`](logs/R12/harness/victimsum.py).
6. The dumps were scanned on `pc82`, not on a controller. TBA-1's scans overlapped only its own restart window, and that
   run's victim view is invalid anyway. TBA-2's scans ran after the run.
7. User linger for `jason92` was already enabled; it was left as found.
