Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Every memtable flush of a table with an SAI index builds an off-heap `RowMapping` trie with one full
primary key per flushed row (`index/sai/disk/RowMapping.java:75`), charged to no budget and grown by whole-buffer
doubling. With long clustering keys and two overlapping flush writers, the live direct memory reaches
2 × 2^⌈log2(≈ 0.57 · heap/12)⌉ + ≈ 44 MiB, which exceeds an explicit `MaxDirectMemorySize` of about heap/4 or less
(`OutOfMemoryError: Direct buffer memory` in the flush thread).

**Condition assessed:** the verdict condition (8 GiB heap / 1 GiB direct, 1,000-character clustering keys, one SAI index on
an `int` column, every capacity constraint at its default); also 4 GiB / 512 MiB and 15,872 / 2,048 MiB (same shape).

**Label: `client-triggerable given an explicit MaxDirectMemorySize ≲ heap/4 · data role; replicas of the written keys (steerable by key), repeatable on every node with such a limit`**

Reach: **given an operator budget choice** (a direct-memory limit set by hand below what `cassandra-env.sh` pairs with the
heap). Lowest privilege: **data role** (MODIFY on an admin-made SAI-indexed table with a `text`/`blob` clustering column).

## Condition and how common

An operator-set direct limit of about heap/4 or less. **Occasional**: `cassandra-env.sh` documents the variable, and
operators who size memory by hand (containers, many instances per host) may set it; nothing ships it that low. No data on
prevalence. The client cannot see or change the limit (it is not in any table a role can read; `system_views.settings`
lists `cassandra.yaml` settings, not JVM flags).

## Blast radius

- **Which node:** every replica of the written partitions flushes its own memtable and builds its own RowMapping, so the
  attacker steers the load to chosen replica sets by partition key (token ownership is readable by any logged-in role,
  `service/ClientState.java:77-85`) — or to all nodes by spreading keys.
- **Repeatable across nodes:** yes, on every node that has the low limit (usually all nodes share one config): with RF 3
  and spread keys, the replicas of a range can fail together.
- **What happens:** `OutOfMemoryError: Direct buffer memory` in the flush thread; `JVMStabilityInspector` turns it into a
  process exit (case §2.1). The data stays in the commit log, so a restart replays and re-flushes it (whether replay fails
  again was not tested).
- **Other tenants:** before the OOM, all writes on the node slow (writes block at the memtable pool limit while two long
  flushes run: case §3.0 A1); after it, unavailability / timeouts for the dead replicas' ranges at their CL.

## Operator visibility

Before: `system.log` `Writing Memtable-t@… (N ops …)` / `Completed flushing` lines with slow flushes; the
`java.nio:type=BufferPool,name=direct` pool climbing in 128/256/512 MiB steps; write timeouts. No guardrail warns about
1,000-B clustering values (warnings only for batches > 5 KiB). Attribution: the table owner/role is known from the schema;
per-statement attribution needs the audit log (ships off) or `nodetool clientstats`.

## 3-b confirm

Feasible (one node, the stage-2 harness with authentication on: admin-made `u13.t` + index, attacker role with `MODIFY`
only, victim role writing small rows to another table and recording its latency/success), but **low priority**: no step
needs more than `MODIFY` and no guardrail on the path applies to ordinary roles, so the result is predictable; the
deciding question is the operator's direct limit, which a confirm run cannot settle.

## Reason

All client steps — writing long clustering keys at a sustained rate into an SAI-indexed table — need only `MODIFY` on a
common table shape (`ModificationStatement.java:249`), pass every default limit, and the RowMapping is built for any SAI
table regardless of the indexed column. The step a client cannot take is the budget: the OOM was reached only with
`MaxDirectMemorySize` set explicitly to heap/4 or less, and every `cassandra-env.sh` pairing survived. Hence
**client-triggerable given an explicit low direct limit, at data role**. Larger multiplicity (several SAI tables or data
directories flushing together) could lower the needed ratio but was not tried, so it is not claimed.
