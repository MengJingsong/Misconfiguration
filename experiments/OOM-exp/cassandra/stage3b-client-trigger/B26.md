# B26 — stage 3-b client trigger check (2026-11-24)

**Case file:** [`../cases/profileload-capacity--local-read-time-sampler-cql-strings/profileload-capacity--local-read-time-sampler-cql-strings.md`](../cases/profileload-capacity--local-read-time-sampler-cql-strings/profileload-capacity--local-read-time-sampler-cql-strings.md)
· **Stage 3-a:** [`../stage3-jira-check/B26.md`](../stage3-jira-check/B26.md).
Analysis only (no node run), by a fresh session that did not design or verify the case. Code references are to the pinned
5.0.9 tree `systems/cassandra/source/`, paths below `src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** While the `LOCAL_READ_TIME` sampler of a table is enabled, every local read of that table renders its whole
command with `command.toCQLString()` and offers the string to a `MaxSampler` that keeps the 256 slowest
(`db/ReadExecutionController.java:134`, `:210-211`, `:236-243`; `metrics/MaxSampler.java:40-49`, `:66-75`). A
single-partition read with a clustering `IN` list renders every value (`db/filter/ClusteringIndexNamesFilter.java:166-197`).
A blob renders as `0x` + hex (`serializers/BytesSerializer.java:64-67`), so an 8 MB request becomes a 16.0 MB string, one
16 MiB G1 humongous region per kept sample. The cap counts strings, not bytes, and `finishSampling` leaves 244 of 256 strings
in the queue until the next session on that table (`MaxSampler.java:52-63`). Verified: heap OOM 3/3 at 2 GiB about 7–9 s
into one default `nodetool profileload b26 t1` (108–110 kept strings, 87 % of the dump); M (no session) 0/3, I (samples cut
to 1,024 characters) 0/3; all-tables 60 s sessions OOM at 15,872 MiB (2 tables) and 31,744 MiB (4 tables).

**Condition assessed:** T-2G (build A, 2 GiB heap, every constraint at its default): a client sends prepared
`SELECT v FROM b26.t1 WHERE pk = ? AND ck IN ?` with 2,000 × 4,000-byte blobs (S16, ≈ 8.01 MB), CL ONE, c = 4, closed
loop; at client second 10 the operator runs `nodetool profileload b26 t1` (defaults: `-s 256`, `-k 10`, all samplers, 10 s).

**Label: `client-triggerable given an operator-run profileload/toppartitions session that covers a table the attacker can read (occasional; continuous under a scheduled -i job) · data role (SELECT only, as run); login role, no grants, given an all-tables session (system_schema/system_traces tables, code reading); the profiled node only, one 10 s session at 2 GiB`**

Reach: **given an outside condition.** The trigger, enabling the sampler, is admin only. A sampler is disabled until
`beginSampling` (`metrics/Sampler.java:109-113`, `:121-124`); `forCommand` records a start time only while it is enabled
(`ReadExecutionController.java:134`), and without it `close()` never renders (`:210-211`). The only callers are JMX
operations: `ColumnFamilyStoreMBean.beginLocalSampling` (`db/ColumnFamilyStore.java:2055-2059`),
`StorageServiceMBean.samplePartitions` (`service/StorageService.java:6533-6566`) and `startSamplingPartitions`
(`:6569-6593` → `metrics/SamplingManager.java:107-122`, `:194-268`), used by `nodetool profileload` / `toppartitions`
(`tools/NodeProbe.java:567-586`; `tools/nodetool/TopPartitions.java` is an empty subclass of `ProfileLoad`). 5.0.9 has no CQL
path to them (as B25's grep: nothing under `cql3/`, `transport/`, `auth/` or `db/virtual/` references a sampler). As run, the
label would be `not client-triggerable (nodetool profileload)`. The client supplies everything else: the large-`IN` reads,
which the sampler keeps preferentially because the render time is part of the measured time (`addSample` takes
`clock.now()` **after** `toCQLString()`, `ReadExecutionController.java:238-239`), so the attacker's renders are by
construction the "slowest reads" an operator is looking for. Unlike B25, **one** default session on one table is enough at
2 GiB (B25 needed ≈ 7 distinct tables profiled one after another).

Lowest privilege:
- **Data role, SELECT only (as run).** The read needs `SELECT` on the table (`cql3/statements/SelectStatement.java:252`)
  and nothing else. No data is needed: the render covers the `IN` values whether or not rows exist, so MODIFY is not needed
  (T's 10 rows per partition only made the read return something). Any table with a clustering column works; blob and text
  give ≈ 2× expansion (text doubles every `'`, `serializers/AbstractTextSerializer.java:80-83`, rendered inside quotes),
  other types less or more (an `int` renders up to 11 characters from 8 request bytes). Clustering values have no length
  check on the read path (only the partition key is checked, `cql3/Validation.java:53`); the `IN` guardrail ships off
  (`conf/cassandra.yaml:2104-2105`).
- **Login role, no grants, given an all-tables session** (code reading, unverified). `nodetool profileload` with no
  arguments, or a scheduled job with no keyspace, samples `ColumnFamilyStore.all()` (`tools/nodetool/ProfileLoad.java:82-104`,
  `metrics/SamplingManager.java:80-94`; `<ks> *` samples only that keyspace), which iterates `Schema.getKeyspaces()` = distributed **and local** keyspaces
  (`schema/Schema.java:350-356`, `db/ColumnFamilyStore.java:2584-2592`). Every authenticated role may SELECT the
  `system_schema` tables and `system_traces.events`/`sessions` without a grant (`service/ClientState.java:77-93`,
  `:461-464`). Ten `system_schema` tables have a text clustering column (`schema/SchemaKeyspace.java:131`, `:145`, `:159`,
  `:171`, `:181`, `:218`, `:229`, `:239`, `:253`, `:267`), e.g. `SELECT * FROM system_schema.tables WHERE keyspace_name = ?
  AND table_name IN ?` with 2,000 values of 4,000 `'` characters renders to ≈ 16 MB, the S16 unit. These reads are local
  (`LocalStrategy`) and take the same `executeLocally` path with a controller (`service/StorageProxy.java:2208-2212`).
  They also spread the kept strings over up to ≈ 13 per-table queues, the multiplier the upward search used.
- **Pre-auth:** no. Every step is a CQL SELECT executed after login. **Default exposure:** `AllowAllAuthenticator` /
  `AllowAllAuthorizer` (`conf/cassandra.yaml:198`, `:217`): on a stock node anyone who reaches 9042 can do the client part.
  The operator part still needs JMX.

## Condition and how common

An operator runs `nodetool profileload` (or the deprecated `toppartitions`) with its defaults, on the node, covering a table
the attacker reads, while the attacker's reads run. One 10 s session suffices at 2 GiB (OOM 7–9 s in). Forms:

- **Per-table session on the attacker's (readable) table** — as run. Operators profile a table when it looks hot or slow,
  and the attacker's 8 MB reads make it look exactly that. **Occasional.**
- **All-tables session** (`nodetool profileload` with no arguments): the simplest form of the command, and it also samples
  `system_schema`, so a login role with no grants is enough (code reading). **Occasional.**
- **Scheduled job** (`profileload -i <interval>`, 5.0's recurring sampling, `SamplingManager.java:107-122`, `:225-268`): it
  re-begins every interval, so the sampler is enabled almost continuously; where an operator has scheduled one, the
  condition is **always met** and the attacker chooses the time. Each `beginSampling` replaces the queue, so holdings do
  not stack across windows (they need not: one window is enough at 2 GiB). Each window's end also writes the top-10
  results to `system.log` through `logger.info(formatResult(rb))` (`SamplingManager.java:255`): with the attacker's
  strings that is a ≈ 160–300 MB message built on the server heap (code reading, untested).

Heap size: a single-table default 10 s session did not OOM at 4 GiB or 8 GiB (3/3 each) because the window closed first,
but left 85 % of a 4 GiB heap (≈ 213 strings) and 5.4–6.0 GiB of 8 GiB held after the session, with reads 30–50 % slower.
OOM at 15,872 / 31,744 MiB needed a 60 s all-tables window and 2 / 4 tables read. A login role spreading reads over the
≈ 13 readable system tables raises the per-session ceiling, but the kept-string rate (≈ 25–45 sampled reads/s in stage 2)
is what limits a 10 s window, so at default duration the endpoint is ≈ 2 GiB-class nodes; larger heaps need a longer or
scheduled window (rarer).

## Blast radius

- **Which node:** only the node whose samplers the operator enables (nodetool talks to one node's JMX; scheduled jobs are
  per node). On that node the strings come from reads it executes locally. Data role on an RF 3 keyspace: the attacker
  chooses the partition key, so it steers to that key's replicas; CL ALL makes each replica run a local read (data or
  digest, both through the controller), so whichever replica is profiled keeps strings. Login role on `system_schema`
  (`LocalStrategy`): the node the attacker connects to, which it chooses.
- **Repeatable:** not at will; each OOM needs another session. Scheduled jobs are held in memory
  (`SamplingManager.activeSamplingTasks`) and are gone after the restart, so there is no crash loop. An operator who
  profiles every node in turn (`nodetool -h` over the ring, or the same scheduled job on each node) takes each one down.
- **Other tenants:** before the OOM the node is GC-bound (38–49 full GCs in ≈ 8 s at 2 GiB) and reads fall to about half;
  then `kill -9`. Requests it coordinates fail, its replicas are missing until restart, hints accumulate for it. Without
  OOM (larger heaps) 244 strings per table stay held until the next session on that table or a restart, leaving the node
  with a fraction of its heap and slower for every tenant.

## Operator visibility

High, because the operator is running the trigger, but only after the fact. The slow-query log stays idle (reads ≪ 500 ms;
stage 2 saw 0 slow-operation lines) and no guardrail warns (`IN` guardrail off). If the session returns, its
`LOCAL_READ_TIME` top-10 is the attacker's own query text (table, key, the `IN` list), but the shipped 128 MiB nodetool client
itself fails with an OOM deserializing 16–30 MB samples (case §3.2 item 2), so the operator sees an error instead. On an OOM
the dump shows ≈ 87 % of the heap as strings under `TableMetrics.topLocalReadQueryTime`; `system_views.clients` names the role
per connection when authentication is on. The audit log ships off.

## 3-b confirm

**Worthwhile (low cost, informative), as a privilege test.** The operator step decides reach, as for C7 and B25, so a
confirm cannot widen the condition; but this case's privilege label rests partly on code reading. Proposed arm on stage 2's
node (`pc91`, 2 GiB, all defaults, `PasswordAuthenticator` + `CassandraAuthorizer`):
1. **Data role, SELECT only:** an admin creates `b26.t1` (no rows); the attacker role holds only `SELECT ON b26.t1`, runs the
   S16 reads at c = 4; the admin runs `nodetool profileload b26 t1` at client second 10. Expected heap OOM as T (tests that
   MODIFY and stored rows are not needed).
2. **Login role, no grants:** the attacker role has `LOGIN` only and reads `system_schema.tables` with 2,000 × 4,000-`'`
   text `IN` values (≈ 8 MB request, ≈ 16 MB rendered); the admin runs `nodetool profileload` with **no arguments**. This
   tests the lower privilege and the all-tables form in one arm.
A victim role reading its own table on the same node measures success rate and latency. Watch for U7's effect
(roles/permissions cache reload timeouts under the GC spiral, `conf/cassandra.yaml:300`, `:327`); it cannot release strings
already held by the sampler.

## Reason

The heap is exhausted by rendered query strings of the attacker's own reads, kept by a sampler whose cap counts strings, not
bytes, and that keeps them after the session. The attacker supplies the size (an 8 MB clustering-`IN` read inside the 16 MiB
frame, ≈ 2× on render) and, because render time is part of the measured time, wins the "slowest reads" queue by construction.
That needs only `SELECT` on a table with a clustering column (`SelectStatement.java:252`), or, in an all-tables session, no
grant at all (the always-readable `system_schema` tables, `ClientState.java:77-93`, `:461-464`). But nothing is rendered or
kept unless an operator enables the sampler over JMX (`ReadExecutionController.java:134`, `Sampler.java:109-113`), and 5.0.9
has no CQL path to it. One default 10 s session is enough at 2 GiB. Hence **client-triggerable given an operator-run
profileload/toppartitions session (occasional; continuous under a scheduled job), at data role as run and login role by code
reading, on the profiled node only**.
