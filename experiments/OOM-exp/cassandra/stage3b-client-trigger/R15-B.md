# R15-B — stage 3-b client trigger check, R15 condition B (2026-11-24)

**Case:** [`ErrorCollector_errorMsgs--humongous-request-during-gc-thrash`](../cases/ErrorCollector_errorMsgs--humongous-request-during-gc-thrash/ErrorCollector_errorMsgs--humongous-request-during-gc-thrash.md),
**condition B only** (true positive, `verified-OOM · deployment`, unprotected accumulation). Condition A is a retry and is
covered by [R20](R20.md). Stage 3-a: not run yet (the case file's own JIRA check: `new` for condition B). Analysis only (no
node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/`.

**Mechanism.** A PREPARE of `SELECT v FROM r15.t WHERE k IN (?,?,…,?)` with 8,388,585 markers fits one 16 MiB frame. The
ANTLR parser buffers ≈ 16.8 M `CommonToken`s, their list arrays and ≈ 8.4 M `AbstractMarker$Raw` (≈ 1.3–1.5 GB per request)
before the 65,535-marker check, which runs only after `parseAndPrepare`. Three such PREPAREs from one client (0.94 of the
per-IP in-flight limit) OOM a 2 GiB heap in ≤ 9 s (3/3). Six OOM 4 GiB and twelve OOM 8 GiB (1/1 each).

**Label: `client-triggerable · login role, no grants; coordinator, repeatable on every node`**

## Threat-model walk of the verified test arm (TB2-1..3; TB4-1, TB8-1)

| Step | As run in stage 2 | Client-reachable? | Privilege / why (code) |
|---|---|---|---|
| Schema / data | `r15.t` existed | **not needed** | The OOM is in `parseStatement` (`cql3/QueryProcessor.java:443`), before `raw.prepare(clientState)` resolves the keyspace and table (`:458`). The OOME stacks are in `Cql_Parser.newBindVariables`, `singleColumnInValues` and `BufferedTokenStream.fetch`. A PREPARE naming a table that does not exist would parse identically, then fail. |
| Connection | protocol v4, STARTUP, then PREPARE | yes, **after login** | The PREPARE body (a 16 MiB string) is decoded before the connection-stage check, but decode alone holds only the wire string. The parse runs in `PrepareMessage.execute` → `queryHandler.prepare` (`transport/messages/PrepareMessage.java:132`). That runs only after `connection.validateNewMessage` (`transport/Dispatcher.java:412`), which refuses everything but AUTH_RESPONSE while `AUTHENTICATING` (`transport/ServerConnection.java:61-83`). So with `PasswordAuthenticator` the client must complete login. Same split as R20 and the confirmed R13. |
| Request | three 16,777,215-byte PREPARE frames in parallel, one source IP | yes, **no grant needed** | `QueryProcessor.prepare` (`:728`) → `parseAndPrepare` (`:754`) → `parseStatement` (`:443`). No `authorize` call exists on the PREPARE path. Permissions are checked only at EXECUTE/QUERY (`QueryProcessor.java:271`). The marker count is checked after the parse and prepare (`:758`, bound `FBUtilities.MAX_UNSIGNED_SHORT`). No guardrail bounds query length or marker count. |
| Admission | in-flight charge 3 × 16.8 MB = 50.3 MB = 0.94 of the per-IP limit (heap/40), nothing paused | yes, one source address | The per-IP limit scales with the heap, so one address can always send ≈ heap/40 / 16.8 MB such requests. **Condition:** none.

**Possible authorizer effect:** none expected. The parse consults no `ClientState` permission or roles cache, unlike U7's
per-cell guardrail path, and the OOM comes within 9 s.

## Blast radius

- **Which node:** the coordinator the attacker connects to; the parse runs on its request threads.
- **Repeatable:** yes. Every node, from one host and one login (the same credentials work cluster-wide), ≈ 50 MB sent per
  node at 2 GiB. Nothing persists, so a restarted node can be killed again at once.
- **Other tenants:** the node dies within seconds via heap OOM and the shipped `kill -9`. Its client connections drop and
  its replica ranges lose a replica until restart. With every node attacked the cluster is down.

## Operator visibility

None before the failure. The PREPARE never completes, so no `Too many markers` error is returned or logged. The heap dump
shows `CommonToken`/`AbstractMarker$Raw` (86–89 % of the dump). With audit logging on (off by default) the login of the role
is recorded. Whether the in-progress PREPARE is recorded is doubtful, since it neither succeeds nor fails before the kill.
Revoking the role's `LOGIN` stops it.

## 3-b confirm (not run): worth it?

**Worth it, cheap.** Like R20 (confirmed at login role, no grants), it would check the "no grant needed" claim end to end.

**Needs:**
- one node at 2 GiB heap, `PasswordAuthenticator` + `CassandraAuthorizer`;
- an attacker role with `LOGIN = true` and **no grants**, with a privilege check that it cannot SELECT anything;
- the case's `client.py` sending 3 marker PREPAREs (the keyspace/table may be absent or unreadable to the role);
- a victim role on its own keyspace.

One run is expected to settle it (OOM ≤ 9 s in 3/3).

## Reason

The verified arm is three large PREPAREs from one address. They need no schema, no data and no permission. The parse that
allocates per token and per marker runs before any permission check and before the late count check. The only thing needed
is a logged-in connection, because the connection-stage check precedes execution. Lowest privilege: **login role, no
grants**. Reach: **alone**. Blast radius: the connected coordinator, repeatable on every node.

### Validity and deviations

- **Valid run, one only.** It followed the `TB2` design (base build, shipped capacities, 2 GiB, N = 3, 180-s hold, dump
  analysis then delete) with authentication on. It reached the endpoint in the same time and frame as stage 2, so no
  further runs were needed to tell a fluke.
- **Schema difference (deliberate).** Stage 2 had created `r15.t`; here the keyspace `r15` did not exist, and the
  attacker could not have created it (no CREATE). The parse, and the OOM, are the same.
- **Harness** (copied to [`logs/R15-B/harness/`](logs/R15-B/harness/)): R20's 3-b `client.py`, `run.sh` and
  `confirm.sh` with the work dir `/mydata/s4/3b-R15-B`, scope unit `3bR15B-<run>`, own credentials, disk guard 50 GiB,
  a `--prefix` option for the M payload's table, a PREPARE/EXECUTE helper and an R15-B shakedown. The other scripts
  (`monitor.sh`, `Jmx.java`, `summarize.py`, `trigsum.py`, `stw.py`, `threadcount.py`, `hprof-*.py`) are the case's own, unchanged.
- **Not run:** repeating the attack on other nodes (single node); audit logging on.

### Label

**`client-triggerable · login role, no grants; coordinator, repeatable on every node` (confirmed).** A LOGIN role holding
no permission, naming a keyspace that does not exist, killed the 2 GiB coordinator with three 16-MiB PREPAREs from one
address in 6.7 s (heap OOM in the parse, token/marker classes 86.3 % of the dump). Authentication is required: pre-auth
PREPAREs are refused before the parse. The reach is alone: no schema, fault or operator step. The victim role on the same
node saw 99.9 % → 59.2 % success (requests stretched to 0.5 s) → 0 %, then the node gone. The confirm covers one
coordinator; repetition across nodes is not tested.
