# R15-B — stage 3-b client trigger check, R15 condition B (2026-11-24)

**Case:** [`ErrorCollector_errorMsgs--humongous-request-during-gc-thrash`](../cases/ErrorCollector_errorMsgs--humongous-request-during-gc-thrash/ErrorCollector_errorMsgs--humongous-request-during-gc-thrash.md),
**condition B only** (true positive, `verified-OOM · deployment`, unprotected accumulation). Condition A is a retry and is
covered by [R20](R20.md). Stage 3-a: not run yet (the case file's own JIRA check: `new` for condition B). Analysis only (no
node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/`.

**Mechanism.** A PREPARE of `SELECT v FROM r15.t WHERE k IN (?,?,…,?)` with 8,388,585 markers fits one 16 MiB frame. The
ANTLR parser buffers ≈ 16.8 M `CommonToken`s, their list arrays and ≈ 8.4 M `AbstractMarker$Raw` (≈ 1.3–1.5 GB per request)
before the 65,535-marker check, which runs only after `parseAndPrepare`. Three such PREPAREs from one client (0.94 of the
per-IP in-flight limit) OOM a 2 GiB heap in ≤ 9 s (3/3). Six OOM 4 GiB and twelve OOM 8 GiB (1/1 each).

**Label: `client-triggerable · login role, no grants; coordinator, repeatable on every node`**

**Condition:** none.

**Possible authorizer effect:** none expected. The parse consults no `ClientState` permission or roles cache, unlike U7's
per-cell guardrail path, and the OOM comes within 9 s.

## Blast radius

- **Which node:** the coordinator the attacker connects to; the parse runs on its request threads.
- **Repeatable:** yes. Every node, from one host and one login (the same credentials work cluster-wide), ≈ 50 MB sent per
  node at 2 GiB. Nothing persists, so a restarted node can be killed again at once.
- **Other tenants:** the node dies within seconds via heap OOM and the shipped `kill -9`. Its client connections drop and
  its replica ranges lose a replica until restart. With every node attacked the cluster is down.

## Operator visibility

None before the failure. The PREPARE never completes, so no `Too many markers` error is returned or logged. The heap dump
shows `CommonToken`/`AbstractMarker$Raw` (86–89 % of the dump). With audit logging on (off by default) the login of the role
is recorded. Whether the in-progress PREPARE is recorded is doubtful, since it neither succeeds nor fails before the kill.
Revoking the role's `LOGIN` stops it.

## 3-b confirm (not run): worth it?

**Worth it, cheap.** Like R20 (confirmed at login role, no grants), it would check the "no grant needed" claim end to end.

**Needs:**
- one node at 2 GiB heap, `PasswordAuthenticator` + `CassandraAuthorizer`;
- an attacker role with `LOGIN = true` and **no grants**, with a privilege check that it cannot SELECT anything;
- the case's `client.py` sending 3 marker PREPAREs (the keyspace/table may be absent or unreadable to the role);
- a victim role on its own keyspace.

One run is expected to settle it (OOM ≤ 9 s in 3/3).

## Reason

The verified arm is three large PREPAREs from one address. They need no schema, no data and no permission. The parse that
allocates per token and per marker runs before any permission check and before the late count check. The only thing needed
is a logged-in connection, because the connection-stage check precedes execution. Lowest privilege: **login role, no
grants**. Reach: **alone**. Blast radius: the connected coordinator, repeatable on every node.
