# C8 — stage 3-b client trigger check (2026-11-24)

**Case file:** [`../cases/segment_write_buffer_size--fixed-1GiB-index-build-small-heap/segment_write_buffer_size--fixed-1GiB-index-build-small-heap.md`](../cases/segment_write_buffer_size--fixed-1GiB-index-build-small-heap/segment_write_buffer_size--fixed-1GiB-index-build-small-heap.md)
· **Stage 3-a:** not filed yet.
Analysis only (no node run). Code references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below
`src/java/org/apache/cassandra/` unless a file under `conf/` is named.

**Mechanism.** Every SAI build from sstables (the initial build after `CREATE INDEX`, `rebuild_index`, every compaction of
an SAI-indexed table) buffers segments on heap under one global soft limit, `segment_write_buffer_size`. Its default is a
fixed 1,024 MiB, whatever the heap (`index/sai/disk/v1/V1OnDiskFormat.java:174-181`). On a 1.5 GiB heap the builder's
≈ 1 GiB, the memtable pool under a write load and the key cache that the build fills → Java heap OOM.

**Condition assessed:** BW at 1,536 MiB (`verified-OOM · deployment`; the heap `cassandra-env.sh` picks on a 3 GiB machine):
`CREATE INDEX … USING 'sai'` on a 2,000,000-row table with distinct 32-character values, while an unthrottled
`cassandra-stress` write runs into another table → heap OOM 3/3, during the initial build. At 2 GiB: 0/3, 93 % post-GC.

**Label: `client-triggerable · DDL role; every replica of the attacker's table at once, nodes with heap ≤ 1.5 GiB`**

Reach: **alone** on a node of the verified size, with one substitution flagged below: flushes and compaction by the server
instead of the harness's `nodetool flush/compact`. Lowest privilege: **DDL role**, because `CREATE INDEX` needs ALTER on the
table, which the attacker has as the table's creator. **Also (untested):** `client-triggerable given an admin table with an
SAI index on a high-cardinality column · data role`. Compaction of SAI-indexed sstables uses the same 1 GiB builder, and the
data role supplies the distinct terms and the concurrent writes.

## Condition and how common

None at DDL role, beyond the node size: the case holds on nodes whose resolved heap is ≤ 1.5 GiB (≤ 3 GiB RAM: small
VMs, containers, edge or test-like production nodes). Bigger nodes are not reached at the verified budget. That is a fact
about the deployment, not an event, so it is put in the label rather than as a condition. At data role: an admin table with
an SAI index on a high-cardinality text column (a common 5.0 schema), where the attacker's inserts both feed and trigger
compactions. This is probable and untested (the compaction path was not run in stage 2).

## Blast radius

- **Which node:** every replica of the attacker's table. The schema change starts the initial build on every replica at
  once, and with RF = node count all small-heap nodes build, and die, together.
- **Repeatable:** yes. After restart an unfinished SAI index is built again. The build alone did not OOM (0/3), so the
  attacker repeats the concurrent writes, or drops and recreates the index.
- **Other tenants:** ≈ 2–3 min of 99–100 % GC stop-the-world before the OOM (timeouts for every tenant on the node), then
  `kill -9`; replica sets lose members.

## Operator visibility

Before: `CREATE INDEX … USING 'sai'` schema-change lines; INFO "Starting a compaction index build. Global segment memory
usage: …" (`V1OnDiskFormat.java:177`); SAI gauge `SegmentBufferSpaceUsedBytes` near the limit. During: GC warnings,
writers blocked on memtable allocation. After: `OutOfMemoryError: Java heap space` with a dump dominated by
`DeltaPackedLongValues$Builder` / `long[]`. The index's table owner identifies the role.

## 3-b confirm

**Worthwhile**, to test the flush and compaction substitution. It needs pc96 at heap 1,536 / direct 768 with
`PasswordAuthenticator` + `CassandraAuthorizer`, and an attacker role with `CREATE ON ALL KEYSPACES` only. The attacker
creates its keyspace and tables, inserts 2 M (or more) distinct 32-character values by CQL (no `nodetool flush/compact`,
no seed copy), then runs stress writes into its second table and, 60 s later, `CREATE INDEX … USING 'sai'`. A victim
role on its own keyspace measures success and latency. An optional data-role arm: the admin makes an SAI-indexed table,
and a MODIFY-only role writes until a compaction builds a ≥ 440 k-term segment under write load.

## Reason

The schema, the 2 M distinct-term rows, the concurrent write load and the `CREATE INDEX` that starts the build are all
CQL steps for a role that owns its table: ALTER comes with creation, and no secondary-index guardrail is set by default.
The only admin steps in the verified arm prepared the sstable layout (`nodetool flush/compact`, a seed copy). The server's
own flushes and STCS compactions, plus `CREATE INDEX`'s own flush, give comparable large sstables, but this was not tested.
The 1 GiB default is fixed, so the reach is limited to nodes whose resolved heap is ≤ 1.5 GiB. Hence **client-triggerable
alone at DDL role on such nodes**, with all replicas building at once. A data role is probable through compaction of an
admin's SAI-indexed table, untested.
