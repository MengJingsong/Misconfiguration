# U3 — stage 3-b client trigger check (2026-11-24)

**Case:** [`items_per_collection--whole-collection-read-materialization`](../cases/items_per_collection--whole-collection-read-materialization/items_per_collection--whole-collection-read-materialization.md)
(true positive, `verified-OOM · deployment`, unprotected configuration + unprotected accumulation). Stage 3-a: not run yet
(the case file's own JIRA check: `new`; whole-collection reads are `documented`). Analysis only (no node run). Code
references are to the pinned 5.0.9 tree `systems/cassandra/source/`, paths below `src/java/org/apache/cassandra/` unless a
file under `conf/` is named.

**Mechanism.** Appends (`UPDATE … SET v = v + ?`) grow a non-frozen collection without limit, because the collection
guardrails are off and count only the written fragment. Every read then deserializes the whole collection into one row
(≈ 150 B per item) on the replica, and again on the coordinator. Nothing bounds the bytes of concurrent reads. 16 concurrent
reads of 10⁶-item sets OOM a 2 GiB heap in 7–14 s.

**Label: `client-triggerable · data role; the replica serving the read (steerable by key) + the coordinator, repeatable on every replica set; OOM at heaps ≤ 8 GiB, GC service loss at 15.5 GiB`**

Reach: **alone**. Lowest privilege: **data role**: `MODIFY` + `SELECT` on any admin-made table with a non-frozen
collection column (`set`/`list`/`map`). A `DDL role` can create such a table itself. A role with `SELECT` only needs
someone else's partition already holding ≳ 10⁶ items per collection, which is rare.

**Condition:** none.

**Possible authorizer effect (not expected):** U7's confirm found per-cell roles-cache reloads timing out under
`CassandraAuthorizer`. Here the reads have no per-cell `ClientState` check: authorization is once per request, at
`QueryProcessor.java:271`. The appends do call `Guardrail.enabled` → `isOrdinaryUser` per cell
(`Sets.java:407` → `UpdateParameters.addCell`), but that happens on a healthy node before the attack. New retries during the
thrash may fail their own permission reload, but the 16 reads already building rows are unaffected. So the OOM is expected
to stand with authorization on.

## Blast radius

- **Which node:** the **replica that executes the data read** builds the row (`StorageProxy.LocalReadRunnable`, dispatched at
  `service/reads/AbstractReadExecutor.java:165`). In a multi-node cluster the coordinator deserializes the response into a
  row again (≈ 150 B per item, stage 4). So both the chosen key's data-read replica and the connected coordinator carry the
  load. Only the single-node case (coordinator = replica) was tested. The attacker picks the replica set by the partition
  key, and the dynamic snitch moves later data reads to the next replica.
- **Repeatable:** yes. The grown collections stay on disk, so after a restart the same reads kill the node again at once.
  One small set of partitions per replica set covers the cluster, and the data costs only ≈ 4 MB on disk per 10⁶ items.
- **Other tenants:** the node is killed (2–8 GiB) or sits in ≥ 90 % STW (15.5 GiB). Every request through it times out,
  and its replica ranges lose a replica. Killing all replicas of a range in turn gives `Unavailable`/timeouts to every tenant
  with keys there.

## Operator visibility

Before: nothing at defaults. The collection guardrail warn threshold is −1, the read thresholds are off, and the partitions
are small on disk (4 B per item, ≈ 4–16 MB), so they do not show as large partitions. During: GC pause warnings and
ReadStage pending in `tpstats`. The heap dump attributes the rows to the table (millions of `ArrayCell`s). With audit/FQL
logging (off by default, `conf/cassandra.yaml:1893`) the role and its appends are attributable.

## 3-b confirm (not run): worth it?

Worth it, cheap. It would confirm the data role under `PasswordAuthenticator` + `CassandraAuthorizer`, which stage 2 never
had (it ran `AllowAllAuthenticator`, i.e. superuser), and rule out a U7-style authorizer effect.

**Needs:**
- one node, 2 GiB heap;
- an admin-made `set<int>` table with `GRANT SELECT, MODIFY` on that table only to the attacker role;
- the attacker grows 8 sets to 10⁶ items itself (80 appends, ≈ 1 min), then runs the case's 16-process reader for 180 s;
- a victim role on its own keyspace on the same node.

One run likely settles it (OOM 3/3 at 7–14 s in stage 2).

## Reason

Every step of the test arm is ordinary CQL from a role that may write and read one table with a collection column. The
schema shape is common, the data is built by accepted appends (the only collection guardrails are off and fragment-only),
and the reads are plain single-partition SELECTs at CL ONE. No fault, operator action or diagnostic aid is in the verified
arm. Lowest privilege: **data role**. Reach: **alone**. Blast radius: the data-read replica of the attacker's keys and the
coordinator, repeatable on every replica set; OOM at heaps ≤ 8 GiB, GC service loss at 15.5 GiB.

## 3-b confirm (ms0625, 2026-11-24)

Fresh OOM-agent session, owner-approved confirm runs (2026-11-24), 13:06–13:43 node time (America/Denver), node lock held
the whole time. **Result: confirmed.** With `PasswordAuthenticator` + `CassandraAuthorizer`, a non-superuser role holding
only `SELECT` + `MODIFY` on one admin-made `set<int>` table grew 8 sets to 10⁶ items itself, then its 16 readers drove the
2 GiB node to `java.lang.OutOfMemoryError: Java heap space` at **+37.4 s** (T-1, 1/1). The shipped `kill -9` killed it
after the heap dump. A victim role on its own keyspace got 2.7 % success during the attack and 0 % after. Two claim
tests also reached the OOM: a **SELECT-only** role reading the sets someone else grew (SO-1, +30.1 s), and the attacker
appending and reading in one node lifetime **without any flush/compact** (NF-1, +27.4 s). No authorizer effect of the
U7 kind appeared. Evidence: [`logs/U3/`](logs/U3/) (one folder per run, `harness/` with every script as run,
`dump-sha.txt`, `T-1/histo.txt`). Small logs stay on the node under `ms0625:/mydata/s4/3b-U3/runs/<run>/logs/`. The
dumps, data, golden copy and copied tree were deleted.

### Which code-reading claims held

- **Pre-auth cannot do it — held.** `probes.txt`: on an unauthenticated connection QUERY, PREPARE and OPTIONS (the attack's
  `SELECT`, and an append) are refused with `0x000A Unexpected message …, expecting SASL_RESPONSE`, and before STARTUP with
  `… expecting STARTUP or OPTIONS`. A wrong password gets `0x0100 Bad credentials`. cqlsh without credentials gets
  `AuthenticationFailed`.
- **MODIFY alone grows the set; the guardrails are off and do not stop a non-superuser — held.** 80 of 80 appends
  accepted as `attacker` (LOAD and NF-1), thresholds −1/null read back.
- **SELECT is the only privilege the reads need — held.** T-1 (`attacker`) and SO-1 (`selonly`, SELECT on that one table
  only) both reached the OOM. So, as the analysis said, a SELECT-only role also triggers it when someone else's
  partitions already hold ≳ 10⁶ items per collection.
- **flush + compact are not needed — held.** NF-1 read unflushed / auto-flushed fragments (4 SSTables + memtable), no
  nodetool, and reached the OOM sooner (+27.4 s).
- **Authorization is once per request; no U7-style roles-cache abort — held.** `auth-failures.txt` is empty in all three
  runs (no `Failed to authorize`, `Roles.java`, `CassandraAuthorizer.java` or `Unable to perform authorization` lines in
  `debug.log`), and no attacker read got `Unauthorized`. The retries during the thrash timed out instead.
- **Timed-out reads keep building and retries add to them — held.** 23 row-building threads in the T-1 dump against 16
  clients: the 16 first reads timed out at 5 s (`ReadTimeout`) and the retries were added while the abandoned builds went on.
  (`tpstats` could not be read during the thrash: nodetool timed out, so the 5 s samples are empty.)
- **The holder is the whole-collection row (≈ 150 B per item) — held** (≈ 162 B per item shallow, 14.6 rows, above).
- **"The replica of the chosen key + the coordinator"; "repeatable on every replica set"; "again at once after a
  restart" — not tested** (single node, coordinator = replica, no restart).
- **Operator visibility — as the analysis said.** No guardrail or threshold WARN before or during. `GCInspector` WARNs,
  then the OOM. The connections carry the authenticated role (`attacker` / `selonly`), so the role can be attributed
  (e.g. `system_views.clients`, audit log) and revoked.

### Deviations

1. Node `ms0625` (aarch64) instead of stage 2's `pc99` (x86_64); t_OOM is later than stage 2's 10–14 s (27–37 s), and
   the dump takes 164–280 s. So the daemon death by the shipped `kill -9` came after the 180 s window in all three runs.

   T2 runs. In SO-1 the `kill -9` came only during the harness's stop (+418 s). Until then the node was unreachable (victim 0 %).

   (n = 1 each), not repeats of T. No matched control or intervention under auth (stage 2 has them).
