# B17 — stage 3-b client trigger check (2026-11-23)

**Case:** [`cql-row-limit--in-order-by-limit-after-materialization`](../cases/cql-row-limit--in-order-by-limit-after-materialization/cql-row-limit--in-order-by-limit-after-materialization.md)
(true positive, `verified-OOM · deployment`). Stage 3-a: [`B17.md`](../stage3-jira-check/B17.md) (`new`). Analysis only (no node run).

**Mechanism.** For `IN` on the partition key plus `ORDER BY`, `getDataLimits` leaves the read's row limit at `NO_LIMIT`
(`cql3/statements/SelectStatement.java:886-895`) and paging is refused (`:537-539`), so every listed partition is
serialized whole into a replica `DataOutputBuffer` and copied into the coordinator `ResultSet` before `LIMIT 10`; one
query over four 256 MiB partitions OOMs a 2 GiB heap.

**Label: `client-triggerable · data role; replica(s) of the chosen keys and the coordinator, repeatable on every node`**

**Condition:** none.

## Blast radius

- **Which node:** the replica serving each listed partition (it serializes the whole partition) — steerable by choosing
  the keys — and the coordinator, which copies every partition into the `ResultSet`. Stage 2 had one node; RF > 1 is
  untested (the data replica per key holds the buffer, digest replicas do not).
- **Repeatable:** yes, by writing wide partitions on keys owned by each node and querying them; one query per node at
  2–4 GiB, a few concurrent at 8 GiB; above that the 5 s read timeout wins.
- **Other tenants:** replicas/coordinator die (heap OOM); requests needing them fail at their CL; clients on the
  coordinator lose their connections.

## Operator visibility

Large-partition warnings at compaction (`compaction_large_partition_warning_threshold` logs partitions > 100 MiB by
default), the 4 GiB write volume, and the `system.log` OOM; with read thresholds enabled (off by default) the query would
warn/fail per user. Attributable to the role with audit/FQL logging on.

## 3-b confirm

Worthwhile. At 2 GiB with `PasswordAuthenticator` + `CassandraAuthorizer`, a role with SELECT and MODIFY on `b17.t`
loads the 16 × 256 MiB partitions and sends the T query; a victim role runs a closed loop on another table.

## Reason

The verified arm is a legal, documented query shape (unpaged `IN` + `ORDER BY`) sent by a role with SELECT, over data the
role can write itself with MODIFY within every default limit; the bounds that could stop it (read-size thresholds,
`partition_keys_in_select`) ship off for every role. No operator condition, fault or diagnostic aid is involved. Lowest
privilege: data role. The replica of each chosen key and the coordinator die, and the attack repeats across nodes by
key choice.
