# row_cache_size + index_summary_capacity — convergence case

> **Run:** 2026-11-02/03, node `node0.jason92-323989.misconfiguration-pg0.cloudlab.umass.edu` (40 cores, 251 GiB, local disk `/dev/sda3` 63 GB), Ubuntu 22.04.2, kernel `5.15.0-198-generic`, OpenJDK 11.0.32.1, Ant 1.10.12. Same build as runs 1-3 (`~/cassandra-run1`, cassandra-5.0.9, unchanged, no rebuild). **First off-heap case in this folder** — unparks the off-heap group from runs 1-2.

> **Harness:** `~/oom-offheap-run4/oom-run.sh` + `~/oom-offheap-run4/isc-profile.yaml` (outside the repo, on the node, per the node safety rules — not committed; this case file links paths on the node, not in-repo copies). Full logs on the node at `~/oom-offheap-run4/logs/{baseline,R_alone,I_alone,converge}/`.

> **Outcome: OOM NOT reached.** All three arms (row-cache-alone, index-summary-alone, converged) completed without a kernel OOM-kill, a JVM `OutOfMemoryError`, or GC-pressure unresponsiveness. The combined arm's peak usage (938 MiB above idle baseline) came in well under the naive additive prediction from the two alone arms (1246 MiB) — the two caches' own enforcement (Caffeine eviction, periodic index-summary resize) kept operating under combined load instead of simply summing their overshoots. See §4 for the full diagnosis.

> **Superseded (2026-11-03) by [run 6](row_cache_size+index_summary_capacity--run6.md):** the same pair OOMed when the row cache was filled to its cap *before* the index-summary burst. This run used the reverse order (burst and flush first, then the row-cache fill) with a 1-minute resize, so the two peaks never coincided. Kept as the record of that schedule; not worth re-running unchanged.

## 1. Constraints and capacities

Both are off-heap/direct-memory config-type **true positives** from if-check-exp, surveyed in `cases/_constraint-groups.md`'s off-heap table and previously parked (run 2) for lack of an off-heap budget setup:

| | `row_cache_size` | `index_summary_capacity` |
|---|---|---|
| if-check-exp case | [`row_cache_size-create-serialized_size--autonomous`](../../../../if-check-exp/cassandra/stage3-ai-deep-read/cases/row_cache_size-create-serialized_size--autonomous.md) | [`index_summary_capacity-distributeRemainingSpace-extraSpaceRequired--autonomous`](../../../../if-check-exp/cassandra/stage3-ai-deep-read/cases/index_summary_capacity-distributeRemainingSpace-extraSpaceRequired--autonomous.md) |

| Capacity check | `SerializingCache.java:52` (`maximumWeight(capacity)`, Caffeine), capacity from `SerializingCacheProvider.java:33` | `IndexSummaryRedistribution.java:341` (`distributeRemainingSpace`, `extraSpaceRequired <= remainingSpace`) |
| What it caps | Off-heap native bytes of cached row partitions — `MemoryUtil.allocate` → JNA `Native.malloc`, read as `RssAnon` | Off-heap native bytes of BIG-format sstable index summaries — same `MemoryUtil.allocate` → JNA `Native.malloc` path |
| Default / how set | yaml `row_cache_size: 0MiB` (disabled); yaml `row_cache_class_name` defaults to `OHCProvider` — this case explicitly switches it to `org.apache.cassandra.cache.SerializingCacheProvider` (the legacy, `Native.malloc`-based implementation) so the bytes are the clean, well-characterized ones if-check-exp verified. Restart-only for the class, JMX-settable for the size. | yaml `index_summary_capacity:` (default empty → 5% of heap); `index_summary_resize_interval: 60m` default, set to `1m` here so a resize fires within the run's own window instead of 60 minutes later. |
| Capacity value this case | 550 MiB | 100 MiB (configured cap — see §2 for why the *effective* constraint on the shared budget is the much larger **raw, pre-resize** bytes, not this number) |

**Shared budget and node total: this is the key methodological finding of this run.** The task's own framing suggested `-XX:MaxDirectMemorySize` as the off-heap analog of `-Xmx`. **That is wrong for this pair of constraints and was corrected before any run was executed:**

- `-XX:MaxDirectMemorySize` only governs `java.nio.DirectByteBuffer`'s own accounting (`Bits.reserveMemory`, checked in the `DirectByteBuffer` constructor).
- Both `row_cache_size` (via `SerializingCache` → `Memory.allocate` → `MemoryUtil.allocate`) and `index_summary_capacity` (via `IndexSummary`/`IndexSummaryBuilder` → the same `Memory.allocate` → `MemoryUtil.allocate` path) allocate through **JNA's `Native.malloc`** — plain libc malloc — which **never touches `DirectByteBuffer`'s bookkeeping at all**. This is explicitly called out in both if-check-exp case files' own A2 sections ("plain libc malloc, so the JVM's NMT does not see it" / "It is plain libc malloc, so the JVM's NMT does not see it") and is why both stage-4 results measure `RssAnon` from `/proc/<pid>/status`, not any JVM-reported metric.
- Consequence: setting `-XX:MaxDirectMemorySize` to any value **has no effect whatsoever** on either constraint's actual ceiling. It was still set on the JVM command line in every arm of this run (visible in each arm's `jvm-args.txt`/startup log, e.g. `-XX:MaxDirectMemorySize=2000M`) purely to honor the task's instruction to try it first — but it is cosmetic here, not load-bearing.
- **The real budget used in this run is a cgroup v2 `memory.max`**, set via `systemd-run --user --scope -p MemoryMax=<N>M -p MemorySwapMax=0 --unit=<name> -- bin/cassandra -f`, wrapping the whole JVM process (heap + every off-heap/native allocation, mmap'd files, thread stacks — everything the kernel charges to that cgroup). This is independently verified to actually enforce a hard ceiling: a throwaway smoke test with `MemoryMax=500M` against a node whose idle baseline RSS is ~900 MiB (i.e., deliberately already over budget) produced a genuine kernel-level kill within ~25 s:
  ```
  [Mon Nov 2 23:33:19 2026] Memory cgroup out of memory: Killed process 120745 (java)
    total-vm:2365300kB, anon-rss:501028kB, file-rss:33092kB, shmem-rss:0kB, UID:20001 pgtables:1516kB oom_score_adj:0
  ```
  (full line in `~/oom-offheap-run4/logs/` is not kept — this was a pre-harness smoke test, not a numbered arm; the `dmesg` line itself is the record, reproduced above.)
- **Node total for this case:** cgroup `memory.max` = **2000 MiB**, same value used in every arm (baseline measurement, both alone arms, convergence arm) so arms are comparable. `-Xmx384M`/`-Xms384M` fixed throughout (small, deliberately not the thing under test).

**Stabilizer applied in every arm (not a studied constraint):** `memtable_heap_space` defaults to `null` → 1/4 of `-Xmx` (96 MiB at `-Xmx384M`), which is tiny enough that a sustained write burst triggers continuous ~30 MiB flushes and tiny compactions back-to-back, which (a) churns CPU/disk badly enough to make `cassandra-stress` writes/reads an order of magnitude slower under this cgroup's memory pressure than in runs 1-3's on-heap cases, and (b) is a third, unstudied on-heap variable that would confound the off-heap reading. Fixed to `memtable_heap_space: 220MiB` in every arm's yaml (see `configure_yaml()` in the harness) so flush frequency is reasonable and the measured growth is attributable to the two off-heap constraints under test.

## 2. Verification solution

### 2.1 Baseline

Idle readings (both constraints at tiny/off values, `-Xmx384M`, cgroup budget 2000 MiB, no load, ~8 s after "listening for CQL clients"), taken fresh in each arm (not reused from a single shared baseline, to catch any drift):

| Arm | `RssAnon` idle | `VmRSS` idle | cgroup `memory.current` idle |
|---|---|---|---|
| R_alone | 893,708 KB ≈ **872.8 MiB** | 1,073,204 KB ≈ 1048.0 MiB | 941,907,968 B ≈ 898.9 MiB |
| I_alone | 908,212 KB ≈ **886.9 MiB** | 1,087,800 KB ≈ 1062.3 MiB | 956,329,984 B ≈ 911.6 MiB |
| converge | 885,456 KB ≈ **864.7 MiB** | 1,065,088 KB ≈ 1040.1 MiB | 932,954,112 B ≈ 889.5 MiB |

Baseline `RssAnon` across arms is consistent to within ~22 MiB (≈2.5%): **b ≈ 875 MiB** (anon), used as the representative baseline for the arithmetic below. This baseline is almost entirely fixed JVM/Cassandra overhead (pre-touched 384 MiB heap, metaspace, Netty direct buffers, JNA libraries, thread stacks) — it is large relative to what a single off-heap cache can practically be grown to within a few minutes of `cassandra-stress`, which directly shapes the sizing choices below (see §4's discussion of why this makes a clean ≥30%-free-alone / clearly->100%-combined result hard to engineer here, unlike the on-heap cases in runs 1-2).

### 2.2 Sizing

**Row cache (`row_cache_size`) — straightforward, settles tightly at its configured cap.** `row_cache_class_name: SerializingCacheProvider`, `row_cache_size: 550MiB`, `keyspace1.standard1` written with 550,000 partitions (`-col size=FIXED(1024)`), then `ALTER TABLE ... WITH caching = {'rows_per_partition':'ALL'}` (cassandra-stress's own `write` auto-creates the table with default caching — keys only — so row caching must be turned on explicitly *after* the table exists, which is fine since caching params are read at query time, not baked into the sstable), then a single read pass over all 550,000 partitions to populate the cache. **Measured (R_alone arm): settles at exactly `size 550 MiB, capacity 550 MiB`** (`nodetool info`) — essentially zero overshoot, consistent with if-check-exp's own finding that the weigher-based cap tracks real native bytes tightly.

**Index summary (`index_summary_capacity`) — the resize-cadence trap, found empirically mid-run.** The configured cap only binds **at the moment a periodic resize runs** (if-check-exp's own stage-4 finding: "caps only on some paths — new sstables bypass it between runs"). A single continuous `cassandra-stress` write burst into a table with `min_index_interval=1` (so every partition gets its own full-level summary entry — the same trick if-check-exp's cluster tier used, via `isc-profile.yaml`'s `table_definition`) produces **raw, un-downsampled** summary bytes that grow the whole time writing is happening, and the 1-minute resize cadence cannot keep up with a multi-minute write burst: new sstables keep flushing at full level between resize ticks. Two earlier attempts in this run (not filed as separate cases, since they never produced a safe "alone" reading to compare against — see the harness's own git history/session logs on the node) drove this raw growth hard enough to genuinely **OOM-kill the node during the write burst itself**, before any resize-driven settling could happen:
```
[Tue Nov 3 00:58:14 2026] Memory cgroup out of memory: Killed process 140272 (java)
  total-vm:4877584kB, anon-rss:2022520kB, file-rss:179428kB, shmem-rss:0kB, UID:20001 pgtables:4660kB oom_score_adj:0
[Tue Nov 3 01:05:33 2026] Memory cgroup out of memory: Killed process 142168 (java)
  total-vm:4928296kB, anon-rss:2024448kB, file-rss:179580kB, shmem-rss:0kB, UID:20001 pgtables:4652kB oom_score_adj:0
```
Both used too many partitions (3,600,000 and 3,000,000, with ~200-byte keys) for the chosen 2000 MiB budget — these are genuine, real OOM-kills, but they happened in what was *meant* to be a "safe alone" control arm, so they are not filed as cases (no safe-alone baseline to compare a convergence arm against) and are recorded here only as the reasoning that led to the final sizing. **Final sizing: `index_summary_capacity: 100MiB`, `index_summary_resize_interval: 1m`, 1,500,000 partitions written to `isc.t`** (`k` a 200-character text column so each summary entry is large, `v` a 32-byte blob) — raw growth from this write burst reached `RssAnon` 1,517,040 KB (≈1481.5 MiB, **+594.6 MiB** over this arm's own 886.9 MiB idle baseline) immediately after the preload, i.e. the *transient, pre-resize* bytes are far above the 100 MiB configured cap. After the write burst finished and a resize was confirmed in `system.log`:
```
INFO [IndexSummaryManager:1] ... IndexSummaryRedistribution.java:154 - Completed resizing of index summaries;
  current approximate memory used: 176.83390045166016 MiB, time spent: 1781ms
```
summary usage settled at **176.8 MiB** — above the 100 MiB configured cap (likely a non-redistributable residue from sstables still involved in post-write compaction, which `IndexSummaryManager` charges but cannot shrink — a documented bypass path in the if-check-exp case, A3 item 7c) but a **real, large reduction from the ~590+ MiB raw peak** — i.e., the resize did genuinely act, just not all the way to the nominal 100 MiB.

**Arithmetic (stated before the convergence arm ran):**

- **R alone**, predicted: `b + R_overshoot ≈ 875 + 550×1.0 = 1425 MiB` of the 2000 MiB budget → **71.3% used, 28.7% free.**
- **I alone**, predicted (using the *measured* transient-growth figure from the calibration above, not the nominal 100 MiB cap, since the transient is what actually threatens the shared budget during any write burst): `b + 648.6 ≈ 875 + 648.6 = 1523.6 MiB` of 2000 MiB → **76.2% used, 23.8% free.**
- **Combined, naive additive prediction**: `b + R_growth + I_growth ≈ 875 + 598.6 + 648.6 = 2122.2 MiB` of 2000 MiB budget → **106.1%**, i.e. predicted to exceed the budget by about 6%.

This is a **smaller, less comfortable margin** than the on-heap cases in runs 1-2 (which used ≥30-56% free alone) — a direct consequence of the large, mostly-fixed ~875 MiB anon baseline on this node/build relative to what two off-heap caches can be grown to inside a few minutes of stress load (see §4 for why a bigger, more comfortable version of this case would need either a much bigger budget or a much longer/larger workload, both of which trade against the project's wall-clock budget for this run).

### 2.3 Workload

- **Row cache workload** ("row"): `cassandra-stress write n=550000 -col 'size=FIXED(1024)' -rate threads=64` into `keyspace1.standard1`, `ALTER TABLE ... caching={'rows_per_partition':'ALL'}`, `nodetool flush`, then `cassandra-stress read n=550000 -col 'size=FIXED(1024)' -pop 'seq=1..550000' -rate threads=48` (one pass over the full population — enough to populate every entry once; an earlier attempt at 4x the reads with 128 threads ran at only ~370 ops/s under this cgroup's memory pressure and would have taken ~2 hours to finish, so this was cut down — see §4's environment note).
- **Index summary workload** ("rebuild"): `cassandra-stress user profile=isc-profile.yaml ops(insert=1) n=1500000 -rate threads=64` into keyspace `isc`, table `t` (`min_index_interval=1`, `max_index_interval=128`, `k` a 200-char text column, `v` a 32-byte blob), `nodetool flush isc t`, then the harness waits up to 150 s (polling `system.log` from an offset captured right before the preload, so it only matches a resize that ran *after* this arm's own data was loaded, not an earlier near-empty one) for a `Completed resizing of index summaries` line.
- **Control arms** (R_alone, I_alone): each workload run alone, same budget/yaml/node as the convergence arm.
- **Convergence arm**: both of the above launched in the same window — the two *preload writes* ran one after another (sequential, both blocking foreground calls in the harness), but the memory-stressing *fill* phases overlap: the row-cache read pass (background) and the index-summary resize wait run concurrently, so both caches are actively being driven toward their respective capacities in the same window, not in disjoint windows with full settling in between. This is a partial, not full, realization of the playbook's "concurrent, not sequential" requirement — noted honestly here rather than glossed over (see §4's Target-3 note).

### 2.4 Instruments

`/proc/<pid>/status` (`VmRSS`, `RssAnon`, `RssFile`, `VmHWM` — the last is the process's own high-water mark, useful since the periodic 5 s samples can miss a brief peak) every 5 s during the run (up to 40 samples / 200 s), then once more after the background workloads finish; the cgroup's own `memory.current`, `memory.max`, and `memory.events` (specifically the `oom`/`oom_kill` counts — the only reliable signal of a *real* OOM, since `memory.current` pegs at `memory.max` under ordinary reclaimable page-cache pressure long before any actual kill, a confound discovered and corrected for mid-run — see §4); `nodetool info`'s cache-stats lines (Row Cache size/capacity/entries); `system.log` for index-summary resize completion lines and `ERROR`; `sudo dmesg -T` grepped for `out of memory`/`oom-kill`/`killed process`; `journalctl --user -u <scope>` for the systemd scope's own record of the kill, if any.

### 2.5 Procedure (as executed)

```
oom-run.sh baseline 2048            # (initial calibration; superseded by the per-arm idle readings in §2.1)
oom-run.sh arm R_alone   2000 550 -   row            550000 -
oom-run.sh arm I_alone   2000 -   100 rebuild         -      1500000
oom-run.sh arm converge  2000 550 100 row,rebuild     550000 1500000
```
Each arm: fresh `conf/cassandra.yaml` from the pinned tag + stated edits (including the `memtable_heap_space: 220MiB` stabilizer), clean `data/`, node started inside a fresh `systemd-run --user --scope -p MemoryMax=<budget>M -p MemorySwapMax=0` cgroup, confirmed `-Xmx384M` and `-XX:MaxDirectMemorySize` from the running process's own args, confirmed resolved row-cache/index-summary values from the node's own startup log, idle sample, schema/workload per §2.3, periodic sampling, final sample, `nodetool info`, log/dmesg/`journalctl`/process checks, node + cgroup scope stopped.

## 3. Runtime results

### 3.1 Control arm 1 — `row_cache_size=550MiB` alone

- Confirmed `-Xmx384M`, cgroup budget 2000 MiB, `Initializing row cache with capacity of 550 MiBs` in the startup log.
- Final reading: `RssAnon` 1,506,672 KB ≈ **1471.4 MiB** (**growth +598.6 MiB** over this arm's 872.8 MiB idle baseline) = **73.6% of the 2000 MiB budget, 26.4% free** — comfortably safe, close to the §2.2 prediction (71.3% predicted vs 73.6% observed).
- `nodetool info`: **`Row Cache: entries 110397, size 550 MiB, capacity 550 MiB`** — settled exactly at the configured cap.
- `ERROR` lines in `system.log`: 0 (the one `OutOfMemoryError` string match is the JVM's own `-XX:+HeapDumpOnOutOfMemoryError` flag name in the startup-args log line, the same false positive seen in runs 1-2 — not a thrown exception). `sudo dmesg -T` grep: 3 lines, all timestamped `23:33:19` — from the pre-harness smoke test (§2.1's citation), well before this arm ran; none from this arm's own window. `journalctl --user -u <scope>`: 0 OOM mentions. cgroup `memory.events`: `oom 0 oom_kill 0` throughout — `memory.current` did peg at the 2000 MiB `memory.max` for several samples near the end (`max` throttle-event counter climbed to 61,889), but this is the kernel reclaiming ordinary page cache from the sstable/commitlog I/O this arm generated, not a sign of real memory pressure (see §4's instrument note). Node stopped cleanly.

### 3.2 Control arm 2 — `index_summary_capacity=100MiB` (effective raw transient ≈595 MiB) alone

- Confirmed `-Xmx384M`, cgroup budget 2000 MiB, `Initializing index summary manager with a memory pool size of 100 MB and a resize interval of 1 minutes` in the startup log.
- Preload (1,500,000 partitions into `isc.t`, flushed) drove `RssAnon` to 1,517,040 KB ≈ 1481.5 MiB **immediately after the preload, before any resize had a chance to run** (**+594.6 MiB** over this arm's 886.9 MiB idle baseline) = 74.1% of budget, 25.9% free at that instant — this is the number that matters for the convergence arithmetic (§2.2), since it's the pre-resize, uncapped bytes a concurrent workload would actually be competing against.
- After the preload, a resize ran and completed within the 150 s wait window: `Completed resizing of index summaries; current approximate memory used: 176.83 MiB` — above the nominal 100 MiB cap (residual non-redistributable bytes from sstables involved in ongoing compaction, per if-check-exp's own documented bypass path) but a substantial real reduction from the raw peak.
- Final reading (after the resize): `RssAnon` 1,571,372 KB ≈ **1535.5 MiB** (**+648.6 MiB** over baseline) = **76.8% of budget, 23.2% free** — slightly *higher* than the immediately-post-preload reading, consistent with ongoing post-write compaction activity continuing to use memory even as the index-summary bytes themselves were being trimmed; still comfortably under budget. No OOM.
- `ERROR` lines: 0 (same flag-name false positive). `dmesg` OOM lines: 9, **all pre-dating this arm** (3 from the `23:33:19` smoke test, 3 from the `00:58:14` sizing attempt that used 3.6M/200-char-key partitions at this same 2000 MiB budget, 3 from the `01:05:33` attempt that used 3.0M partitions — both of those *did* genuinely OOM-kill the node, which is exactly why this arm's final sizing (1.5M partitions) was chosen smaller; see §2.2). `journalctl`: 0. cgroup: `oom 0 oom_kill 0`, `memory.current` pegged near `memory.max` for a few samples (reclaimable cache again, not real pressure). Node stopped cleanly.

### 3.3 Convergence arm — both at capacity, same window

- Confirmed `-Xmx384M`, cgroup budget 2000 MiB, both startup lines (`row cache with capacity of 550 MiBs`, `memory pool size of 100 MB`) present.
- `after-row-preload`: `RssAnon` 979,256 KB ≈ 955.9 MiB (**+91.2 MiB** over this arm's 864.7 MiB idle baseline — row cache is still filling at this point, reads haven't run yet).
- `after-isc-preload` (the isc.t write burst ran next, sequentially after the row preload — see §2.3): `RssAnon` 1,459,884 KB ≈ 1425.7 MiB (**+561.0 MiB** over baseline).
- Row-cache reads and the index-summary resize wait then ran concurrently. A resize completed: `Completed resizing of index summaries; current approximate memory used: 88.37 MiB` (even lower than I_alone's 176.8 MiB settled value — plausibly because this run had less concurrent compaction backlog at the moment of the resize, or simple run-to-run variance; not independently isolated given the time budget for this run).
- **Peak usage** (from `VmHWM`, the process's own high-water mark, which catches the true peak even if a 5 s sample missed it): 1,844,620 KB ≈ **1801.4 MiB** (**+936.7 MiB** over baseline) = **90.1% of the 2000 MiB budget** — the highest point reached in this run, still under 100%.
- **Final reading**: `RssAnon` 1,544,236 KB ≈ **1508.0 MiB** (**+643.3 MiB** over baseline) = **75.4% of budget, 24.6% free.**
- `nodetool info` at the end: **`Row Cache: entries 110397, size 550 MiB, capacity 550 MiB`** — row cache still settled exactly at its cap even under the combined load.
- `ERROR` lines: 0 (same flag-name false positive). `dmesg` OOM lines: 9, **all from before this arm's own time window** (same three pre-existing events cited in §3.1/§3.2 — confirmed by timestamp: this arm ran from `01:09` to `01:28`, and the latest `dmesg` OOM entry is `01:05:33`, i.e. from the immediately-preceding I_alone sizing attempt, not this arm). `journalctl --user -u <scope>`: 0 OOM mentions. cgroup `memory.events`: **`oom 0 oom_kill 0`** throughout — `memory.current` pegged at/near `memory.max` for many samples (`max` throttle-event counter reached 68,668, the highest of any arm, consistent with this arm doing the most combined I/O), but **no actual kill ever fired.**

**Matching the prediction (§2.2):** predicted combined, naive additive: 2122.2 MiB (106.1% of the 2000 MiB budget). **Observed peak: 1801.4 MiB (90.1%)** — about 320 MiB (15%) *below* the naive additive prediction, and never exceeding the budget at all. The prediction was wrong in the direction of over-estimating the overshoot. See §4 for the diagnosis.

## 4. Conclusion

**The node did not OOM, and the predicted combined sum did not actually exceed the budget when both constraints were driven together.** Both individually-measured alone-arm growth figures (R: +598.6 MiB, I: +648.6 MiB) were real and reproducible, and their naive sum (1247.2 MiB) was used, correctly, to predict combined usage over the shared 875 MiB baseline would reach ~2122 MiB against a 2000 MiB budget. The actual combined peak (1801.4 MiB, +936.7 MiB over baseline) came in about 310 MiB short of that naive sum. Diagnosis, ruling out the usual suspects in order:

- **Not a sizing error in either constraint alone**: both alone arms independently reproduced their expected growth figures closely (R: 598.6 MiB predicted-and-observed to settle exactly at the 550 MiB cap; I: 594.6-648.6 MiB raw/settled, consistent across both the calibration reading and this arm's own control-arm reading). The individual numbers that went into the sum were not wrong.
- **Not a timing/synchronization failure in the strict sense**: both workloads did run in the same window and both did reach substantial usage concurrently (the 90.1%-of-budget peak is itself evidence real overlap occurred — it is well above either workload's baseline-plus-single-constraint level).
- **The actual mechanism is that each constraint's own enforcement kept operating under combined load, not that the pools were somehow not really shared.** Row cache's Caffeine eviction is a hard, continuously-enforced ceiling (`maximumWeight`) that does not pause or weaken just because a second, unrelated off-heap consumer is also growing — it kept the cache at exactly 550 MiB throughout, including at the very end of the converge arm. Index summary's periodic resize similarly ran and brought usage down from its raw peak (observed: resize completed mid-run at 88.37 MiB, versus the >550 MiB raw bytes the write burst alone would have produced absent any resize) — i.e., the *bypass window* (the time between flush and the next resize tick) that let the raw bytes grow large in the I_alone calibration was, in this arm, caught by a resize before the row-cache's own fill phase added its full weight on top. The two "overshoots" measured in isolation were each captured at each workload's own *worst* moment (I_alone's reading was taken right after a long, resize-less write burst specifically chosen to maximize the pre-resize transient); the converge arm's actual schedule did not reproduce both constraints' individual worst moments at exactly the same instant.
- **A different sizing or workload shape is worth a retry, and the specific direction is clear from the data above**: a version of this case that (a) delays the index-summary resize further (a longer `index_summary_resize_interval`, so the raw transient has more time to grow before any resize can trim it) or (b) runs the index-summary write burst and the row-cache read pass fully concurrently from the start, rather than sequentially-then-concurrently as this run did (§2.3), would more faithfully realize "both constraints at their own worst transient moment, in the same instant" and is the straightforward next attempt if this group is reopened. A bigger shared budget was *not* the lever used here and would not by itself fix the gap — the gap is about the *timing* of each constraint's own self-correcting mechanism relative to the other's growth, not about the budget being too generous.
- **This group's margin-sizing is also structurally tighter than runs 1-2's on-heap cases**, for a reason independent of the above: the fixed ~875 MiB anon baseline on this node (JVM/Cassandra overhead, not under this experiment's control) is large relative to what either off-heap cache can be grown to inside a few minutes of `cassandra-stress`, which left this run's "safe alone" margins (24-29% free) comfortable but not generous, and the predicted combined overshoot (6%) was accordingly small and sensitive exactly the kind of timing effect described above.

**Target-3 note:** this combination is **less realistic from a single operator's misconfiguration than the on-heap cases.** `row_cache_size=550MiB` and `index_summary_capacity=100MiB` (the *configured* cap) are each plausible single-knob choices, but the actual mechanism that nearly converges them here — a continuous, large write burst landing in the narrow window before a periodic resize — needs either an unusually long `index_summary_resize_interval` (itself a second deliberate misconfiguration, not the default) or an unusually sustained write-heavy workload that happens to coincide with heavy row-cache-driven read traffic. It is a real, documented bypass mechanism (if-check-exp's own stage-4 finding), but demonstrating it convincingly needs engineered timing, not just two independently-plausible knob values — closer to the causal-chain/timing-sensitive end of the spectrum than runs 1-2's "set every cache bigger than you should" story.

## Instrument check and process hygiene

- **The `-XX:MaxDirectMemorySize`-doesn't-bind-this-off-heap-allocation finding (§1) was confirmed from source, not assumed**: both if-check-exp case files' own A2 sections independently state the allocation path is `Memory.allocate → MemoryUtil.allocate → JNA Native.malloc`, outside the JVM's `DirectByteBuffer`/NMT accounting, and both stage-4 results measure `RssAnon`, not any JVM-reported "direct memory" metric — this case's choice to use a cgroup instead was made *before* any run, on this basis, not discovered as a surprise after a run failed to show the expected ceiling.
- **`memory.current`/`memory.max` alone are a misleading "percent used" metric for this group** — discovered mid-run (not anticipated in the design) when a *safe*, non-OOMing arm showed `memory.current` pegged at `memory.max` for dozens of consecutive 5 s samples while `oom_kill` stayed at 0. The cgroup counts reclaimable page cache from ordinary sstable/commitlog I/O toward `memory.current`, and the kernel evicts that cache under pressure instead of killing the process — `RssAnon` (mirroring if-check-exp's own stage-4 instrument choice for these exact two constraints) is the metric that actually tracks the "hard", non-reclaimable usage this case's budget arithmetic is about; `memory.current`/`memory.events`' `oom`/`oom_kill` fields are used here only as the kill-or-no-kill signal, not as a percent-used reading.
- **Harness fixes made mid-run, recorded so a retry doesn't rediscover them:** (1) `bin/cassandra -f` (foreground, required so the JVM is the systemd scope's own tracked process) never writes a pidfile — PID detection is by `pgrep`, not a pidfile. (2) The `systemd-run --user --scope` cgroup path includes an `app.slice/` component (`.../user@<uid>.service/app.slice/<unit>.scope`) not documented in `systemd-run`'s own help text — found by `find`-ing for it. (3) `index_summary_resize_interval`'s first scheduled run fires on a fixed delay from the **manager's startup**, not from when data is loaded — a resize-wait that just greps for "any" completion line can match a near-empty resize that ran before the workload's own data was in; fixed by capturing a `system.log` line-count offset right before the preload and only matching completions after it. (4) `cassandra-stress user profile=...` requires a `queries:` section in the yaml even when only `ops(insert=1)` is ever run — omitting it is a hard `AssertionError` at startup, not a warning. (5) A 16-byte text key for the index-summary table made each summary entry too small (~28 bytes) to reach a meaningful raw size within a feasible partition count (would have needed ~25M partitions); switched to a 200-character key (~212 bytes/entry, matching if-check-exp's own cluster-tier calibration) so a few million partitions is enough.
- **Two sizing attempts that genuinely OOM-killed the node were not filed as cases** (§2.2): with the final `memtable_heap_space`/budget/cap choices fixed, an index-summary-alone write burst of 3,600,000 or 3,000,000 partitions (vs. this case's 1,500,000) both drove the node to a real kernel OOM-kill during the write burst itself, before any resize could run — these are the direct evidence behind this case's final, smaller sizing, and are cited in §2.2/§3.2 by their `dmesg` timestamps rather than given their own case files (no safe "alone" baseline was ever established at those sizes to compare a convergence arm against).
- Node data (`data/`), commit log, and logs lived under `~/cassandra-run1` on local disk (`/dev/sda3`); nothing was written to `/proj`. The repository's `systems/cassandra/source/` was never touched. The harness and support files (`oom-run.sh`, `isc-profile.yaml`) live outside the repo at `~/oom-offheap-run4/`, per the node safety rules; they are not committed, same as prior runs' on-node harness scripts.
- After every arm: `pgrep -f '[o]rg.apache.cassandra.service.CassandraDaemon'`, `pgrep -f '[c]assandra-stress'`, and `systemctl --user list-units 'oom*'` all returned empty before the next arm started, and again at the end of this run.
