Stage 5 ran only for the two cases whose stage 4 finished: order 19 `dfs.qjournal.queued-edits.limit.mb-reserveQueueSpace-queueSizeLimitBytes--autonomous` and order 21 `CachePoolInfo_limit-rescanFile-pool.getLimit--autonomous`, both true positive. ## Reads with no candidate

**Case file:** `dfs.qjournal.queued-edits.limit.mb-reserveQueueSpace-queueSizeLimitBytes--autonomous` (order 19) · **Agent:** autonomous · **Candidates:** 0

Case file: dfs.qjournal.queued-edits.limit.mb-reserveQueueSpace-queueSizeLimitBytes--autonomous. Candidates: 0. At the shipped defaults I found nothing that could run the NameNode out of heap on this path. The per-JournalNode queue of edit batches is capped at 10 MiB by reserveQueueSpace (IPCLoggerChannel.java:448-458). Stage 4 measured the cap in both tiers: a plateau within bytes of the limit, the matching heap difference, and refused arrays that GC could collect. Every batch array is shared across all channels (AsyncLoggerSet.java:254-262), so the total held is at most the number of lagging JournalNodes, which must be a minority, times 10 MiB. That is about 20 MiB for 5 JournalNodes. The one allowed overshoot is a single batch into an empty queue. A batch stays near the 512 KiB flush size plus one op (EditsDoubleBuffer.java:99-101, QuorumJournalManager.java:108). At the default ipc.client.rpc-timeout.ms of 120 s (core-default.xml:2490), a hung JournalNode's call fails, which sets outOfSync, and the rest of the queue then fails fast (IPCLoggerChannel.java:360-369, 416-423). Neither QuorumCall nor the futures keep a refused batch's array reachable. The only unbounded case I saw is not a default setting: at L = 2047 the int sum queuedEditsSizeBytes + size at IPCLoggerChannel.java:451 can overflow when a batch is over 1 MiB, and before that happens the heap already holds about 2 GiB. Values of 2048 and above wrap at IPCLoggerChannel.java:171-173 to a zero or negative limit, which refuses more batches and holds less memory.

## OC-1

**Case file:** `dfs.qjournal.queued-edits.limit.mb-reserveQueueSpace-queueSizeLimitBytes--autonomous` · **Agent:** guided · **Patterns:** CP-1, CP-2

**Summary:** NameNode QJM per-JournalNode send queue (IPCLoggerChannel): the dfs.qjournal.queued-edits.limit.mb counter charges only data.length of each queued edit batch, but each queued batch also pins ~800 B of uncounted objects (future task, lambda, queue node, callbacks, and through a listener its whole QuorumCall with the other channels' futures). Stage 4 measured NN heap held at 1.7-2.1x the counted bytes; with single-op batches about 9x, roughly 90 MB per lagging JN at the default 10 MiB.

Clue (CP-1, counted unit is smaller than held memory). The per-channel limit compares `queuedEditsSizeBytes + size` against `queueSizeLimitBytes`, where size is `data.length` of the edit batch (Where: hadoop-hdfs-project/hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/qjournal/client/IPCLoggerChannel.java:346 and :451; the limit is 1024*1024*conf at :171-173, default 10 MiB at DFSConfigKeys.java:1477-1478). Only the payload bytes are charged.

An accepted batch is a task on an unbounded `Executors.newSingleThreadExecutor` queue (IPCLoggerChannel.java:243-250, submit at :357). While a JournalNode lags (slow disk, GC pause, or a stall up to the default ipc.client.rpc-timeout.ms = 120 s, core-default.xml:2489-2490), each accepted batch keeps all of the following reachable:
- the TrustedListenableFutureTask, the capturing lambda and the LinkedBlockingQueue node;
- the unreserve FutureCallback and its listener entry (IPCLoggerChannel.java:400-410);
- the QuorumCall listener registered on every future (QuorumCall.java:71-88). That listener pins the QuorumCall object: its successes and exceptions HashMaps (:48-49), its allCalls ArrayList (:69), a StopWatch and a Timer (:67-68, :105-109), plus the completed futures of the healthy channels (AsyncLoggerSet.java:254-262).

None of this is charged. The uncounted part scales with the number of queued batches, and only the payload-byte total limits that number. Small batches therefore multiply the overhead (CP-2 flavour: the item count is not bounded per item).

Measured gap in the stage-4 cluster tier (results.md, run1/cluster/histo-*.txt; NN with JN3 SIGSTOPped, NNThroughputBenchmark mkdirs). The figures are heap (b)-(c) Total:
- L=10: 18.0 MB total for 10.49 MB counted (1.72x).
- L=64: 115.4 MB total for 67.1 MB counted (1.72x); 1.48 M extra objects, about 25 objects and about 800 B of overhead per batch at an average batch of about 1.15 KB.
- L=512 (uncapped): 311.5 MB total for W = 150.5 MB (2.07x); 4.95 M extra objects for about 198 k batches.
The stage-4 verdict counted only `[B` bytes, so it saw 'caps'.

Rough size at defaults: with async edit logging and a low or serial write rate, each sync can carry one small op (about 50-150 B). The 10 MiB limit then admits about 100 k batches, and at about 900 B held each that is about 90 MB of NN heap per lagging JN, against a nominal 10 MiB (about 9x). The per-channel parts repeat for each lagging JN (up to the minority, e.g. 2 of 5). This is modest at the default. The ratio holds when operators raise the limit: the int allows up to 2047 MiB, which gives several GB to about 18 GB with small batches. That can exceed a NameNode heap sized for its namespace.

## OC-2

**Case file:** `CachePoolInfo_limit-rescanFile-pool.getLimit--autonomous` · **Agent:** autonomous · **Patterns:** —

**Summary:** NameNode heap: one CachedBlock per COMPLETE block of every file a directive reaches. The pool limit is unlimited by default, and the entry stays even when no DataNode can cache the block (the default DN cache capacity is 0), so it grows with the namespace at about 40-80 B per block.

Clue: rescanFile creates and inserts a CachedBlock into the NameNode's cachedBlocks GSet for every COMPLETE block of every file that passes the pool check. At the shipped default the pool limit is LIMIT_UNLIMITED = Long.MAX_VALUE (CachePoolInfo.java:54-55), so the check at :403 never fails and every block of every file under any directive gets an entry. An entry is removed only when neededCached == 0 and both pending lists are empty. While the directive exists neededCached = replication > 0. That holds even when no DataNode has cache capacity: dfs.datanode.max.locked.memory defaults to 0, but dfs.namenode.caching.enabled defaults to true, and addNewPendingCached then finds no target, so the entry is kept for as long as the directive lives. Even with a limit set, the bound is in bytes, not blocks: tiny files give one CachedBlock per file, up to L of them. dfs.namenode.path.based.cache.block.map.allocation.percent (default 0.25%) sizes only the hash table, not the element count. Rough size: CachedBlock = object header + long blockId + nextElement ref + short + triplets ref, about 40 B, plus a triplets array of about 16 + 12 B per DataNode once it is pending or cached. That is about 40-80 B per block. Directives on directories holding 50-100M blocks add about 2-8 GB of NameNode heap on top of the BlockInfo the NameNode already holds, and the rescan keeps it alive every 30 s. Nothing caps the number of directives or blocks a pool may reference.
Where: hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/blockmanagement/CacheReplicationMonitor.java:403 (check; with an unlimited pool it never fails), :425-429 (new CachedBlock / cachedBlocks.put), :369-372 (a directory directive takes all child files), :623-631 (removed only when neededCached == 0), :684 (addNewPendingCached; no DN with capacity means no pending entry and no removal); server/namenode/CachedBlock.java:44,49,55,67 (fields); server/namenode/CacheManager.java:244-246 (GSet sized by percent, not by count); DFSConfigKeys.java:193 (0.25f), :509 (caching enabled true); hdfs-default.xml:2985-2986 (DN locked memory default 0).

## OC-3

**Case file:** `CachePoolInfo_limit-rescanFile-pool.getLimit--autonomous` · **Agent:** autonomous · **Patterns:** —

**Summary:** DataNode native memory and mappings: each cached replica is its own mmap, and the reservation is page-rounded, so tiny files admitted by a byte limit give one mapping per file. About 65k cached small blocks (a DN cap of about 256 MiB or more) can exhaust Linux vm.max_map_count (65530), after which DataNode native allocations fail with OutOfMemoryError (for example 'unable to create native thread').

Clue: the pool limit (and the DataNode cap dfs.datanode.max.locked.memory) count bytes, never the number of cached blocks. Every cached replica is mapped separately with FileChannel.map and then mlocked, and it stays mapped while cached. The DataNode reserve rounds each replica up to the OS page size (the case cites FsDatasetCache.java:388-389 and CacheStats.java:209-210), so a 1-byte file costs 4 KiB of the DN cap but a whole mapping. Nothing in Hadoop checks vm.max_map_count (grep finds no reference). With a DN cap of 256 MiB or more and a cached directory of at least 65k small files (pool demand only about 64 MiB at 1 KiB per file, well under any plausible limit, and unlimited by default), the DataNode reaches about 65530 mappings. FileChannel.map itself fails with an IOException wrapping OutOfMemoryError('Map failed') after a forced System.gc and retry, which CachingTask catches. But the JVM's other native mappings in the same process then fail: thread stacks for every new DataXceiver, malloc arenas, direct buffers. Those surface as java.lang.OutOfMemoryError: unable to create new native thread or a native allocation failure, which can kill the DataNode. Each cached block also holds about 250 B of DataNode heap: a HashMap node, ExtendedBlockId, Value, MemoryMappedBlock, DirectByteBuffer and Cleaner. That is about 4 GB at 16M cached 4 KiB blocks, which a 64 GiB DN cap allows, against the default 1 GB-class DataNode heap. Not at the fully shipped defaults: it needs caching on, with a DN cap of roughly 256 MiB or more, which is the normal setting for any cache deployment.
Where: hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/datanode/fsdataset/impl/MemoryMappableBlockLoader.java:79-82 (blockChannel.map plus mlock per block, new MemoryMappedBlock); FsDatasetCache.java:414-423 (reserve, bytes only), :446-448 (IOException from load caught), :120 and :463 (mappableBlockMap HashMap holding one Value per cached block); CacheReplicationMonitor.java:395-403 (pool check counts bytes, not blocks); hdfs-default.xml:2985-2986 (DN cap in bytes).

## OC-4

**Case file:** `CachePoolInfo_limit-rescanFile-pool.getLimit--autonomous` · **Agent:** guided · **Patterns:** CP-1, CP-9

**Summary:** DataNode centralized cache: one mmap (VMA) plus mlock per cached block. The pool limit counts file bytes (1 B for a 1-byte file), the DN cap counts page-rounded bytes (4 KiB), and nothing counts mappings, so a pool of tiny files can use up vm.max_map_count (65530) and the DN's native allocations then fail.

Clue. The pool limit (default unlimited) charges `file length x directive replication` per file. For a file of s bytes it charges s, but the DataNode holds one separate FileChannel.map plus mlock of that block, and the kernel locks ceil(s/4096) pages. It also keeps a per-block Value/MemoryMappedBlock/MappedByteBuffer/HashMap entry on the DN heap. The DN's own cap (dfs.datanode.max.locked.memory) charges the page-rounded bytes. Neither limit counts mappings, and a mapping is the scarce resource here: Linux vm.max_map_count defaults to 65530 (the value on this node), and the DN JVM already uses a few thousand maps for thread stacks (2 per xceiver thread, up to 4096 transfer threads), malloc arenas and jars.

Size at defaults. With 1-byte files, pool limit L = 64 KiB admits 65,536 files (counted : held = 1 B : 4096 B locked, plus about 200 B of DN heap per block). A DN cap of only 256 MiB fits 65,536 page-rounded blocks, so the cache reaches the default map count. A 1 GiB DN cap fits 262,144 tiny blocks by bytes, 4x the map count. With the pool limit left at its default (unlimited), the count is bounded only by the number of small files under the directives.

What happens at the limit. FileChannel.map fails. In JDK 8 it first runs System.gc() and retries, then throws IOException("Map failed") caused by OutOfMemoryError. The DN catches that per block, releases the reservation and logs. The NameNode re-sends the block as pending-cached every retry interval, so the DN keeps trying, with a GC each time. Meanwhile every other mmap in the DN process can fail too (new thread stacks: "unable to create new native thread"; malloc arenas; direct buffers; short-circuit shm segments). The process-level failure is OutOfMemoryError or a native crash, not a graceful refusal.

Where:
- hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/blockmanagement/CacheReplicationMonitor.java:395-403: the pool counter is file length x replication, with no per-block or per-mapping cost.
- hadoop-hdfs/.../datanode/fsdataset/impl/CacheStats.java:94-106: the DN reserve counts only page-rounded bytes.
- hadoop-hdfs/.../datanode/fsdataset/impl/MemoryMappableBlockLoader.java:79-80: one blockChannel.map(READ_ONLY, 0, length) plus mlock per block.
- FsDatasetCache.java:120-121 and :484: a per-block Value in mappableBlockMap on the DN heap.
- FsDatasetCache.java:448-450: an IOException from load is caught; the block is not cached.
- FsDatasetCache.java:419-423: the reserve fails only on bytes.
- Case file A3 'Page rounding' ("< 1 page per replica"). That is small for 1 MiB blocks but 4096x for 1-byte files. Stage 4 used only 1 MiB blocks (6 blocks), so it never exercised this.

## OC-5

**Case file:** `CachePoolInfo_limit-rescanFile-pool.getLimit--autonomous` · **Agent:** guided · **Patterns:** CP-9, CP-8, CP-16

**Summary:** The DataNode cache's mlocked memory sits outside -Xmx and the direct-memory limit, and dfs.datanode.max.locked.memory is checked only against RLIMIT_MEMLOCK, not against RAM, the container or the DN heap. With pool limits unlimited by default, the DN cap alone decides how much unevictable memory the DN pins.

Clue. The memory this case's constraint governs is mmapped, mlocked block-file pages. The JVM heap limit and MaxDirectMemorySize do not bound them. They are unevictable, and they count against the node's RAM and against a memcg container that holds the DN. The pool limit ships unlimited (CachePoolInfo.DEFAULT_LIMIT = Long.MAX_VALUE, CachePoolInfo.java:54-55), and the sum of pool limits is never compared with cluster cache capacity (CentralizedCacheManagement.md:75 only says they are 'normally' about equal). So the only stop is the per-DN dfs.datanode.max.locked.memory (default 0, which turns caching off; hdfs-default.xml:2985-2986). When an admin enables caching, the DataNode validates that value only against RLIMIT_MEMLOCK (DataNode.java:1892-1911). Nothing compares it with physical RAM, the DN's -Xmx, a container limit, or other memory on the same node. That other memory includes NodeManager containers, the DN's own heap and direct buffers, and Lazy Persist RAM_DISK replicas. RAM_DISK draws on the same cache budget (FsDatasetImpl.java:3770-3778) but its tmpfs pages are memory in their own right.

The docs tell admins to raise `ulimit -l`, and the DN commonly runs with unlimited or a very large ulimit; on this node ulimit -l is 16,492,912 KB, about 15.7 GiB. Any value up to that passes.

Size. Once caching is enabled, locked memory is whatever the admin sets: up to ulimit -l per DN, and the pool limits (default unlimited) let directives fill it. Example: max.locked.memory = 16 GiB plus a DN heap of a quarter of RAM plus NodeManager containers on a 64 GiB worker over-commits RAM. Because mlocked pages cannot be reclaimed, the kernel OOM killer or the memcg kill picks a process, and that may be the DN itself. Not reachable at shipped defaults (cap 0), but reachable as soon as the feature is turned on as documented.

Where:
- hadoop-hdfs/src/main/java/org/apache/hadoop/hdfs/server/datanode/DataNode.java:1892-1911: the only validation is native mlock available and maxLockedMemory <= RLIMIT_MEMLOCK.
- hadoop-hdfs/.../datanode/fsdataset/impl/MemoryMappableBlockLoader.java:79-80: mmap plus mlock outside the JVM limits.
- hadoop-hdfs-client/.../protocol/CachePoolInfo.java:54-55: the pool default is unlimited.
- hdfs-default.xml:2985-2986: the DN cap default is 0.
- Case file A4: other consumers of the same locked memory, and pool sums not checked.
