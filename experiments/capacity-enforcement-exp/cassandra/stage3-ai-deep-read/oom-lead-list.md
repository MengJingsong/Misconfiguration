# OOM lead list — leads from phase 1 (Cassandra)

Started 2026-11-16 as `recheck-flags.md`; renamed 2026-11-17, when stage-3 cases began adding leads
too. One row per **OOM lead** (called an *OOM-lead flag* in files filed before 2026-11-17) written by:

- a guided case's §8a ([`playbook-guided.md`](../../stage3-ai-deep-read/playbook-guided.md) §3.2),
- an autonomous case's section E ([`playbook-autonomous.md`](../../stage3-ai-deep-read/playbook-autonomous.md);
  the session that files the case copies the row here, since the autonomous agent works outside the repo),
- a recheck of a filed case (guided §5, autonomous "Recheck mode").

A lead says real memory can exceed what a constraint governs; it is not a result. **This is OOM-exp's
candidate list from phase 1:** a queuing agent takes rows from here under the
[queuing playbook](../../../OOM-exp/queuing-playbook.md) and writes back the status.

**Mode:** `blind` (picked from phase 1 alone, OOM-exp not read), `back-link` (named by a back-link
row for a verified OOM-exp case), or `new` (written while the case was first filed, 2026-11-17 on).
Only `blind` and `new` leads count toward how well phase 1 predicts phase 2.

**Status** (added 2026-11-17), changed only forward:

| Status | Meaning |
|---|---|
| `lead` | recorded, not yet taken up |
| `stage-4 measured` | a phase-1 stage-4 run measured the real resource against the counter (cite it in the queue row) |
| `queued as <ID>` | a campaign row exists (`OOM-exp/cassandra/campaign-plan.md`) |
| `verified (<ID>)` / `negative (<ID>)` | the row reached a verdict; `back-link` rows that explain an already verified case say `verified (<ID>, back-link)` |
| `screened out: <reason>` | the queuing agent excluded it (queuing playbook §3) |
