| 1 | OC-533 | yes (the client picks LZ4 in STARTUP; no server setting) | single ARM node | On a v3/v4 connection that negotiated LZ4, `Envelope.Decompressor` reads `uncompressedLength` from the first 4 bytes of the client's body and calls `heapBuffer(uncompressedLength)` before anything validates it (checked in source). `native_transport_max_frame_size` and both in-flight limits see only the compressed length, so a 13–20 byte frame can ask for up to about 2 GiB of heap. The default AllowAll auth answers STARTUP with READY, so any client can do it. Size: one frame declaring about 1.9 GiB fails a 2 GiB heap at once, and 3–4 concurrent frames of about 500 MiB from different event loops pass it. A stronger design than one failing giant allocation is a valid repetitive LZ4 body: 16 MiB compressed expands up to about 255x (capped near 2 GiB), the expanded body is decoded while 16 MiB is charged, and Snappy gives about 20x (about 340 MiB per request). Test time: minutes. Caveat: the bogus-length buffer is transient (freed when decompression fails), so the design must make the allocations overlap or use valid bodies so the heap really fills. | No existing case. ## Notes

1. **Already covered.** Each row below repeats an existing case. Where the case is a retry, it was re-picked on 2026-11-20 (retry list), so these rows should go to that retry, not to a new case.
- U2 (true positive): OC-529, OC-530, OC-531, OC-532, OC-534, OC-536, OC-541, OC-542, OC-543, OC-544, OC-545, OC-546. These are pre-STARTUP partial envelopes in decoder cumulations. OC-542 adds that a limit enabled at runtime leaves open channels uncounted, and OC-545 adds a raised frame size.
- B9 (true positive): OC-418, OC-419, OC-423, OC-424. These are the v4 force-allocate past the limit (as OC-183 and OC-270, closed against B9) and v4 frames cumulated before the in-flight check.
- C2 (true positive): OC-421, OC-425. These are uncounted responses to a client that does not read, on v4.
- B13 (true positive): OC-426. The same over v5, with networking-pool overflow.
- C4 (true positive): OC-427, OC-430, OC-496, OC-503, OC-521. These are index summaries at full sampling between hourly resizes, and untrimmed upsampled builders.
- C7 (true positive): OC-428, OC-429, OC-434, OC-552, OC-553, OC-554, OC-555, OC-559, OC-560, OC-561, OC-562. These are coordinator Merkle trees x unlimited concurrent_merkle_tree_requests.
- C8 (true positive): OC-439, OC-441. These are the fixed 1 GiB SAI segment buffer. The trie chunk-doubling slack these rows add is inside C8's holder.
- B7 (retry; R8 is itself retry and was re-picked as R11): OC-444, OC-485, OC-486, OC-506, OC-507, OC-508. These are the key- and counter-cache weigher gaps. OC-507 and OC-486 add the table/sketch kept after a runtime shrink, as the legacy OC-52 (open), which is small.
- B12 (true positive): OC-538, OC-539, OC-549, OC-550. These are the Paxos cache weigher without the partition key. OC-538/539 are the large-key form B12 already tested.
- U7 (true positive): OC-449. The pk IN x ck IN rows built in a batch before verifyBatchSize.
- U5 (retry, re-picked as R14): OC-414. The clustering IN product on the slice path (isColumnRange), which never calls the cartesian guardrail. This could be one more arm of R14, since it builds two bound sets per composite.
- B14 (retry, re-picked as R13): OC-465. Batch mutations built before the size check, and single-partition batches exempt.
- B11 (retry, re-picked as R12): OC-445, OC-452, OC-463. OC-452/463 are the traced-EXECUTE render. OC-445 is the slow-query monitor (MonitoringTask failed and slow queues, 50 items each, no byte count, kept up to 5 s and rendered uncut at drain). It is exactly the holder B11's dumps found at 42–49 % of heap, and R12 adds it as its own domain. OC-445 is a strong mechanism but should go to R12, not a new case. Untraced, it needs only reads slower than 500 ms that carry large filter values.
- U10 (true positive): OC-457, OC-464. An unpaged aggregate without GROUP BY read as one sub-read into one replica buffer.
- U4 (true positive): OC-413, OC-416, OC-458, OC-475, OC-476, OC-484, OC-537, OC-548. These are pages and results sized by a row count with read thresholds off. Paging off or a huge client page size is the client's explicit choice; the server-side unpaged paths are U10 and B17.
- C9 (true positive): OC-471, OC-473, OC-482, OC-483, OC-492, OC-500, OC-568, OC-569, OC-570, OC-572. These are the 256 KiB read-ahead buffer per scanner, plus each uncached reader's 16 KiB chunk buffer and its unpooled allocateDirect overflow past file_cache_size. C9's run (40 scans x 2,000 sstables, about 80k readers) already crossed the 512 MiB pool, and read-ahead 0 removed the OOM, so the overflow is a minor part of C9. The legacy OC-28 (open) is the same overflow.
- U9 (true positive): OC-495. The BIG row index for a wide partition on the writer heap.
- U3 (true positive): OC-497, OC-505. A whole appended collection read into one row.
- C6 (true positive): OC-513, OC-515, OC-518, OC-519. A 1 MiB slab region per written table, uncounted.
- B18 (retry, re-picked as R16): OC-514, OC-516, OC-517, OC-520. Allocations past the limit in a blocking OpOrder group at each flush barrier (the legacy OC-41 family).
- S2 (true positive): OC-524, OC-558, OC-566. The coordinator's own local writes queued on the unbounded MutationStage after the client was answered, with expired ones re-queued as hints.
- U6 (retry, re-picked as R15): OC-540, OC-551. PREPARE lexed, parsed and measured before the cache check; this is U6's arm B (PREPARE markers).
- B8 (true positive): OC-567, OC-575. Commit-log replay backlog counted in serialized bytes.
- C3 (negative; retry by the mapping rule, re-picked as R9): OC-576. DOB scratch buffers kept per thread, at most 1 MiB each; C3 measured 183–195 MiB peak. Do not rerun it separately.
- R1-V (true positive): OC-501, OC-527. Chunk-cache + networking pools + off-heap memtable over-commit a 2 x heap container. OC-527 notes that cassandra_latest.yaml ships offheap_objects.

2. **Not reachable at shipped defaults** (grouped by the setting needed).
- Trie memtable or an off-heap memtable allocation type (cassandra_latest.yaml): OC-438, OC-440, OC-448. These are InMemoryTrie doubling chunks charged by allocatedPos, and off-heap SAI tries charged as 0. They are near the legacy OC-55 and OC-47.
- Row cache (row_cache_size 0, caching rows NONE): OC-437, OC-443, OC-564. These are full-partition CachedBTreePartition builds on every miss.
- CDC, MV-on-repair or streamToMemtable write path for streaming: OC-435, OC-446.
- partition_denylist_enabled (false) or operator-written denylist rows via JMX: OC-477, OC-487, OC-488, OC-489, OC-490, OC-491, OC-498, OC-499. The per-table reload ignores the total; the cap is a key count with keys up to 64 KiB. This is the legacy OC-42 (open). It needs an operator to denylist 50+ tables with large keys.
- Corrupt sstable, message or commit-log data: OC-417, OC-511, OC-512, OC-481. These are byte[] lengths read before validation (max_value_size 256 MiB, or unchecked vint lengths). OC-481 also needs commit-log compression.
- Raised commitlog_segment_size or max_mutation_size (hint slabs are 2 x max_mutation_size): OC-502, OC-525.
- Full query log or audit log (off; enabled with nodetool): OC-526.
- Non-default -Dcassandra.memtable.row_overhead_size: OC-447.
- CassandraAuthorizer (AllowAllAuthorizer ships, so there is no permissions cache): OC-571.
- file_cache_enabled true: OC-573.
- Very large chunk_length_in_kb table option (as OC-363 and OC-364 in the 11-18 triage): OC-574.
- Commit-log compression or encryption: OC-577.
- Per-table min_index_interval = 1 (about 0.17 B per key at the default 128): OC-528.

- SAI vectors at scale: OC-454 (PQ codes on heap at about 784 B per vector, so 2M+ vectors, as OC-381/392/393 in the 11-18 triage) and OC-460 (brute-force pairs, about 16 B per in-range row, needing about 100M vectors).
- Small per query: OC-459 (memtable brute-force list, 13–40 MB per query, with the memtable capped at heap/4) and OC-461 (16,000 keys copied per sstable segment, about 0.5 MB, needing hundreds of overlapping vector sstables).
- Thread-local read-ahead map entries never removed (about 300 B per thread and file, about 250 MB per thread per year, as OC-304): OC-472, OC-474.
- Repair-state caches capped by entry count (100,000 entries x up to tens of KB, kept 3 days), which needs tens of thousands of repair commands: OC-556, OC-563.
