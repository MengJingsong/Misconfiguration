## 4. Known limitations

- **Getters:** a capacity is linked to its field through a getter only when the getter is one line
  (`return f;` or `return f.x();`). Most `Config.java` fields reach the code through longer
  `DatabaseDescriptor` getters, so the capacity-set row found is usually the nearer one (for example
  `SubPool.limit` in a constructor); stage 3 traces on to the constraint.
- **Local variables** that hold a capacity (`allowance` in `CDCSizeTracker`) are not capacity-set rows.
- **Verdict depth:** helpers are followed 2 call levels down (dispatch included); deeper chains are not.
- **Equality rows and usage fields:** stage 1 cannot tell the usage operand from the capacity operand,
  so the field rows include usage fields (offsets, counters reset to 0).

## 5. For review (decisions before stage 2)

1. **Counted loops.** Should the 970 `for-counter` rows be excluded (a structural filter, like the
   existing null and literal filters) or kept for stage 2 to put in band D? No case target is one
   except a `no_constraint` case.
2. **Volume.** Up to about 5,300 new enforcement places plus 2,500 capacity-set rows, against 4,789
   banded units today. That is about 4,350 without the counted loops.
3. **Uids.** New rows need uids that cannot collide with the `path:line#n` uids already in `bands.csv`.
   Proposal: a prefix, `E:` for enforcement rows and `C:` for capacity-set rows.
4. **Where they go next.** Cassandra's bands A–C are fully read, so new Cassandra rows would be a new
   write-up set. Hadoop stage 3 is in progress, so new Hadoop rows would be appended at the end of the
   queues. Hadoop copies of the two queries are not written yet.
