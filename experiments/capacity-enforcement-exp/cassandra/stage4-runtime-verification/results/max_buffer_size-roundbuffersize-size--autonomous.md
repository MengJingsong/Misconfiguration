### 4.2 Conclusion and logic

**Unit tier.**

1. **Validity.** Each copy printed its own constant (65536 / 32768 / 1048576) [observed: `unit/probe-<v>.txt` line 1], so the `realclean` rebuild compiled the patch in, including into inlined callers [inferred: `chunk` (computed in `FileHandle.Builder.complete`, a different class) follows the patched value, e.g. v1m r = 1 MiB chunk 1048576]. All 32 readers were opened on one 4 MiB uncompressed file with no chunk cache and rebuffered once [observed: `MaxBufferSizeProbeTest.java`, 16 rows per copy]. The record size reached 256x the cap [observed: r = 16777216 rows]. Valid.
2. **Readings.** No gap or outlier: 48 / 48 rows equal B2f exactly [observed: `unit/unit-analysis.md`].
3. **Matched row (B2g row 1):** "v64: perReader = 65536 for every r >= 65536; v32: 32768; v1m: grows to 1048576 — Claim confirmed at unit level: the per-reader buffer follows the constant." v64 perReader = 65536 for r = 65536 … 16 MiB, both strategies; v32 = 32768; v1m = 1048576 at r = 1 MiB and 16 MiB [observed: `unit/probe-v64.txt`, `probe-v32.txt`, `probe-v1m.txt`]. Disallow evidence: the clamp's output `bufferSize` = 65536 at r = 16 MiB on v64 is the `Math.min(size, MAX_BUFFER_SIZE)` branch taken [observed: `probe-v64.txt`].
4. **Excluded rows.** "perReader > 65536 on v64": max is 65536 [observed: `unit-analysis.md`]. "bufferSize clamped but bufCap/dUsed larger than chunk": bufCap = chunk and dUsed = 32 x chunk in all 48 rows [observed]. "v1m equals v64 at r = 1 MiB": 1048576 vs 65536 [observed]. "dUsed = 0 for all rows": dUsed > 0 in every row [observed]. "Small-r rows differ": identical [observed: `unit-analysis.md`].
5. **Observed vs. inferred.** Only that the patched constant reached inlined callers is inferred, and it is backed by the `chunk` column.
6. **Deviations and gaps.** None in the procedure. Pool accounting and `ByteBuffer.capacity()` are read, not RSS (B2d names the gap; the cluster tier reads JVM direct memory).
7. **Core question.** The per-reader read buffer is exactly `min(f(r), MAX_BUFFER_SIZE)` and moves with the constant (32 / 64 / 1024 KiB at r ≥ 1 MiB); the constant caps per-reader direct memory on this path (parts 1, 3, 4).

**Conclusion (unit, one line):** B2g row 1 — **confirmed**.

**Cluster tier.**

1. **Validity.** The limit was exercised: 32 (or 8) uncompressed SSTables of 1 MiB partitions, p95 partition-size bucket 1131752 B ≫ 64 KiB [observed: `sstablemetadata.txt`, `tablestats-before.txt`], compacted by one major task holding K inputs [observed: `system.log` `Compacting (…)` line with K `Data.db` files], sampled while it ran (20 / 20 compacting samples, K=8: 17 / 20) [observed: `compactionstats.txt`]. Hold-fixed settings: `disk_access_mode: mmap_index_only` giving "DiskAccessMode is standard" [observed: `system.log`], `file_cache_enabled: false`, `ssd`, compression off, compaction disabled [observed: `cassandra.yaml`, `run.log` DESCRIBE], same heap 2G, same data volume per size class. The build under test is the patched one [observed: `run.log` `MAX_BUFFER_SIZE = 1 << 16/20/15`]. Valid.
2. **Readings.** Pool gauges are flat at the exact level in every compacting sample (no noise) [observed: `during.txt`]. Δdirect on the pooled runs is ≈ 0 (−0.12 … +0.05 MiB): the buffers came from a macro chunk already reserved at baseline (direct ≈ 57.5–58.0 MB) [observed: `base.txt`, `during.txt`; inferred: pool slab reuse, B2d/B3d's named 8 MiB-step gap]. The K=8 compaction ended inside the window, so 3 samples are excluded by A5's filter [observed: `compactionstats.txt`]. The loader changed mid-tier (H4); the repeat `v64-1m-k32-nd` gives the same three Δ as `v64-1m-k32` [observed: `cluster-analysis.md`].
3. **Matched row (B3g row 1):** "v64 ΔUsed ≈ 2 MiB, v1m ΔUsed ≈ ΔOverflow ≈ Δdirect ≈ 32 MiB — Confirmed: direct memory per open reader follows the constant." v64 ΔUsed = 2.000 MiB (B3f accepts 1.5–3); v1m ΔUsed = ΔOverflow = 32.000 MiB, Δdirect = 31.99 MiB [observed: `cluster-analysis.md`, `cluster-v1m-1m-k32/during.txt`]. Row 5 also holds ("ΔUsed scales with K (8 vs 32) at 64 KiB each — Expected"): K=8 0.5 MiB, K=32 2 MiB, 64 KiB each [observed]. The refute threshold of B3f (ΔUsed/K ≥ 128 KiB or ΔOverflow ≥ 16 MiB on v64) is not met [observed].

B3a's `ant jar` was covered by the unit tier's `build-test` in the same copies. RSS was not measured (B3d's named gap for pooled slabs).
7. **Core question.** The direct memory held by open data-file readers on the standard, uncompressed, cache-less path follows the constant: 32 / 64 / 1024 KiB per reader for the three builds with 1 MiB partitions, and the same 8 KiB per reader in every build when partitions are below the cap (parts 1, 3, 4). The constant caps the **per-reader** buffer; the total is K x cap and grows with the number of open readers (part 3, row 5).

**Conclusion (cluster, one line):** B3g row 1 — **confirmed** (with row 5, per-reader cap, total = K x cap).
