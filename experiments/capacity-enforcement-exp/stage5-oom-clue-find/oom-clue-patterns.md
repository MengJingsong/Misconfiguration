# OOM clue patterns

*Started 2026-11-17.* The known shapes of code that lead to out-of-memory failures, for the stage-5
**guided** agent ([`playbook-guided.md`](playbook-guided.md)). **The autonomous agent never opens this
file.** System-agnostic; examples are per system.

Each pattern: an ID (`CP-<n>`, never reused), the shape in one line, the question that finds it in a case
file, examples, and its **sources**: `JIRA <system>` (a JIRA OOM report:
[Cassandra](../cassandra/stage5-oom-clue-find/jira-oom-report.md),
[Hadoop](../hadoop/stage5-oom-clue-find/jira-oom-report.md)) and/or `phase 2: <case ID>` (a phase-2 true
positive), with the date added. Add a pattern when a JIRA report or a phase-2 true positive shows a shape
no pattern covers; do not re-label existing candidates.

## Patterns

| ID | Pattern (shape) | Question to ask of a case | Examples | Sources | Added |
|---|---|---|---|---|---|
| CP-1 | **Counted unit ≠ held memory.** The counter charges a smaller unit than the memory really held: serialized or on-wire bytes for deserialized objects, payload without per-entry overhead, an estimate, or one copy where several live | What unit does the counter charge, and how many bytes does an admitted object really hold (deserialized, with container or node overhead, with copies)? Held ÷ counted × the default cap: what share of the budget is that? | Cassandra: JIRA 3741 → 6655 → 9194 (deletes charged as 0 bytes), 4315, 4860 (cache entry size), 6078, 16071; phase 2 B6 (internode queues count on-wire bytes, tiny-cell mutations ≈ 17–20× on heap), B8 (replay bound counts serialized bytes, ≈ 15× held), B7 (cache weigher omits ≈ 90 B per entry). Hadoop: none yet | JIRA cassandra; phase 2: B6; phase 2: B8 | 2026-11-17 |
| CP-2 | **Item count, not bytes.** The limit bounds how many items (rows, entries, mutations, tombstones, columns, statements) are held, not how large each one is | Does the limit count items? What bounds one item's size at defaults, and is count × largest item within the budget, per operation and over the operations that may run at once? | Cassandra: JIRA 2652, 3624 (hint pages sized in columns), 8639 (replay ≤ 1000 mutations), 6107 (prepared cache by entry count). Hadoop: none yet | JIRA cassandra | 2026-11-17 |
| CP-3 | **Counter released before the memory is freed.** The charge is returned at an earlier event (flush, response hand-off, first acknowledgement, an accounting switch) while the object stays reachable | When is the counter released, and when does the memory become unreachable? What still references the object in between (callback, hint, queue, outbound buffer, index), and for how long? | Cassandra: JIRA 157, 8164, 12358, 11026, 3163; phase 2 S2 (in-flight charge returned at the first CL=ONE ack while the coordinator's own write still waits), C2 (request charge returned at response hand-off; unsent responses never charged), B6 (send queue released at flush, mutation kept until response). Hadoop: none yet | JIRA cassandra; phase 2: S2; phase 2: C2; phase 2: B6 | 2026-11-17 |
| CP-4 | **Lifetime ends on response or timeout, and a fault stalls it.** Memory is held until a peer, disk or client answers; a realistic fault keeps it, and timeout × arrival rate × size is the only bound | What ends this allocation's lifetime? What is arrival rate × timeout × size? | Cassandra: JIRA 8969 (the yaml warns high timeouts build up memory), 9318, 3537 (expiry timer died), 1607; phase 2 B6 (sent mutations kept until response or deadline; replica expiry runs only on stalled stage threads). Hadoop: none yet | JIRA cassandra; phase 2: B6 | 2026-11-17 |
| CP-5 | **Accepting queue with a slow, stalled or dead consumer.** Producers keep adding to a queue with no byte bound while its consumer is slower, blocked or gone, and nothing pushes back | If this queue's consumer slows, blocks or throws, what stops the producers? Hadoop: none yet | JIRA cassandra; phase 2: S2; phase 2: C2 | 2026-11-17 |
| CP-6 | **No graceful stop at the limit.** The disallow path still allocates (pool overflow, fallback buffer, a refused request processed anyway), or nothing refuses before the JVM's own `OutOfMemoryError` / direct-memory limit | What happens when the limit is reached: reject, block, evict, shrink, or a fallback allocation? If nothing refuses, is the JVM's error the real enforcement? | Cassandra: JIRA 11082 (Netty water marks set but never checked), 21529, 16154, 11710; phase 2 C2 (pool overflow and unsent responses bounded only by `MaxDirectMemorySize`). Hadoop: none yet | JIRA cassandra; phase 2: C2 | 2026-11-17 |
| CP-7 | **Per-owner limit × unbounded owners.** A limit (or a natural size) holds per connection, peer, table, sstable, thread, range or job, and nothing caps the total | Per what does the limit apply? Hadoop: none yet | JIRA cassandra; phase 2: C1; phase 2: S1 | 2026-11-17 |
| CP-8 | **Defaults that together over-commit a shared budget.** Several constraints, each within its own default, add up past the memory domain they share (heap, direct, native, container) at a deployment size; fixed defaults that do not scale with the heap are the usual culprits, and so is a limit that exists but ships off (0, −1, unlimited; *reworded 2026-11-18 from the Hadoop JIRA report*) | Which domain does this draw on, what else draws on it, and do the shipped defaults, resolved at a small and a typical deployment, sum to more than that domain's default budget? | Cassandra: JIRA 1469, 1641, 2413, 6059 (memtable and cache defaults vs the heap), 2142, 11710; phase 2 R1-V (off-heap memtable + chunk-cache pool vs the container), S1 (stacked direct pools). | CP-9 | **Memory outside every JVM limit.** Native `malloc`, mmap, allocator arenas or JDK caches bounded by neither `-Xmx` nor the direct-memory limit, or a JVM limit sized from the host rather than the container | Is this memory bounded by the heap limit, the direct limit, or only by the container or kernel? How are the JVM limits derived (from the heap, from host RAM), and do they leave room for it? | Cassandra: JIRA 2868, 9573, 13008 / 14474 (map count), 10689, 13931, 19976 (JDK temporary direct buffers), 8723, 11109, 20565 (unexplained RSS growth to a kernel kill); phase 2 R1-V (JNA-malloc memtable outside both JVM limits, memcg kill). Hadoop: none yet | JIRA cassandra; phase 2: R1-V | 2026-11-17 |
| CP-10 | **A path that skips the limit.** The same objects are created on a path the check does not cover: replay, hints, batchlog, streaming, repair, index or view build, another protocol version, an exempt caller, an unpaged branch | List every path that creates what this limit governs (startup replay, hint and batchlog replay, streaming, repair, index and view builds, error paths, each protocol version, privileged callers): does each go through the same check? | Cassandra: JIRA 609 (replay ignored memtable limits), 20052 (v5 messages had no size limit), 13299, 12707, 21401. **Origin (2026-11-17).** The patterns consolidate three retired sets: the guided stage-3 enforcement
properties E1–E4, the phase-2 case patterns P1–P6 and search patterns S1–S6 (with their "Ask" questions),
and the cause shapes of the [Cassandra JIRA OOM report](../cassandra/stage5-oom-clue-find/jira-oom-report.md)
(its §7 maps them). Old labels: **E1** → CP-1 (what is counted) and CP-3 (for how long); **E2** → CP-6;
**E3** → CP-7; **E4** → CP-8 (CP-9 where the domain is native memory or the container). **S1** → CP-1, CP-2;
**S2** → CP-4; **S3** → CP-5; **S4** → CP-7; **S5** → CP-10; **S6** → CP-9. **P1** → CP-1; **P2** → CP-4
(with CP-3); **P3** → CP-8; **P4** → CP-7; **P5** (fill the standing pool, then burst; a pool capped only at
a periodic resize) → CP-11; **P6** (at larger heaps the endpoint is GC collapse, not OOM) → none: it
describes the failure's form, not a code shape, and stays a phase-2 design note.
