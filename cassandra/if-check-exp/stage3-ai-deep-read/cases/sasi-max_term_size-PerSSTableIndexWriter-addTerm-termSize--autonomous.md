## A. Constraint trace

**A1. The constraint.** `OnDiskIndexBuilder.MAX_TERM_SIZE`, a compile-time constant `public static final int MAX_TERM_SIZE = 1024;` first declared at `src/java/org/apache/cassandra/index/sasi/disk/OnDiskIndexBuilder.java:128`. Unit: bytes (compared with `ByteBuffer.remaining()`). Default 1024, not derived from anything. Not settable (no yaml key, no `-D`, no JMX); a change needs a source edit and rebuild. SASI itself is gated by `sasi_indexes_enabled` (default false; `Config.java:606`, `conf/cassandra.yaml:1992`), which must be set true to create a SASI index.

**A2. What it caps.** Neither heap nor disk directly. It rejects any single analyzed term whose length is >= 1024 bytes (so the largest accepted term is 1023 bytes). The compared quantity is `token.remaining()`, the size of one token produced by the column's analyzer. Resources touched downstream: heap (the `OnDiskIndexBuilder.terms` map, `OnDiskIndexBuilder.java:143`, `:159`) and disk (SASI `SI_*.db` component files).

**A3. Mechanism.**
1. A row reaches `PerSSTableIndexWriter.nextUnfilteredCluster` (`PerSSTableIndexWriter.java:121`), which calls `Index.add(value, currentKey, currentKeyPosition)` at `:136`.
2. `Index.add` (`:205`) runs the column analyzer over the value (`:212-215`) and takes `size = token.remaining()` (`:216`).
3. At `:218` `token.remaining() >= OnDiskIndexBuilder.MAX_TERM_SIZE` logs "Rejecting value" at INFO (`:220-225`) and `continue`s: the token is skipped, the row/write is still accepted, and the other tokens of the same value are still indexed. No exception, no error to the client.
4. Surviving tokens go through the validity check (`:229-241`) and `currentBuilder.add(token, key, keyPosition)` (`:243`). `OnDiskIndexBuilder.add` repeats the same check at `OnDiskIndexBuilder.java:167` (logs at ERROR, `:169-172`, and prints `Short.MAX_VALUE`, not 1024, as the maximum, a message inconsistency) and accumulates `estimatedBytes` (`:182`, `:194`).
5. After each value, `currentBuilder.estimatedMemoryUse() < maxMemorySize` (`:247`) decides whether to flush a segment asynchronously (`:250`). `maxMemorySize` is `1073741824L` when `source == OperationType.FLUSH` and `columnIndex.getMode().maxCompactionFlushMemoryInBytes` otherwise (`:365-369`); the latter defaults to 0.15 * 1 GiB = 161,061,273 bytes (`IndexMode.java:59-60`; amended 2026-10-25, B5.1: was `:60-61`, line 61 is blank) and can be set with the index option `max_compaction_flush_memory_in_mb` (`IndexMode.java:58`, `:186-188`; values over 100 GiB revert to the default, `:190-194`). The comment at `:367` ("1G for memtable") does not describe the compaction default.
6. The memtable-side index duplicates the check: `TrieMemIndex.add` skips terms >= 1024 (`TrieMemIndex.java:84-92`) with INFO log; memory is accounted via `ConcurrentTrie.add` overhead (`TrieMemIndex.java:116-137`).
7. Overshoot / bypass: the cap is on terms, so (a) a value of any size is indexed if the analyzer splits it into small tokens (tokenizing analyzer, `StandardAnalyzer.isTokenizing`, `StandardAnalyzer.java:210`); (b) the number of distinct 1023-byte terms is unbounded by this check; (c) the flush threshold check happens only after a whole value has been added (`:247`), so the builder can exceed `maxMemorySize` by one value's worth of tokens; (d) the memtable-side `IndexMemtable` (`ColumnIndex.java:64`, `:80`, `:116`) has no flush-time size cap of its own beyond the table memtable's.

**A4. Other consumers.** The table memtable and its flush; the SASI `IndexMemtable`/`pendingFlush` trie (`ColumnIndex.java:64-65`); the `OnDiskIndex` segments held open during merge (`PerSSTableIndexWriter.java:266`, `:320-323`); the 8-thread SASI flush pools (`:63-74`); transient `_N` segment files plus the final component on disk (`:341`, `:361`); the compaction/flush data files themselves.

**A5. Evidence beyond the source.** Test `testThatTooBigValueIsRejected` (`test/unit/org/apache/cassandra/index/sasi/SASIIndexTest.java:1453-1481`) shows too-big values are silently not indexed (query returns 0 rows before and after flush). Cassandra SASI docs (https://cassandra.apache.org/doc/latest/cassandra/developing/cql/indexing/sasi/) not consulted offline; otherwise none.

## B. Verification solution

**B1. Claim under test.** Total SASI index memory (builder `estimatedMemoryUse()`) and on-disk index size do not follow `MAX_TERM_SIZE`: with every term kept at 1023 bytes (just under the limit) or tokenized to small tokens, index size grows linearly with the number of distinct terms and the data volume, up to the separate flush threshold, whereas `max_compaction_flush_memory_in_mb` does move the point at which segments are flushed. The 1024-byte limit only decides which individual terms are dropped.

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Copy the tree to local disk (`rsync -a ~/cassandra-5.0.9/ /local/$USER/c509/`); `cd /local/$USER/c509 && ant jar` (or `ant build-test`). Run: `ant testsome -Dtest.name=TermSizeCapProbeTest`. JVM options: the stock `-Xmx` from build.xml test config; add `-Xmx2g` if needed.

**B2b. Knobs.** (1) Term size S in bytes: 1022, 1023, 1024, 1025 (boundary). (2) Number of distinct terms N: 1k, 10k, 100k. (3) Positive control: `max_compaction_flush_memory_in_mb` index option, 1 vs 8 vs default, with `OperationType.COMPACTION` as source. Set by constructing `IndexMode` through `ColumnIndex` options map, or by calling `OnDiskIndexBuilder` directly for (1)-(2).

**B2c. Workload.** Feed N distinct terms of exactly S bytes (unique prefix 8 bytes of counter + fill) through `PerSSTableIndexWriter.Index.add` with a non-tokenizing analyzer, one key per term. Per-term estimate in the builder is 64+48+S plus 60+40+8 = S+220 bytes (`OnDiskIndexBuilder.java:182`, `:194`). With S=1023, N=100k gives about 124 MB estimated, reaching the 1 MiB option threshold at the 844th term (843 x 1243 = 1,047,849 < 1,048,576 <= 844 x 1243; amended 2026-10-25, B5.2: was "about 860") and the 0.15 GiB default at the 129,575th term (so use N=200k for default crossing).

**B2d. Observables and instruments.** `currentBuilder.estimatedMemoryUse()` (via reflection or test subclass) after each add; count of `segments` (`PerSSTableIndexWriter.java:190`); log lines "Rejecting value" (count); final index file length from `outputFile`; JVM heap via `MemoryMXBean` after `System.gc()` as a cross-check of the estimate. Not observable directly: the true heap cost of the estimator's constants.

**B2e. Procedure.** 1) Build; 2) for each S in the list with N=10k: add terms, record accepted count (expect N for S<=1023, 0 for S>=1024), `estimatedMemoryUse()`; 3) for S=1023 vary N in 1k/10k/100k and record estimate and final file size after `complete()`; 4) repeat step 3 with source COMPACTION and `max_compaction_flush_memory_in_mb`=1, 8, default; record number of segments; 5) tokenizing run: one 1 MB text value split into 5-byte words by `StandardAnalyzer`, record estimate (no rejection); 6) clean temp dirs.

**B2f. Predictions.** [Rewritten 2026-10-25 before any reading of this case, B5.3-B5.5; the old text is quoted in B5.] All arms drive `PerSSTableIndexWriter.Index.add` (COMPACTION source, PREFIX, non-analyzed unless stated) with one distinct key per add; Cmin = ceil(cap_bytes / 1243) is the number of adds that first reaches the cap. (5) FLUSH source, same adds, option ignored: 0 cuts at N=100,000 (1 GiB = 1,073,741,824 B -> Cmin 863,831). (6) Tokenized arm: one value of 131,072 distinct 7-byte words ("w000000 " ... , 8 bytes each with the space, 1 MiB = 1,048,576 bytes) through the writer with `analyzed=true, analyzer_class=StandardAnalyzer`: zero rejections although the value is 1024 x the limit; estimate = 131,072 x (64+48+7+108) = 29,753,344 exactly; with option 1 (cap 1,048,576) exactly one cut, at that single add, with the estimate 28.4 x the cap (the check runs only after a whole value, `:247`). ### B5. Stage-4 audit amendments (2026-10-25, before any reading of this case's runs)

Every cited line of A1-A4 and B2d was re-read in the pinned source; the only wrong cite is the first below. The read of the sibling case's results (`sasi-max_term_size-OnDiskIndexBuilder-add-termSize--autonomous`, closed) informed B5.6 and B5.10 (disclosed here); no reading of this case exists.

1. `IndexMode.java:60-61` is `:59-60` (the multiplier at `:59`, the default at `:60`; `:61` is blank). The comment at `PerSSTableIndexWriter.java:367` ("1G for memtable and configuration for compaction") is accurate for FLUSH; the default of the configuration for compaction is 0.15 GiB = 161,061,273 B (`IndexMode.java:60`, truncated by `(long)`).
2. B2c: 1,048,576 / 1243 = 843.6, so the 1 MiB cap is reached at the 844th term, not "about 860"; the 0.15 GiB default at the 129,575th (161,061,273 / 1243 = 129,574.4); the 8 MiB cap at 6,749; 16 MiB at 13,498; the 1 GiB flush cap at 863,831.
3. B2f segment counts made exact: cuts = floor(N / Cmin) and the inline leftover `scheduleSegmentFlush(false).call()` (`PerSSTableIndexWriter.java:300-304`) logs one more "Flushed index segment" line, so lines = cuts + 1 when cuts > 0 and a remainder exists. For N=100k the old "about 118 / about 15 / 0" are 118 / 14 / 0 cuts. When there are no cuts, `complete()` builds the whole index in one final flush (`:293-297`) with no segment line.
4. B2f "no file bytes beyond header" is wrong: an empty builder's `finish` calls `file.createFileIfNotExists()` and returns false (`OnDiskIndexBuilder.java:241-246`), and `scheduleSegmentFlush` returns null for it, so the file is created with zero length.
5. B2e step 5 (tokenized value) was not computable: "a 1 MB value split into 5-byte words" does not say whether the words are distinct, and the estimator charges 108 B per posting but 64+48+size only per new term. Made exact in B2f(6): 131,072 distinct 7-byte words, 227 B each (one key). `StandardTokenizerOptions` defaults (`minTokenLength 0`, `maxTokenLength 255`, `StandardTokenizerOptions.java:35-36`; stop words ignored, lower case) do not touch "w000000"-style words; note a tokenized term can never reach 1024 bytes, since tokens over 255 are dropped by the tokenizer before the writer's check.
6. B3f "1.0-1.3 KB per row" assumed size + about 100 B per term; the builder writes 4 KiB blocks (`OnDiskIndexBuilder.java:127`) with token trees, so absolute bytes per row are not predictable from source. Replaced by a lower bound (term bytes alone, N x 1023) and a ratio (3.5-4.5 for 4x rows). Old text: "column a: SI_ file size grows linearly with N (about 1.0-1.3 KB per row, so about 100-130 MB at 100k, about 4x at 400k)".
7. CONTAINS mode is not run: suffix expansion makes S entries per term (about 52 GB at S=1023 and 400k rows). PREFIX only.
8. Column `c` of 5 KB random words in the 400k-row table inserts about 280 million postings (700 per row) and a trie of that size does not fit a 2 GiB heap; moved to its own table with 2,000 and 8,000 rows (about 1.4 and 5.6 million postings).
9. B3b(4) had two cap values (1 vs default); a third (16) was added so the control has three values including the default, as the audit group A asks.
10. Autocompaction is disabled (`nodetool disableautocompaction ks t`) before loading, so every "Flushed index segment" line in the compaction window comes from the one `nodetool compact` (a major compaction, not `FLUSH`). Node heap 2 GiB (`-Xms2g -Xmx2g`); the cap control is judged on the segment count, not on peak heap (the heap peak is G1 `used` and includes garbage).
11. Old B2f text, quoted: "S=1022,1023: all N accepted; S=1024,1025: zero accepted, N INFO log lines, estimate 0, no file bytes beyond header. For S=1023: estimate = N*(1023+220) within 5 percent, file size linear in N (R^2 > 0.99), no plateau at any N up to the flush threshold. Segments: N=100k with option=1 MB gives roughly 100k*1243/1 MiB, about 118 segments; option=8 gives about 15; default gives 0 extra segments (single final flush). The 1 MB tokenized value yields an estimate far above 1024 bytes while zero terms are rejected." Old B3f, quoted: "Column a: SI_ file size grows linearly with N (about 1.0-1.3 KB per row, so about 100-130 MB at 100k, about 4x at 400k); column b: zero indexed rows, one INFO "Rejecting value" per row, SI_ file of header size only; column c: index size proportional to total tokens, with no rejections. Heap during flush rises with the builder estimate and drops after segment flush; with default option, compaction produces fewer "Flushed index segment" lines than with option=1 (about 100x more segments at 1 MB). Index disk is not bounded at any N by the 1024 limit."
12. Left for stage 3 (not applied): the B3d instruments `jstat -gc` sampled every 5 s are replaced by the harness's own 500 ms JMX heap sampler; `nodetool tablestats` is run but not a decision row; the message at `OnDiskIndexBuilder.java:171` prints `Short.MAX_VALUE` where the limit is 1024 (cosmetic).
