## A. Constraint trace

**A1. The constraint.** `CQLLimits.rowLimit`, the `protected final int` field at `DataLimits.java:349`, set in the constructor at `:365-370`. It comes from the CQL `LIMIT n` clause or the paging page size (`forPaging`, `:392-395`). Unlimited is `NO_LIMIT = Integer.MAX_VALUE` (`:48`). Kind: runtime query parameter (not a config entry or JVM property). Unit: rows. Default: `NO_LIMIT` when no LIMIT is given (`DataLimits.cqlLimits`, `:99`); with paging the driver page size (default 5000 rows in the Java driver) becomes the row limit. Setting: per query (CQL `LIMIT`, driver page size, `PAGE SIZE` in cqlsh). *(Amended 2026-10-27: "no limit" is the singleton `DataLimits.NONE`, whose `hasEnoughLiveData` is overridden to return `false` (`DataLimits.java:50-56`), so it never reaches `:414`. With paging (`SelectStatement.java:338`: paged when `pageSize > 0` and `limit.count() > pageSize`) the first page's limits are `forPaging(pageSize)` (`SinglePartitionPager.java:90`, `DataLimits.java:392`): through a driver with its default page size 5000 the row limit seen at `:414` is `L` for `L <= 5000` and 5000 for `L = 100000` and for no LIMIT.)* No restart. Server-side maximums (`aggregation_subpage_size`, `page_size` caps) are separate. The operand actually checked at `:414` is `cached.rowsWithNonExpiringCells()` (`CachedBTreePartition.java:140`, computed `:87-109`) against `rowLimit`.

**A2. What it caps.** Number of rows returned by a query (result size), not memory or disk. The related real resource limits are the row cache: `row_cache_size` (`Config.java:474`, default 0 MiB, i.e. disabled), applied as OHC capacity in `OHCProvider.java:40`, and the per-table `caching = {'rows_per_partition': N}` (`CachingParams.java`, used at `SinglePartitionReadCommand.java:566`).

**A3. Mechanism.**
1. `SinglePartitionReadCommand.getThroughCache` (`:507`) looks up `CacheService.instance.rowCache.get(key)` (`:515`).
2. On a non-sentinel hit it calls `cfs.isFilterFullyCoveredBy(...)` (`:528`).
3. `ColumnFamilyStore.isFilterFullyCoveredBy` (`:1916-1939`): if `cachedLiveRows < rowsPerPartitionToCache` the partition is fully cached, so return true (`:1931`). *(Amended 2026-10-27: line `:1930` -> `:1931`. With `rows_per_partition = 'ALL'`, `rowsPerPartitionToCache` is `Integer.MAX_VALUE` (`CachingParams.java:81`), so this test is always true and `hasEnoughLiveData` is never called: the `LIMIT` cannot matter for a table with `ALL`.)* Otherwise, for a head filter, it calls `limits.hasEnoughLiveData(...)` (`:1938`).
4. `CQLLimits.hasEnoughLiveData` (`DataLimits.java:407-431`): if `rowsWithNonExpiringCells >= rowLimit` return true (`:414`, the target); else if `rowCount < rowLimit` return false (`:417`); else re-count through a `CQLCounter` over the cached partition (`:422-430`).
5. True: `rowCacheHit` is incremented and the cached partition serves the query (`:528-535`). False: `rowCacheHitOutOfRange` is incremented and a normal memtable/sstable read happens (`:538-541`).
Outcomes at the limit: no error, no truncation, no eviction. Larger `LIMIT` just makes the cache less likely to serve the query. The re-count path (`:422-430`) iterates at most the cached partition (bounded by `rows_per_partition`) and allocates only a counter and iterator, so it is transient and small. Note the cached partition built by `CachedBTreePartition.create` (`:566-590`) is bounded by `rowsToCache`, not by any query limit. Bypass note: the target is not on the write or cache-population path at all.

**A4. Other consumers.** Row cache (off-heap OHC) is shared by all tables with row caching on; key cache, chunk cache (`file_cache_size`), memtables and the read path result buffers (`PartitionRangeReadCommand.java:418` also calls the same check) use heap/off-heap independent of `rowLimit`. A huge result set with a large `LIMIT` is bounded elsewhere (paging, `aggregation_subpage_size`, `native_transport_max_frame_size`), not at line 414.

**A5. Evidence beyond the source.** Comment at `DataLimits.java:409-413` describes it as a cheap shortcut to avoid re-counting. Row cache docs: https://cassandra.apache.org/doc/5.0/cassandra/developing/cql/ddl.html (caching option) and `row_cache_size` in `cassandra.yaml`. CASSANDRA-3862 (sentinel scheme, referenced in `SinglePartitionReadCommand.java:512`).

## B. Verification solution

**B1. Claim under test.** Memory used by the row cache (and the node) does not follow the per-query `LIMIT` value evaluated at `DataLimits.java:414`: varying `LIMIT` over a fixed cached partition changes only hit vs hit-out-of-range counters, not cache weight or heap/off-heap. Refuted if cache size or process memory scales with `LIMIT`.
