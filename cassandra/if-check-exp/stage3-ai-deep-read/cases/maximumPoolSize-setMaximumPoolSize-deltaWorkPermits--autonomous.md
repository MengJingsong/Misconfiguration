Note on the entry pointer: line 384 is the `if (deltaWorkPermits == 0) return;` early exit in `setMaximumPoolSize`. It is a no-op guard (skips the permit update, log line and listener call when the new value equals the old one). It is not itself an enforcement point; the constraint is the maximum pool size that this method resizes.

## A. Constraint trace

**A1. The constraint.** `SEPExecutor.maximumPoolSize` (an `AtomicInteger`, SEPExecutor.java:~53 declaration, set at :75). Kind: configuration entries feeding a runtime-resizable value. For the request stages it comes from yaml `concurrent_reads`, `concurrent_writes`, `concurrent_counter_writes`, `concurrent_materialized_view_writes` (Config.java:179-182, all default 32; conf/cassandra.yaml:722-724 documents the first three). The stage table binds them: `Stage.READ`, `MUTATION`, `COUNTER_MUTATION`, `VIEW_MUTATION` use `DatabaseDescriptor::getConcurrentReaders` etc. as the thread-count supplier and `setConcurrent*` as the listener (Stage.java:46-49), all built through `Stage::multiThreadedLowSignalStage` (Stage.java:229-235), which calls `SharedExecutorPool.SHARED.newExecutor` (ExecutorFactory.java:244-246; SharedExecutorPool.java:146-150). `REQUEST_RESPONSE` also uses SEPExecutor but with `getAvailableProcessors` and no yaml key. Unit: concurrent tasks (threads). Default 32, taken literally from Config. Setting: yaml at startup (restart needed); at runtime `nodetool setconcurrency <stage> <core> <max>` -> `StorageService.setConcurrency` (StorageService.java:2397-2403) -> `Stage.setMaximumPoolSize` (Stage.java:275-277) -> `SEPExecutor.setMaximumPoolSize` (SEPExecutor.java:368-396), also reachable by the SEPExecutorMBean JMX. Core size cannot be set (`setCorePoolSize` throws, :357-360).

**A2. What it caps.** Resource: other, a thread/concurrency count (work permits). Compared quantity: `workPermits(permits)`, the high 32 bits of the packed `AtomicLong permits` (:60, :403-406). It is initialised to `maximumPoolSize` (:77) and `takeWorkPermit` refuses when it is `<= 0` (:196). It is not a byte quantity.

**A3. Mechanism.**
1. Construction: `permits = combine(0, maximumPoolSize)` (:77): 0 task permits, N work permits.
2. `addTask` enqueues first, then increments the task-permit half (:123-133), never blocking or rejecting despite the comment about a queue limit (:129-130); if it was 0 it starts a spinning worker (:135-143).
3. `maybeSchedule` (:110-117) / `maybeExecuteImmediately` (:217-240) call `takeWorkPermit`, which needs both a work permit and (optionally) a task permit (:188-203). So at most N workers run tasks of this executor at once; excess tasks wait in `tasks`.
4. Resize: `setMaximumPoolSize` (:368-396) rejects negatives (:373-376), CASes `maximumPoolSize` (:379), computes `deltaWorkPermits` (:378), returns early on 0 (:384-385, the target line), otherwise adds the delta to the work permits (:387), logs (:388), starts a spinning worker (:393) and calls the stage listener (:395; for READ etc. that writes `DatabaseDescriptor.conf.concurrent_*`, DatabaseDescriptor.java:2406-2412 etc.). Shrinking makes work permits negative; `takeTaskPermit(true)` returns permits so workers exit (:165-172, enum :147-152).
5. Outcome at limit: nothing is rejected or dropped; tasks queue without bound. Overshoot paths: unbounded queue; `maybeExecuteImmediately` only runs inline when a work permit is free (:221-237) so it does not exceed N; a shrink leaves already-running tasks running (permits go negative, active count `maximumPoolSize - workPermits` can exceed the new max transiently, :347-350).
6. Target line 384 outcome: equal value is a no-op, so repeated identical `setconcurrency` calls neither log nor wake workers nor call the listener (and so do not re-sync `DatabaseDescriptor`).

**A4. Other consumers.** Memory per running read/write is dominated by things the knob does not control: memtable heap/off-heap (`memtable_heap_space`, `memtable_offheap_space`), chunk cache / buffer pool, row cache, key cache, native transport request limits (`native_transport_max_request_data_in_flight*`), response/serialisation buffers, compaction. The shared pool's worker threads are shared across executors (SharedExecutorPool), so the thread count is also driven by other SEP executors and `spinningCount`.

**A5. Evidence beyond the source.** none (no external docs relied on; the yaml comments at conf/cassandra.yaml:710-721 describe it as an IO/CPU-parallelism tuning knob, not a memory limit).

## B. Verification solution

**B1. Claim under test.** Increasing or decreasing the SEP maximum pool size changes the number of concurrently running tasks but does not bound memory: queued-task memory is unbounded regardless of the value, and a node's heap/off-heap use under a fixed read/write load does not plateau at a value set by the knob. Refutation: memory held by queued or running work plateaus at a level proportional to the knob and is independent of offered load.

### B2. Unit tier

**B2a. Environment and build.** Linux, JDK 11, Ant. `git clone` the pinned tag to local disk (e.g. `/local/$USER/c509`; never build in the shared clone), `ant jar` (or `ant build-test`). Put a driver class in the local clone's `test/unit/org/apache/cassandra/concurrent/SepCapProbe.java` (a JUnit test or `main`), run with `ant testsome -Dtest.name=org.apache.cassandra.concurrent.SepCapProbe` or `java -cp build/classes/main:build/test/classes:lib/*:build/lib/jars/*`. JVM options: `-Xmx1g -Xms1g -Xss256k -XX:+UseG1GC -XX:NativeMemoryTracking=summary -Dcassandra.config=...` is not needed (no DatabaseDescriptor use if the pool is built directly via `new SharedExecutorPool("probe").newExecutor(n, "internal", "probe")`). [Amended 2026-10-22: see U1 in "Audit amendments".]

**B2b. Knobs.** `maxConcurrency` n in {1, 4, 32, 128} passed to `newExecutor`. Also resize at runtime with `setMaximumPoolSize` to 4 -> 32 -> 32 (repeat, hits line 384) -> 8. Reason: spans below, at and above the default 32 and exercises grow, shrink and the no-op path.

**B2c. Workload.** Submit T = 2000 tasks. Each task allocates a `byte[1 MiB]`, stores it in a static `ConcurrentLinkedQueue` registry (live-set accounting), then blocks on a `CountDownLatch` gate (so running tasks pile up to the limit), and on release drops the buffer. Arithmetic: running tasks at the gate = min(n, T); held memory by running = n MiB; queued tasks = T - n, each holding only the small closure (but see variant: allocate the 1 MiB at submit time in the submitting thread, so queued tasks also hold 1 MiB: queued memory = (T - n) MiB, i.e. ~2000 MiB at n=1 which exceeds -Xmx1g, so use T = 600 for the heap-fit variant). Variant A (allocate in task): measures running-set memory; Variant B (allocate at submit): measures queued memory.

**B2d. Observables and instruments.** `executor.getActiveTaskCount()` (:347-350), `getPendingTaskCount()` (:335-339), `getMaximumPoolSize()`; `ThreadMXBean` live thread count and `Thread.getAllStackTraces()` filtered by the pool's thread names; registry byte total (counter of allocated MiB); `MemoryMXBean` heap used after `System.gc()` at each stage; `jcmd <pid> VM.native_memory summary` (thread stack category). Sample once the gate has been closed for 2 s. Cannot observe directly: per-thread resident stack (only NMT committed).

**B2e. Procedure.** (1) Build the tag locally. (2) For each n: create pool + executor(n); submit T tasks (variant A); wait 2 s; record active, pending, thread count, registry total, heap-after-GC, NMT thread; release gate; wait for completion; shutdown pool (`shutdownAndWait`). (3) Repeat variant B. (4) Resize test: with the gate closed and executor(4) at 600 queued tasks, call `setMaximumPoolSize(32)` and record the active count growth; call it again with 32 and confirm no second "Resized" log line and no listener invocation (use a counting `MaximumPoolSizeListener`); then `setMaximumPoolSize(8)` and record active count after releasing a few tasks. (5) Positive control (B2h). (6) Confirm no leftover JVM (`pgrep -f SepCapProbe`). [Amended 2026-10-22: see U2, U3 in "Audit amendments".]

**B2f. Predictions.** Variant A: active = min(n, T); registry total = n MiB; pending = T - n; heap-used grows linearly with n (about n MiB) and stays well below the offered T MiB. Variant B: heap-used about T MiB regardless of n (queue unbounded), identical across n=1..128 within allocation noise. Thread count grows with n only up to n plus a few spinners; NMT thread category changes by about 256 KiB per added thread (at most ~32 MiB between n=1 and n=128 if all committed; in practice less). No rejection or blocking in `execute` at any n. Resize: grow raises active toward 32; repeated 32 gives zero extra log/listener calls; shrink to 8 leaves already-running tasks running (active may exceed 8 until they finish).

**B2g. Readings.** [Amended 2026-10-22: see U4 in "Audit amendments".]

| Observation | Meaning |
|---|---|
| Variant B heap equal across n; queue unbounded; no rejection | Claim confirmed: knob does not cap queued memory |
| Variant A heap rises linearly with n | Expected indirect effect; shows the knob scales usage but does not bound it (not a refutation) |
| Variant B heap or pending count plateaus, or `execute` blocks/throws, at a value that depends on n | Claim refuted: knob caps queued memory |
| Positive control (bounded queue / semaphore) pending plateaus at its bound while SEP pending keeps growing | Claim confirmed (control moved, SEP flat) |
| Control did not plateau, or n never reached (active < n) | Not confirmed (harness or load insufficient) |
| Second `setMaximumPoolSize(32)` logs or fires the listener | Early return at :384 misread; revise A3 step 6 |

**B2h. Controls.** Positive control: same T tasks into `new ThreadPoolExecutor(n, n, 0, ms, new ArrayBlockingQueue<>(64))` with `CallerRunsPolicy` or an `AbortPolicy`, where the queue bound is a known cap: pending must plateau at 64 and Variant B heap stay near 64 MiB + n MiB. Also repeat each n three times to bound GC noise; run `System.gc()` before each reading; keep gate closed identically.

### B3. Cluster tier

**B3a. Environment and build.** One node (second optional for CL=ONE realism) on a Linux host, JDK 11, built from a local clone (`ant jar`; run from `build/`, not the shared clone). Data, commitlog, hints on local disk of known size (>= 20 GB free, directories under `/local/$USER/cass1/`). JVM: `-Xms2g -Xmx2g` fixed (set `MAX_HEAP_SIZE`/`HEAP_NEWSIZE` in cassandra-env.sh copy or jvm11-server.options), `-XX:NativeMemoryTracking=summary`. Config changes: `concurrent_reads` and `concurrent_writes` as in B3b; `native_transport_max_request_data_in_flight` left default for the main run; `memtable_allocation_type: heap_buffers` to keep memory on heap and observable; `commitlog_sync` default.

**B3b. Knobs.** `concurrent_writes` in {4, 32, 256} and `concurrent_reads` in {4, 32, 256}, set in yaml before start (restart per value) and, as a second path, via `nodetool setconcurrency MutationStage 0 <n>` (and `ReadStage`) on a running node, including a repeat of the same value (target line 384). Reason: below, at default and well above; large enough to exceed client concurrency. [Amended 2026-10-22: see C1, C2 in "Audit amendments".]

**B3c. Workload.** `cassandra-stress` (from the same build `tools/bin`) against a table with 1 KiB-ish values: write phase `n=3,000,000 -rate threads=400`, then read phase mixed `-rate threads=400` for 10 min each, so offered concurrency (400 client threads) exceeds every n except 256 partially; `-mode native cql3`. Arithmetic: 400 in-flight client requests > 4 or 32 workers, so the stage queues (pending grows) and tasks run n at a time. Duration: 10 min write + 10 min read per knob value; after each, a 3 min idle. [Amended 2026-10-22: see C3 in "Audit amendments".]

**B3d. Observables and instruments.** Heap used and after-GC via `jstat -gc <pid> 1000` (and GC log `-Xlog:gc*:file=...`); off-heap via `jcmd <pid> VM.native_memory summary` every 30 s; RSS via `ps -o rss= -p <pid>`; live thread count via `jcmd <pid> Thread.print | grep -c ReadStage` or JMX `java.lang:type=Threading`; stage state via `nodetool tpstats` (Active/Pending/Completed for ReadStage/MutationStage) every 5 s; JMX `org.apache.cassandra.metrics:type=ThreadPools,...,name=PendingTasks`; disk via `du -sb` on the data dirs. Cannot observe: per-request memory attributable to a stage. [Amended 2026-10-22: see C4 in "Audit amendments".]

**B3e. Procedure.** (1) Clone tag to local disk, `ant jar`; copy conf to a local conf dir with the yaml/jvm edits. (2) For each n: start node, create the stress keyspace (RF=1), wait for `UN`. (3) Start samplers (tpstats, jstat, jcmd NMT, ps). (4) Run write phase then read phase. (5) Record peak/steady heap-after-GC, peak RSS, peak Pending, Active, thread count. (6) At n=32 on a running node, run `nodetool setconcurrency MutationStage 0 32` (expect no log line "Resized"), then `... 0 8` and `... 0 64` mid-load and record tpstats/heap change. (7) Positive control run (B3h). (8) `nodetool drain`, stop node, `pgrep -f CassandraDaemon`, remove the local data dirs.

**B3f. Predictions.** Active tasks cap at about n (tpstats Active <= n, plus transient excess after shrink); Pending grows when offered concurrency (400) exceeds n, so Pending(n=4) >> Pending(n=256) ~ near 0. Steady heap-after-GC is dominated by memtables and caches and is nearly identical (within ~10-15%) across n at the same data volume; there is no heap or RSS plateau set by n and Pending is not capped by n (it is bounded only by the 400 client threads here). Thread count differs by at most about the n difference, adding at most a few tens of MiB of RSS between n=4 and n=256. `setconcurrency` with an unchanged value produces no "Resized ..." log line in system.log, a changed value produces one (:388). [Amended 2026-10-22: see C5 in "Audit amendments".]

**B3g. Readings.** [Amended 2026-10-22: see C5, C6 in "Audit amendments".]

**B3h. Controls.** Positive control: same workload with `native_transport_max_request_data_in_flight` (global in-flight request bytes cap, verify exact key in Config.java before use) and `native_transport_max_request_data_in_flight_per_ip` lowered, plus a second control that lowers `memtable_heap_space` (bound memtable heap) at fixed n=32 and shows heap-after-GC following it. ### Audit amendments (stage 4, step 0, 2026-10-22)

Made before any reading, each for a reason that does not depend on one (source, arithmetic or an ambiguity). B1, B2f and B3f are not changed; rows are only added or terms defined. The as-filed sha256 is `2054f1d98e8f6fa75d3dba0312219fac7bae8fb8c6d865bb5b675473218f7083`.

**Unit tier**

- **U1 (JVM, driver).** The driver is a main class `SepCapProbe` run with `java -cp` (B2a's second option), JVM `-Xmx2g -Xms2g -Xss256k -XX:+UseG1GC -XX:G1HeapRegionSize=4m -XX:NativeMemoryTracking=summary`, not `ant testsome`. With 4 MiB regions a 1 MiB array is ordinary.
- **U2 (repeats).** B2e's "repeat each n three times" is three JVM runs (rep1, rep2, rep3), each building a fresh `SharedExecutorPool` per configuration. Order in a run: variant A n = 1 · 4 · 32 · 128 (T = 2000), variant B n = 1 · 4 · 32 · 128 (T = 600), control n = 4 · 32 · 128 (T = 600, `AbortPolicy`, variant B allocation), then the resize sequence. The sample is taken 2 s after the last `execute` returned; heap = live bytes after three `System.gc()` minus the live bytes before the pool existed ("heapDelta").
- **U3 (terms for B2f).** "About n MiB" (variant A) = `|heapDelta - n| <= 8` MiB. "About T MiB" (variant B) = `T <= heapDelta <= T + 8` MiB, and `max - min` of heapDelta across n <= 5 MiB. "Active = min(n, T)" = `getActiveTaskCount()`. "No rejection or blocking" = no exception from `execute` and the longest `execute` call (excluding the allocation) <= 100 ms. "A few spinners" = pool worker threads (name prefix `probe-Worker`) <= n + 8. The NMT sub-prediction = `Thread` category committed at n = 128 minus at n = 1 <= 32 MiB. Control: queue = 64, accepted = n + 64, heapDelta within `[n + 64 - 2, n + 64 + 8]` MiB. Resize sequence (recorded, one counting `MaximumPoolSizeListener` and a logback appender on `SEPExecutor`): 4 queued-up to 600 tasks, then `setMaximumPoolSize` 32, 32, 32, 8, then 4, 20, 2 tasks released. Prediction as filed in B2f: growth raises active to 32; each repeat of 32 adds no "Resized" line and no listener call; the shrink to 8 leaves the running tasks running (active stays above 8 until they finish). **Runbook fix D1 (2026-10-22, from the cluster instrument check; B1, B2f, B3f and every row unchanged).** C4 said all SEP worker threads are named `SharedPool-Worker-<id>`; that holds only for idle workers. `SEPWorker.java:125` renames a worker to `<executor name>-<id>` when it takes a task (`ReadStage-3`, `MutationStage-12`), so B3d's `grep -c ReadStage` was right and C4's was wrong. The thread count is the JMX `ThreadCount` (the figure the comparisons use) plus, from `Thread.print`, the counts of `ReadStage-`, `MutationStage-` and `SharedPool-Worker-` threads (recorded). The instrument check confirmed C1 (`setconcurrency MutationStage 0 4` printed "Unable to set concurrency: Cannot resize core pool size of SEPExecutor", exit 1).

**Runbook fix D2 (2026-10-22, from the cluster instrument checks, before any run-1 reading; B1, B2f, B3f and every row unchanged).** (a) C4's "heap after GC = `jcmd GC.run` then `GC.heap_info` used" reads the live set plus the allocation after the GC (a 1 GiB eden at 100,000 ops/s: 1,456 MiB against 399 MiB for the same state in two shakedown lifetimes).
