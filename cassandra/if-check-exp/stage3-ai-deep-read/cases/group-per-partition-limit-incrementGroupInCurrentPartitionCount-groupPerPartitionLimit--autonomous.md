# GROUP BY ... PER PARTITION LIMIT (groupPerPartitionLimit) — verification solution

| Field | Value |
|---|---|
| Entry pointer | `src/java/org/apache/cassandra/db/filter/DataLimits.java:1000` |
| Pinned source | `cassandra-5.0.9` |
| Session / date | Claude Sonnet 5.5 (claude-sonnet-5-5), Claude Code CLI, 2026-10-27 |
| Estimate | `negative`: the operand is a per-query, user-supplied result-count limit (PER PARTITION LIMIT on a GROUP BY query), not a node-level memory/disk cap. It counts groups, not bytes, and a single group can hold unbounded rows/bytes. |
| Ground | The limit is chosen by each client query and counts groups returned per partition. The page row limit (`rowLimit` = page size) bounds the result, and the limit has no relation to bytes. Rows within one group are still read and aggregated, so memory and disk reads do not scale with `groupPerPartitionLimit` in any bounded way. The node-wide bounds on read memory are elsewhere (paging, `tombstone_*_threshold`, `max_value_size`, etc.). |

## A. Constraint trace

**A1. The constraint.** `groupPerPartitionLimit`, an `int` field of `CQLGroupByLimits` (`DataLimits.java:663`, set at `:681`), compared at `DataLimits.java:1000` in `GroupByAwareCounter.incrementGroupInCurrentPartitionCount()` and at `:1007` in `isDoneForPartition()`. Kind: runtime, per-query value. Source: the CQL clause `PER PARTITION LIMIT n` parsed into `SelectStatement.perPartitionLimit` (`SelectStatement.java:130`), evaluated by `getPerPartitionLimit(options)` (`:942`, bind markers allowed), and passed by `getDataLimits` (`:882-913`) into `DataLimits.groupByLimits(cqlRowLimit, cqlPerPartitionLimit, pageSize, spec)` (`DataLimits.java:115-122`). Note the third argument is `rowLimit`, which is set to the page size. Unit: number of GROUP BY groups. Default: `NO_LIMIT = Integer.MAX_VALUE` (`DataLimits.java:48`) when the clause is absent. It is settable only per query (CQL text or bind variable), with no yaml key, `-D` property or JMX, so no restart question. Rejected with aggregate-everything queries (`SelectStatement.java:1246-1248`) and with DISTINCT (`:1236`). In the non-GROUP-BY case it is also forced off when the query uses post-query ordering (`:892-897`).

**A2. What it caps.** Other (result cardinality): the number of completed groups emitted from one partition. It is not a memory or disk quantity. The compared value `groupInCurrentPartition` (`:994-1001`) is incremented once per completed group at `applyToRow` (`:926-964`; `isNewGroup` at `:931`, the `incrementGroupInCurrentPartitionCount()` call at `:936`). *Amended 2026-10-27 (stage-4 audit, before any reading):* the earlier cites `:~944-951` and `:~917-920` were wrong. The only other call sites are `applyToPartition` (`:895`, taken only when `isDone()`, i.e. the group limit is reached, so the pager can resume), `onPartitionClose` for a static-only partition (`:1026`) and `onClose` at the end of the data (`:1044`, when `rowsCounted < rowLimit`). A group that is pk-prefix-only (`GROUP BY pk`) never reaches the `applyToRow` call inside its own partition, because `groupMaker.isNewGroup(pk, clustering)` is false for every row of the same partition key; the group is closed by the first row or static row of the next partition, which calls `incrementGroupCount()` but not `incrementGroupInCurrentPartitionCount()` (`:888-895`). So under `GROUP BY pk` the compared value `groupInCurrentPartition` stays 0 and `:1000` is not reached; the limit cannot stop such a partition, which is the mechanism behind shape B below.

**A3. Mechanism.** 1) `Counter.attachTo(rows)` (`DataLimits.java:~318-326`) calls `applyToPartition`, which resets `groupInCurrentPartition = 0` for a new partition (`:~927-931`). 2) In `applyToRow`, when `groupMaker.isNewGroup(...)` and an unfinished group exists, `incrementGroupCount()` and `incrementGroupInCurrentPartitionCount()` run. 3) At `:1000`, if `groupInCurrentPartition >= groupPerPartitionLimit`, `stopInPartition()` stops iteration of the rest of that partition's rows. 4) `isDoneForPartition()` (`:1007`) makes the following rows return null (`applyToRow` `:~953-957`). Reached: stop reading that partition and continue with the next. Not reached: nothing. Bypass or overshoot: (a) the group-ending detection fires only when the next group starts, so one extra row is examined (`isNewGroup` at `:931`); (b) all rows inside one group (e.g. a whole partition with GROUP BY on partition key only) are consumed and aggregated before the group counts, so one huge group is not capped; (c) with `enforceLimits == false` (`onlyCount()`), nothing stops; (d) the global row limit (page size) is the effective result bound; (e) tombstones and deleted rows are scanned without counting (`:928-930` comment), so the scan can go past the limit; (f) on paging resume, `PagingGroupByAwareCounter` (`:1113-1126`) restores the count from the last returned key.

**A4. Other consumers.** Read path memory outside this limit: memtable and sstable iterators, row cache/chunk cache, `max_value_size`, tombstone thresholds, `page_size` fail/warn thresholds (`Config.java:873-874`), coordinator result buffering, and native transport frame limits.

**A5. Evidence beyond the source.** Cassandra docs, CQL SELECT section on `PER PARTITION LIMIT` and GROUP BY (https://cassandra.apache.org/doc/5.0/cassandra/developing/cql/dml.html); CASSANDRA-7017 (PER PARTITION LIMIT), CASSANDRA-10707 (GROUP BY). Cited from memory of the public tracker, not re-read here.

## B. Verification solution

**B1. Claim under test.** Memory and disk read by a query with GROUP BY do not follow `groupPerPartitionLimit`: with the limit set to 1 versus a large value, the heap/bytes read for a workload dominated by one large group per partition stay essentially equal, whereas the page size (the row limit) moves them. The limit only changes the number of groups returned per partition.

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Copy the tree to local disk (`rsync -a ~/cassandra-5.0.9/ /local/c509/`); `cd /local/c509 && ant jar`. Put a JUnit test in the copy at `test/unit/org/apache/cassandra/db/filter/DataLimitsGroupLimitProbeTest.java`; run with `ant testsome -Dtest.name=DataLimitsGroupLimitProbeTest`. JVM options: default test options plus `-Xmx512m`. *Amended 2026-10-27 (stage-4 audit, before any reading):* the build is `copy-source.sh ~/s4-b11-g80` then `ant build-test` (the `ant testsome` form, with the probe as a `CQLTester` subclass in package `org.apache.cassandra.db`, copied to `test/unit/org/apache/cassandra/db/GroupPerPartitionLimitProbeTest.java`; the file name and path in the first sentence were a placeholder); the JVM runs with the test heap build.xml gives (`-Xmx` from `maxMemory`, recorded in the results file), not `-Xmx512m`, because the 4 x 100000-row memtable below must not flush mid-run. One JVM runs all values in sequence (no fresh JVM per value).

**B2b. Knobs.** `groupPerPartitionLimit` in {1, 10, NO_LIMIT}; `rowLimit` (page size) in {100, 10000, NO_LIMIT} (*amended 2026-10-27:* NO_LIMIT added: with a binding rowLimit nothing else can be seen in shape B); group shape: groups of size 1 row versus a single group of 100000 rows in the partition. Set by calling `DataLimits.groupByLimits(NO_LIMIT, gppl, rowLimit, AggregationSpecification.aggregatePkPrefixFactory(comparator, k).newInstance(QueryOptions.DEFAULT)`) directly, with k=1 (group by the clustering column: shape A) or k=0 (group by the partition key only: shape B). *Amended 2026-10-27:* `aggregatePkPrefix` does not exist; the factory method is `aggregatePkPrefixFactory` (`AggregationSpecification.java:112`).

**B2c. Workload.** Build in-memory `UnfilteredRowIterator`s (via `UnfilteredRowIterators` test builders or `ReadCommand` on a local table in a unit-test schema): 20 partitions x 1000 clusterings with groups of 1 row (1000 groups per partition), and 20 partitions x 100000 rows grouped by partition key (1 group). Apply `limits.newCounter(nowInSec, false, false, true).applyTo(iter)` and consume. *Amended 2026-10-27 (stage-4 audit, before any reading):* shape B is 4 partitions x 100000 rows (400,000 rows, not 2,000,000: the insert time and memtable size of 2,000,000 rows do not fit a unit test, and every B2f prediction holds per partition); both shapes are rows of a local table `(k int, ck int, v blob)` (v = 100 bytes) read through a `PartitionRangeReadCommand` (`Util.cmd(cfs).build()`) so the counter sees all partitions of the shape in one pass, in two tables.

**B2d. Observables and instruments.** `counter.counted()`, `countedInCurrentPartition()`, `rowsCounted()`; count of rows pulled from the source (a transformation under the counter that counts `applyToRow`) and rows returned by the counter; allocated bytes via `com.sun.management.ThreadMXBean.getThreadAllocatedBytes` before and after consumption. Not observable here: real sstable/disk reads.

**B2e. Procedure.** For each (gppl, rowLimit, shape): build the iterator, record allocated bytes, consume with the counter, record rows pulled, groups counted, bytes allocated; repeat 5 times and take the median. *Amended 2026-10-27:* the values are run as the cross product gppl x rowLimit x shape, with a first-trigger check before anything else (shape A, gppl=10, rowLimit=NO_LIMIT must return 200 rows and pull fewer than 1000; otherwise the test stops).

**B2f. Predictions.** *(Replaced 2026-10-27 by the stage-4 audit, before any reading: the original text stated shape B as "about 100000 rows pulled for every gppl", which holds only when `rowLimit` does not bind, and gave no numbers for shape A under a binding `rowLimit`.)* Let G = 20 x min(gppl, 1000) be the groups the per-partition limit allows over the 20 partitions of shape A. Shape A (1-row groups), rowLimit = NO_LIMIT: rows returned = G (20, 200, 20000 for gppl = 1, 10, NO_LIMIT); rows pulled = 20 x (gppl + 1) for finite gppl (40, 220) and 20000 for NO_LIMIT; `counted()` (read after the partition iterator is closed) = G for finite gppl and 20000 for NO_LIMIT (the open last group is counted by `onClose`, `:1044`). With a binding rowLimit (G > rowLimit) rows returned = rowLimit and rows pulled lie in [rowLimit, rowLimit + 21]; otherwise as for NO_LIMIT. Shape B (one 100000-row group per partition, 4 partitions), rowLimit = NO_LIMIT: rows returned = rows pulled = 400000 for every gppl including 1, `counted()` = 4 and `countedInCurrentPartition()` = 1 after close (the single count of the last group by `onClose`, `:1044`; no group is counted inside a partition, so the limit never fires, see A2), and median allocated bytes within 10 % across gppl. Shape B with rowLimit 100 or 10000: rows pulled in [rowLimit, rowLimit + 1] for every gppl, so the work follows the row limit and not gppl.

**B2g. Readings.**

|---|---|

**B2h. Controls.** Positive control: the same workload with `rowLimit` 100, 10000 and NO_LIMIT (*amended 2026-10-27:* NO_LIMIT added), where the row cap is known to bind (`incrementRowCount` `:983-988`). Negative control: gppl=NO_LIMIT. Warm up the JIT and call `System.gc()` before each reading.

### B3. Cluster tier

**B3a. Environment and build.** One node, JDK 11, local copy built with `ant jar`; data, commitlog, hints on local disk (`/local/n1`, at least 5 GB free); `-Xms1g -Xmx1g` in `conf/jvm11-server.options`; `num_tokens: 1`; no other config change. Client: `cqlsh` or a python driver script kept outside the source tree. *Amended 2026-10-27:* tree from `copy-source.sh`; data on tmpfs `/dev/shm/s4-b11-g80` (not `/local/n1`, which does not exist on the node; the data set is under 1 GB); loopback address 127.0.10.1, JMX 7200; the client is the python driver (copy of 3.29.0 outside the repo). The node JVM also gets `-XX:G1HeapRegionSize=4m -XX:G1NewSizePercent=1 -XX:G1MaxNewSizePercent=2` so the young generation is about 20 MB and a sampled heap peak is not dominated by garbage (found in a sibling case's shakedown; Cassandra's `jvm11-server.options` otherwise floors the young generation at half the heap). The table has compression disabled so bytes read are raw bytes.

**B3b. Knobs.** CQL `PER PARTITION LIMIT` in {1, 100, unset}; client page size (driver `fetch_size`) in {100, 5000} *(amended 2026-10-27: plus 100000 as the page-size control, see B3h)*; query shape: `SELECT pk, count(*) ... GROUP BY pk, ck1` (many small groups) versus `GROUP BY pk` (one large group per partition). Set per query.

**B3c. Workload.** Table `t(pk int, ck1 int, ck2 int, v blob, PRIMARY KEY(pk, ck1, ck2))`. Load 50 partitions x 200000 rows (v = 100 bytes), about 1.5 GB raw; *amended 2026-10-27:* 20 partitions x 200000 rows = 4,000,000 rows, about 0.5 GB on disk (the 10,000,000 rows of 50 partitions would make each unlimited full scan about 3 minutes and the whole grid several hours; the claim is per partition, so 20 partitions test it equally; 1.5 GB was also an overestimate: 10,000,000 x 100 B is 1 GB); flush, then run each query 3 times, and check the sstable data size with `nodetool tablestats`. Rows per ck1 value: 100 (so 2000 groups per partition under `GROUP BY pk, ck1`).

**B3d. Observables and instruments.** Heap used: `jcmd <pid> GC.heap_info` before, and sampled each 100 ms during the arm by a JMX sampler (`HeapMemoryUsage.used`, thread-allocated bytes; *amended 2026-10-27*, replacing `jstat`); peak RSS via `/proc/<pid>/status` VmHWM; rows scanned from `nodetool tablehistograms` / `tablestats` (`Local read count`), sstable bytes read via `/proc/<pid>/io` `rchar` read at the start and end of each arm (*amended 2026-10-27:* `drop_caches` is not used on a shared node; `file_cache_enabled` is off by default in 5.0.9, so data reads are `read()` calls that `rchar` counts; `read_bytes` stays 0 on tmpfs); `system.log` for tombstone/size warnings. The exact group count in the result is read from the client.

**B3e. Procedure.** 1) Start the node, create the schema, load data, flush. 2) For each combination of knobs: restart-free, run the query, record the result group count, peak sampled heap, `/proc/<pid>/io` delta. 3) Repeat three times, then compare. *Amended 2026-10-27:* the 16 arms of B3f run forward, then the page-size 5000 arms again in reverse order in the same node lifetime (no restart; the restart of B3h is not done and is a named gap: with `file_cache_enabled` off nothing is cached by the node, and the OS page cache cannot change `rchar`). The query is a range query over the whole table: `SELECT pk, ck1, count(*) FROM t GROUP BY pk, ck1 [PER PARTITION LIMIT n]` (shape A) and `SELECT pk, count(*) FROM t GROUP BY pk [PER PARTITION LIMIT n]` (shape B), every page read. 4) Stop the node with `nodetool drain; kill <pid>` and verify with `pgrep -f CassandraDaemon`.

**B3f. Predictions.** *(Replaced 2026-10-27 by the stage-4 audit, before any reading. The original text asked that a fetch_size change from 100 to 5000 change the peak heap; 5000 rows x about 2.5 KB is about 12 MB, below the 50 MB floor B3g itself names, so that control could never register. The page-size control is now 5000 versus 100000, estimated at 250 MB, and every threshold is numeric.)* Rows per query (all arms): shape A returns 20 x min(L, 2000) groups (20, 2000, 40000 for L = 1, 100, unset); shape B returns 20 (one per partition) for every L. Bytes read (`rchar` delta per full query, median of 3, F = 5000): shape A with L = 1 is at most 10 % of L = unset, and with L = 100 at most 50 % of L = unset; shape B with L = 1, 100 and unset are within 10 % of each other (max/min <= 1.10), because the whole group is read. Peak sampled heap (F = 5000, shape B): spread across L = 1, 100, unset <= 30 MB. Control: shape B, L = unset, F = 100000 has a peak heap more than 50 MB and more than 3 x the run-to-run spread above F = 5000. Disk bytes of the data directory unchanged (within 1 %). The heap peak therefore tracks the page size, not the limit.

**B3g. Readings.**

| Observation | Meaning |
|---|---|
| All row counts as stated; shape B bytes read within 10 % and peak heap within 30 MB across L; the page-size control moves the peak by more than 50 MB; disk unchanged | Confirmed: the limit does not cap what a one-group-per-partition query reads |
| Shape B bytes read at L = 1 more than 10 % below L = unset | Refuted: the limit bounds a single group's reads |
| The page-size control moves the peak by 50 MB or less (or by less than 3 x the spread) | Not confirmed: control did not move |
| A row count differs from the stated count, or peak heap differences in all arms are below the noise (spread > 30 MB) | Not confirmed: limit never reached or noise too large |
| Any other reading (for example shape B flat but shape A bytes not scaling) | Not confirmed (no matching row) |

**B3h. Controls.** Positive control: fetch_size (the page row limit, a cap known to bind) at 5000 vs 100000 on the same query *(amended 2026-10-27, was 100 vs 5000, see B3f)*; fetch_size 100 is also run and printed, not judged. A noise arm of unrelated point reads gives the spread. Repeat on a freshly restarted node to rule out cache warming; fixed heap; no concurrent compaction (`nodetool disableautocompaction`); the same data for all runs.

**B4. Risks and cleanup.** Disk: about 2 GB under `/local/n1` plus sstables; delete the directory at the end. Shared storage untouched, since build and data are on local disk. Processes: confirm no `CassandraDaemon`, `jstat` or `ant` process remains (`pgrep -af 'Cassandra|jstat|ant'`). Remove `/local/c509` when done. Never run `drop_caches` on a shared machine without permission, and use `rchar` otherwise.
