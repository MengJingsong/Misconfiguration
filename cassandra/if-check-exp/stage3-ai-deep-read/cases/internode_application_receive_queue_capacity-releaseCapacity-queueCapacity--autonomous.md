The target line is the release half of the per-connection inbound byte accounting (`if (oldQueueSize > queueCapacity)`), not the enforcement point; the constraint it belongs to, `internode_application_receive_queue_capacity`, does bound (together with the two reserve limits) the serialized bytes of inbound internode messages that are admitted but not yet fully processed, which is a heap-significant object population. ## A. Constraint trace

**A1. The constraint.** `internode_application_receive_queue_capacity`; configuration entry. Declared at `src/java/org/apache/cassandra/config/Config.java:256-257` as `DataStorageSpec.IntBytesBound`, default `"4MiB"` (fixed literal, not derived). Old name `internode_application_receive_queue_capacity_in_bytes` still accepted via `@Replaces` (`Config.java:256`). Set in `cassandra.yaml` (commented example `conf/cassandra.yaml:1389`); read once via `DatabaseDescriptor.getInternodeApplicationReceiveQueueCapacityInBytes()` (`DatabaseDescriptor.java:3040-3042`) inside `MessagingService.getInbound()` (`MessagingService.java:675-681`) when the first connection from a peer appears, then copied into each handler as `final long queueCapacity` (`AbstractMessageHandler.java:145,185`). No JMX setter was found; changing it needs a restart (the value is baked into handlers created per peer). Unit: bytes. Sibling limits it works with: `..._receive_queue_reserve_endpoint_capacity` (128MiB, `Config.java:258-259`, shared per peer, `InboundMessageHandlers.java:119`) and `..._receive_queue_reserve_global_capacity` (512MiB, `Config.java:260-261`, node-wide, `MessagingService.java:308-310`). Startup validation: `internode_max_message_size` (default = min of receive/send endpoint reserve, `DatabaseDescriptor.java:991-996`) must not exceed the reserves (`:978-982`) but there is no relation required to `queueCapacity`.

**A2. What it caps.** Resource: JVM heap (and Netty buffers holding the frame bytes, see A4). Quantity compared: `queueSize` (`AbstractMessageHandler.java:146`, bytes of admitted-but-not-yet-released inbound messages on this one connection) plus the incoming message's serialized size `bytes`, against `queueCapacity` (`:419`). It is a per-connection allowance; the overflow beyond it is borrowed from the endpoint and global reserve `Limit`s.

**A3. Mechanism.**
1. `InboundMessageHandler.processOneContainedMessage` (`InboundMessageHandler.java:120-152`) infers the on-wire size (`:127`) and calls `acquireCapacity(...)` (`:140`); first frame of a multi-frame large message does the same with the full message size (`:217`), so the whole large message is accounted at its first frame.
2. Outer `acquireCapacity` (`AbstractMessageHandler.java:~395-409`) calls the inner one (`:411`). Inner: if `queueSize + bytes <= queueCapacity` add and SUCCESS (`:419-423`). Otherwise `allocatedExcess = min(queueSize + bytes - queueCapacity, bytes)` (`:426`); needs `globalReserve.tryAllocate` (`:428`, else INSUFFICIENT_GLOBAL) then `endpointReserve.tryAllocate` (`:431`, else give global back and INSUFFICIENT_ENDPOINT, `:433-435`). On success add to `queueSize` (`:438`) and refund any over-estimated excess (`:439-456`).
3. Non-SUCCESS: the handler registers on the endpoint or global `WaitQueue` (`:400-403`), `throttledCount++` (`:405-406`), returns false so the decoder deactivates; nothing is dropped, the TCP stream backs up (sender blocks).
4. SUCCESS: the message is deserialized (`InboundMessageHandler.java:163`, small path) or accumulated (large) and dispatched to a Stage.
5. **Target line.** `releaseCapacity(bytes)` (`AbstractMessageHandler.java:461-474`) does `oldQueueSize = getAndAdd(-bytes)` (`:463`); only if `oldQueueSize > queueCapacity` (`:464`, target) does it hand back `min(oldQueueSize - queueCapacity, bytes)` (`:466`) to the endpoint and global reserves (`:468-469`) and signal both wait queues (`:471-472`). So the exclusive per-connection allowance is released first-in-last-out: a release when `queueSize` was at or below `queueCapacity` returns nothing to the reserves, and a release that straddles the boundary returns only the part above it. This mirrors the acquire side (`:426`), keeping reserves consistent; if it were wrong (e.g. `>=`, or comparing the new size) reserves would leak or go negative (`ResourceLimits.Concurrent.release` throws `UnrecoverableIllegalStateException` below zero, `ResourceLimits.java:159-169`).
6. Callers of release: after the verb handler finishes (`InboundMessageHandler.java:438-440`, via `releaseProcessedCapacity` `AbstractMessageHandler.java:483-486`), on deserialize failure (`InboundMessageHandler.java:185`), plus expiry/abort paths in LargeMessage.

Bypasses and overshoot: (a) a single message can exceed `queueCapacity` and is admitted by borrowing, so per-connection usage can reach `queueCapacity + reserve`-sized amounts; (b) a message larger than a reserve can never be admitted (hence the `internode_max_message_size` validation); (c) already-expired messages are skipped before acquire (`InboundMessageHandler.java:130-138`) and use no permits; (d) the unit is serialized bytes, so deserialized heap size is larger by a message-dependent factor; (e) `corrupt`/header bytes and frame decoder buffers are not accounted.

**A4. Other consumers.** Heap used by everything else: memtables, key/row/chunk caches, query execution, coordinator state, response/callback maps. Within internode receive: the Netty/`FrameDecoder` buffers and kernel socket buffers (`internode_socket_receive_buffer_size`) for bytes not yet admitted are outside the accounting; per node the number of handlers is peers x connection types (urgent, small, large, legacy; `InboundMessageHandlers.java:130-149`), so total exclusive allowance scales as `peers x types x queueCapacity` (also noted in `conf/cassandra.yaml:1373-1377`). Streaming uses a separate path and is not counted.

**A5. Evidence beyond the source.** In-tree: the class Javadoc of `AbstractMessageHandler` (flow control section, lines ~84-117) and `conf/cassandra.yaml:1373-1391`; CASSANDRA-15066 (internode messaging rewrite that introduced this scheme) is where the design came from per the code comments, not fetched here. Existing sibling case in this repo: `cases/internode_application_receive_queue_capacity-acquireCapacity-queueCapacity--guided.md` (read for orientation only, not as proof). Test scaffolding: `test/burn/org/apache/cassandra/net/ConnectionBurnTest.java:102-109,374` (builds `InboundMessageHandlers` with explicit `queueCapacity` and asserts `usingCapacity()`/`usingEndpointReserveCapacity()` return to 0). Otherwise `none`.

## B. Verification solution

**B1. Claim under test.** For inbound internode traffic from one peer, the bytes held in admitted-but-unreleased messages never exceed `queueCapacity` (per connection) plus what the endpoint/global reserves grant, with the release at line 464 returning exactly the above-allowance part to the reserves; and, on a real node, the heap actually retained by queued inbound messages tracks this accounted total (so shrinking the three limits shrinks the backlog heap, growing them grows it) rather than being bounded elsewhere. Falsified if accounted bytes exceed the sum of the limits, if reserve `using()` does not return to 0 after drain, or if real retained heap does not respond to the limits.

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Clone the tag to local disk: `git clone --branch cassandra-5.0.9 --depth 1 /proj/misconfiguration-PG0/git-repos/cassandra-src $WORK/c509` (never build in the shared tree), `cd $WORK/c509 && ant jar build-test` (do not run the whole suite). Put a new test class `ReleaseCapacityProbeTest` in `test/unit/org/apache/cassandra/net/` of the local clone (package `org.apache.cassandra.net` so package-private `queueSize` and the `InboundMessageHandler` constructor are reachable). Run with `ant testsome -Dtest.name=ReleaseCapacityProbeTest -Dtest.methods=...`. JVM opts: default test opts; no special heap.

**B2b. Knobs.** Constructor args rather than yaml: `queueCapacity` Q in {1024, 4096} bytes (small so boundaries are cheap; 4096 stands for scaled default), `endpointReserve` E = `new ResourceLimits.Concurrent(R)` and global G similarly, R in {2048, 8192}. Also a yaml-level check in a separate method: assert `DatabaseDescriptor.getInternodeApplicationReceiveQueueCapacityInBytes()` equals 4194304 under defaults and `8388608` after `DatabaseDescriptor.daemonInitialization(() -> { Config c = ...; c.internode_application_receive_queue_capacity = new DataStorageSpec.IntBytesBound("8MiB"); return c; })` (use a separate JVM/class since config init is once-only).

**B2c. Workload.** Build `InboundMessageHandler` as in `ConnectionBurnTest.java:592-602` (anonymous subclass supplying a no-op message consumer) on an `EmbeddedChannel` or `TestChannel`, with a stub `FrameDecoder`. Drive `acquireCapacity(E, G, bytes)` / `releaseCapacity(bytes)` directly (both are protected/public in-package) with a scripted sequence, avoiding the wire path: with Q=1024, R=2048: acquire 600 (queueSize 600, reserves 0), acquire 600 (allocatedExcess = min(600+600-1024,600)=176; E.using=G.using=176), acquire 2000 (allocatedExcess = min(1200+2000-1024, 2000) = 2000, but only 2048-176 = 1872 remains in the reserves, so expect INSUFFICIENT_GLOBAL or INSUFFICIENT_ENDPOINT and no state change). Then releases: release 600 (old 1200 > Q: excess = min(176,600)=176, reserves to 0), release 600 (old 600 <= Q: nothing). Also boundary cases: release when old == Q exactly (expect no reserve release; this is the `>` vs `>=` question), old == Q+1 with bytes 5 (expect 1 released). Concurrency case: 4 threads releasing while the single "event loop" thread acquires, 100k iterations, final state check.

**B2d. Observables and instruments.** `handler.queueSize` (package-private field, read directly), `E.using()`, `G.using()` (`ResourceLimits.java:125`), return value of `acquireCapacity` (`Outcome`), `handler.throttledCount`, WaitQueue signals (use a recording `WaitQueue` or check ticket state; may not be directly observable, then infer from `reactivate` call count on the stub decoder). Cannot observe heap here: this tier measures the operand only.

**B2e. Procedure.** (1) Write the test with the scripted sequence above and boundary cases, assertions inline. (2) `ant testsome ...`. (3) Run the concurrent case 5 times. (4) Mutation check: in the local clone copy only, change `>` to `>=` at line 464 and rerun to confirm the boundary test fails (proves the test is sensitive). Revert.

**B2f. Predictions.** Stated before any run: after each step the invariant `E.using() == G.using() == max(0, queueSize - Q)` summed over handlers holds (single handler: exactly `max(0, queueSize-Q)`); never `queueSize - Q > R` for admitted state; the sequence above gives (queueSize, E.using) = (600,0), (1200,176), (1200,176 unchanged on refusal), (600,0), (0,0). Boundary: old == Q releases 0 to reserves; old == Q+1 with bytes 5 releases 1. After all releases queueSize == 0 and both reserves == 0. Concurrent case ends at (0,0) with no `UnrecoverableIllegalStateException`. With Q doubled to 4096 the same byte script borrows nothing (reserves stay 0 throughout). `throttledCount` increments exactly once per refused acquire in the outer method (`:405`), and zero if only the inner method is called directly (note this to avoid misreading).

**B2g. Readings.**

| Observation | Meaning |
|---|---|
| Invariant holds at every step, final state (0,0) | Claim holds at the accounting level: release at 464 mirrors acquire |
| `queueSize - Q > R` for an admitted state | Admission overshoots the reserve; claim wrong |
| Reserves non-zero after full drain | Release path leaks reserve (bug in or around 464) |
| Reserves negative / `UnrecoverableIllegalStateException` | Over-release; claim wrong |
| `>=` mutation does not change the boundary result | Test insensitive; redo with exact-boundary values |
| Q=4096 case shows reserve use | Allowance not honored |

**B2h. Controls.** The Q=4096 run (same byte script, no borrowing expected) is the control that reserve traffic is due to Q; the `>=` mutation is the sensitivity control; single-threaded vs. concurrent runs separate logic from race effects. Not a `does not cap` judgment, so no extra rows required.

### B3. Cluster tier

**B3a. Environment and build.** Two nodes, A (sender/coordinator) and B (receiver under test), both from a local clone (`$WORK/c509`, `ant jar`), on local disk (e.g. `/tmp`-class local volume of known size >= 20 GB each; commitlog, data, hints, saved_caches all under `$WORK/nodeX/`). JDK 11. Node B JVM: `-Xms2G -Xmx2G` with G1 (set in `conf/jvm11-server.options`), plus `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=$WORK/nodeB/dumps` only if disk permits (otherwise omit). Node A heap 2G. `num_tokens: 1`, `endpoint_snitch: SimpleSnitch`, RF=1 keyspace on B only is not possible; use `NetworkTopologyStrategy` one DC, RF=2 so every write is forwarded A->B. Both nodes: `concurrent_writes: 32` default. Make B slow to drain inbound writes so messages queue up: install Byteman 4.0.x agent on B (`-javaagent:byteman.jar=script:$WORK/slow.btm`) with a rule delaying `org.apache.cassandra.db.MutationVerbHandler.doVerb` by 200 ms (`AT ENTRY DO Thread.sleep(200)`). This is test-only instrumentation outside the Cassandra tree. (Fallback without Byteman: SIGSTOP is not valid because it stops reads too.)

**B3b. Knobs.** On B only (receive side), via `cassandra.yaml`, restart each run: `internode_application_receive_queue_capacity` Q in {64KiB, 4MiB (default), 32MiB}; endpoint/global reserves fixed at tiny-then-default: run set 1 with `internode_application_receive_queue_reserve_endpoint_capacity: 16MiB`, `internode_application_receive_queue_reserve_global_capacity: 16MiB` and `internode_max_message_size: 8MiB` (must not exceed the reserves, `DatabaseDescriptor.java:978-982`; also keep send-side reserves >= 8MiB, defaults are). Run set 2 uses defaults 128MiB/512MiB. Rationale: with small reserves, total admitted is about `3 types x Q + 16MiB`; with Q=64KiB the cap is dominated by the reserves so set 1 isolates the reserve, and Q=32MiB shows the allowance term (only the small and large connection types carry mutations). A's send-side limits are raised (`internode_application_send_queue_capacity: 64MiB`, send reserves 512MiB/1GiB) so A does not itself throttle before B does.

**B3c. Workload.** From A, use `cassandra-stress` (from the same build, `tools/bin/cassandra-stress`) with a user profile writing 512 KiB blobs (a single `blob` column; stays below `max_mutation_size` = half commitlog segment, 16 MiB default) at CL=ONE through A with RF=2 so each write sends a 512 KiB `MUTATION_REQ` to B: `cassandra-stress user profile=big.yaml 'ops(insert=1)' n=200000 cl=ONE -rate threads=200 -node A`. Arithmetic: 200 threads x 512 KiB = ~100 MiB in flight; B drains 5 per second per mutation thread x 32 threads ~ 160 mutations/s ~ 80 MiB/s versus a 100 MiB offered window, so the queue builds up to the admission limit (Q-term 3 x Q for Q up to 32 MiB gives 96 MiB, plus 16 MiB reserve). Messages above `LARGE_MESSAGE_THRESHOLD` (about 64 KiB, `OutboundConnections.java:69`) go on the large connection. Duration: 10 minutes steady after 2 minute warmup per configuration; disk written is bounded because `n` and blob size bound it (200000 x 512 KiB would be about 100 GB, too much, so use `n=20000`, about 10 GiB at most per node; check free space first).

**B3d. Observables and instruments.** On B: (1) JMX `org.apache.cassandra.metrics:type=InboundConnection,scope=<A-address>,name=ThrottledCount` and `ThrottledNanos` (`InternodeInboundMetrics.java:67-68`) via `nodetool sjk mx` or a JMX client sampled every 1 s: proves the cap bound. `ScheduledBytes`/`ScheduledCount` (`:61-62`) are counters of scheduled work; their exact semantics (cumulative vs. outstanding) must be read from `InboundCounters` before use. `queueSize` itself is not exposed by any metric (`usingCapacity()` at `InboundMessageHandlers.java:321` is Java-only), so it cannot be read directly in a real node; use the Byteman rule on `AbstractMessageHandler.releaseCapacity` to log `queueSize` per call as a sampled proxy if needed. (2) Retained heap of queued messages: `jcmd <pid> GC.class_histogram` every 10 s, bytes for `org.apache.cassandra.db.Mutation` (and `org.apache.cassandra.db.partitions.PartitionUpdate`, `byte[]`, `java.nio.DirectByteBuffer` count) with `-all` off (live objects after a full GC is intrusive; instead trigger `jcmd GC.run` once before each sample so retained rather than garbage is counted; note the cost and keep sampling at 30 s). (3) Heap used after GC from `jstat -gc <pid> 1000` (old gen `OU`) and `nodetool info` heap line. (4) Off-heap Netty usage: `jcmd <pid> VM.native_memory summary` requires `-XX:NativeMemoryTracking=summary`, enable it; plus `nodetool tpstats` MutationStage pending count. Cannot observe: bytes in kernel socket buffers (use `ss -tmi` on B's port 7000 for rcv queue as a side view).

**B3e. Procedure.** 1) Build, create `$WORK/nodeA`, `$WORK/nodeB` dirs, confirm `df` free space >= 40 GB. 2) For each of the 2 reserve sets x 3 Q values (6 runs): write `cassandra.yaml` for B, start A then B, wait for UN. 3) Create keyspace (`NetworkTopologyStrategy`, dc1:2) and table with a blob column. 4) Start the sampler scripts (jstat, jcmd histogram every 30 s after `GC.run`, JMX throttled counters 1 s). 5) Run the stress warmup 2 min, then 10 min measured. 6) Stop stress, record `ThrottledCount` deltas, wait for MutationStage pending to reach 0, sample once more (leak check: histogram `Mutation` bytes back to baseline). 7) `nodetool drain`, stop both nodes, `rm -rf $WORK/node*/{data,commitlog,hints,saved_caches}`; confirm no `java` process of this run remains (`pgrep -af cassandra`).

**B3f. Predictions.** Stated before any run. Accounted ceiling on B for mutations = `types x Q + endpoint reserve` bounded also by global reserve; with set 1 (16MiB reserves): Q=64KiB => ~16 MiB + 2x64 KiB; Q=4MiB => ~16 + 8 = 24 MiB (small and large connections carry data); Q=32MiB => ~16 + 64 = 80 MiB. Retained `Mutation`+`byte[]` bytes in the histogram should scale with these totals up to a factor k of 1.2-3 (deserialized form is larger than wire form), and the ThrottledCount rate should fall as Q rises (zero at 32 MiB if offered window ~100 MiB is below the sum, which it is not for set 1; so non-zero but reduced). With set 2 (128/512 MiB) and Q=4MiB the offered 100 MiB window fits under the limits, so throttling is near zero and the peak queued heap is bounded by the workload (about 100 MiB x k), not by the limits. Claim wrong if peak retained message heap at Q=64KiB/16MiB reserves is much greater than ~16 MiB x 3, or if it does not change when Q goes from 64KiB to 32MiB.

**B3g. Readings.**

| Observation | Meaning |
|---|---|
| Peak retained message heap rises with Q (set 1) and `ThrottledCount` falls | Limit governs real usage; claim holds |
| Peak retained heap far above `types x Q + reserve` x 3 | Accounting under-counts (proxy breaks) or other unaccounted buffering; claim wrong or weak |
| Peak retained heap flat across Q though `ThrottledCount` > 0 | Q does not matter once reserves dominate; shows only reserve binds (partial: refines the claim) |
| `ThrottledCount` stays 0 in all runs | Limit never reached; workload too light, not confirmed |
| After drain, `Mutation` bytes do not return to baseline | Release path leaks (target-line suspicion); investigate |
| Heap OOM or GC pressure while `ThrottledCount` > 0 | Cap bounds queue but not enough to protect heap; note k factor |

**B3h. Controls.** (a) Byteman off (B fast): queued bytes should stay near zero regardless of Q, showing the slowdown rule created the backlog. (b) Positive control that a cap binds and moves usage: lower the reserves from 16MiB to 4MiB with Q fixed at 64KiB (and `internode_max_message_size: 2MiB`): peak retained heap must drop proportionally. (c) Same workload with A->B traffic of 1 KiB writes to show small messages do not hit the limits. (d) Repeat the middle config 3 times to estimate run-to-run noise; require differences > 2x noise.

**B4. Risks and cleanup.** Disk: node dirs on local disk only, `n` and `duration` cap writes to <= 10 GiB per node; check `df` before and after, delete `$WORK/node*` after each run. Heap dumps off unless local space allows (2 GiB each). No shared storage written. Processes: Cassandra A/B, stress, Byteman agent, samplers; stop with `kill` of recorded PIDs, then `pgrep -af 'cassandra|stress|jstat'` must be empty. Unit tier builds only in the local clone; the `>=` mutation lives in that clone only and is reverted.
