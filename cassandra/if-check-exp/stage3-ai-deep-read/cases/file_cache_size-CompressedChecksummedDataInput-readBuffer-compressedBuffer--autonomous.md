## A. Constraint trace

**A1. The constraint.** `file_cache_size` (yaml; legacy `file_cache_size_in_mb`), declared `config/Config.java:496-497` as `DataStorageSpec.IntMebibytesBound`. Read once in a static initialiser: `BufferPools.java:38` `FILE_MEMORY_USAGE_THRESHOLD = DatabaseDescriptor.getFileCacheSizeInMiB()*1024*1024`, passed to `new BufferPool("chunk-cache", threshold, true)` (`BufferPools.java:39`). Unit MiB. Default if unset: `min(512, maxHeap/4 MiB)` (`DatabaseDescriptor.java:576-577`). Set by yaml only (no JMX setter; the static is fixed at class load), so changing it needs a restart. The hint reader reaches it through `private static final BufferPool bufferPool = BufferPools.forChunkCache()` (`CompressedChecksummedDataInput.java:35`).
Related: `networking_cache_size` (`Config.java:493-494`) is the other pool, not used here; `file_cache_enabled` (`Config.java:499`, default false) only gates the ChunkCache, not the pool; `buffer_pool_use_heap_if_exhausted` (`Config.java:514`, deprecated).

**A2. What it caps.** Off-heap (direct) memory held in the chunk-cache BufferPool: `memoryAllocated` in whole `MACRO_CHUNK_SIZE` units must stay <= threshold **[Amended 2026-10-25, stage-4 audit: `MACRO_CHUNK_SIZE = 64 * NORMAL_CHUNK_SIZE = 64 * 128 KiB = 8 MiB`, not 1 MiB (the comment at `BufferPool.java:384` says 1 MiB; the constant at `:385` and the runtime log text "cannot allocate chunk of 8.000MiB" say 8 MiB). So pooled memory moves in 8 MiB steps and a threshold below 8 MiB (the 1 MiB value) lets the pool allocate nothing at all: every request goes to overflow.]** (`BufferPool.java:443-452`). The quantity compared is `memoryAllocated + MACRO_CHUNK_SIZE > memoryUsageThreshold`. Buffers outside the pool are tracked separately in `overflowMemoryUsage` (`:149, 263`) and are not part of that comparison.

**A3. Mechanism.** At `CompressedChecksummedDataInput.java:118` `readBuffer()` reads the 8-byte block header (`:110-116`), and if `compressedBuffer` is null or too small it computes `compressedSize*1.05` (`:120`), returns the old buffer (`:123`) and calls `bufferPool.get(bufferSize, compressor.preferredBufferType())` (`:125`). The same is done for the decompressed `buffer` (`:134-139`). `BufferPool.get` (`BufferPool.java:206-211`): ON_HEAP -> `allocate` heap array; else `LocalPool.get`. `LocalPool.tryGet` (`:926-960`): size > 128 KiB -> miss, null; otherwise try the thread's chunks, then `addChunkFromParent` -> `GlobalPool.allocateMoreChunks` (`:436-455`) which returns null when the threshold would be exceeded. Outcomes at the limit: null -> `LocalPool.get` falls back to `allocate(size, OFF_HEAP)` = `allocateDirect` and adds to `overflowMemoryUsage` (`:904-923, 233-238, 261-264`). So reaching the limit does not fail or block the read; it just stops pooling. Bypasses: (1) any block > 128 KiB, (2) pool exhausted, (3) ON_HEAP compressors, (4) `allocateDirect` OOM in `allocateMoreChunks` is caught (`:462-470`). The only hard cap on direct memory is `-XX:MaxDirectMemorySize` (`conf/jvm-server.options:174`, unset by default).
Block sizes: the hint file writer aggregates hints in a 256 KiB buffer (`HintsWriteExecutor.java:50`), and a hint larger than the remaining space is written on its own (`HintsWriter.java:200-228`, `Session.append`), so one compressed block holds up to one hint, bounded by `max_mutation_size` (default commitlog_segment_size/2 = 16 MiB, `DatabaseDescriptor.java:898-899`). Compression is enabled by `hints_compression` (`conf/cassandra.yaml:125`); LZ4/Snappy/Zstd are OFF_HEAP, Deflate/Noop ON_HEAP (`io/compress/*Compressor.java preferredBufferType`).
Lifetime: buffers live as long as the reader; `close()` returns `compressedBuffer` to the pool (`:155-159`) and then runs `ChecksummedDataInput.close()` (`ChecksummedDataInput.java:242-246`), which only `FileUtils.clean`s the decompressed `buffer` (no `bufferPool.put`, so no counter decrement). Readers exist per hints file being dispatched, with at most `max_hints_delivery_threads` (default 2, `conf/cassandra.yaml:93`) concurrent dispatchers.

**A4. Other consumers.** Same pool: ChunkCache (when `file_cache_enabled`), uncompressed-file `RandomAccessReader`/`BufferManagingRebufferer` buffers, compression-metadata readers. Outside the pool: hints write buffer (`WRITE_BUFFER_SIZE` 256 KiB direct, `HintsWriteExecutor.java:50`), `HintsBufferPool` (>= 32 MiB, `HintsService.java:79,110`), memtables, JVM direct memory generally.

**A5. Evidence beyond the source.** `conf/cassandra.yaml:735-760` comment: "beyond which it will not cache buffers but allocate on request" (documents the overflow behaviour). CASSANDRA-15358 (buffer pool exhaustion / heap fallback). Unit tests in `test/unit/org/apache/cassandra/hints/HintsCompressionTest.java` and `utils/memory/BufferPoolTest.java` exist as templates (not read in depth).

## B. Verification solution

**B1. Claim under test.** The amount of memory used by the compressed-hint reader's two block buffers does not follow `file_cache_size`: for hint blocks > 128 KiB (or with the pool exhausted) the buffers are allocated outside the pool, so peak direct memory for the reader is about `1.05*(compressed+uncompressed)` per active reader for every `file_cache_size` value, including 1 MiB, and `BufferPool` `OverflowSize` exceeds `Capacity`.

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Copy the tree to local disk (`rsync -a ~/cassandra-5.0.9/ /local/scratch/c509/`; never build in the shared copy), `cd /local/scratch/c509 && ant jar` (and `ant build-test` for the test classes). Add a JUnit test `test/unit/org/apache/cassandra/hints/HintsReadBufferUsageTest.java` in the copy only, run with `ant testsome -Dtest.name=org.apache.cassandra.hints.HintsReadBufferUsageTest` or a main class on the built classpath. JVM options: `-Dcassandra.config=file:///local/scratch/fcs-<N>.yaml` (yaml with `file_cache_size: <N>MiB`, `hints_compression` unset in yaml; compressor is passed in code), `-Xmx1g`, `-XX:MaxDirectMemorySize=3g`. **[Amended 2026-10-25, stage-4 audit: was 1g; the control at the 512 MiB value holds 512 MiB pooled plus 1 GiB of overflow, which does not fit in 1g. The unit tier is a main class compiled against `build/classes/main` and `build/test/classes` (not `ant testsome`), one JVM per cell.]** One JVM per `file_cache_size` value, because the threshold is read in a static initialiser.

**B2b. Knobs.** `file_cache_size` in {1MiB, 8MiB, 64MiB, 512MiB} (1 MiB is smaller than one 8 MiB macro chunk, so the pool can hold nothing and every request is overflow; 8 MiB = exactly one macro chunk; 512 MiB = default) **[Amended 2026-10-25: was "1 MiB = one macro chunk"]**. Block size B (hint payload) in {32 KiB, 100 KiB, 1 MiB, 6 MiB}: below 128 KiB blocks are poolable, above not. Compressor in {LZ4 (OFF_HEAP), Deflate (ON_HEAP)}; payload random bytes (incompressible, so compressed ~ uncompressed).

**B2c. Workload.** In the test: build a `HintsDescriptor` with `ParameterizedClass(LZ4Compressor)` params, write a file through `HintsWriter.create` (-> `CompressedHintsWriter`) with 40 hints of B bytes, using the `HintsWriter.Session.append` path; closing the session to flush each hint as its own block when B >= 256 KiB, or aggregated up to 256 KiB for small B. **[Amended 2026-10-25, stage-4 audit: for B <= 100 KiB aggregation would make blocks of about 256 KiB (`Session.append(Hint)`, `HintsWriter.java:232-240`), which are unpoolable (> 128 KiB). To get the poolable regime, open one Session per hint so each block holds one hint (compressed and decompressed block <= about 106 KiB with the +5% margin). Hints per file n: 40 for B = 32/100 KiB, 8 for 1 MiB, 6 for 6 MiB. Readers share one file (read-only), no per-reader copies. In production this regime is reached only by short blocks (a final or timer-flushed partial block), never by the 256 KiB aggregates.]** Then open `HintsReader.open(file)` and iterate all pages so `CompressedChecksummedDataInput.readBuffer` runs for every block. Run R readers concurrently on separate threads (R = 1, 2, 8) over copies of the file, holding each reader open at its last block before closing. Arithmetic: B = 6 MiB -> compressedSize ~ 6 MiB, bufferSize ~ 6.3 MiB for each of the two buffers, so ~12.6 MiB per reader, R = 8 -> ~100 MiB, far above a 1 MiB or 8 MiB threshold.

**B2d. Observables and instruments.** Direct in-process reads, sampled every 10 ms from a sampler thread and once with all readers parked: `BufferPools.forChunkCache().sizeInBytes()`, `.usedSizeInBytes()`, `.overflowMemoryInBytes()`, `.memoryUsageThreshold()`; the JMX `java.nio:type=BufferPool,name=direct` (`MemoryUsed`, via `ManagementFactory.getPlatformMXBeans(BufferPoolMXBean.class)`) for independent JVM-level truth; `Runtime` heap used for the ON_HEAP compressor case. Cannot be seen directly: which buffer belongs to which reader (use the parked-reader delta of the above).

**B2e. Procedure.**
1. Build as in B2a; write the 4 yaml files.
2. For each (`file_cache_size`, B, compressor, R): start a fresh JVM, record baseline of the 5 observables after class init, write the hints file, start R readers, park at last block, read observables, release readers, close, read again, shut down.
3. Positive control (same JVM options): skip the hint reader and call `BufferPools.forChunkCache().get(64*1024, OFF_HEAP)` repeatedly, holding the buffers, from one thread until 3x the threshold in bytes is requested; read the observables. **[Amended 2026-10-25: all "pooled" figures below mean `sizeInBytes() - overflowMemoryInBytes()` (= `memoryAllocated`), because `BufferPool.sizeInBytes()` (`BufferPool.java:274-277`) and the `Size` metric already include the overflow (`BufferPoolMetrics.java` doc of `size`).]**
4. Tabulate (threshold, B, R, compressor) -> (size, used, overflow, direct MemoryUsed).

**B2f. Predictions (before any run).**
- Control (step 3): pooled (`sizeInBytes - overflowMemoryInBytes`) rises in 8 MiB steps and stops at `floor(threshold / 8 MiB) * 8 MiB` (0, 8, 64, 512 MiB for the four values; at 1 MiB it never leaves 0 and every buffer is overflow); beyond that `overflowMemoryInBytes` grows by every further buffer (about 2 x threshold at the end, the total request being 3 x threshold). Cap binds.
- B = 6 MiB, LZ4: for every threshold, `overflowMemoryInBytes` while readers parked ~ R * 12.6 MiB (within +-10%) and pooled ~ 0 from the readers; `direct MemoryUsed` rises by the same amount. **[Amended 2026-10-25: each reader's first `readBuffer` also does `bufferPool.put` on the 4 KiB initial buffer (`ChecksummedDataInput.java:56`, `CompressedChecksummedDataInput.java:137`), which is not a pool buffer, so `overflowMemoryInBytes` is lowered by 4096 per reader; the +-10% band covers it.]** The values are identical across thresholds (within 5%), including the 1 MiB case, so `overflow > Capacity`.
- B = 1 MiB: same, ~2.1 MiB per reader.
- B = 100 KiB, small B (one hint per block, see B2c): buffers (~105 KiB, <= 128 KiB) are pooled: pooled memory is in 8 MiB steps: at threshold 1 MiB (no macro chunk fits) all reader buffers go to overflow (R * 2 * ~105 KiB, no unit of pooled memory), and at >= 8 MiB they come from the pool's free normal chunks (reader share of overflow ~ 0, reader share of in-use pooled memory ~ R * 2 * 105 KiB rounded to 128 KiB chunks). **[Amended 2026-10-25: macro chunk is 8 MiB, not 1 MiB.]** This is the only regime where `file_cache_size` is visible.
- Deflate (ON_HEAP): pooled unchanged, overflow counter ~ the same sum, heap used rises by it; direct unchanged.
- After reader close (B2h 4) **[Amended 2026-10-25]**: the compressed buffer is returned (counter lowered by its size) but the decompressed buffer is only `FileUtils.clean`ed, never `put` (`ChecksummedDataInput.java:242-246`). So the real direct `MemoryUsed` falls back to baseline (+-1 MiB) while `overflowMemoryInBytes` stays at about `1.05*B - 4096` per reader (6 MiB: ~6.3 MiB per reader), i.e. a counter that leaks; for B = 100 KiB the pooled decompressed slice is never freed either (`usedSizeInBytes` stays up by ~105 KiB per reader).
Wrong-claim signature: for B = 6 MiB, `sizeInBytes + overflow` (or direct MemoryUsed) is capped by or scales with the threshold (e.g. the total at 1 MiB is clearly less than at 512 MiB, or the reader fails/blocks when the pool is full).

**B2g. Readings.**

| Observation | Meaning |
|---|---|
| Control: pool `size` plateaus at <= threshold and overflow grows | positive control works; cap binds for poolable requests |
| B = 6 MiB: reader memory (overflow, direct delta) ~ R*12.6 MiB and equal across thresholds incl. 1 MiB | claim confirmed: usage does not follow `file_cache_size` |
| B = 6 MiB: reader memory shrinks with the threshold, or is bounded by it | claim refuted: something caps it that the trace missed |
| B = 100 KiB: `size` capped at the threshold, overflow only after | cap binds only for small blocks; consistent with the trace |
| Flat reader memory but the control did not move (size not capped, or overflow not rising) | not confirmed: control invalid, rerun |
| Threshold never reached (R*B too small) | not confirmed |

**B2h. Controls.** (1) Positive control in B2e step 3. (2) Same B and R with different thresholds isolates the knob. (3) Baseline reading before the readers start excludes other pool users. (4) Check `usedSizeInBytes` and the real `direct MemoryUsed` before/after close; the real memory must fall back to baseline (the numbers then measure live reader buffers), while the counter residual predicted in B2f is expected. (5) Compare LZ4 vs Deflate to show the heap/direct split. (6) Use random payload so compressed size ~ uncompressed (a compressible payload would shrink only `compressedBuffer`).

### B3. Cluster tier

**B3a. Environment and build.** Three nodes on one Linux host (or three hosts) from a local build (`ant jar` in a local copy), loopback addresses 127.0.0.1-3, each with its own data/commitlog/hints directories on local disk (>= 20 GiB free each). Three runs on node1 with `file_cache_size` = 1MiB, 64MiB, 512MiB (restart node1 each time, wipe its hints directory).

**B3b. Knobs.** `file_cache_size` (above, via yaml, restart). Blob size per row: 6 MiB (above 128 KiB). `max_hints_delivery_threads` = 2 (default; with two down hosts there are 2 concurrent readers). **B3c. Workload.** Keyspace `ks` with RF=3 (SimpleStrategy), table `t(id int primary key, b blob)`. Stop nodes 2 and 3.
