## A. Constraint trace

**A1. The constraint.** `commitlog_segment_size`, configuration entry ([`Config.java:396-397`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/Config.java#L396-L397), `IntMebibytesBound`, default `32MiB`; legacy `commitlog_segment_size_in_mb`), yaml `conf/cassandra.yaml:660` (comment `:650-659`). Checks: `== 0` → `ConfigurationException` "must be positive" ([`DatabaseDescriptor.java:891-893`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L891-L893)); `>= 2048` → "must be smaller than 2048" (`:894-896`). Getter `getCommitLogSegmentSize()` returns bytes (`:2875-2878`); setter is test-only (`:2887-2890`). Restart required.


**Limit type (2026-10-29).** config: yaml entry. The traced constraint decides ([README §6](../README.md#6-rules-that-hold-for-both-agents)).
**A2. What it caps.** Disk: size of each `CommitLog-*.log` file. Memory: size of each segment's mapped buffer (mmap, legacy mode) or of the per-segment write buffer in compressed/encrypted/direct-IO modes (`CompressedSegment.java:116`, `EncryptedSegment.java:112,176`, `DirectIOSegment.java:201-206`). Indirectly: default `max_mutation_size = segment/2`.

**A3. Mechanism.**
1. Startup checks ([`DatabaseDescriptor.java:891-896`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L891-L896)); then `max_mutation_size` default or the 2× invariant (`:898-901`).
2. `MemoryMappedSegment.createBuffer` maps `[0, segmentSize)` of the new file and adds `segmentSize` to the manager's size ([`MemoryMappedSegment.java:60-64`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/MemoryMappedSegment.java#L60-L64)); `onDiskSize()` returns it (`:103-106`).
3. `CommitLog.add` validates the mutation against `max_mutation_size` ([`CommitLog.java:304`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/CommitLog.java#L304), [`Mutation.java:169-176`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/Mutation.java#L169-L176)), then `segmentManager.allocate` ([`CommitLog.java:311`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/CommitLog.java#L311)); `CommitLogSegment.allocate(int)` returns −1 if `prev+size >= endOfBuffer` ([`CommitLogSegment.java:240-255`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/CommitLogSegment.java#L240-L255)), and the manager advances to a new segment ([`CommitLogSegmentManagerStandard.java:47-60`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/CommitLogSegmentManagerStandard.java#L47-L60)).
4. Total commit-log size is governed separately by `commitlog_total_space` (default min(8192 MiB, ¼ of the volume), [`DatabaseDescriptor.java:664-675`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L664-L675)) via flush-to-reclaim ([`AbstractCommitLogSegmentManager.java:246-248`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/AbstractCommitLogSegmentManager.java#L246-L248)).
- Bypass: none for per-segment size in legacy mode; in compressed mode the on-disk file is smaller than the buffer ([`CompressedSegment.java:93`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/commitlog/CompressedSegment.java#L93)).

**A4. Other consumers.** Number of segments (governed by `commitlog_total_space` and flush progress), CDC segments (`CommitLogSegmentManagerCDC.java:201-207`), hints, SSTables.

**A5. Evidence beyond the source.** `conf/cassandra.yaml:650-660`.

(3) Active segments: `activeSegments` holds, in creation order, the segment being allocated (its tail, `:85`, `:311`) and older segments not yet discarded. When allocation moves on, the old segment's unused tail is discarded (`:330`; `CommitLogSegment.java:258-287`) and an extra sync is requested (`:334`). The next sync of such a segment cannot allocate a sync marker (`CommitLogSegment.java:327-332`), so it flushes and closes it (`:356-368`), which unmaps it. So a full active segment holds its mapping from its creation until the first sync after it was left, and none afterwards. How many full segments are still mapped at a reading depends on sync timing, which the source does not fix. The allocating segment holds its mapping unless a sync found less than one sync marker of room left (`CommitLogSegment.java:240-247, 327-332`) before the next write moved allocation on.
