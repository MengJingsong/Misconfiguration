## A. Constraint trace

**A1. The constraint.** `MAX_SHARD_SPLIT` is a compile-time constant (not a yaml entry, not a `-D` property, not JMX), declared `static final double MAX_SHARD_SPLIT = Math.scalb(1, MAX_SHARD_SHIFT)` at [`Controller.java:141`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/compaction/unified/Controller.java#L141), with `MAX_SHARD_SHIFT = 20` at `Controller.java:139`; so it is 2^20 = 1048576, a unitless multiplier on `baseShardCount` (comment `Controller.java:140`). Changing it needs a recompile. The check is `if (count > MAX_SHARD_SPLIT) count = MAX_SHARD_SPLIT;` at `Controller.java:305-306`, inside `getNumShards(double localDensity)` (`Controller.java:264`), in the `sstableGrowthModifier == 0` branch (`Controller.java:299`). `count` is `localDensity / (targetSSTableSize * INVERSE_SQRT_2 * baseShardCount)` (`Controller.java:304`; `INVERSE_SQRT_2` at `Controller.java:166`). The non-zero-growth branch has the same cap in exponent form: `pow >= MAX_SHARD_SHIFT` gives `baseShardCount << MAX_SHARD_SHIFT` (`Controller.java:338-339`). Correction to the earlier trace: it said the cap applies "when sstableGrowthModifier == 0", correct, but that is not the default; `sstable_growth` defaults to 0.333 (`CassandraRelevantProperties.java:613`, read at `Controller.java:110-111`), so by default the line-305 branch is not taken and the line-338 form applies. The operands are real settings: `target_sstable_size` (option `Controller.java:80`, default `UCS_TARGET_SSTABLE_SIZE` = `unified_compaction.target_sstable_size`, "1GiB", `CassandraRelevantProperties.java:615`, read at `Controller.java:81-82`, per-table override `Controller.java:432-434`, minimum 1 MiB `Controller.java:83` enforced at `Controller.java:505-510`), and `base_shard_count` (default `unified_compaction.base_shard_count` = "4", `CassandraRelevantProperties.java:609`, `Controller.java:77-78`, per-table override `Controller.java:422-430`, must be positive `Controller.java:476-480`). `sstable_growth` is validated to [0,1] (`Controller.java:633-638`) and set per table (`Controller.java:441-442`) or by `unified_compaction.sstable_growth`. Per-table options apply when the table's controller is created (`fromOptions`, `Controller.java:408`); the `-D` properties need a node restart. Unit: shards (a count); `localDensity` is bytes per unit of token space (size / token-span share).

**A2. What it caps.** The number of shards (output sstable split points) UCS cuts a flush or compaction output into: at most `baseShardCount * 2^20`. It is not a cap on heap, off-heap or disk bytes. The quantity compared is `count`, in units of "base-shard-count multiples of sqrt(0.5) * target size" (`Controller.java:304`). Indirectly it bounds the number of sstables produced from one given amount of data (which affects per-sstable heap structures and file handles), but the data volume on disk is unchanged by it.

**A3. Mechanism.** (1) Callers: flush path `UnifiedCompactionStrategy.createSSTableMultiWriter` computes `flushDensity` and calls `controller.getNumShards` (`UnifiedCompactionStrategy.java:272-274`); compaction path `UnifiedCompactionTask.getCompactionAwareWriter` calls it with `density * shardManager.shardSetCoverage()` (`UnifiedCompactionTask.java:57-58`). Density comes from `ShardManager.calculateCombinedDensity` = `onDiskLength / span` when span >= 2^-48 (`ShardManager.java:42`, `ShardManager.java:147-165`), so a small total size over a narrow token span gives a large density. (2) `getNumShards` first applies the `min_sstable_size` branch (`Controller.java:266-294`): if `localDensity / minSSTableSize < baseShardCount` (or NaN) it returns a value at or below `baseShardCount` and never reaches line 305; the default min is 100 MiB (`CassandraRelevantProperties.java:610`, `Controller.java:61`), `0` disables it. (3) If `sstable_growth == 1` it returns `baseShardCount` (`Controller.java:296-302`). (4) If `== 0`, line 304 computes `count`, line 305-306 clamps it to 2^20, line 307 asserts non-negative, line 313 `shards = baseShardCount * Integer.highestOneBit((int) count | 1)` rounds down to a power of two, so the maximum is `baseShardCount * 2^20`. (5) Otherwise lines 327-343 use the log form. (6) The result goes to `ShardManager.boundaries(numShards)` (`ShardManagerNoDisks.java:95-98`, `BoundaryTracker` constructor `ShardManagerNoDisks.java:111-121`), which computes boundaries lazily (`getEndToken`, `ShardManagerNoDisks.java:124-135`), and `ShardedCompactionWriter.shouldSwitchWriterInCurrentLocation` starts a new sstable writer at each crossed boundary only if bytes were already written (`ShardedCompactionWriter.java:67-80`), so the real sstable count is also bounded by the amount of data and the number of distinct partitions. Outcomes: below the cap, shards track density; at or above it, shards stay at `baseShardCount * 2^20`. Bypass/overshoot: (a) `shards` is an `int`: `baseShardCount * 2^20` overflows when `baseShardCount >= 2048` (2048 * 2^20 = 2^31 wraps to negative, 4096 * 2^20 = 2^32 wraps to 0); `fromOptions` validates only `> 0` (`Controller.java:476-480`), so the cap does not protect that case (verify by test, B2). (b) Line 338-339 uses `<<` on an int with the same overflow. (c) `NaN` density skips the clamp (comparison false) and yields `baseShardCount` (`Controller.java:307-313`).


The check itself is the if statement at [`src/java/org/apache/cassandra/db/compaction/unified/Controller.java:305`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/db/compaction/unified/Controller.java#L305).

**A4. Other consumers.** Disk and heap used by the same compaction outside this constraint: the data itself, memtable and flush sizes, the sstable index/bloom filter/compression metadata held per open sstable, compaction throughput limits (`Config.java:337`), `concurrent_compactors` (`Config.java:335`), and the maximum sstables per compaction (`Controller.java:131`, `max_sstables_to_compact`). Temporary disk during compaction (input plus output) is determined by the input size, not by shard count.

**A5. Evidence beyond the source.** The javadoc of `getNumShards` (`Controller.java:247-263`) and the `sstable_growth` description (`Controller.java:86-108`) describe the intent (shard count as power-of-two multiple of base count, sstable sizes within sqrt(0.5) to sqrt(2) of target). The existing unit test `test/unit/org/apache/cassandra/db/compaction/unified/ControllerTest.java` (lines 103-104, 275-280) exercises `getNumShards`; it has no assertion on the 2^20 clamp (searched for `MAX_SHARD`: no hit under `test/unit/.../db/compaction`). Public docs: Cassandra 5.0 "Unified Compaction Strategy" page (https://cassandra.apache.org/doc/5.0/cassandra/managing/operating/compaction/ucs.html), CEP-26. Otherwise none.

## B. Verification solution

**B1. Claim under test.** Because the estimate is negative: raising or lowering the quantity that `MAX_SHARD_SPLIT` clamps (the shard count, via density or `target_sstable_size`) does not change the bytes of heap or disk the node uses for the same data; the clamp only changes the sstable count, and is only reached at density above `2^20 * sqrt(0.5) * target_sstable_size * base_shard_count`. Refuted if heap or total on-disk bytes track the shard count at the cap.

**B2b. Knobs.** Per case, options map passed to `fromOptions`: `sstable_growth` in {0 (line 305 branch), 0.333 (default, line 338 branch), 1}; `min_sstable_size` = `0MiB` (so the min-size branch cannot return early); `target_sstable_size` in {1MiB (minimum, `Controller.java:83`), 1GiB (default)}; `base_shard_count` in {1, 4, 2047, 2048, 4096} (2047 and 2048/4096 bracket the int overflow in A3). **B2c. Workload.** Call `controller.getNumShards(d)` with densities around the knee. Knee `K = 2^20 * 0.70711 * target * base`. For target 1MiB, base 1: K = 0.70711 * 2^40 B = about 7.8e11 B. Sweep d = K/4, K/2, K*0.99, K*1.01, 2K, 2^10 K, 2^40 K, `Double.MAX_VALUE`, `Double.POSITIVE_INFINITY`, `NaN`, 0. For defaults (1GiB, base 4): K = 0.70711 * 2^20 * 2^30 * 4 B = about 3.2e15 B. Also build the output via `ShardManagerNoDisks.boundaries(shards)` for a few values and call `shardIndex/advanceTo` once, to check the tracker's cost is independent of count.

**B2d. Observables and instruments.** Return value of `getNumShards`; number of distinct boundaries not enumerated. Heap of a `BoundaryTracker` after construction: `Runtime.totalMemory()-freeMemory()` after `System.gc()`, 10 repetitions, or JOL (`org.openjdk.jol`) `GraphLayout.parseInstance(tracker).totalSize()` if on the classpath. Cannot be observed: disk or real heap use (that is B3).

**B2e. Procedure.** (1) Build. (2) Write the test to loop over the knob grid and densities and print `growth, target, base, d, shards`. (3) Run. (4) For a `BoundaryTracker` built at shards = 4, 2^10, 2^20: record retained heap before/after. (5) Compare to predictions.

**B2f. Predictions (before any run).** growth 0, min 0, target 1MiB, base 1: d <= K*0.99 gives a value below 2^20 (power of two, `highestOneBit`); d >= K*1.01 gives exactly 2^20 = 1048576; d = 2K, 2^10 K, 2^40 K, MAX_VALUE, +Inf all give 1048576 (clamped, flat). ### B3. Cluster tier

**B3a. Environment and build.** One node (second node not needed), JDK 11, Ant, local copy of the tag, `ant jar` in `$WORK/cassandra-5.0.9`. Data, commit log, hints and saved caches on a local disk of known size (e.g. 20 GiB partition) via `-Dcassandra.storagedir=$WORK/data` and yaml directory entries. `cassandra.yaml`: `partitioner: ByteOrderedPartitioner` (so keys can be chosen to fall in a narrow token window), `num_tokens: 1`, `concurrent_compactors: 1`, `compaction_throughput: 0MiB/s`, `commitlog_sync: periodic`. JVM: `-Xms2g -Xmx2g -XX:+UseG1GC`, `-Dunified_compaction.base_shard_count=1`, `-Dunified_compaction.sstable_growth=0`, `-Dunified_compaction.min_sstable_size=0MiB` unless the table options below are used. Table: `CREATE TABLE ks.t (k blob PRIMARY KEY, v blob) WITH compaction = {'class':'UnifiedCompactionStrategy','scaling_parameters':'T2','base_shard_count':'1','target_sstable_size':'1MiB','sstable_growth':'0','min_sstable_size':'0MiB'}`.

**B3b. Knobs.** `target_sstable_size` (1MiB minimum vs 64MiB vs 1GiB default, per table via `ALTER TABLE`), `sstable_growth` (0 vs 0.333 vs 1), and the token window width of the keys (which scales density via `onDiskLength / span`, `ShardManager.java:147-165`). The cap point is reached when density > `2^20 * 0.70711 * target * base`; with target 1MiB, base 1 that is about 7.8e11 B, which a small data set reaches only if span is tiny: with keys confined to a window of 2^-24 of the ring (BOP: fix the top 3 key bytes) 64 MiB of data gives density about 1.1e15 B, above the knee. The window must stay >= 2^-48 (`ShardManager.java:42`) or the span is replaced by 1 (`ShardManager.java:119-121`).

**B3c. Workload.** Through cqlsh/`cassandra-stress` or a small driver script: insert rows with key = fixed 3-byte prefix + 12 random bytes, value = 4 KiB random blob; 16384 rows per batch = 64 MiB; flush (`nodetool flush ks t`) after each batch; run 8 batches (about 512 MiB) in the narrow window ("dense" arm). Control arm: same data volume with keys across the whole ring (random 16-byte keys) so density is about 512 MiB, below the knee. Compact (`nodetool compact ks t`, or wait for UCS) after the last flush. Duration about 10 to 20 minutes per arm. Repeat for target 1MiB and 1GiB.

**B3d. Observables and instruments.** (1) Number of sstables after compaction: `nodetool tablestats ks.t` (`SSTable count`), `ls $DATA/ks/t-*/*Data.db | wc -l`. (2) Total live and on-disk bytes: `nodetool tablestats` (`Space used (live)`) and `du -sb`. (3) Heap: `jcmd <pid> GC.heap_info` and `nodetool info` (heap memory), sampled every 10 s with `jstat -gc <pid> 10s`; off-heap via `nodetool tablestats` (`Bloom filter off heap memory used`, `Index summary off heap memory used`, `Compression metadata off heap memory used`). (4) Enable debug logging for `org.apache.cassandra.db.compaction.unified.Controller` (`nodetool setlogginglevel org.apache.cassandra.db.compaction.unified.Controller DEBUG`) to read the logged `Shard count ... for density` line (`Controller.java:316-320`), which reports the computed shards. Cannot be observed directly: the `count` variable; use the log line.

**B3e. Procedure.** (1) Copy the tree, `ant jar`. (2) Start the node with the settings in B3a, check `nodetool status`. (3) Create the table, enable the DEBUG log level. (4) Dense arm: load 8 batches with flush after each; record `tablestats`, heap and file counts. (5) `nodetool compact ks t`; record again and grep the log for `Shard count`. (6) Truncate, repeat with the control arm. (7) `ALTER TABLE` to `target_sstable_size` 1GiB and `sstable_growth` 0.333 (new controller on schema change) and repeat both arms. (8) Stop the node (`nodetool drain; kill <pid>`), delete `$WORK/data`.

**B3f. Predictions (before any run).** Dense arm, target 1MiB: the logged shard count is 1048576 (the clamp) while the sstable count is far smaller (bounded by data: 512 MiB at about 1 MiB target gives hundreds, not a million, since writers switch only after bytes are written, `ShardedCompactionWriter.java:71`); total on-disk bytes after compaction about equal to the sum of inputs (not affected by the clamp). Control arm: logged shard count well below 2^20 (about 512 MiB / (0.707 MiB) rounded down to a power of two, 512 or less). Heap and off-heap in the dense and control arms differ by no more than the sstable-count-proportional metadata; heap does not scale with the logged shard count (1048576 vs a few hundred gives no 1000x heap change). Default target 1GiB: shard count stays near 1 in both arms; the clamp is never reached.
