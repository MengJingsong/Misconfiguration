## A. Constraint trace

**A1. The constraint.**
- Name: the maximum serialized size of one `SerializingCache` entry, `Integer.MAX_VALUE` (2^31-1 bytes, just under 2 GiB). Kind: constant (a literal compared at runtime). There is no config entry for it.
- First declared at `SerializingCache.java:94` (`if (serializedSize > Integer.MAX_VALUE) throw new IllegalArgumentException(...)`). The same limit appears in the default weigher at `SerializingCache.java:71-73` (message "Serialized size must not be more than 2GiB"), because Caffeine weights are `int` (:74 casts to `int`).
- Unit: bytes. Default: n/a (fixed). Not settable by yaml, `-D` or JMX; changing it needs a code change and rebuild.
- Related, and the real aggregate cap: `row_cache_size` (`Config.java:474`, default `0MiB`, `conf/cassandra.yaml:564`; read by `DatabaseDescriptor.getRowCacheSizeInMiB()` at `DatabaseDescriptor.java:3916-3918`). It is passed as `size*1024*1024` to `SerializingCache.create` at `SerializingCacheProvider.java:33` and becomes Caffeine `maximumWeight(capacity)` at `SerializingCache.java:52`. It is changeable at runtime via `CacheService.setRowCacheCapacityInMB` (`CacheService.java:325-332`, which calls `SerializingCache.setCapacity`, :124-127), exposed over JMX as `CacheServiceMBean`.
- `SerializingCache` is used only when `row_cache_class_name: org.apache.cassandra.cache.SerializingCacheProvider` (`conf/cassandra.yaml:550-553`). The default in `Config.java:472` is `OHCProvider`. `CacheService.initRowCache` (`CacheService.java:140-169`) swaps in `NopCacheProvider` when `row_cache_size` is 0, so the row cache is off by default.

**A2. What it caps.** Off-heap native memory (`Memory` allocates with `MemoryUtil.allocate` -> `Native.malloc`, `Memory.java:65`, `MemoryUtil.java:81-84`; not Java heap, and not tracked by JVM NMT because it is libc `malloc`). The quantity compared at :94 is `serializer.serializedSize(value)` for a single value: for the row cache, 1 byte for the sentinel flag plus `CachedPartition.cacheSerializer.serializedSize(partition)` (`SerializingCacheProvider.java:60-67`). The quantity compared by `row_cache_size` is the sum of Caffeine weights, i.e. of those same per-entry sizes (`weightedSize()`, :139-142).

**A3. Mechanism.**
1. A read of a partition with `caching = {'rows_per_partition': ...}` goes to `SinglePartitionReadCommand` (~:545-615). It first `putIfAbsent`s a `RowCacheSentinel` (:561), reads the partition, builds a `CachedBTreePartition` bounded by `rowsPerPartitionToCache` (:589-600), then `rowCache.replace(key, sentinel, toCache)` (:608).
2. `SerializingCache.replace` (:210-249) and `put`/`putIfAbsent` (:166-208) all call `serialize(value)` (:91-117).
3. `serialize` computes `serializedSize` (:93). If it exceeds `Integer.MAX_VALUE`, throw `IllegalArgumentException` (:94-95). In the read path the exception is a `RuntimeException`, so the user read fails (caught only to close the iterator, :623-627), and the `finally` invalidates the sentinel (:629-632).
4. Otherwise `new RefCountedMemory(serializedSize)` mallocs the full size immediately (:100). If `malloc` fails (`OutOfMemoryError`, `Memory.java:69`), `serialize` returns `null` and the put is silently skipped (:102-105; callers :169-170, :190-191, :230-231).
5. The value is written into the memory (:109), then inserted into Caffeine (:175/:196/:236). Caffeine weighs it (:69-75) and evicts when total weight exceeds `maximumWeight`. Eviction (via `ImmediateExecutor`, :53) runs the removal listener, which `unreference()`s (frees) the memory only if `cause.wasEvicted()` (:54-58). Explicit removal/replacement is handled by callers (:183-184, :244-245, :253-255).
- Outcomes at the limit: size > 2^31-1 -> exception, nothing allocated. Size <= 2^31-1 but > `row_cache_size` -> memory is allocated in full, inserted, and the entry is evicted at once (weight exceeds max) and freed by the listener. So the transient peak is `row_cache_size` + the largest in-flight entry(ies).
- Bypasses/overshoots: (a) allocation precedes admission, so each concurrent writer can hold up to one entry of up to 2 GiB that is not yet counted; (b) the weigher counts only value bytes, not malloc headers/fragmentation or the heap-resident `RowCacheKey` and Caffeine node; (c) `Memory` size 0 raises an `AssertionError` (`Memory.java:60-61`), not relevant here; (d) a `RefCountedMemory` still referenced by a reader (:154, :162) is not freed on eviction until the reader unreferences, so live bytes can exceed the weighted size briefly; (e) `weightedSize` is maintained by Caffeine asynchronously-maintained drain (an immediate executor makes maintenance run in the calling thread), so reads can briefly lag.

**A4. Other consumers.** Off-heap native memory also used by: key cache and counter cache are on-heap Caffeine (`CaffeineCache.create`, `CacheService.java:128,179`), so not this resource; memtables (offheap if configured), bloom filters/compression metadata/index summaries (`Memory`/`SafeMemory`), chunk cache, direct buffers (networking, `-XX:MaxDirectMemorySize`), JNA mallocs, and the OS page cache. RSS therefore moves for reasons other than the row cache.

**A5. Evidence beyond the source.**
- `conf/cassandra.yaml:545-580` (row cache provider and size comments); `test/unit/org/apache/cassandra/cache/CacheProviderTest.java:145-152` shows the `SerializingCache.create(CAPACITY, weigher, RowCacheSerializer)` usage that the unit tier can imitate.
- Caffeine documentation for `maximumWeight`/`Weigher` (weights are `int`; entries heavier than the maximum are evicted immediately): https://github.com/ben-manes/caffeine/wiki/Eviction
- Otherwise none.

## B. Verification solution

**B1. Claim under test.** The `Integer.MAX_VALUE` check at `SerializingCache.java:94` does not cap the total off-heap memory used by a `SerializingCache`: (i) the total is governed by `row_cache_size` (Caffeine weight), and (ii) it can transiently exceed `row_cache_size` because each entry is allocated before admission. Falsified if native memory usage stays bounded by the 2 GiB per-entry limit rather than by `row_cache_size`, or if no allocation exceeds `row_cache_size` before eviction (the transient overshoot is absent).

### B2. Unit tier

**B2a. Environment and build.** Linux, JDK 11, Ant. Copy the tree to local disk (`rsync -a ~/cassandra-5.0.9/ /local/work/c509/`; never build in the shared tree). `cd /local/work/c509 && ant jar` (and `ant build-test` for test classpath). Add a probe test `test/unit/org/apache/cassandra/cache/SerializingCacheLimitProbe.java` (in the local copy only) that calls `SerializingCache.create(capacity, serializer)` with a custom `ISerializer<byte[]>` (the `serialize` writes `len` bytes with `out.write`, `serializedSize` returns `len` or a forced value). Run with `ant testsome -Dtest.name=org.apache.cassandra.cache.SerializingCacheLimitProbe -Dtest.methods=...`, with `-Xmx512m -XX:+UseG1GC` and `test.jvm.args` adding `-XX:NativeMemoryTracking=summary` (does not track `malloc`, so also use RSS). Machine needs at least 4 GiB free RAM; use an 8 GiB cgroup/`ulimit -v` guard if shared.

**B2b. Knobs.** (1) Entry serialized size `S` (fake `serializedSize`): `2^31-1` (boundary, allowed), `2^31` (just over, must throw), `2^31+4096`. For the boundary case the serializer writes nothing, so pages stay untouched. (2) For the aggregate tests, capacity `C` in {64 MiB, 128 MiB, 256 MiB} (the programmatic equivalent of `row_cache_size`), entry size `E` = 1 MiB (many-entry test) and `E` = 4*C... bounded to 512 MiB (single oversize-entry test; must be <2 GiB). Set via the `create(capacity, serializer)` argument and `setCapacity`.

**B2c. Workload.**
- W1 (guard test): `put(k, v)` with a fake serializer returning `S` = 2^31-1, 2^31, 2^31+4096 from `serializedSize`. Arithmetic: only the `>` comparison at :94 matters.
- W2 (aggregate cap): insert 1024 distinct keys of `E` = 1 MiB real bytes (1 GiB offered) into caches with C = 64/128/256 MiB. Offered = 1 GiB >> C, so eviction must engage.
- W3 (transient overshoot): with C = 64 MiB, `put` one entry of `E` = 512 MiB (real bytes, written). 512 MiB > C, so Caffeine evicts it right after insertion. Also run 8 threads each putting a distinct 256 MiB entry concurrently (offered 2 GiB, in-flight up to 8 x 256 MiB).

**B2d. Observables and instruments.** (a) Exception type/message from `put` (W1). (b) `cache.weightedSize()`, `cache.size()`, `cache.capacity()` after each batch (public API, :119-142). (c) Native usage: sample `VmRSS` and `VmHWM` of the JVM from `/proc/self/status` every 10 ms in a sampler thread (the entries are written, so pages are touched); report peak minus baseline (take baseline after JVM warmup and `System.gc()`). (d) Exact native bytes: wrap by counting live `RefCountedMemory` bytes in the fake serializer (add `size` at `serialize`, subtract when the removal listener frees, approximated by `weightedSize` plus an `AtomicLong` incremented in the serializer and decremented from a `Cleaner`-free check: simplest is `/proc/self/smaps_rollup` Rss). Cannot be observed directly: malloc overhead and per-allocation fragmentation (glibc retains freed arenas, so RSS after free can stay high; use `MALLOC_ARENA_MAX=1` and `MALLOC_TRIM_THRESHOLD_=0` env for the test JVM to reduce this).

**B2e. Procedure.**
1. Copy and build as in B2a.
2. Run W1 for the three `S` values; record exception or success. After the 2^31-1 case, call `cache.clear()`.
3. For each C in {64, 128, 256} MiB: new cache, start the RSS sampler, run W2, record `weightedSize()` and peak RSS minus baseline; `cache.clear()`; re-baseline.
4. Run W3 (single 512 MiB, then 8x256 MiB), recording peak RSS minus baseline and `weightedSize()` afterwards.
5. Call `setCapacity(C/2)` on a full cache and record `weightedSize()` (shrink path).
6. `cache.clear()`; check no `java` process of the probe remains (`pgrep -f SerializingCacheLimitProbe`).

**B2f. Predictions.** (Stated before any run.)
- W1: 2^31-1 -> no exception (allocation of ~2 GiB attempted; with a non-writing serializer RSS barely moves); 2^31 and 2^31+4096 -> `IllegalArgumentException` with message "Unable to allocate 2.000GiB" (the first prints "2.000GiB").
- W2: `weightedSize()` <= C (<= 64/128/256 MiB) at quiescence for every C, and `size()` ~ C / 1 MiB; peak RSS delta ~ C + a small margin (expected < C + 64 MiB), growing in proportion to C. It does not approach the 2 GiB guard.
- W3: single 512 MiB entry with C = 64 MiB: `weightedSize()` ends at 0 (entry evicted), but peak RSS delta >= ~512 MiB during the put (overshoot ~ 8 x C). With 8 x 256 MiB threads: peak RSS delta up to ~ C + 2 GiB, i.e. far above C.
- Shrink: `weightedSize()` falls to <= C/2 after `setCapacity`.
- Claim wrong if: RSS delta in W2 does not scale with C but with the 2 GiB limit, or W3 shows peak delta <= C (no pre-admission allocation).

**B2g. Readings.**

| Observation | Meaning |
|---|---|
| W1: 2^31 throws, 2^31-1 passes | The guard works as traced at :94 (per-entry only). |
| W1: 2^31 does not throw | Trace wrong (a different path, e.g. `replace`/weigher, handles it). |
| W2: weightedSize <= C and RSS delta tracks C (slope ~1) while offered is 1 GiB | Usage follows `row_cache_size`, not the :94 limit (claim confirmed). |
| W2: RSS delta flat at ~1 GiB regardless of C | `row_cache_size` does not cap native usage (claim stronger; investigate eviction/removal listener). |
| W3: peak RSS delta >> C while `weightedSize()` <= C | Allocation precedes admission: transient overshoot confirmed. |
| W3: peak RSS delta <= C + small | No overshoot; claim (ii) refuted. |
| RSS delta in W2 identical for C = 64/128/256 (flat) while the positive control moves | Usage does not follow the knob; refutes the "usage follows `row_cache_size`" half. |
| Sampler shows no RSS rise at all | Pages untouched (the serializer did not write) or the limit was never reached; not confirmed. |

**B2h. Controls.** Positive control: the same workload with C varied, showing RSS delta moves with C (the known binding cap). Negative controls: (1) run with a trivial on-heap `ConcurrentHashMap<byte[]>` baseline to show the sampler sees heap-independent RSS changes only for native allocation (heap pinned with `-Xmx512m`, and verify `Runtime.totalMemory()` is flat); (2) repeat W2 after `cache.clear()` and confirm RSS delta returns to near baseline (with the malloc env vars), ruling out leaks as the cause of growth; (3) run W2 twice to rule out JIT/class-load RSS noise.

**B2i. Stage-4 audit amendments (2026-10-25, before any reading; each is derivable from the source or from the arithmetic alone).**
1. *Value type.* A `byte[]` value of 256 to 512 MiB cannot live in the forked test JVM's heap (ant's `maxmemory` is 1 GiB). The probe's value type is a small `Blob(declaredSize, bytesToWrite, barrier)`; its serializer writes `bytesToWrite` bytes from one pre-filled 1 MiB heap buffer through `out.write(buf, 0, n)` (so the native pages are written) and `serializedSize` returns `declaredSize`. Native allocation is unchanged.
2. *Allocator settings (instrument).* The test JVM runs with `MALLOC_ARENA_MAX=1 MALLOC_MMAP_THRESHOLD_=65536 MALLOC_TRIM_THRESHOLD_=0`, so that every entry of 64 KiB or more is its own `mmap`ed chunk and `free()` returns it at once; resident anonymous memory then tracks live bytes. The usage reading is `RssAnon` from `/proc/self/status` (sampled every 10 ms), not `VmRSS`. Baseline = `RssAnon` after `System.gc()` and 300 ms of settling, per arm.
3. *Arms added (the workload of B2c is otherwise as filed).* **W2big**: C = 3072 MiB, 4096 distinct 1 MiB entries (4 GiB offered), the one arm that puts total native usage above `Integer.MAX_VALUE` while each entry is 1 MiB. **W3b**: 8 threads x 512 MiB (4 GiB in flight). **W3a** is the filed 8 x 256 MiB. In W3a and W3b the serializer waits on a `CyclicBarrier(8)` after writing its bytes and before returning, so all eight allocations are live at once (otherwise the peak depends on thread timing). **Control `nocache`**: the W2 loop (1024 x 1 MiB) with the same serializer into a discarding stream, no cache. **Repeat**: W2 at C = 64 MiB run twice. **Clear probe**: after the first W2 at C = 64 MiB, call `clear()` and read `RssAnon` (see 5).
4. *Emptying the cache between arms.* B2e steps 2, 3 and 6 say `cache.clear()`. In the source, `clear()` is `cache.invalidateAll()` (`SerializingCache.java:144-147`), the removal cause is `EXPLICIT`, and the listener frees only `cause.wasEvicted()` entries (:54-58), so `clear()` leaves the native memory allocated (a leak; only `remove(key)` unreferences, :251-256). The harness therefore empties a cache by `remove(key)` for each key, then checks `RssAnon` is back to within 32 MiB of the baseline.
5. *Extra source-derived prediction (does not alter B1 or the B2g rows):* after `clear()` on the C = 64 MiB cache, `size()` = 0 and `weightedSize()` = 0 while `RssAnon` minus baseline stays at 0.9 x its pre-clear value or more (the memory is not freed). If it falls, the trace of :54-58 is wrong, which is recorded but leaves B1 as it is.
6. *Numeric form of B2f (the filed text keeps its claims; these are its thresholds).* Peak and end values are `RssAnon` minus the arm's baseline. W1: S = 2^31-1 no exception; S = 2^31 and 2^31+4096 throw `IllegalArgumentException("Unable to allocate 2.000GiB")` (`prettyPrintMemory` formats both to 2.000); `weightedSize()` = 0 after each (the 2^31-1 entry, 2 GiB unwritten, is heavier than C = 64 MiB and is evicted at once); peak below 64 MiB for all three. W2: `weightedSize()` between 0.95 C and C at the end; `size()` within 2 entries of C/1 MiB; peak between 0.95 C and C + 16 MiB; the slope of peak against C between C = 64 and 256 MiB is 0.9 to 1.1. W2big: `weightedSize()` between 0.95 and 1.0 of 3072 MiB and peak between 2918 and 3104 MiB, i.e. above 2048 MiB (the :94 limit). W3 single 512 MiB at C = 64 MiB: end `weightedSize()` = 0, `size()` = 0, peak at least 480 MiB (7.5 C), end at most 32 MiB. W3a: peak at least 1946 MiB (1.9 GiB), end `weightedSize()` = 0. W3b: peak at least 3891 MiB (3.8 GiB, above 2048 MiB), end `weightedSize()` = 0. Shrink 256 to 128 MiB: `weightedSize()` between 0.9 x 128 and 128 MiB right after `setCapacity`, `RssAnon` minus baseline at most 144 MiB. `nocache`: peak below 32 MiB. Repeat: second W2 peak within 10 percent of the first.
7. *B2g rows added:* (a) "W2big or W3b peak above 2048 MiB while every single entry is within the :94 limit": total native use exceeds the per-entry limit; the B1 falsifier "usage stays bounded by the 2 GiB limit" does not hold (supports the claim). (b) "W2big or W3b peak at or below 2048 MiB although the offered load and C allow more": the limit-never-reached row; Not confirmed for that part. (c) "`nocache` peak above 32 MiB": the sampler is not specific to native cache memory; Invalid for the RSS readings.
8. *Citations (stage-3 notes, no effect on the design).* `Memory.java:60-61` is :62-63 in the pinned source; the `finally` of `SinglePartitionReadCommand` is :632-636 (not :629-632); `CacheService.initRowCache` is :141-170 and `setRowCacheCapacityInMB` :327-334. The rest were re-read and hold (`SerializingCache.java:52-58, 62-76, 91-117, 119-142, 166-256`, `SerializingCacheProvider.java:33, 59-67`, `RefCountedMemory.java:29-55`, `Memory.java:65, 69`, `MemoryUtil.java:81-84`, `FBUtilities.java:935-945`, `Config.java:472-474`, `conf/cassandra.yaml:553, 564`).

### B3. Cluster tier

**B3a. Environment and build.** One node suffices (a 3-node cluster is optional and not needed: the row cache is node-local). Linux, JDK 11, Ant. Copy the source to `/local/work/c509-node/`; `ant jar`; node data, commitlog, hints, saved_caches on local disk with a size cap (e.g. a 20 GiB local partition; use `df` before and after). `conf/cassandra.yaml` changes: `row_cache_class_name: org.apache.cassandra.cache.SerializingCacheProvider`, `row_cache_size: 256MiB` (varied, see B3b), `row_cache_save_period: 0s`, `key_cache_size: 0MiB`, `memtable_allocation_type: heap_buffers`, `file_cache_size: 64MiB`, `native_transport_max_threads` default. JVM: `-Xms2g -Xmx2g -XX:MaxDirectMemorySize=256m -XX:NativeMemoryTracking=summary`, env `MALLOC_ARENA_MAX=1`. Row-cache memory is `malloc`, so heap is fixed at 2 GiB and RSS minus heap/direct/metaspace gives the cache.

**B3b. Knobs.** `row_cache_size` in {64MiB, 256MiB, 1024MiB} (yaml, node restart per value; also runtime change with `nodetool setcachecapacity 0 <row_MiB> 0` -> `CacheService.setRowCacheCapacityInMB`). Table option `caching = {'keys':'NONE','rows_per_partition':'ALL'}`. Workload parameter: partition size P in {64 KiB (many entries), 64 MiB (a few large entries)}. The :94 limit itself cannot be pushed on a real node without a >2 GiB partition; see B3c.

**B3c. Workload.** Table `ks.t(pk int, ck int, v blob, PRIMARY KEY (pk, ck))`, one-time load via `cassandra-stress`-free CQL driver script (or `cqlsh` COPY): P = 64 KiB partitions: 16,384 partitions (1 GiB total, 4x the 256 MiB cache, 16x the 64 MiB one); then read each partition once with `SELECT * FROM ks.t WHERE pk = ?` (reads populate the cache through `SinglePartitionReadCommand`, :545-615), two passes, 10 min. Large-entry run: 8 partitions of 64 MiB (each ~64 MiB serialized, > the 64 MiB cache's C), read concurrently by 8 clients. An actual partition > 2 GiB (the :94 guard) is not recommended on shared disk; if wanted, make one partition of 2.1 GiB (needs ~2.1 GiB of disk plus compaction headroom; local disk only) with `rows_per_partition: ALL` and read it; expected a failed read with `IllegalArgumentException` "Unable to allocate 2.000GiB"-style message in `system.log` and the read erroring.

**B3d. Observables and instruments.** (a) Native usage: `/proc/<pid>/status` `VmRSS` every 5 s; subtract heap used (`jcmd <pid> GC.heap_info` or JMX `MemoryMXBean`) and NMT summary (`jcmd <pid> VM.native_memory summary`) to get "non-JVM malloc" = RSS - heap committed - NMT committed; this approximates the row cache. (b) Cache accounting: `nodetool info` ("Row Cache : entries, size, capacity"), and JMX `org.apache.cassandra.metrics:type=Cache,scope=RowCache,name=Size|Capacity|Entries|HitRate`. (c) `system.log` for the :94 exception and OOM messages. Cannot be observed directly: per-allocation malloc overhead and in-flight uncounted memory (inferred from the gap between RSS-derived usage and `Size`).

**B3e. Procedure.**
1. Build, configure as in B3a, start the node with `bin/cassandra -f` in a screen/background with log to a local file; record PID.
2. Create keyspace/table; load data (B3c). Run `nodetool flush` and `nodetool compact` if needed.
3. Baseline: record RSS, heap, NMT, `nodetool info`.
4. Read pass 1 and pass 2 (B3c); sample every 5 s for the whole run; record peaks.
5. Repeat steps 3-4 for each `row_cache_size` (restart between values) and for the 64 MiB-partition run.
6. Runtime-change test: `nodetool setcachecapacity 0 32 0` while full; record `Size` and RSS-derived usage afterwards.
7. Stop the node (`nodetool drain`, then `kill <pid>`), `pgrep -f CassandraDaemon` must return nothing; remove the data directories.

**B3f. Predictions.**
- 64 KiB partitions: `Size` stays <= `row_cache_size` (64/256/1024 MiB; the 1024 MiB case holds the whole ~1 GiB dataset plus per-entry overhead, so ~entries all of 16,384); RSS-derived non-JVM usage ~ `row_cache_size` + the baseline for the other malloc users (chunk cache 64 MiB, bloom filters, etc.), growing with `row_cache_size` roughly one-for-one, never reaching 2 GiB for the first two values.
- 64 MiB partitions with 64 MiB cache: `Size` stays near 0 to 64 MiB (an entry only just above the maximum is evicted immediately), but the RSS-derived peak can reach ~8 x 64 MiB = 512 MiB, i.e. well above `row_cache_size`, during concurrent puts.
- 2.1 GiB partition (optional): read fails with the :94 exception; no allocation occurs; `Size` unchanged.
- Claim wrong if the RSS-derived peak never exceeds `row_cache_size` + baseline in the large-entry case, or if usage is flat across `row_cache_size` values.

**B3i. Stage-4 audit amendments (2026-10-25, before any reading; each follows from the source or the arithmetic).**
1. *Node.* Single node on a loopback alias with its own ports (the node shares its host with other runs); `row_cache_size` set in the yaml per phase and the node restarted (the data directory is loaded once and kept). JVM: `MAX_HEAP_SIZE=2G HEAP_NEWSIZE=512M`, `JVM_EXTRA_OPTS="-XX:+AlwaysPreTouch -XX:MaxDirectMemorySize=256m -XX:NativeMemoryTracking=summary"` (heap resident from the start, so the heap does not move `RssAnon`), env `MALLOC_ARENA_MAX=1 MALLOC_MMAP_THRESHOLD_=65536 MALLOC_TRIM_THRESHOLD_=0` (every cache entry of 64 KiB or more is its own `mmap`ed chunk and is returned on `free`; page rounding adds at most 4 KiB, about 6 percent for a 64 KiB entry). The usage reading is `RssAnon` of the node's PID (`/proc/<pid>/status`, every 100 ms), minus a baseline taken after start-up and 20 s of idle, and minus the control phase's value (below). The B3d recipe "RSS minus heap minus NMT" is replaced by this, because the heap is pre-touched and constant.
2. *Phases and tables.* Phase `c0`: `row_cache_size: 0MiB` (control; the provider is `NopCacheProvider`, `CacheService.java:146-147`) with the data load and two read passes. Phases `c64`, `c256`, `c1024`: two read passes each. Phase `big`: `row_cache_size: 64MiB`, the large-entry arms. Tables (`caching = {'keys':'NONE','rows_per_partition':'ALL'}`, compression off): `t_small(pk bigint, ck int, v blob, PRIMARY KEY (pk, ck))` with 16,384 partitions of one row of 65,536 random bytes (1 GiB); `t_big8` with 8 partitions of 64 rows x 1 MiB (each partition serializes to a little over 64 MiB, more than C = 64 MiB); `t_big256` with one partition of 256 rows x 1 MiB (a little over 256 MiB, 4 C). Read: `SELECT v FROM t WHERE pk = ? AND ck = 0` (on a table with clustering columns and `rows_per_partition: ALL` the whole partition is read and cached whatever the query asks, `SinglePartitionReadCommand.java:547-558`, so the client receives 64 KiB or 1 MiB, not the partition). Pass 1 and pass 2 each read all 16,384 `pk` once, 32 requests in flight. `big8`: 8 concurrent clients, each reading its own partition, repeated for 20 rounds; `big256`: 5 reads of the one partition, 5 s apart.
3. *Optional 2.1 GiB partition: not run.* The partition is materialised on the heap (`CachedBTreePartition.create`, :604) before `serialize` can reach :94; with a 2 GiB heap that fails with `OutOfMemoryError` first, so the arm would not reach :94. The unit tier W1 is the test of the guard.
4. *Numeric form of B3f (thresholds; the claims are unchanged).* `Size` and `entries` are read from `nodetool info` (Row Cache line) every 5 s; after pass 2, `jcmd <pid> GC.class_histogram` counts `org.apache.cassandra.cache.RefCountedMemory` instances. `c0`: capacity 0, fewer than 100 `RefCountedMemory` instances; its `RssAnon` rise D0 over the reads is recorded. For C in {64, 256, 1024} MiB: `Size` never exceeds C at any sample and ends between 0.95 C and C; `RefCountedMemory` instances are within 5 percent of `entries` (plus at most a few in-flight sentinels); D(C) minus D0 is between 0.8 C and 1.25 C + 64 MiB, with D the peak `RssAnon` rise during the phase; D(256) - D(64) is between 0.8 and 1.25 of 192 MiB and D(1024) - D(256) between 0.8 and 1.25 of 768 MiB. All of these stay below 2048 MiB (the :94 limit); the largest, D(1024), is about 1.1 GiB. `big8` (C = 64 MiB): the end `Size` is 0 and `entries` 0 (each entry is heavier than C and is evicted at once); the peak `RssAnon` rise is at least 96 MiB (1.5 C, more than one entry in flight) in some round; if it is only between 64 and 96 MiB the arm does not show the overshoot and the claim rests on `big256`. `big256` (C = 64 MiB): the end `Size` is 0; the peak rise is at least 200 MiB (3 C) in each of the 5 reads; the end rise is at most D0 + 32 MiB. Runtime shrink (in `c256`, after pass 2): `nodetool setcachecapacity 0 32 0` leaves `Size` at most 32 MiB within 10 s and `RssAnon` rise minus D0 at most 104 MiB (1.25 x 32 + 64).
5. *B3g row added:* "a reading outside every row above (for example D(C) - D0 above 1.25 C + 64 MiB at steady state)": Not confirmed for that value; recorded as a gap, and the tier cannot be Confirmed on it.
6. *Hold fixed, with evidence to record:* the yaml values (read back from `system.log` startup lines and `nodetool info` capacity), the provider (the "Initializing row cache with capacity of N MiBs" line and the `RefCountedMemory` count, with no `org.caffinitas` class in the histogram), the JVM flags (`/proc/<pid>/cmdline`), the malloc variables (`/proc/<pid>/environ`).
