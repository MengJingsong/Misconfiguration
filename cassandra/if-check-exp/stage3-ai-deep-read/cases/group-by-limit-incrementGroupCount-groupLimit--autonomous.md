# GROUP BY group limit (CQLGroupByLimits.groupLimit) — verification solution

| Field | Value |
|---|---|
| Entry pointer | `src/java/org/apache/cassandra/db/filter/DataLimits.java:993` |
| Pinned source | `cassandra-5.0.9` |
| Session / date | Claude (Sonnet 5.5), Claude Code CLI via Agent SDK, 2026-10-27 |
| Estimate | `negative`: `groupLimit` counts completed GROUP BY groups (an integer), not bytes or rows, and a single group may span an unbounded number of rows, so heap and disk read volume do not scale with it. |
| Ground | The operand `groupCounted` is a count of groups. The size of one group is not bounded by this check (rows inside an unfinished group are counted only by `rowLimit`, which is the internal page size, and the scan continues across sub-pages until the group closes). The limit therefore bounds the number of result groups, not the memory or disk touched to produce them. The real memory-significant caps are `rowLimit` (sub-page size, 10000 by default), the client page size, and the guardrails. |

## A. Constraint trace

**A1. The constraint.** `groupLimit` field of `DataLimits.CQLGroupByLimits` (`DataLimits.java:658`), checked as `groupCounted >= groupLimit` at `DataLimits.java:993` (in `incrementGroupCount`) and again at `:1013` (`isDone`) and `:1041`. Kind: runtime-derived constant per query, not a yaml key or JVM property. It is first filled by `DataLimits.groupByLimits(groupLimit, groupPerPartitionLimit, rowLimit, spec)` (`DataLimits.java:116-122`), called from `SelectStatement.getDataLimits` (`SelectStatement.java:881-915`) as `groupByLimits(cqlRowLimit, cqlPerPartitionLimit, pageSize, aggregationSpec)`. So initially `groupLimit` = the user's CQL `LIMIT` (`cqlRowLimit = userLimit`, `SelectStatement.java:895`; `NO_LIMIT` when absent or when post-query ordering is needed) *[Amendment 2026-10-27, A1: line numbers corrected from 893-896 to 895; 901-902 to 902; the call is at 911.]*, and the constructor's `rowLimit` argument = the page size, defaulting to `DEFAULT_PAGE_SIZE = 10000` (`SelectStatement.java:114`, `:902`) when the client sets none. Unit: groups. Default: unlimited (`NO_LIMIT`) if the query has no LIMIT. Settable: per query via CQL `LIMIT n` (and client page size); no yaml key; effective per statement, no restart. In internal paging the instance is recreated by `forGroupByInternalPaging` (`DataLimits.java:740-746`) with `groupLimit = rowLimit` (the remaining page size), and by `forPaging` (`:725-736`) with `groupLimit = pageSize`; this is where line 993 acts as the per-sub-page group cap used by `AggregationQueryPager.GroupByPartitionIterator` (`AggregationQueryPager.java:~225-300`).

**A2. What it caps.** Nominally "other": the number of GROUP BY groups returned by a query or sub-page. The compared quantity is `groupCounted`, incremented once per closed group (`incrementGroupCount`, `:990-995`, called from `applyToRow` `:931-937`, `onPartitionClose` `:1022-1028`, `onClose` `:1041-1045`). It is not a byte or heap quantity.

**A3. Mechanism.** `GroupByAwareCounter.applyToRow` (`:926-957`) asks the `GroupMaker` whether the row starts a new group (`:931`); if so and the previous group had live rows, it increments `groupCounted` and `groupInCurrentPartition` (`:933-937`). At `groupCounted >= groupLimit` it calls `stop()` (`:993-994`), which ends the data stream; later rows of the partition are dropped (`:943-947`), and a new partition's static row is dropped (`:917-921`). Rows of the current, unfinished group are counted per live row by `incrementRowCount` (`:983-988`), which calls `stop()` when `rowsCounted >= rowLimit` (the internal page size). Consequence: a group is counted only when closed, so the group limit never interrupts a group in progress; a huge group is read until the rows run out or `rowLimit` stops the sub-page (the pager then resumes from `GroupingState`, `AggregationQueryPager.java:~270-275`). Overshoot or bypass: (1) a single group of arbitrary size passes through the limit; (2) `LIMIT` with `ORDER BY`/post-query ordering sets `cqlRowLimit = NO_LIMIT` (`SelectStatement.java:893-896`), so the group limit is absent while all groups are collected; (3) `onClose` (`:1041`) counts the trailing group only if limits are not yet reached.

**A4. Other consumers.** Memory outside this constraint: the per-sub-page row buffer (bounded by `rowLimit` rows, not bytes), aggregate function state in the coordinator, memtables, key/chunk/row caches, sstable index summaries, bloom filters, tombstones scanned (`tombstone_failure_threshold`, `conf/cassandra.yaml:1815`), `page_size_warn/fail_threshold` guardrails (`conf/cassandra.yaml:2089-2090`, `Guardrails.pageSize.guard` at `SelectStatement.java:517`), and `native_transport_max_frame_size`/response size on the client path. Disk: the sstable bytes read for a scanned group are unrelated to `groupLimit`.

**A5. Evidence beyond the source.** None used. (Public docs on CQL GROUP BY and paging could be cited, but nothing was relied on.)

## B. Verification solution

**B1. Claim under test.** The GROUP BY group limit does not bound memory or disk usage: with the same table, increasing `LIMIT` (the group limit) from 1 to 1000 does not raise peak heap or bytes read beyond what is set by the group size and page size, and a query with `LIMIT 1` over a single enormous group still scans and processes the whole group (heap churn and disk reads scale with rows in the group, not with `groupLimit`). Falsified if peak memory or bytes read grow roughly linearly with `groupLimit` while group size is held constant, or if `LIMIT 1` stops the scan after about one sub-page.
