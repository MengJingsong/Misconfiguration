## A. Constraint trace

**A1. The constraint.** There is no named limit at the entry point. The operands are:
- `buffer.capacity()`, the current decompression buffer. It starts at `RandomAccessReader.DEFAULT_BUFFER_SIZE = 4096` (`io/util/RandomAccessReader.java:34`), allocated in the `ChecksummedDataInput` constructor (`hints/ChecksummedDataInput.java:56`) from `compressor.preferredBufferType()` (`CompressedChecksummedDataInput.java:45`). It is not pooled at creation.
- `uncompressedSize`, an int read from the 8-byte block header (`:115`). It is the `originalSize` that `CompressedHintsWriter.writeBuffer` wrote (`CompressedHintsWriter.java:49,64`).

The nearest real limits are:
- `file_cache_size` (yaml; `config/Config.java:497`; default 512MiB per `conf/cassandra.yaml:753`, or derived when unset; restart needed). It becomes `FILE_MEMORY_USAGE_THRESHOLD` (`utils/memory/BufferPools.java:38`) for the "chunk-cache" `BufferPool`, which `CompressedChecksummedDataInput` uses (`:35`). The unit is MiB.
- `max_mutation_size` (yaml; `Config.java:407`; default commitlog_segment_size/2 = 16MiB, `DatabaseDescriptor.java:898-899`), which indirectly bounds the largest hint.
- `max_hints_file_size` (128MiB, `Config.java:447`), which bounds file size, not block size.

**A2. What it caps.** Nothing explicit. Line 134 decides whether the off-heap or heap reader buffer (type from the compressor; LZ4 is direct) is replaced by a larger one. The quantity compared is block uncompressed bytes against current buffer capacity. The resource is off-heap memory of one hint-dispatch reader per replay.

**A3. Mechanism.**
1. `readBuffer()` (`:104`) reads the 8-byte header at `filePosition` (`:110-116`).
2. The compressed buffer is grown at `:118-126`, to compressedSize*1.05, from `bufferPool.get` (pool = `BufferPools.forChunkCache()`).
3. At `:134`, if `buffer.capacity() < uncompressedSize`, the old buffer is returned to the pool (`:137`) and `bufferPool.get(uncompressedSize*1.05)` is called (`:136,138`). Otherwise the buffer is reused, so capacity never shrinks within one reader.
4. `BufferPool.get` (`BufferPool.java:~900-925`): a request <= `NORMAL_CHUNK_SIZE` (128 KiB, `:128`) is served from pool chunks, and new 1 MiB macro chunks are only allocated while `memoryAllocated + 1MiB <= memoryUsageThreshold` (`:443`). Otherwise `tryGet` returns null (`:940-943` for size > 128 KiB, `:445-451` for a full pool) and `allocate()` (`:233-239`) does a plain `allocateDirect(size)`. That allocation is only counted in `overflowMemoryUsage` (`:263`), and no threshold is checked.
5. The producer side: `HintsWriteExecutor.WRITE_BUFFER_SIZE = 256<<10` (`HintsWriteExecutor.java:50`). `HintsWriter.Session.append` (`HintsWriter.java:204-221`) flushes the buffer as a block when the next hint does not fit. A hint bigger than 256 KiB is written as its own block (`:220`). `HintsBuffer.allocate` rejects hints > slab/2 (`HintsBuffer.java:152`), where slab = max(2*max_mutation_size, 32MiB) (`HintsService.java:110`), so block size <= max(256 KiB, max(max_mutation_size, 16MiB)).
6. Bypass: the header is not validated. A corrupt or crafted file with an enormous `uncompressedSize` goes straight to `bufferPool.get(~size)` with no bound, and `uncompressedSize + uncompressedSize/20` can overflow int. (Only `HintsDescriptor` CRC covers the file header, not block headers. Verify in stage 4 whether `ChecksummedDataInput` CRC checks happen before this point; they do not, since the CRC is per hint, after decompression.)
7. Overshoot at line 138: there is no `catch` for OOM beyond `Throwable` handling upstream.

**A4. Other consumers.** The same chunk-cache pool serves the SSTable chunk cache and other compressed readers (`BufferPools.java:35-39` comment). The unpooled initial 4096-byte buffer, hint `HintsBuffer` slabs (`allocateDirect`, `HintsBuffer.java:77`, up to `MAX_HINT_BUFFERS`=3 each >= 32 MiB, `HintsBufferPool.java:41`), the writer's 256 KiB direct buffer, and `CompressedHintsWriter.compressionBuffer` are all outside this check.

**A5. Evidence beyond the source.** none (no web access used). `test/unit/org/apache/cassandra/hints/HintsCompressionTest.java` and `ChecksummedDataInputTest.java` exist and can be used as templates.

## B. Verification solution

**B1. Claim under test.** The size of the decompression buffer held by a `CompressedChecksummedDataInput` equals roughly 1.05 x the largest block's `uncompressedSize` in the file, independent of `file_cache_size`; for blocks > 128 KiB, off-heap usage exceeds the `file_cache_size` pool threshold without any refusal. (Falsified if capacity is clamped by any configured value, or if the memory needs stay under the threshold.)

### B2. Unit tier

**B2a. Environment and build.** JDK 11, Ant. Copy the tree: `rsync -a ~/cassandra-5.0.9/ /local/work/c509/`; `cd /local/work/c509 && ant jar build-test`. Add a JUnit test `test/unit/org/apache/cassandra/hints/ReaderBufferGrowthTest.java` (in the copy only), modelled on `HintsCompressionTest`/`ChecksummedDataInputTest`. Run with `ant testsome -Dtest.name=org.apache.cassandra.hints.ReaderBufferGrowthTest` under `-Dcassandra.config=file:///local/work/cfg/cassandra-test.yaml` copies, `-XX:MaxDirectMemorySize=1g`. A small harness must call `DatabaseDescriptor.daemonInitialization()` after setting `file_cache_size`.

**B2b. Knobs.** (1) Block uncompressed size S in {2 KiB, 100 KiB, 128 KiB, 129 KiB, 1 MiB, 16 MiB}: below the initial 4096 capacity, pooled range, edge, just beyond the pool limit, large, and the max_mutation_size default. (2) `file_cache_size` in {1MiB (the minimum useful, < one macro chunk plus), 512MiB}. 1MiB gives `cur + 1MiB > 1MiB` after the first chunk, so the pool is exhausted early. Set in the yaml/test config before `DatabaseDescriptor` init. (3) Compressor: `LZ4Compressor` (direct) and `SnappyCompressor` or `DeflateCompressor` (deflate also direct; check `preferredBufferType`).

**B2c. Workload.** Write a hint file with `HintsWriter` + `CompressedHintsWriter` (via `HintsDescriptor` with compression params) in which each block holds one synthetic value of size S (random bytes, so compression does not shrink; the block header records S regardless). Make a file of 4 blocks with sizes [S, S, 2S... ] rather: block sizes [2 KiB, S] in one file and a second file with [S, 2 KiB] to check capacity does not shrink. Read back through `HintsReader.open(file)`, iterating all hints. Arithmetic: for S=1 MiB the reader needs 1.05 MiB for output plus compressedBuffer ~1.05 MiB, well above the 128 KiB pool class and above the 1 MiB `file_cache_size`.

**B2d. Observables and instruments.** (i) `reader.input.buffer.capacity()` via reflection on `ChecksummedDataInput.buffer` after each block. (ii) `BufferPools.forChunkCache().sizeInBytes()`, `.usedSizeInBytes()` and `.overflowMemoryInBytes()` (`BufferPool.java:274,284,290`). (iii) `java.lang.management` `BufferPoolMXBean` "direct" `getMemoryUsed()` before and after. (iv) Not observable directly: native memory freed to the OS (depends on GC of direct buffers).

**B2e. Procedure.**
1. Build; write the test; for each (compressor, S, file_cache_size) generate the file in a temp dir under `/local/work/tmp` (<= 100 MiB total).
2. Record baseline pool and direct-buffer numbers.
3. Open the reader, read hints one by one; after each, record the observables from B2d.
4. Close the reader; record again (expect compressedBuffer returned via `put`, `:157`; `buffer` released by `super.close()`, check).
5. Repeat with the order of block sizes swapped.
6. Positive control (below).

**B2f. Predictions.** Before any run:
- S=2 KiB: capacity stays 4096, no pool use except compressedBuffer.
- S=100 KiB / 128 KiB: capacity ~ 1.05*S (rounded up by the pool to allocation units of 2 KiB), pooled, so `sizeInBytes()` grows by whole 1 MiB macro chunks when file_cache_size = 512MiB; with 1MiB, only the first macro chunk is created, then overflow grows.
- S=129 KiB .. 16 MiB: capacity ~ 1.05*S in both settings, `overflowMemoryInBytes()` ~ capacity (+ compressedBuffer), pool `sizeInBytes()` unchanged by these requests, and direct memory used exceeds 1 MiB with `file_cache_size=1MiB`. Capacity is identical for the two `file_cache_size` values.
- Swapped order: capacity after the small block remains the large value.
- Wrong-claim signature: capacity clamped (e.g. <= 128 KiB or <= file_cache_size) or an exception for S above some configured limit.

**B2g. Readings.**

| Observation | Meaning |
|---|---|
| capacity ~ 1.05*S for all S, same for both file_cache_size values; overflow > threshold for S > 128 KiB | claim confirmed (usage does not follow the knob) |
| capacity or direct memory scales with file_cache_size, or is clamped by it | claim refuted |
| capacity plateau at some value < S with an error | claim refuted: a hidden bound exists; trace it |
| positive control pool stays <= threshold while hint blocks exceed it | confirmed that the pool limit binds only the pooled path |
| positive control pool does not stop at threshold, or overflow does not rise with S | control did not work: not confirmed; fix the harness |
| S never reached the header (reader stopped early, e.g. CRC) | limit never reached: not confirmed |

**B2h. Controls.** Positive control: in the same JVM request many 64 KiB buffers directly from `BufferPools.forChunkCache()` (pooled-size class) with `file_cache_size=1MiB`; expected `sizeInBytes()` stops at <= 1MiB (`BufferPool.java:443`) and further requests fall to overflow. Same sizes with 512MiB must keep growing in whole macro chunks. This shows a cap that does bind. Also: run with the compressed buffer disabled isn't possible, so subtract the compressedBuffer capacity (`compressedBuffer` field, reflection) from direct-memory deltas. Run each case in a fresh JVM to exclude pool state carried over.

### B3. Cluster tier

**B3a. Environment and build.** One node suffices (a second node is optional as a hint target). Build `ant jar` in the local copy; run from `/local/work/node1` with data, commitlog, hints and saved caches directories all on local disk (>= 20 GiB free, known size). `cassandra.yaml`: `hints_compression: - class_name: LZ4Compressor`, `max_hints_file_size: 128MiB`, `max_mutation_size: 16MiB` (default), `commitlog_segment_size: 32MiB`, `hinted_handoff_enabled: true`, `max_hint_window: 3h`, `file_cache_size: 1MiB` in run A and `512MiB` in run B. JVM: `-Xmx2g -XX:MaxDirectMemorySize=2g -XX:NativeMemoryTracking=summary`. Use 2 nodes on loopback (127.0.0.1/127.0.0.2, via `ccm`-less manual config) so a replica can be stopped: RF=2, node2 is the down replica; node1 holds the hints and replays them.

**B3b. Knobs.** `file_cache_size` {1MiB, 512MiB}; row/blob size B in {1 KiB, 100 KiB, 1 MiB, 8 MiB} (below and above the 128 KiB class and 256 KiB write buffer; 8 MiB < max_mutation_size). Each is set in yaml with a restart.

**B3c. Workload.** Create keyspace RF=2, table `(k int primary key, v blob)`. Stop node2. With `cassandra-stress` user mode or a small driver, write N rows through node1 at CL=ONE with blob size B: N = 200 for 8 MiB (1.6 GiB of hints? use N=64: 512 MiB, under 4 hint files of 128 MiB), N = 2000 for 1 MiB, N = 5000 for 100 KiB, N = 50000 for 1 KiB. Each hint is stored on node1 (hints dir). Then start node2 so node1 replays hints. Duration: write phase minutes; replay until `nodetool statushandoff`/hints directory is empty.

**B3d. Observables and instruments.** (i) node1 RSS (`/proc/<pid>/status` VmRSS, 1 s sampling), (ii) `jcmd <pid> VM.native_memory summary` (Internal/Other, and direct buffers via `jcmd <pid> PerfCounter.print` or JMX `java.nio:type=BufferPool,name=direct`), (iii) JMX `org.apache.cassandra.metrics:type=BufferPool,scope=chunk-cache,name=Size`/`UsedSize`/`OverflowSize`, (iv) `du -sb` of the hints dir, (v) log line "Maximum memory usage reached" (`BufferPool.java:447`). Not observable: per-reader buffer capacity (use a heap dump or the JMX direct pool only in aggregate). `HintsDispatcher` replay uses one reader per file at a time, so at most one reader per dispatch thread (`max_hints_delivery_threads`, default 2).

**B3e. Procedure.**
1. Start node1 and node2 with `file_cache_size: 1MiB`; create schema; stop node2.
2. Take the baseline (RSS, direct pool, chunk-cache metrics).
3. Run the workload for B=1 KiB, then record metrics; start node2; sample every second during replay; stop sampling when the hints dir is empty.
4. Repeat for 100 KiB, 1 MiB, 8 MiB (wipe data between runs; restart node1 so the pool starts empty).
5. Repeat the entire matrix with `file_cache_size: 512MiB`.
6. Positive control (B3h). 7. Stop all JVMs; `pgrep -f CassandraDaemon` is empty; delete `/local/work/node*`.

**B3f. Predictions.** Peak direct-buffer usage during replay minus baseline, per B: 1 KiB: compressed block <= 256 KiB so the buffer <= ~270 KiB, and with the pool mostly <= 128 KiB class up to ~1 MiB pool chunk; 100 KiB: same, about 1-2 MiB; 1 MiB hints: ~2.1 MiB (compressedBuffer + buffer), 8 MiB hints: ~17 MiB (random data does not compress). For 1 MiB and 8 MiB, values are the same (within 1 MiB of macro-chunk rounding) for `file_cache_size` 1MiB and 512MiB, with `OverflowSize` carrying them in the 1MiB run. The peak above `file_cache_size=1MiB` for 8 MiB hints shows the cap is not enforced. The disk (hints dir) follows the writes, bounded by `max_hints_size_per_host` only if set (0 here).

**Audit amendments (stage 4 step 0, 2026-10-25).** Made before any harness, run or reading, from the pinned source only. The claim in B1, the Readings rows of B2g/B3g and the control logic stand; the corrections below replace the numbers and procedure they name, and where an amendment corrects text above, the amendment governs. Reasons and line checks are in the results file section 1.1.

- **R1 (B2b, B2f, B2h, B3a-B3h: the pool grows in 8 MiB steps, not 1 MiB).** `MACRO_CHUNK_SIZE = 64 * NORMAL_CHUNK_SIZE` = 8 MiB (`BufferPool.java:385`); a macro chunk is added only while `memoryAllocated + 8 MiB <= file_cache_size` (`:443`). So `file_cache_size` = 1 MiB never lets the pool allocate a chunk: every request, including those of 64 KiB, is an unpooled `allocateDirect` counted in `overflowMemoryInBytes()`. Knob values are `file_cache_size` in {1 MiB, 16 MiB, 512 MiB}: 1 MiB = no pool at all, 16 MiB = two chunks, 512 MiB = the default. The positive control (B2h) uses 16 MiB: 400 requests of 64 KiB (25 MiB) held at once must give pooled bytes (`sizeInBytes() - overflowMemoryInBytes()`) = 16 MiB and overflow = 144 x 64 KiB = 9 MiB; at 512 MiB pooled = 32 MiB (4 chunks) and overflow = 0; at 1 MiB pooled = 0 and overflow = 25 MiB. A control that gives anything else is a harness fault (B2g row 5).
- **R2 (B2f: exact capacity, no rounding).** The new buffer is `bufferPool.get(Z + Z/20)` with Z the block header's `uncompressedSize` (`CompressedChecksummedDataInput.java:136-138`); `Chunk.get` returns a slice of exactly the requested size (`BufferPool.java:1394-1398,1464`; rounding applies to the slots, not the capacity). Capacity after a block is `cap(Z) = 4096` if `Z <= 4096` (the line-134 test is false), else `Z + Z/20` in int arithmetic. A request is pooled only if `cap <= 131072` (`BufferPool.java:940`) and a chunk can be had (R1): so Z <= 124,831 is pooled (at 16/512 MiB) and Z >= 124,832 is not. A 128 KiB block (cap 137,625) is therefore unpooled; B2f's "S = 100 KiB / 128 KiB pooled" holds for 100 KiB only. The compressed buffer follows the same rule with `C + C/20` (`:120,125`), where C is the header's `compressedSize`.
- **R3 (B2b item 3, compressors).** `DeflateCompressor.preferredBufferType()` is `ON_HEAP` (`DeflateCompressor.java:228-231`): `BufferPool.get` then returns `ByteBuffer.allocate` (`BufferPool.java:208-209,233-239`), counted in overflow but not in the direct pool. LZ4 and Snappy are `OFF_HEAP`. The unit tier runs LZ4 (all cases) and Deflate (2 cases, capacity relation and heap class only).
- **R4 (A3 step 6: where the header size is checked).** Nowhere before the allocation. `HintsDescriptor` CRC covers only the file header; the block header (`:110-116`) is read raw and used at `:134-138`. What is checked afterwards: (a) `LZ4Compressor.uncompress(ByteBuffer, ByteBuffer)` reads its own 4-byte decompressed length from the compressed payload (`LZ4Compressor.java:167-190`) and fails with `IOException` only if that length exceeds `buffer.remaining()` = Z, i.e. a header that is too small; a header that is too large is accepted silently; (b) the per-hint CRCs after decompression (`HintsReader.java:224,254`); (c) the global file CRC is only written (`HintsWriter.java:104-115`), never read. Added unit case F (forged header): a valid 2 KiB block whose `uncompressedSize` field is rewritten to 512 MiB must read all its hints without error and leave a reader buffer of 563,714,457 bytes (`cap(536870912)` = 536,870,912 + 26,843,545), with `-XX:MaxDirectMemorySize=2g`. This is supplementary to B2g (it shows the bypass of any bound, not a knob).
- **R5 (B2e step 4: what close() returns).** `CompressedChecksummedDataInput.close()` puts only `compressedBuffer` back (`:157`); `super.close()` is `FileUtils.clean(buffer)` plus `channel.close()` (`ChecksummedDataInput.java:113-116`), which neither returns a pooled slice nor decrements the overflow counter. Expected after close: an unpooled reader buffer is freed from the OS but `overflowMemoryInBytes()` stays higher by `cap(Z)`; a pooled one keeps its slot (`usedSizeInBytes()` stays higher by `cap(Z)`). Also at growth, `bufferPool.put(buffer)` on the unpooled 4096-byte initial buffer runs `LocalPool.put` with no parent chunk, which cleans it and subtracts 4096 from the overflow counter that never counted it (`BufferPool.java:811-820`): the overflow counter is 4096 lower after a growth. Both are accounting findings, recorded, not part of the claim.
- **R6 (B2c: how blocks are built and Z is known).** One block per `HintsWriter.Session` (open a session, `append(Hint)` one hint, close the session: `Session.close()` flushes, `HintsWriter.java:269-275`); the block's Z is the serialized hint plus `ENTRY_OVERHEAD_SIZE` = 12 (`HintsBuffer.java:58`, `HintsWriter.java:232-263`). The harness parses Z and C from the raw file with its own 8-byte header reader and uses them, not the nominal value size, in every expectation. Random bytes (incompressible), so C is about Z. Value sizes: 1 KiB, 100 KiB, 120 KiB, 128 KiB, 129 KiB, 1 MiB, 16 MiB minus 1 KiB; two orders ([2 KiB, Z] and [Z, 2 KiB]). Each case runs in a fresh JVM (child process of the test) per `file_cache_size`, so pool state is not carried over; counters are read before open, after the last hint, and after close.
- **R7 (B3c/B3e: blocks are aggregations, so B3f is corrected).** `HintsWriteExecutor` hands each `HintsWriter.Session` one shared 256 KiB buffer (`HintsWriteExecutor.java:50,241`); small hints are batched into blocks of up to 262,144 bytes (`HintsWriter.Session.append`, `:200-221`), so 1 KiB and 100 KiB hints do not produce small blocks. Corrected B3f, with Z_max the largest block header in the file read from the raw `.hints` files before replay (the harness does this): the reader's buffer capacity at the end of a file is `cap(Z_max)` exactly, for both `file_cache_size` values; for 1 KiB values Z_max is in (255 KiB, 256 KiB] so cap is about 274-275 KB; for 100 KiB values (two per block) Z_max ~ 205 KB so cap ~ 215 KB; for 1 MiB values Z_max ~ 1,048,700 so cap ~ 1.10 MB; for 8 MiB values Z_max ~ 8,388,700 so cap ~ 8.81 MB. Compressed buffer: `C_max + C_max/20`, about the same. All four exceed 128 KiB, so every one is unpooled in the cluster; the chunk-cache `OverflowSize` rises by about `cap + compressed cap` while a file is read (1 KiB: ~0.55 MB; 100 KiB: ~0.43 MB; 1 MiB: ~2.2 MB; 8 MiB: ~17.6 MB), and the pooled part of the pool (`Size - OverflowSize`) is 0 at 1 MiB and unchanged by the replay at 16/512 MiB. The B3f sentence "pool mostly <= 128 KiB class up to ~1 MiB pool chunk" is withdrawn.
- **R8 (B3c: workload sizes).** N = 50,000 (1 KiB), 500 (100 KiB), 64 (1 MiB), 8 (8 MiB): 50-64 MiB of hints per cell, one `.hints` file each (below `max_hints_file_size`). The filed 2,000 x 1 MiB and 5,000 x 100 KiB (2 GiB and 0.5 GiB, plus the same again in the commit log of the coordinating node) add nothing: the reader's buffers depend on the largest block, which these reach. `file_cache_size` for the cluster: {1 MiB, 16 MiB, 512 MiB}. Values are `os.urandom` bytes through the bundled driver at protocol 4 (CL ONE, a fresh JVM of node 1 per cell so the pool starts empty, node 2 stopped while writing and started for the replay); `hinted_handoff_throttle` is raised to 100 MiB/s so the replay is not rate-bound.
- **R9 (B3d: instruments).** Per-reader capacity IS observable: a Byteman rule at `CompressedChecksummedDataInput.readBuffer` `AT LINE 141` logs Z, C, `buffer.capacity()`, `compressedBuffer.capacity()` and the chunk-cache `sizeInBytes()`, `usedSizeInBytes()`, `overflowMemoryInBytes()` for every block, and a 1 s sampler logs the `java.nio` direct pool, RSS (`RssAnon`) and the JMX chunk-cache metrics. The B3d "not observable" sentence is withdrawn. The node's other direct-memory use during replay (Netty frames of the outgoing hint messages) is in the direct-pool total but not in the chunk-cache counters, so the chunk-cache counters and the rule's capacity are the readings; the direct total is supporting.
- **R10 (B3h: the positive control).** The control is a read workload where the pool is known to bind, at `file_cache_size` = 16 MiB with `file_cache_enabled: true`, a table with LZ4 compression and `chunk_length_in_kb: 64`, 128 MiB of data read through a full scan with 8 clients: the pooled part (`Size - OverflowSize`) must reach and not exceed 16 MiB. At 512 MiB the same workload must exceed 16 MiB pooled. A control that does not plateau at 16 MiB (or does not reach it) is a control that did not move: B3g row 5 applies (Not confirmed). B3g gains the row: | the control reading is missing or the pooled part never reaches 16 MiB | the instrument or workload cannot show a binding cap: Not confirmed |.

- **R11 (B3h: the control's mechanism; 2026-10-25, after the first control attempt of cluster run 1, results file section 3 D2; replaces the workload of R10, not its row).** Reads through the chunk cache cannot make the pool bind: the cache is sized `file_cache_size - 32 MiB` (`ChunkCache.RESERVED_POOL_SPACE_IN_MiB`, `ChunkCache.java:49-50`) and exists only if that is positive (`:53-54`). The R10 control at 16 MiB therefore ran with the cache disabled and left the pool at its start-up 8 MiB (peak pooled part 8 MiB, OverflowSize 0), and at 512 MiB it grew the pool to 160 MiB without meeting the threshold. A cache that is sized below the pool threshold never presses on it, by design. The control is now the unit tier's control run in the node's own JVM: node A alone with `file_cache_size` in {1, 16, 512} MiB and Byteman `hu-inject.btm`, which (flag file, `HintsDispatchTrigger.run`, every 10 s) makes the node's chunk-cache pool serve and hold 400 x 64 KiB and later give them back. Predictions (before the run): UsedSize rises by exactly 26,214,400; at 1 MiB the pooled part (`Size - OverflowSize`) stays 0 and OverflowSize rises by 26,214,400; at 16 MiB the pooled part is exactly 16,777,216 and OverflowSize rises by between 1 and 26,214,399 (the rest); at 512 MiB the pooled part grows past 16 MiB and OverflowSize does not move. The R10 reads stay as supplementary readings. The B3g control rows apply to these readings unchanged.
