**Note on scope.** One method holds **three** comparisons against three limits: the per-connection capacity (`:398`, this case), the per-peer and node-wide reserves (`:419`, reached only for the part of a message beyond the capacity), and a count cap (`:391`). They feed one outcome and one decision point, so they are one case (README §6.1, "one case, several check sites"); §4 names which config key governs each. The reserve comparison itself is `ResourceLimits.Concurrent.tryAllocate():138`, the mechanism `deferred.md` §5 item 3 asks about: it is **cited here as a mechanism, not filed**, and that row stays open for the filing decision it names.

## 2. Context

When a Cassandra node sends a message to a peer — a replicated write, a read request, a reply, a gossip message — it does not write the message to the network at once. It places the message in a per-peer outbound queue, and a delivery thread writes it out. If the peer or the network is slow, messages pile up in that queue, and each one keeps its data in memory until it is sent. This check is the gate on the queue: before a message is queued, the connection adds the message's size to the bytes already waiting and compares the total with a per-connection allowance. Beyond the allowance the connection may borrow from shared reserves (one per peer, one for the whole node); if those are exhausted as well, the message is not queued but **dropped** — the sender is not slowed down, and the request the message belonged to is told it failed. Without the gate, a slow or dead peer would let the sender's memory grow until the requests' own timeouts removed the messages.

## 5. Decision point & branch semantics

| Field | Content |
|-------|---------|
| **Decision point** | [`OutboundConnection.enqueue():335-346`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L335-L346) |
| **Verdict** | The `ResourceLimits.Outcome` returned by `acquireCapacity()`: `SUCCESS`, `INSUFFICIENT_ENDPOINT` or `INSUFFICIENT_GLOBAL` (the enum also has `BELOW_LIMIT`/`ABOVE_LIMIT`, used by `release()`, [`ResourceLimits.java:290`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/ResourceLimits.java#L290)). **Set** at [`:402`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L402) (the capacity fits), [`:393`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L393) (count cap), [`:411`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L411) (peer unreachable) and by the reserve claim at `:419` (which returns one of the three). **Read** at `enqueue():335`. Nothing resets or ignores it between the two. |

| Outcome | Condition (*P* = pending bytes, *M* = this message, *C* = the capacity) | Effect |
|---------|-----------|--------|
| **Allow, within the capacity** | *P* + *M* ≤ *C* | `pendingCountAndBytes` is advanced by compare-and-set; `SUCCESS`; no reserve is touched; the message is queued. |
| **Allow, borrowing** | *P* + *M* > *C*, and the node-wide and the per-peer reserve can each supply `min(M, P + M − C)` (**only the excess**, not the whole message) | The excess is claimed from both reserves first, then `pendingCountAndBytes` is advanced; `SUCCESS`; the message is queued. |
| **Disallow** | *P* + *M* > *C* and a reserve cannot supply the excess; **or** the link is connecting after a failed attempt (**no reserve is tried at all**, so *C* is a hard cap for an unreachable peer); **or** the count cap is reached | `INSUFFICIENT_*`; nothing is added to `pendingCountAndBytes`, and any reserve already claimed is handed back ([`:436-437`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L436-L437)). `enqueue()` then drops the message — or, for `INSUFFICIENT_ENDPOINT`, first prunes expired messages and retries once. |

### 6b. Disallow path effect

**Not a rejection of the sender and not a wait: the message is dropped, and its request is told it failed.**

1. [`acquireCapacity()`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L419-L423) returns `INSUFFICIENT_GLOBAL` or `INSUFFICIENT_ENDPOINT`. State: `pendingCountAndBytes` unchanged; a claim that got past the node-wide reserve but failed the per-peer one is returned by [`EndpointAndGlobal.tryAllocate():271`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/ResourceLimits.java#L271). The node-wide reserve is tried **first** ([`:265`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/ResourceLimits.java#L265)), so when both are short the outcome is `INSUFFICIENT_GLOBAL`.
2. [`enqueue():337-346`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L337-L346) — for `INSUFFICIENT_ENDPOINT` only, [`maybePruneExpired()`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundMessageQueue.java#L209-L220) runs the pruning **only if the earliest queued deadline has passed** ([`:216-217`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundMessageQueue.java#L216-L217)), which hands back the capacity of the expired messages, and the acquire is tried once more **only if the prune ran**; success `break`s out to the allow path. Otherwise control falls through to `onOverloaded(message)` and `return`: **`queue.add()` is never reached**, and `enqueue()` returns normally, so the sending thread neither blocks nor sees an exception.
3. [`onOverloaded():456-468`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L456-L468) — counts the message and its bytes ([`overloadedCount`/`overloadedBytes`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1669-L1677), published per link, §9d), logs a WARN through a [30-second no-spam logger](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L102) (`overloaded; dropping N message (queue: … local, … endpoint, … global)`), and calls the request callbacks.
4. [`RequestCallbacks.onOverloaded():268-272`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/RequestCallbacks.java#L268-L272) → [`removeAndExpire():118-122`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/RequestCallbacks.java#L118-L122) → [`onExpired():149-158`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/RequestCallbacks.java#L149-L158): the registered callback is removed and, if it asks for failures (a write's message carries `CALL_BACK_ON_FAILURE`, [`StorageProxy:1519-1522`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageProxy.java#L1519-L1522), and `sendWriteWithCallback()` [asserts it](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/MessagingService.java#L423)), **`onFailure(peer, TIMEOUT)` is submitted at once**, not after the timeout. A forwarded write also expires its forwarding targets ([`:292-300`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/RequestCallbacks.java#L292-L300)). A message with **no callback** (a response, a gossip message, a fire-and-forget send) leaves nothing behind: `remove()` finds no entry and the message is simply gone.
5. For a write, [`AbstractWriteResponseHandler.onFailure():294-311`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/AbstractWriteResponseHandler.java#L294-L311) counts the failure, signals the client when too few replicas remain, and, when the mutation supplies one, `shouldHint()` allows and the request may still send hints ([`shouldSendHints()`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/transport/Dispatcher.java#L258-L266), true unless `enforce_native_deadline_for_hints`, default `false`, is on and the client deadline has passed), **submits a hint for that replica** ([`:309-310`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/AbstractWriteResponseHandler.java#L309-L310)). 6. **Not re-queued, not retried, and the memory is freed only if nothing else holds the message.** The next write to the same peer is judged afresh. One `Message` object is shared by every replica of a write ([`StorageProxy:1517-1523`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageProxy.java#L1517-L1523), sent to each in a loop at [`:1572-1576`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/service/StorageProxy.java#L1572-L1576)), so a drop on one link frees nothing while another link still queues it.

**State-dependent variants (derived):** (i) while the link is connecting after a failed attempt, the reserves are not consulted ([`:409-413`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L409-L413)), so the capacity is a hard cap for a peer that cannot be reached, and any message past it is dropped at once; (ii) messages leave the queue also by **expiry** ([`onExpired():475-483`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L475-L483), deadline from [`Message.outWithFlags():222-237`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/Message.java#L222-L237)), on a failed serialization ([`:490-498`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L490-L498)) and on close ([`:505-509`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L505-L509)); each hands the bytes back; (iii) **expiry is lazy while the link is connected**: a message past its deadline is dropped only when something prunes — delivery consuming the queue ([`WithLock.peek()/poll()`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundMessageQueue.java#L154-L187)), an `add()` that got past the check ([`:90`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundMessageQueue.java#L90)), or the `INSUFFICIENT_ENDPOINT` retry above; the 100 ms maintenance task exists only **while the link is disconnected** ([`setDisconnected():1403-1407`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1403-L1407), cancelled at [`:1124`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1124) on connect). A connected link that is full and **not draining** (the small and urgent links' delivery returns at once while the channel is unwritable, [`:759-760`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L759-L760); the large link's delivery is busy streaming the one message it polled, and consumes nothing meanwhile) refuses offers before `add()`, so under `INSUFFICIENT_GLOBAL` nothing reclaims even its expired messages until delivery runs again or the connection is dropped (derived from the code, not an observation; the code's own comment says the same of the retry, [`:340`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L340): "messages will be expired on ~100ms cycle, and by Delivery when it runs").

**Escape hatch / bypass: none found on the check itself** — every outbound application message goes through `OutboundConnection.enqueue()`: its only caller is `OutboundConnections.enqueue()`, whose only production caller is `MessagingService.doSend()`, and `OutboundMessageQueue.add()` is called nowhere else (the `OutboundConnection` constructor is called only from `OutboundConnections`; searched over `src/java`, 2026-10-07). ## 7. Object & resource

| Field | Content |
|-------|---------|
| **Object created** | The check gates **retention**: the `Message<?>` (header plus typed payload, for a write a `Mutation`) is built by the caller **before** the check, then held by the connection's queue — a linked-queue node per message and a slot in the delivery thread's array queue ([`OutboundMessageQueue:45-46`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundMessageQueue.java#L45-L46)) — until it is written, expires or fails. Delivery then builds its **wire form**: an off-heap `FrameEncoder.Payload` (small and urgent links) or 32 KiB streaming buffers (large link), both from the networking buffer pool. A dropped message gets none of this. |
| **Resource consumed** | JVM **heap** held by queued messages (the payload objects), measured in **serialized bytes** (`canonicalSize`, [`:1045-1048`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1045-L1048)), not in heap bytes; plus a message count. Delivery's off-heap frames are *not* in the count and are bounded elsewhere (the networking pool, `networking_cache_size`, item 10 of `pending.md`, and the flush water marks). |
| **Rough sizing** | Accounted bytes = the message's serialized size at the current version (a mutation with one 128 KiB value is a few hundred bytes more than 128 KiB). Heap bytes per accounted byte is **not constant**: an in-memory mutation is larger than its serialization, and **one `Message` is shared by all replicas of a write** while each link accounts its full size, so retained heap grows with the *distinct* queued messages, not with the sum over links. For a mixed-version peer the accounted size can differ from the bytes serialized ([`:764`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L764)). |
| **Lifetime / release** | [`releaseCapacity():445-454`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L445-L454) when the flush completes, on expiry, on a failed serialization, on close, or in the closing race at [`enqueue():354-358`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L354-L358). It returns the **reserve first**: only `min(pending − C, bytes)` goes back to the reserves, the rest reduces the local count. A release that would take a shared reserve below zero throws `UnrecoverableIllegalStateException` ([`ResourceLimits:160-169`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/ResourceLimits.java#L160-L169)), so the accounting must return to zero (§9d, "Drain"). |

**Why this passes Rule 2, and the caveat.** README §3.5's queue-depth edge case applies: each slot holds a memory-significant object (a message with its payload, up to `internode_max_message_size`), so queue depth *is* a memory limit in disguise, and the filed `rejected.md` entry for `internode_max_message_size` already relies on this check as the node's bound. **The caveat for Rule 3:** unlike the inbound twin, whose gated object (the deserialized message) is created *after* its check, the outbound message exists before the check, so the branches diverge on its **retention and its serialization buffers**, not on its creation. §10 records this for stage 3.

## 8. Maximum memory bound

Raising `internode_application_send_queue_capacity` by *x* raises by *x* the accounted bytes **one link** may hold before it borrows; for a node with *P* peers the allowance moves by up to `3 × P × x` (urgent, small and large links), as the shipped yaml itself says ([`conf/cassandra.yaml:1373-1378`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/conf/cassandra.yaml#L1373-L1378)). It is a **scoped limit**: the capacity bounds one link's share, not the node.

The reserves sit on top and are shared: a link whose pending bytes exceed *C* borrows exactly the excess, so one link can hold at most `C + min(E_left, G_left)`, where *E* is the per-peer reserve (shared by the peer's three links) and *G* the node-wide one. The accounted ceiling of the node is therefore

`Σ over links C  +  min( Σ over peers E ,  G )  =  3·P·C + min(P·E, G)`

— with the defaults, for 10 peers, `3·10·4 MiB + min(1280 MiB, 512 MiB) = 632 MiB`, and for 50 peers 1112 MiB. **At the defaults the capacity is the small term:** 12 MiB per peer against up to 128 MiB per peer (512 MiB node-wide) from the reserves, so changing `internode_application_send_queue_capacity` alone moves the ceiling by `3·P·x` while the reserves, left alone, supply most of the allowance. Lowering *C* does not shrink the reserve term (a borrower takes only its excess over *C*).

Three qualifications. (1) **Which key moves the per-peer term** is not the send-side one (§4): a user who lowers `internode_application_send_queue_reserve_endpoint_capacity` to cap outbound memory changes no limit on this path (it changes only the derived `internode_max_message_size`). (2) **For a peer that cannot be reached** the reserves are not used and the link's ceiling is *C* itself. (3) **The unit is serialized bytes, not heap:** the heap held can be below the accounted total (one message shared by several replicas' queues) or above it (the in-memory form of a mutation), and delivery's off-heap frames and Netty's buffers are outside the count. A second, **time** bound exists but is **lazy** (§6b (iii)): a queued message past its deadline (writes: `write_request_timeout`, capped by the client deadline) is dropped when something prunes, not at the instant of the deadline, and a connected link that is full and not draining reclaims nothing by itself; so the byte bound is the only bound that holds at every instant. §9 keeps the load shorter than the deadline so that pruning cannot mask the byte bound. Also outside this case: the hard cap of about 4.19 million pending messages per link ([`:152-156`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L152-L156): the code leaves 22 bits for the count where the field's comment says 20).

### 9a. Procedure and conclusions

**Testability:** config, **restart-only** — the capacity is copied into a `final long` of each of a peer's three connections when the first message to that peer is sent ([`OutboundConnection.java:311`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L311)), from a non-`volatile` `Config` field with no setter, JMX or nodetool path ([`DatabaseDescriptor:3025-3038`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/config/DatabaseDescriptor.java#L3025-L3038) has getters only), and a reconnect refuses a changed value (`:1312`). Each value costs a restart of the **sending** node only. The global reserve is built once at `MessagingService` construction.

**Claim under test:** `internode_application_send_queue_capacity` bounds the serialized bytes of unsent messages **one link** may hold; past it a link borrows only the excess from a per-peer and a node-wide reserve, and when either is short the message is **dropped** (counted, logged, its request failed at once, a plain write hinted), never queued and never waited for. The node-wide allowance is `3·P·C + min(P·E, G)`, the per-peer reserve is read from the **receive-side** endpoint key, and a link to an unreachable peer is capped at *C* with no borrowing (§4, §6b, §8).

**How this verifies the hypothesis** (a restatement of the claim, procedure, prediction and conclusions in this section; it adds none):

- **Hypothesis:** with both reserves pinned low, a link's pending bytes plateau within one message of `C + F` (*F* = the smaller reserve) and move one-for-one with *C*; the drop counters and the endpoint-reserve gauge show the disallow branch; the sum over *P* links follows `P·C + G`; a reserve key set only on the send side changes nothing.
- **Test:** hold the sender's large-link delivery (a Byteman rule) so nothing drains; offer 128 KiB writes from far more client threads than fit; sweep *C* (512 KiB, 1 MiB, 4 MiB the default, 16 MiB) with both reserves at 1 MiB; then 1, 2 and 3 replicas at the default *C*; then the default reserves; then each endpoint-reserve key alone. Read the pending bytes, the overload counters, the reserve gauge, the sender's heap and the clients' errors.
- **Logic:** (1) the load must exceed `C + F`, or the run is invalid. (2) Pending bytes stop within one message of `C + F` and `overload_count` rises: usage **stops at the limit**, by the disallow branch (the counter moves only in `onOverloaded`). (3) The plateau moves with *C*: usage **follows the constraint**. (4) It moves with *P* as `P·C + G`: **§8's multiplier**. (5) With the default reserves nothing is dropped and the plateau is the offered load: the reserves, not *C*, bind (§8). (6) Only one of the two endpoint-reserve keys moves the plateau: the **reserve wiring** of §4. (7) The plateau stays past the deadline while the hold lasts, and after the hold is lifted (past the deadline) the parked delivery resumes by itself, expires the queued messages, and the pending bytes and the reserve gauge return to zero: the accounting balances. *(Amended 2026-10-07: the old text had one more write re-trigger delivery. At the plateau that write is refused inside `acquireCapacity()` and `enqueue()` returns at `:344-345`, before `delivery.execute()` at `:349`; and `INSUFFICIENT_GLOBAL`, the first refusal in every reserves-low arm, does not even take the prune-and-retry branch of `:337-341`. Nothing else restarts a stopped link, so the accounting would never have been seen to drain.)*
- **Refuted if:** with the reserves low the plateau does not follow *C*, or passes `C + F` while the check is evaluated; the drop counters stay at zero at the plateau; or the send-side endpoint key governs (rows of the Conclusions table).

**Procedure:**

1. **Unit tier** — run the harness tests `SendQueueCapacityTest` and `SendQueueWiringTest` (9c): drive `acquireCapacity` through the boundary, the borrow, both refusals, the release, the unreachable-peer short-circuit and an `enqueue` that is accepted and one that is dropped; read back which config keys reach the connection's limits. 2. **Cluster tier** — four processes on one machine (the sender *S* and replicas *R1* to *R3*, 9b); restart *S* per capacity value.
3. **At each capacity value:** idle control → **scenario A**, offered load below *C* with the hold on → **scenario B**, offered load above `C + F` with the hold on. **Once, at the default capacity:** the peer sweep, and **scenario C**, the arms in which only one of the two endpoint-reserve keys is lowered (the arm for a setting that may not take effect, §4; it is the bypass-like arm of this case).
4. **Compare** with the prediction and read the result in the table.

**Prediction.** Notation: *C* the capacity; *E* the **effective** per-peer reserve; *G* the node-wide reserve; *F* = min(*E*, *G*); *M* one message's `canonicalSize` (a mutation with one 131,072-byte value, about 128 KiB plus a few hundred bytes — read it from the trace, which prints `bytes`); *X* a link's peak pending bytes; *D* = threads × *M*, the offered load (256 threads, about 32 MiB).

Two rules behind this table. **A confirmation needs both** the plateau following *C* **and** direct evidence that the disallow branch fired (`overload_count`, the `INSUFFICIENT_*` trace lines, the WARN): a plateau alone can come from the client or from expiry. **A message that is refused and one that expires are different counters,** and an expiry that did run would free bytes, so the timed-out counter must stay at zero while *X* is read; the load is shorter than the deadline for that reason.

### 9c. Workload

**Unit tier.** Commands are in 9c. `SendQueueCapacityTest` builds one connection with *C* = 4096, *E* = 1500, *G* = 1000 (large type, never connected) and asserts, in order, reading `pendingBytes()` and the two reserves' `using()`:

1. **U1, the boundary:** acquire 4096 → `SUCCESS`, pending 4096, both reserves 0 (the compare is `≤`: a message that exactly fills *C* borrows nothing).
2. **U2, one byte over:** acquire 1 → `SUCCESS`, pending 4097, both reserves 1.
3. **U3, to the reserve's edge:** acquire 999 → `SUCCESS`, pending 5096, both reserves 1000 (= *G*).
4. **U4, the first refusal:** acquire 1 → **`INSUFFICIENT_GLOBAL`**, pending 5096, both reserves still 1000 (a refused claim changes nothing).
5. **U5, release returns the reserve first:** release 1000 → pending 4096, both reserves 0; release 4096 → pending 0.
6. **U6, only the excess is borrowed:** acquire 3000 → `SUCCESS`, reserves 0; acquire 2000 → `SUCCESS`, pending 5000, both reserves **904** (= 3000 + 2000 − 4096, not 2000).
7. **U7, the other refusal:** a fresh connection with *E* = 1000 and *G* = 1500, filled to the edge as in U1 to U3, then acquire 1 → **`INSUFFICIENT_ENDPOINT`**, and the node-wide reserve's `using()` is back at its value before the attempt (the claim is rolled back).
8. **U8, `enqueue` accepts and drops** (needs an inbound socket open, as `testInsufficientSpace` does; copy its setup): *C* = 64 KiB, *E* = 32 KiB, *G* = 64 KiB. A message of 80 KiB (16 KiB beyond *C*, below `C + F` = 96 KiB) → accepted, delivered, `overloadedCount` 0. A message of 256 KiB (upstream's case) → dropped, `overloadedCount` 1, `overloadedBytes` = its size, its callback failed, nothing delivered.
9. **U9, an unreachable peer borrows nothing:** a connection to a loopback port where nothing listens, one small `enqueue` to start connecting, then poll `connectionAttempts()` until it is at least 2 (the counter rises when an attempt **starts**, [`:1194`](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1194), and the retry starts only after the first attempt failed and a [delayed retry was scheduled](https://github.com/apache/cassandra/blob/cassandra-5.0.9/src/java/org/apache/cassandra/net/OutboundConnection.java#L1104), which is what makes the link "failing to connect"). Acquire `C − pending + 1` with both reserves empty and large: → **`INSUFFICIENT_ENDPOINT`** and both reserves' `using()` still 0. The same acquire on a connection that is not connecting (the one of U2, which was never connected) borrows. *(Reworded 2026-10-07: U2's connection is not connected; what `:409` tests is that it is not failing to connect.)*

## 11. Notes

- **Why one case, three comparisons.** The capacity (`:398`), the reserves (`:419`) and the count cap (`:391`) feed one `Outcome` and one `switch`; the reserve comparison is the shared `ResourceLimits` mechanism (`deferred.md` §5 item 3, still open), cited here as the mechanism behind the reserves of all four net cases.
- **Why this qualifies, and where it is weak.** Rule 1: usage and limit are both bytes, the limit a configuration entry. Rule 2: the queue-depth edge case holds (each slot is a message with its payload); the capacity moves the accounted ceiling by `3·P·x`, though at the defaults the reserves are the larger term (§8), and the heap is only loosely proportional to the accounted bytes (§7). Rule 3: the verdict reaches `enqueue()`, which queues or drops; the branches diverge on retention and on the serialization buffers, not on the creation of the message (§7). The folder records a constraint that governs less than its name as a result, not a rejection (playbook §3), so the case is filed with that said in §4, §8 and §10 and tested in §9.
- **Why pattern (b).** The check returns a verdict and a separate decision point reads it; between them nothing resets or ignores it. The inbound twins are (b) too, but the internode twin's disallow waits and the native-transport twin's depends on its configuration; this one drops.
- **Contrast with the inbound twins.** Receive (internode): `AbstractMessageHandler.acquireCapacity()` registers the handler on a wait queue and keeps the bytes, applying backpressure to the sender. Send: `OutboundConnection.acquireCapacity()` drops the message and fails its request; nothing waits. The two share `ResourceLimits` and the `Outcome` enum, and both draw their per-peer reserve from the **receive**-side endpoint key (§4).
- **What this design does not cover.** The urgent and small links (only the large link is loaded); streaming; a peer that is unreachable in the cluster tier (a unit step, U9, answers it; a real node with the peer's process killed would need the failure detector's window, about ten seconds, and the hold's flag logic); mixed messaging versions; the remote-data-centre forwarding path; counter mutations (a drop is not hinted) beyond the §6b reading; replies and gossip as the dropped messages; `internode_tcp_user_timeout` and the Netty watermarks; the hard count cap; and hinting beyond the optional observation. Each is recorded from the source in §6b, §7 or §8.
- **Nothing here was run.** No measured number appears in this file; every figure in §9 is derived from the source and is a prediction.
