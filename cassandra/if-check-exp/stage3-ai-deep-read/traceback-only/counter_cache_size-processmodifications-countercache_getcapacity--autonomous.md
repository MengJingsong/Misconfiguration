## A. Constraint trace

**A1. The constraint.** `counter_cache_size` (configuration entry) caps the memory used by the counter cache, which the check at `CounterMutation.java:213` (`CacheService.instance.counterCache.getCapacity() != 0`, in `processModifications`, declared at line 207) tests. A capacity of 0 skips the cache lookup and goes straight to reading counters from the column family store (lines 221-222). The entry is first declared at `Config.java:479-480` as `DataStorageSpec.LongMebibytesBound counter_cache_size = null`, replacing the deprecated `counter_cache_size_in_mb`. The unit is MiB. The yaml entry is `counter_cache_size:` at `conf/cassandra.yaml:595`, left empty, and its comment says empty means "auto", while 0 disables the cache (`cassandra.yaml:592`). `DatabaseDescriptor.java:834-836` derives the default when the value is null as `min(max(1, (int)(Runtime.getRuntime().totalMemory() * 0.025 / 1024 / 1024)), 50)` MiB. That is 2.5% of the JVM's currently committed heap, because it uses `totalMemory()` and not max heap, capped at 50 MiB. A negative value is rejected (`DatabaseDescriptor.java:838`). The result is written back to `conf.counter_cache_size` at line 864 and stored in `counterCacheSizeInMiB` (line 203, getter at line 3947). `CacheService.initCounterCache` (`CacheService.java:172`) converts it to bytes at line 176 and builds the `CaffeineCache` with that capacity at line 179, and `getCapacity()` returns that value. It is set through the yaml key, which needs a restart. At runtime it can be changed through JMX `CacheServiceMBean.setCounterCacheCapacityInMB` (`CacheServiceMBean.java:58`, implemented at `CacheService.java:344-350`, which rejects negative values and calls `counterCache.setCapacity(capacity * 1024 * 1024)`), which `NodeProbe.java:1093` calls, so no restart is needed for that route.
